## 1. Purpose

This document establishes the governance standard for domain models within the AIS programme. It defines how entities are managed, how terminology is controlled, how change severity is classified, what quality criteria must be met, and how changes flow through the control process. All domain model artefacts must comply with this standard.

The standard ensures:

- Domain models evolve in a controlled, traceable manner.
- Every entity has clear ownership, lifecycle rules, and invariant definitions.
- Terminology is consistent, versioned, and centrally governed.
- Quality is objectively measurable and verifiable.
- Changes are risk-classified and routed through appropriate review.

## 2. Entity Management Rules

### 2.1 New Entities

- Every new entity must be introduced via a **DADR** (see GOV-003).
- The DADR must specify: entity name, owner, lifecycle states, invariants, aggregate membership, and relationship to existing entities.
- The entity must be registered in the Unified Lexicon (UL) before the DADR is approved.
- Entity IDs are **permanent** and must never be reused, even after deprecation.

### 2.2 Entity Modification

- Any modification to an existing entity's attributes, behaviour, invariants, or relationships requires an **impact analysis**.
- The impact analysis must cover: affected domains, affected invariants, downstream consumers, event producers/consumers, and data migration needs.
- Modifications that alter an entity's invariant set or aggregate membership are classified at minimum **S2**.

### 2.3 Entity Deprecation

- An entity may only be deprecated via a DADR that specifies:
  - Reason for deprecation.
  - Replacement entity or migration path (if any).
  - Timeline for removal.
  - Impact on existing data and consumers.
- A deprecated entity enters a **read-only** state — no new instances may be created.
- The deprecated entity ID remains permanently reserved.

### 2.4 Entity ID Permanence

- Once assigned, an entity ID is immutable and permanent.
- Entity IDs follow the format: `ENTITY-<domain>-<sequential>`.
- The sequential counter is never reset or reused.

## 3. Terminology Governance

### 3.1 Unified Lexicon (UL)

- The UL is the **single source of truth** for all programme terminology.
- The UL is versioned; every term addition or modification increments the UL version.
- All domain models, ADRs, DADRs, and implementation code must reference UL-defined terms.

### 3.2 New Term Introduction

- New terms must be proposed via a DADR and registered in the UL before use.
- The DADR must justify: why the existing vocabulary is insufficient, the precise definition, the domain of origin, and any synonyms.

### 3.3 Synonym Management

- Synonyms are tracked in the UL but are **not** preferred terms.
- Every synonym entry maps to exactly one canonical (preferred) term.
- Code, documentation, and decision records must use canonical terms; synonyms are listed only for discoverability and onboarding.

### 3.4 Term Lifecycle

| State | Description |
|---|---|
| **Proposed** | Term submitted via DADR, under review. |
| **Active** | Term approved and published in UL. |
| **Deprecated** | Term marked for removal; replaced by a preferred term. |
| **Retired** | Term removed from active use; retained in UL history. |

## 4. Severity Levels

All domain changes are classified by severity, which determines the review and approval requirements:

| Level | Name | Description | Examples |
|---|---|---|---|
| **S1** | Critical / Breaking | Changes that break existing contracts, remove entities, or alter invariants in a non-backward-compatible way. | Entity removal, invariant deletion, API contract change, aggregate restructuring. |
| **S2** | Major / Ownership | Changes that alter entity ownership, aggregate boundaries, or cross-domain relationships. | Owner reassignment, aggregate reassignment, new cross-domain dependency. |
| **S3** | Moderate / Attributes | Changes that add, remove, or modify entity attributes or lifecycle states without breaking invariants. | New optional attribute, state name change, attribute type refinement. |
| **S4** | Minor / Relationships | Changes to internal relationships, documentation, or non-behavioural aspects. | New internal reference, relationship cardinality update, comment correction. |
| **S5** | Trivial / Docs | Changes to documentation, formatting, or presentation only. | Typo fix, README update, diagram reformatting. |

## 5. Quality Criteria

Every entity in the domain model must satisfy the following quality criteria. Compliance is verified during the **Verify** phase of the Change Control Process.

### QC-001: Entity Has Owner

- Every entity must have exactly one assigned owner (individual or role).
- The owner is responsible for the entity's correctness, lifecycle, and change approvals.
- Owner reassignment is an S2 change.

### QC-002: Entity Has Lifecycle

- Every entity must define a finite set of lifecycle states.
- The lifecycle must include at minimum: creation state and terminal state(s).
- State transitions must be explicitly enumerated and enforced.

### QC-003: Entity Has Invariant

- Every entity must have at least one defined invariant that constrains its state.
- Invariants must be testable and expressed in a verifiable form.
- An entity without an invariant is incomplete and must not be approved.

### QC-004: Aggregate Has Root

- Every aggregate must designate exactly one entity as its aggregate root.
- The aggregate root is the sole entry point for external access to aggregate-internal entities.
- All invariants within an aggregate are enforced through the root.

### QC-005: No Circular Dependencies

- Domain dependency graphs must be acyclic.
- If entity A depends on entity B, entity B must not transitively depend on entity A.
- Cycle detection is performed automatically as part of the Verify phase.

### QC-006: Events Have Producers and Consumers

- Every domain event must have at least one defined producer entity.
- Every domain event must have at least one defined consumer (handler, projection, or subscriber).
- Orphaned events (no consumer) are flagged as incomplete.

### QC-007: Value Objects Are Immutable

- All value objects must be immutable after construction.
- Value objects must implement equality by value, not by reference.
- No value object may expose mutable state or setters.

## 6. Change Control Process

All domain model changes follow this five-phase process:

### 6.1 Phase 1: Propose

- The change proposer creates a DADR (for S1–S3) or a change request (for S4–S5).
- The proposal includes: rationale, severity classification, affected entities, impact analysis, and proposed implementation.
- The DADR is submitted to the Domain Owner.

### 6.2 Phase 2: Review

- The Domain Owner reviews the proposal for completeness and correctness.
- For S1–S2 changes, the Architecture Board also reviews.
- Reviewers check: UL compliance, quality criteria impact, invariant preservation, and cross-domain effects.
- Review feedback is documented on the DADR. The proposer must address all feedback before proceeding.

### 6.3 Phase 3: Approve

- Authority to approve is determined by severity:
  - **S1**: Steering Committee approval required.
  - **S2**: Architecture Board + Domain Owner approval required.
  - **S3**: Domain Owner approval required.
  - **S4**: Domain Owner or delegate approval required.
  - **S5**: Self-approval with logging.
- Approval is recorded on the DADR with the approver's identity and date.

### 6.4 Phase 4: Implement

- The approved change is implemented in the domain model, code, and documentation.
- For S1–S2 changes, a migration plan must be executed alongside the implementation.
- The UL is updated if new or modified terms are involved.
- Implementation commits reference the DADR number.

### 6.5 Phase 5: Verify

- Automated and manual verification confirms:
  - All affected quality criteria (QC-001 through QC-007) still pass.
  - No circular dependencies have been introduced (QC-005).
  - All events have valid producers and consumers (QC-006).
  - The UL is consistent with the updated domain model.
- Verification results are recorded on the DADR.
- On failure, the change is rolled back or amended and re-enters Phase 4.

## 7. Compliance Matrix

The following matrix maps each Quality Criterion to the relevant Control Point (CP), Assurance Level (AL), and Deliverable/Product (DP) categories:

| Quality Criterion | Control Point | Assurance Level | Deliverable / Product |
|---|---|---|---|
| **QC-001** — Entity Has Owner | CP-ENT-001: Owner assignment verified at DADR approval | AL-2: Reviewed by Domain Owner | DP-DADR: Owner field populated; DP-UL: Owner recorded |
| **QC-002** — Entity Has Lifecycle | CP-ENT-002: Lifecycle states enumerated in DADR | AL-2: Reviewed by Domain Owner | DP-DADR: Lifecycle section complete; DP-DM: State machine defined |
| **QC-003** — Entity Has Invariant | CP-INV-001: Invariant definition present and testable | AL-2: Reviewed by Domain Owner | DP-DADR: Invariant section complete; DP-TEST: Invariant test cases |
| **QC-004** — Aggregate Has Root | CP-AGG-001: Root entity designated in aggregate DADR | AL-2: Reviewed by Architecture Board | DP-DADR: Aggregate root declared; DP-DM: Aggregate boundary verified |
| **QC-005** — No Circular Dependencies | CP-DEP-001: Dependency graph acyclicity checked at Verify | AL-3: Automated verification | DP-TOOL: Cycle detection output; DP-VERIFY: Pass/fail result |
| **QC-006** — Events Have Producers and Consumers | CP-EVT-001: Event registry completeness verified | AL-3: Automated verification | DP-EVT: Event registry entry; DP-VERIFY: Consumer mapping confirmed |
| **QC-007** — Value Objects Are Immutable | CP-VO-001: Immutability enforced at code review | AL-2: Reviewed by Domain Owner | DP-CODE: No setters exposed; DP-TEST: Immutability assertion tests |

### 7.1 Assurance Levels

| Level | Description |
|---|---|
| **AL-1** | Self-attested by proposer; no independent review. |
| **AL-2** | Reviewed and approved by the assigned authority (Domain Owner or Architecture Board). |
| **AL-3** | Automated tool verification plus authority review. Results are machine-generated and human-confirmed. |

### 7.2 Compliance Reporting

- Compliance status for all QC criteria is reported at each programme milestone.
- Non-compliant entities are flagged with their QC gaps and must be remediated before the next milestone.
- A compliance dashboard aggregates QC pass/fail rates across all domains.

---

## 8. Enforcement

- Entities that do not meet QC-001 through QC-003 are considered **incomplete** and must not be promoted to a production domain model.
- Aggregates that violate QC-004 or QC-005 are considered **structurally invalid** and must be remediated.
- Changes that bypass the Change Control Process are **ungoverned** and must be retroactively documented.
- This document is governed by GOV-001 and may only be amended per the process defined therein.
