## 1. Domain Vision

The AIS domain is the problem space of **adaptive, context-aware assistance** for security platform operators. It encompasses the behaviours, data structures, and rules that govern how the system observes user actions, builds behavioural profiles, generates confidence-driven predictions, and delivers proportionate, role-appropriate notifications — all while maintaining strict trust boundaries and auditability. The domain is not a technical implementation specification; it is a conceptual model of the business logic that makes the platform intelligent, responsive, and respectful of the humans who operate it.

The vision defines clear scope and boundaries. **In scope** are all concerns that relate directly to adaptive behaviour: user behaviour tracking, profile accumulation over time, confidence assessment of predictions, predictive assistance generation, adaptive notification delivery with role-aware narrative, provider abstraction for external services, plugin lifecycle management, and trust management across autonomy levels. **Out of scope** are all infrastructural and implementation concerns: concrete UI rendering logic, HTTP routing definitions, database schema design, external API contracts, and infrastructure provisioning. These out-of-scope concerns are addressed by separate architecture and implementation documents that conform to this domain vision but do not define it.

AIS exists to make security operators faster and more effective by meeting them where they are — adapting its behaviour to theirs, not the reverse. The system must never create cognitive overhead; every prediction, notification, and adaptive response must justify its existence by reducing the operator's effort or improving their decision quality. The ultimate measure of the domain's success is whether operators complete security tasks with greater speed, accuracy, and confidence than they would without assistance.

The domain operates under a core tension: the system must be proactive enough to be useful, yet restrained enough to avoid becoming intrusive. Resolving this tension is the central design challenge of AIS, and every principle, invariant, and concept defined in this document exists to navigate that balance.

## 2. Core Concepts

The domain is composed of 20 core entities. Each is defined below with a descriptive summary of its role, responsibilities, and relationships within the domain.

These entities are the building blocks of all domain logic. No implementation construct — class, module, service, or data store — should exist without tracing back to one or more of these entities.

### 2.1 UserProfile
Accumulated behavioural profile representing a user's interaction patterns, preferences, and observed capabilities over time. Serves as the primary input for all adaptive decisions including prediction generation, notification tuning, and confidence calibration. The profile is immutable in the sense that historical observations are never altered, but new observations are continuously appended, causing the profile to evolve organically with the user's behaviour.

### 2.2 UserAction
Atomic interaction event capturing a single user behaviour such as a click, navigation, dwell time measurement, notification dismissal, or explicit feedback submission. Each action is immutable once recorded and feeds into profile updates through the session context pipeline. UserActions are the fundamental raw material from which all higher-order adaptive intelligence is derived.

### 2.3 SessionContext
Aggregated session state combining the current UserProfile snapshot, active predictions, recent actions, and environmental conditions such as time of day and active page. Defines the operating context for a single user session and serves as the input to both the prediction engine and the notification delivery subsystem. SessionContext is ephemeral by nature but may be persisted for audit and learning purposes.

### 2.4 ConfidenceResult
Confidence assessment output produced when the system evaluates a prediction or recommendation against available evidence. Contains a numeric score in the range [0, 100], a classification level mapped from that score, and optional narrative text explaining the reasoning. ConfidenceResults drive presentation decisions and determine whether a prediction is surfaced as a suggestion, a recommendation, or an automated action.

### 2.5 ConfidenceLevel
Classification enum governing how confidence is expressed to the user and to downstream systems. The five levels — **Very Low**, **Low**, **Moderate**, **High**, **Very High** — map from numeric score ranges and directly drive UI presentation decisions, notification urgency, and autonomy gating. Higher confidence levels unlock higher autonomy actions; lower levels restrict the system to advisory roles.

### 2.6 AISPrediction
Predicted next user need generated by the intelligence subsystem. Combines profile data, session context, and historical patterns to forecast what the user will require next, producing a ConfidenceResult that qualifies the prediction's reliability. Predictions are the core value proposition of AIS, transforming passive observation into proactive assistance.

### 2.7 AISNotification
Adaptive notification produced for the user based on an active prediction, system event, or contextual trigger. Its content, medium, lifetime, and frequency are all determined by the user's profile, role, and current confidence context. Notifications are the primary communication channel through which AIS delivers its intelligence to the operator.

### 2.8 NotificationType
Type classification governing notification semantics and visual treatment. The six types — **info**, **success**, **warning**, **error**, **tip**, **achievement** — determine visual treatment, persistence policy, and the degree to which the notification demands attention. Error and warning notifications are inherently more persistent than tips, for example.

### 2.9 NotificationLifetime
Adaptive lifetime policy controlling how long a notification remains visible to the user before automatic expiry or dismissal. Adjusts dynamically based on the user's observed reading speed, historical dismissal patterns, and the intrinsic importance of the notification type. The goal is to ensure every notification is visible long enough to be consumed but not so long that it creates clutter.

### 2.10 UserRole
User role classification within the security platform: **CEO**, **DevOps**, **Engineer**, **Analyst**. Determines the narrative style, data granularity, technical depth, and notification priority for a given user. The same underlying data or event is rendered differently depending on the role, ensuring relevance and avoiding information overload.

### 2.11 ReadingSpeed
Reading behaviour pattern observed from the user's interaction with text-based content within the platform. Classified as **fast**, **normal**, or **slow**, this metric directly influences notification lifetime calculations. Users who read quickly receive shorter-lived notifications, while slower readers are given more time to absorb content.

### 2.12 NavigationSpeed
Navigation behaviour pattern observed from the user's movement through the interface, measured by page transition frequency and scroll behaviour. Classified as **fast**, **normal**, or **slow**, this metric influences prediction timing and notification pacing. Fast navigators receive more concise, rapidly-delivered assistance.

### 2.13 FrequencyMode
Notification frequency classification controlling the rate at which notifications are delivered to a user. The three modes — **Rare**, **Normal**, **Frequent** — are adaptively assigned per user based on their historical response to notification volume and their dismissal patterns. The system continuously adjusts frequency to match user tolerance.

### 2.14 LifetimePolicy
Notification display duration rules defining minimum and maximum display times per notification type. Provides guard rails for the adaptive lifetime calculation, ensuring that no notification disappears too quickly to be useful or persists so long that it becomes noise. Each NotificationType has its own LifetimePolicy boundaries.

### 2.15 ProviderInfo
External provider metadata describing a connected service such as an LLM, security scanner, storage backend, or embedding service. Holds connection state, capability flags, health indicators, and configuration parameters. ProviderInfo is the domain's abstraction boundary for all external service interactions.

### 2.16 ProviderType
Provider classification enum defining the category of external service: **LLM**, **Scanner**, **Storage**, **Embedding**. Determines the abstraction interface, integration contract, and trust zone assignment for the provider. Each ProviderType has its own interface specification and capability set.

### 2.17 PluginManifest
Plugin capability declaration defining what a plugin provides, what permissions it requires, and its trust zone assignment. Must be registered and validated before the plugin can execute. The manifest serves as the plugin's contract with the platform, establishing a bounded scope of interaction that the runtime enforces.

### 2.18 PluginPermission
Plugin permission scope defining the specific operations a plugin is authorised to perform within the platform. Permissions are bounded by the manifest declaration and can never exceed it at runtime. The permission model follows the principle of least privilege, granting only the minimum access necessary for the plugin to fulfil its declared purpose.

### 2.19 TrustFactor
Trust-building observable representing a single event or condition that contributes to the overall trust assessment of a user, provider, or plugin. Examples include successful authentication events, consistent behaviour patterns, timely data provision, and positive user feedback. TrustFactors are the atomic inputs to the trust scoring system.

### 2.20 TrustScore
Aggregated trust metric combining multiple TrustFactors into a single numeric score used to gate access to sensitive operations and higher autonomy levels. The TrustScore evolves over time as new TrustFactors are observed and old ones decay, creating a living measure of reliability that the domain uses to make safety-critical decisions.

## 3. Category Taxonomy

The 20 core entities are organised into six categories, each representing a coherent sub-domain within AIS. This taxonomy supports modular reasoning, allowing teams to work on independent sub-domains while maintaining a unified view of the whole.

### 3.1 User (5 entities)
Entities that model the human operator and their observed behavioural characteristics. Together, these entities form the foundation of the adaptive system — without accurate user modelling, no prediction or notification can be meaningfully personalised.

- **UserProfile** — Accumulated behavioural profile representing interaction patterns and preferences.
- **UserAction** — Atomic, immutable record of a single user interaction event.
- **UserRole** — Classification of the user's organisational function (CEO, DevOps, Engineer, Analyst).
- **ReadingSpeed** — Observed speed at which the user consumes text content.
- **NavigationSpeed** — Observed speed at which the user moves through the interface.

### 3.2 Intelligence (3 entities)
Entities that model the system's predictive and confidence assessment capabilities. These entities represent the core reasoning layer of AIS, transforming raw behavioural data into actionable foresight.

- **ConfidenceResult** — Output of a confidence assessment containing score, level, and narrative.
- **ConfidenceLevel** — Classification enum governing confidence expression (Very Low through Very High).
- **AISPrediction** — Forecast of the user's next need generated from profile and context data.

### 3.3 Communication (5 entities)
Entities that model how the system delivers adaptive notifications to the operator. This category governs the entire notification lifecycle from creation through display to expiry, ensuring messages are proportionate and non-intrusive.

- **AISNotification** — Adaptive notification tuned by profile, role, and confidence.
- **NotificationType** — Type classification governing notification semantics (info, success, warning, error, tip, achievement).
- **NotificationLifetime** — Adaptive lifetime policy controlling notification visibility duration.
- **FrequencyMode** — Notification frequency classification (Rare, Normal, Frequent).
- **LifetimePolicy** — Display duration guard rails per notification type.

### 3.4 Provider (2 entities)
Entities that model the abstraction of external service integrations. This small but critical category enforces the provider opacity principle, ensuring the domain remains decoupled from specific external implementations.

- **ProviderInfo** — Metadata describing a connected external provider service.
- **ProviderType** — Provider classification enum (LLM, Scanner, Storage, Embedding).

### 3.5 Plugin (2 entities)
Entities that model the plugin extension system and its security boundaries. These entities enforce the principle of least privilege for all third-party code running within the platform.

- **PluginManifest** — Declaration of a plugin's capabilities, permissions, and trust zone.
- **PluginPermission** — Permission scope defining the operations a plugin may perform.

### 3.6 Trust (2 entities)
Entities that model the trust assessment and gating system. Trust is the safety layer that governs autonomy escalation and access to sensitive operations across the entire domain.

- **TrustFactor** — Single observable event or condition contributing to trust assessment.
- **TrustScore** — Aggregated trust metric combining multiple TrustFactors.

## 4. Domain Principles

Domain principles are the foundational rules that guide all design and implementation decisions within the AIS domain. Each principle captures a non-negotiable behavioural expectation. Principles are not aspirational goals; they are enforceable constraints that must be demonstrably upheld by every implementation artefact that conforms to this document.

Principles are organised by thematic area: user respect (DP-001 through DP-005), communication integrity (DP-006 through DP-007, DP-011 through DP-013), system architecture (DP-008 through DP-009), trust and safety (DP-010, DP-014), and governance (DP-015).

### DP-001: Behavioural Profile Ownership
The user owns their behavioural profile. All data derived from user behaviour belongs exclusively to the user and is used solely to improve their individual experience. Profile data must never be shared across users, sold to third parties, or used for purposes beyond adaptive assistance without explicit consent.

### DP-002: Confidence Drives Presentation
Confidence level directly determines the form in which a prediction is presented to the user. Low-confidence predictions are surfaced as tentative suggestions that require explicit user acceptance; high-confidence predictions may be presented as recommended actions or, at the highest autonomy levels, executed automatically. The system must never present a low-confidence prediction as a high-certainty recommendation.

### DP-003: Context Continuity
Session context persists and accumulates throughout a user session, providing continuity of understanding across page transitions and interactions. The session context is never silently reset without user awareness; any context reset must be explicit, logged, and communicated to the user. This ensures the system maintains a coherent mental model of the user's current task and intent.

### DP-004: Dismissal Is Data
When a user dismisses a notification, ignores a suggestion, or explicitly rejects a recommendation, that dismissal is treated as a first-class behavioural signal. Dismissal data is recorded, analysed, and used to refine future predictions, adjust notification frequency, and recalibrate confidence scores. Dismissal is not a failure of the system; it is valuable training data.

### DP-005: Adaptation Over Time
The system evolves continuously with user interaction. Behavioural profiles, notification frequencies, lifetime policies, and confidence calibrations are all refined over time and must never remain static. Adaptation is gradual and observable, never abrupt or opaque, ensuring the user can understand and trust the changes in system behaviour.

### DP-006: Role Determines Narrative
The same underlying data or event is rendered in different narrative styles, levels of technical detail, and degrees of urgency depending on the user's role. A critical vulnerability finding is described with technical specifics for an Engineer, with operational impact for a DevOps lead, and with business risk framing for a CEO. The system must always match its communication to the audience.

### DP-007: Notification Proportionality
The notification medium and persistence must be proportional to the message importance. Critical errors warrant persistent, high-visibility banners; informational tips warrant transient, low-intrusion toasts. The system must never use a high-urgency channel for a low-importance message, as this trains users to ignore all notifications.

### DP-008: Provider Opacity
Domain modules communicate with external providers exclusively through abstract interfaces and never through implementation details. The domain layer has no knowledge of provider internals such as API endpoints, authentication tokens, or response schemas beyond what the interface contract specifies. This opacity enables provider substitution without domain logic changes.

### DP-009: Plugin Isolation
Plugins operate within strictly bounded scopes defined by their manifest and cannot mutate domain entities outside their declared permission boundary. Plugin isolation ensures that a misbehaving or malicious plugin cannot corrupt core domain state, compromise user profiles, or escalate its own privileges beyond what was declared at registration time.

### DP-010: Trust Through Transparency
Trust is built by exposing the system's reasoning, confidence levels, and data sources to the user rather than hiding them. When the system makes a prediction or takes an adaptive action, it must be able to explain why — citing the profile signals, confidence scores, and contextual factors that drove the decision. Opacity erodes trust; transparency builds it.

### DP-011: Sound As Brand
When audio cues are employed, the sound identity must be unique, brief, and consistent with the platform's overall brand character. Audio notifications are used sparingly and only for events that genuinely benefit from an auditory channel, such as critical alerts that the user may not be visually monitoring at the time.

### DP-012: Lifetime Adaptation
Notification lifetime adapts dynamically to the user's observed reading speed and historical interaction patterns. Users who read quickly are shown shorter-lived notifications to avoid clutter; users who read more slowly are given extended display times to ensure content is fully consumed. The adaptation is smooth and bounded by the applicable LifetimePolicy.

### DP-013: Frequency Adaptation
Notification frequency adapts dynamically to the user's demonstrated tolerance for interruption. Users who frequently dismiss notifications without engaging are progressively shown fewer notifications over time; users who engage positively may receive more frequent assistance. Frequency adaptation respects the user's attention as a finite and valuable resource.

### DP-014: Autonomy Alignment
Every action taken by the system on behalf of the user must be aligned with the current autonomy level. The system must never take an action that exceeds the user's current autonomy setting, whether that setting was explicitly configured by the user or implicitly determined by their trust score and role. Higher autonomy levels are earned, not assumed.

### DP-015: Audit Without Exception
All side effects produced by the AIS domain are fully auditable. Every state change, prediction generation, notification delivery, plugin execution, and trust assessment produces an immutable audit log entry that records the actor, intent, timestamp, and outcome. There are no silent operations and no exceptions to the audit requirement.

## 5. Domain Invariants

Domain invariants are statements that must always hold true within the AIS domain. They define the non-negotiable constraints that all implementations must enforce. Violation of any invariant constitutes a domain-level defect that must be resolved before the affected component can be considered conformant.

Invariants are expressed in formal language for precision and are accompanied by a rationale explaining why the constraint exists. Each invariant maps to one or more domain principles and can be verified through automated testing.

| ID | Invariant | Rationale |
|---|---|---|
| INV-001 | A session has exactly one UserProfile. | A session represents a single user's interaction stream; multiple profiles would create ambiguous behavioural signals and invalidate adaptive decisions. |
| INV-002 | Confidence is always in range [0, 100]. | Numeric confidence scores must have a bounded, universal range to ensure consistent comparison, level mapping, and threshold evaluation across all domain operations. |
| INV-003 | Autonomy level is always in range [L0, L4]. | The autonomy spectrum has a fixed number of levels with precisely defined semantics; values outside this range would have no defined behavioural meaning and could bypass safety gates. |
| INV-004 | No notification is created without a NotificationType. | The notification type drives visual treatment, persistence policy, and priority routing; a notification without a type cannot be rendered, routed, or managed correctly by the delivery subsystem. |
| INV-005 | No plugin runs without a registered and validated PluginManifest. | The manifest defines the plugin's permission boundary and trust zone; without it, the runtime cannot enforce isolation, track capabilities, or audit the plugin's behaviour. |
| INV-006 | No provider is accessed without valid credentials and a declared ProviderType. | Provider access requires both authentication and type classification to ensure correct interface usage, trust zone assignment, and audit trail generation. |
| INV-007 | No data flows across trust zones without an explicit gate check. | Cross-zone data flow represents an escalation of trust; uncontrolled flow could leak sensitive data from high-trust zones to lower-trust zones, violating the principle of least privilege. |
| INV-008 | No automated action is taken outside the current autonomy level. | The autonomy level defines the maximum action authority; exceeding it would take control away from the user, violating the fundamental principle that the operator remains in command. |
| INV-009 | No audit log entry is created without both an actor and an intent. | Audit entries without actor attribution or intent documentation are useless for accountability, forensics, and compliance; they represent a silent, untraceable side effect. |
| INV-010 | No dismissed notification is repeated without a meaningful context change. | Repeating a dismissed notification under the same conditions would train the user to ignore all notifications, undermining the entire adaptive communication system. |
| INV-011 | No confidence narrative is generated without reference to a UserRole. | Narrative content depends on the target audience; without a role, the narrative cannot be calibrated for appropriate detail, tone, and urgency, and may misinform or overwhelm the user. |
| INV-012 | No domain event is emitted without a classification. | Event classification drives routing, processing logic, and audit behaviour; unclassified events would bypass domain event handling rules and could cause silent processing failures. |
| INV-013 | No plugin is granted permissions beyond its declared manifest scope. | The manifest defines the maximum permission boundary; runtime permissions must be a subset of manifest permissions to enforce isolation and prevent privilege escalation. |
| INV-014 | No session exists without an associated SessionContext. | The SessionContext is the operational foundation for all adaptive decisions within a session; a session without context cannot generate predictions, notifications, or profile updates. |

## 6. Ubiquitous Language

The ubiquitous language is the shared vocabulary used by all stakeholders — domain experts, developers, designers, and operators — when discussing the AIS domain. Consistent use of these terms eliminates ambiguity and ensures that every participant shares the same mental model.

When new terms are introduced during design or implementation, they must be evaluated against this table. If they represent a genuinely new concept, the table should be extended through the change control process defined in CON-001.000. If they are synonyms for existing terms, the existing term must be used instead.

| Term | Definition |
|---|---|
| UserProfile | The accumulated behavioural profile of a user, representing their interaction patterns, preferences, and observed capabilities over time. |
| UserAction | An atomic, immutable record of a single user interaction event such as a click, navigation, dwell, or dismissal. |
| SessionContext | The aggregated state of a user session, combining the profile snapshot, active predictions, recent actions, and environmental conditions. |
| ConfidenceResult | The output of a confidence assessment, containing a numeric score, a classified level, and optional narrative text. |
| AISPrediction | A forecast of the user's next need, generated from profile data, session context, and historical behavioural patterns. |
| AISNotification | An adaptive notification delivered to the user, tuned by their profile, role, and current confidence context. |
| UserRole | The classification of a user's organisational function within the security platform: CEO, DevOps, Engineer, or Analyst. |
| ReadingSpeed | The observed speed at which a user consumes text-based content, classified as fast, normal, or slow. |
| NavigationSpeed | The observed speed at which a user moves through the interface, classified as fast, normal, or slow. |
| ProviderInfo | Metadata describing a connected external provider service, including connection state, capabilities, and health. |
| PluginManifest | A declaration of a plugin's capabilities, required permissions, and assigned trust zone, registered before execution. |
| TrustFactor | A single observable event or condition that contributes to the overall trust assessment of an entity. |
| AutonomyLevel | The current level of system autonomy granted to or assumed for a user, ranging from L0 (manual) to L4 (fully autonomous). |
| TrustZone | A bounded region governing data flow and access control, ranging from Z0 (untrusted) to Z4 (fully trusted). |
| ConfidenceLevel | A classification of confidence intensity: Very Low, Low, Moderate, High, or Very High. |
| FrequencyMode | The current notification frequency setting for a user, adaptively assigned as Rare, Normal, or Frequent. |
| LifetimePolicy | The rules governing minimum and maximum notification display durations per notification type. |
| EventClassification | The category of a domain event, determining its routing and processing: info, action, result, error, or state-change. |
