## 0. Introduction

This document is the Architecture Baseline of the Adaptive Intelligence System. It defines the system's shape, boundaries, functional pillars, design requirements, trust model, autonomy model, and interface contracts.

All sections conform to the Constitutional Principles (CP-001–CP-023) and Architectural Laws (AL-001–AL-012) defined in CON-001.000.

---

## 1. System Overview

AIS is the adaptive intelligence layer that sits between the platform and its human operators. It transforms a collection of tools into a proactive companion that understands context, predicts intent, and delivers assistance at the right moment, in the right form, with the right confidence.

### 1.1 Functional Pillars (FP)

The system is organised around eight Functional Pillars:

| FP | Name | Responsibility |
|----|------|----------------|
| FP-01 | **Adaptive Memory** | Capture, store, and adapt to user behaviour patterns (reading speed, navigation speed, preferences, role, goals). |
| FP-02 | **Context Prediction** | Predict what the user needs based on current page, recent actions, and accumulated profile. |
| FP-03 | **Confidence Engine** | Calculate and present the system's confidence in its recommendations on a 0–100 scale. |
| FP-04 | **Notification System** | Deliver adaptive notifications with variable lifetime, dismissal-awareness, and frequency control. |
| FP-05 | **Trust Management** | Build trust through transparency, honesty, and consistency of behaviour. |
| FP-06 | **Provider Abstraction** | Isolate the system from specific LLM, scanner, storage, and embedding providers. |
| FP-07 | **Event Bus** | Provide the asynchronous spine for cross-module coordination. |
| FP-08 | **Plugin Platform** | Enable third-party and internal extensions within a controlled trust envelope. |

### 1.2 Architectural Style

AIS follows the **Modular Monolith** pattern (ADR-001). All Functional Pillars live in a single codebase but are separated by explicit interfaces and the Event Bus. Splitting into microservices is deferred until evidence of need.

## 2. Design Requirements (DR)

The 11 Design Requirements define non-negotiable constraints.

| DR | Title | Constraint |
|----|-------|------------|
| DR-01 | **Provider-Independent Core** | No FP may contain a direct import of any specific provider SDK. All providers go through the Provider Abstraction layer. |
| DR-02 | **Event-Driven Coordination** | Cross-FP communication uses the Event Bus. Direct cross-FP method calls are forbidden except within the AIS Controller. |
| DR-03 | **Single Memory Authority** | Exactly one Adaptive Memory instance per session. No private copies of behavioural state. |
| DR-04 | **Confidence Always Present** | Every recommendation or notification that implies a system judgement MUST include a confidence level. |
| DR-05 | **Dismissible Notifications** | Every notification MUST have a dismiss action. Dismissal is persisted and respected. |
| DR-06 | **Role-Aware Output** | All narratives and recommendations are generated with the user's role as an explicit input. |
| DR-07 | **File-Based Persistence** | All persisted artefacts are files at stable paths. No opaque blob storage. |
| DR-08 | **TypeScript Contract Surface** | All public interfaces are expressed as TypeScript types. |
| DR-09 | **Zone-Compliant Flow** | Data may flow between Trust Zones only through declared gates. |
| DR-10 | **Autonomy-Level Aware** | Every action the system takes on behalf of the user is checked against the current Autonomy Level. |
| DR-11 | **Audit-Log All Side Effects** | Every state change with external side effects is logged with actor, intent, before-state, after-state, rationale. |

## 3. Trust Zones (Z0–Z4)

The system is partitioned into five Trust Zones. Data and execution flow between zones only through declared, audited gates.

### 3.1 Zone Definitions

| Zone | Name | Description | Access |
|------|------|-------------|--------|
| **Z0** | **Constitutional** | The normative documents themselves (CON, ARC, DOM, ADR, SEC, GOV). Immutable by design. | Read-only for all tiers. |
| **Z1** | **Core AIS** | The AIS Controller, Memory, Context Predictor, Confidence Engine, Event Bus. | Read/execute. No direct user writes. |
| **Z2** | **Plugin Sandbox** | Plugin execution environment. Plugins run with declared permissions and declared event subscriptions. | Scoped read/write within declared permissions. |
| **Z3** | **Provider Interface** | The abstraction layer through which AIS talks to external providers (LLM, scanner, storage). | Unidirectional: AIS calls out; providers do not call in. |
| **Z4** | **External** | Third-party services, user workspaces, remote APIs. | Accessed only through Z3. Never directly from Z1/Z2. |

### 3.2 Zone Gate Rules

| Gate | From → To | Check |
|------|-----------|-------|
| G-01 | Z0 → Z1 | Reference validation (document exists, is in baseline). |
| G-02 | Z1 → Z2 | Permission check, event subscription validation. |
| G-03 | Z1 → Z3 | Provider availability, rate limit, credential validity. |
| G-04 | Z2 → Z1 | Plugin result sanitisation, schema validation. |
| G-05 | Z3 → Z4 | Network policy, TLS, credential scope. |
| G-06 | Z4 → Z3 | Response validation, size limit, timeout. |

## 4. Autonomy Spectrum

AIS operates on a five-level Autonomy Spectrum. The level determines how much the system may act without explicit user approval.

### 4.1 Levels

| Level | Name | Behaviour |
|-------|------|-----------|
| **L0** | **Observe** | AIS watches and learns but never acts. It may display information on the user's explicit request. |
| **L1** | **Suggest** | AIS may show suggestions and recommendations but never executes any action. |
| **L2** | **Act on Approval** | AIS proposes an action; the user approves or rejects before execution. |
| **L3** | **Act and Report** | AIS executes the action and informs the user of the result. The user may undo. |
| **L4** | **Autonomous** | AIS acts without asking. The user is notified asynchronously. Full audit trail is mandatory. |

### 4.2 Default

The default Autonomy Level is L1 (Suggest). The user may raise it at any time. The system may suggest lowering it if confidence is below threshold (CP-003).

## 5. Module Architecture

### 5.1 Core Modules

| Module | FP | Zone | Responsibility |
|--------|-----|------|----------------|
| AIS Controller | FP-01 | Z1 | Unified entry point; routes requests; enforces autonomy level. |
| Adaptive Memory Engine | FP-01 | Z1 | Captures, stores, adapts to behavioural patterns. |
| Context Predictor | FP-02 | Z1 | Predicts user intent from page + profile. |
| Confidence Engine | FP-03 | Z1 | Calculates confidence scores and selects narratives. |
| Notification Manager | FP-04 | Z1 | Delivers adaptive notifications with variable lifetime. |
| Trust Builder | FP-05 | Z1 | Aggregates trust factors and presents Trust Builder UI. |
| Provider Factory | FP-06 | Z1/Z3 | Creates provider instances behind abstraction interfaces. |
| Event Bus | FP-07 | Z1 | Asynchronous event spine for cross-module coordination. |
| Plugin Host | FP-08 | Z1/Z2 | Loads, sandboxes, and monitors plugins. |

### 5.2 Event Bus

Events are typed, versioned, and classified.

| Classification | Description |
|----------------|-------------|
| **info** | Low-impact, informational. |
| **action** | Carries a request for execution. |
| **result** | Carries the outcome of an action. |
| **error** | Carries an error condition. |
| **state-change** | Carries a state transition notification. |

## 7. Data Model Overview

The architecture operates on the following core data entities (formal definitions in DOM-001.000 and DOM-002.000):

| Entity | Owner Module | Description |
|--------|-------------|-------------|
| UserProfile | Adaptive Memory | Accumulated behavioural profile of the user. |
| UserAction | Adaptive Memory | Atomic record of a user interaction event. |
| ConfidenceResult | Confidence Engine | Numeric confidence with level classification and narrative. |
| AISPrediction | Context Predictor | Predicted next action or need of the user. |
| AISNotification | Notification Manager | A single adaptive notification with lifetime, type, content. |
| ProviderInfo | Provider Factory | Metadata about a single provider instance. |
| PluginManifest | Plugin Host | Declaration of a plugin's capabilities, permissions, and event subscriptions. |
| SessionContext | AIS Controller | Aggregated context for the current user session. |

## 8. Security Model

The security model is defined in ADR-010 (Trust Boundaries), ADR-011 (Data Sovereignty), and ADR-012 (Minimal Privilege). Key principles:

- Plugin default zone is Z2 with no elevation path (AL-011).
- Provider credentials are scoped per session, never shared across sessions.
- All external data is sanitised at zone boundaries.
- Audit log is append-only, stored in Z1, replicated to Z0 for baseline integrity.
