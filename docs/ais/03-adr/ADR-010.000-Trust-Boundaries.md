# ADR-010: Trust Boundaries

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS system handles data and operations of varying sensitivity levels. Constitutional principles define user data rights, but the system also needs a formal model for enforcing boundaries between components of different trustworthiness.

Consider the following scenarios that motivated this decision:

- A plugin installed from a third-party source must not be able to read the user's constitutional preferences or core profile data.
- An external AI provider receiving a prompt must not gain access to internal AIS state or other users' data.
- The constitutional layer (principles, rights) must be immutable and untamperable, even by the AIS's own core systems.

Without formal trust boundaries, the system relies on ad-hoc access controls that are difficult to reason about, audit, and maintain. A systematic approach is needed.

Several models were considered:

1. **Flat permission model** — Every component requests permissions individually. This is flexible but creates an unmanageable combinatorial explosion of permission checks and does not provide a clear mental model of the system's security topology.

2. **Two-tier model (trusted/untrusted)** — A simple binary split between trusted core and untrusted extensions. This is easy to implement but too coarse; not all core components have the same trust level, and not all external components are equally untrusted.

3. **Multi-zone model with declared gates** — The system is divided into trust zones, and data flow between zones is only permitted through explicitly declared gates with enforced checks. This provides clear security topology while remaining practical.

## Decision

Adopt a **five-zone Trust Boundary model** with the following zones:

| Zone | Name | Description |
|------|------|-------------|
| Z0 | Constitutional | The immutable constitutional layer: principles, rights, and constraints. This is the highest-trust, most-restricted zone. Only read access is permitted by other zones; no zone can modify Z0 data. |
| Z1 | Core AIS | The central AIS runtime: Controller, Reasoning Engine, Memory Manager, and core domain logic. Has read access to Z0 and full control of its own state. |
| Z2 | Plugin Sandbox | The execution environment for installed plugins. Plugins run in isolation with no direct access to Z0 or Z1 state. All data exchange occurs through declared gate interfaces. |
| Z3 | Provider Interface | The boundary layer for external AI/ML providers. Z3 manages API keys, prompt construction, and response parsing. It has no access to raw user data from Z1; it only receives specifically formatted, minimal-context prompts. |
| Z4 | External | Everything outside the AIS system: third-party services, the network, the user's broader computing environment. All interaction with Z4 passes through Z3. |

**Key design rules:**

- **Data flows between zones only through declared gates:** Every gate is an explicitly defined interface with input/output contracts, validation rules, and audit logging.
- **No direct zone crossing:** Components in one zone cannot directly access data or call functions in another zone. All cross-zone interaction must pass through a gate.
- **Zone crossings are auditable:** Every gate logs all data flow, enabling complete traceability of information movement through the system.
- **Default deny:** If a gate is not declared for a given data flow, the flow is denied by default.

## Consequences

### Positive

- **Clear security boundaries:** Each zone has a well-defined trust level, making the system's security topology easy to understand, document, and reason about.
- **Auditable data flow:** All zone crossings pass through gates with logging, enabling complete traceability for security auditing and compliance.
- **Strong constitutional protection:** Z0 is isolated from all modification attempts, ensuring the constitutional layer remains immutable and trustworthy.
- **Plugin isolation:** Plugins in Z2 cannot access core system state or constitutional data, limiting the blast radius of a compromised or malicious plugin.
- **Minimal data exposure to providers:** Z3 ensures that external AI providers receive only the minimum data necessary for their function, reducing privacy exposure.

### Negative

- **Gate overhead:** Every zone crossing passes through a gate with validation and logging, which adds latency and computational overhead. This is an acceptable trade-off for security but must be monitored for performance impact.
- **Upfront design cost:** Gates must be declared and designed upfront, requiring careful analysis of data flow requirements before implementation.
- **Potential over-restriction:** If gates are too narrowly defined, legitimate data flows may be blocked, requiring gate redesign and refinement.
- **Complexity in multi-zone operations:** Operations that span multiple zones require careful orchestration through multiple gates, increasing implementation complexity.

## Compliance

- **CP-005 (Privacy):** Trust boundaries enforce data minimisation, especially at Z3, ensuring only necessary data leaves the system.
- **CP-006 (Security):** The zone model provides a formal security architecture with enforceable boundaries.
- **AL-012 (Audit Trail):** Gate logging provides the audit trail for all cross-zone data flows.
