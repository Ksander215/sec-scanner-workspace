# ADR-009: Autonomy Spectrum

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS system must support varying degrees of autonomous action depending on user trust, system confidence, and the nature of the task being performed. Not all users will be comfortable with the same level of system autonomy, and not all tasks carry the same risk profile.

A rigid binary model (either fully manual or fully autonomous) is insufficient. Consider a user who trusts the AIS to reorder their calendar but not to send emails on their behalf. Similarly, a high-confidence routine task (e.g., sorting files) may warrant more autonomy than a low-confidence novel task (e.g., drafting a sensitive communication).

Several models were considered:

1. **Binary consent** — Every action requires explicit user approval. This is safe but creates severe interaction fatigue for routine operations.

2. **Whitelist-based** — Pre-approved actions execute autonomously; everything else requires consent. This is practical but lacks nuance and does not adapt to changing trust levels.

3. **Continuous spectrum** — A multi-level autonomy model where the degree of independence is continuously adjustable, providing granular control over what the AIS can do without user involvement.

The continuous spectrum approach was selected because it aligns with the Constitutional Principle of user control (CP-003) while still allowing the AIS to operate efficiently when trust and confidence are high.

## Decision

Adopt a **five-level Autonomy Spectrum** as the governing model for AIS action authority:

| Level | Name | Behaviour |
|-------|------|----------|
| L0 | Observe | AIS observes user behaviour and system state but takes no action. Used for learning and analysis only. |
| L1 | Suggest | AIS analyses the situation and presents suggestions to the user. The user must explicitly accept before any action is taken. This is the **default level**. |
| L2 | Act-on-Approval | AIS prepares an action plan and presents it for user approval. The user reviews and approves the plan before execution. |
| L3 | Act-and-Report | AIS executes actions autonomously within its current scope and reports results to the user after execution. No pre-approval required. |
| L4 | Autonomous | AIS operates fully autonomously within its defined scope. Actions are logged but not reported in real-time. Full audit trail is mandatory (see AL-012). |

**Key design rules:**

- **Default is L1 (Suggest):** New sessions and new users start at L1. This ensures the system never acts without the user's awareness unless they have explicitly elevated trust.

- **User-controllable:** The user can adjust the autonomy level at any time through the AIS interface. Level changes take effect immediately for subsequent actions.

- **Every action checked against current level:** Before the AIS executes any action, the AIS Controller checks the current autonomy level and either proceeds, requests approval, or presents a suggestion as appropriate.

- **Per-task and per-domain granularity:** The autonomy level can be set globally or overridden for specific tasks or domains (e.g., L3 for file management, L1 for email).

## Consequences

### Positive

- **Flexible trust model:** Users can calibrate the system's autonomy to their comfort level, building trust gradually as they observe the AIS's behaviour and reliability.

- **Reduced interaction fatigue:** For routine, high-confidence tasks at L2-L4, users are not burdened with approving every minor action.

- **Clear behavioural contract:** Each level has a well-defined contract, making it straightforward for developers to implement and for users to understand.

- **Adaptive:** The system can recommend autonomy level changes based on observed patterns, though the user always retains final control.

### Negative

- **Higher levels require stronger audit:** L3 and especially L4 require comprehensive audit logging (AL-012) to maintain accountability. This adds storage and processing overhead.

- **Implementation complexity:** Every action path in the AIS must include a level check, which adds branching logic throughout the codebase.

- **User education required:** Users must understand what each level means to make informed decisions. Poorly understood autonomy levels could lead to unexpected behaviour and eroded trust.

- **Potential for level drift:** If autonomy levels are too easy to change, users may inadvertently set them higher than intended, leading to actions they did not expect.

## Compliance

- **CP-003 (User Control):** The Autonomy Spectrum is entirely user-controlled; the system never elevates its own autonomy.
- **AL-012 (Audit Trail):** L4 Autonomous mode requires a full, immutable audit trail of all actions taken.
- **CP-015 (Transparency):** Each autonomy level's behaviour is clearly communicated to the user.
