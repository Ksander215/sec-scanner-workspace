# ADR-013: Refinement Strategy

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS architecture is not designed in a single waterfall phase. It evolves through iterative refinement as understanding deepens, requirements change, and implementation reveals new constraints. This is not a weakness but a deliberate strategy — the architecture must adapt to reality rather than forcing reality to fit an initial design.

However, unmanaged evolution leads to chaos: lost decisions, contradictory specifications, and inability to trace why a design choice was made. A formal refinement strategy is needed to ensure evolution is disciplined, traceable, and reversible.

Several approaches were considered:

1. **Revolutionary rewrite:** Discard the old version entirely and write a new one when significant changes are needed. This is clean but loses all history and context, making it impossible to understand the evolution of decisions.

2. **In-place mutation:** Edit documents in place, overwriting previous versions. This keeps the document current but loses the ability to trace what changed and why.

3. **Incremental versioned refinement:** Each task produces a new version of the affected documents (e.g., ARC-001.000 becomes ARC-001.001). Previous versions are preserved as a baseline. All changes are tracked in associated ADRs or DADRs (Decision ADRs).

The versioned refinement approach was selected as it provides full traceability while maintaining a clear current state.

## Decision

Adopt an **Incremental Refinement Model** with the following rules:

- **Versioned documents:** Every architectural document carries a version number in its filename (e.g., ARC-001.000). When a task modifies a document, it produces a new version with an incremented version number (e.g., ARC-001.001).

- **Baseline preservation:** Previous versions of documents are preserved in the baseline. They are not deleted or overwritten. The current version is the one with the highest version number.

- **Change tracking through ADR/DADR:** Every non-trivial change to an architectural document is accompanied by an ADR or DADR that records the rationale for the change, what was changed, and what the implications are.

- **Semantic versioning:** Version numbers follow a semantic pattern: MAJOR.MINOR. MAJOR increments indicate breaking changes; MINOR increments indicate non-breaking refinements.

- **Task-driven refinement:** Refinements are driven by specific tasks or change requests, not by speculative redesign. Each refinement has a clear trigger and scope.

## Consequences

### Positive

- **Stable evolution:** The system evolves incrementally, avoiding the disruption and risk of revolutionary rewrites.

- **Full history:** Every version of every document is preserved, enabling complete traceability of the architecture's evolution.

- **Reversibility:** If a refinement proves problematic, the previous version is available to support rollback.

- **Clear rationale:** ADR/DADR change records ensure that the reasoning behind every change is documented and discoverable.

### Negative

- **Accumulation of document versions:** Over time, the number of document versions grows. This requires a clear organisational structure and potentially archival policies for very old versions.

- **Version management overhead:** Maintaining version numbers, change records, and baseline preservation adds process overhead to every refinement task.

- **Potential version confusion:** If not managed carefully, users and developers may reference outdated versions of documents.

## Compliance

- **CP-018 (Documentation):** The refinement strategy ensures all architectural decisions are documented and traceable.
- **CP-019 (Transparency):** Versioned refinement makes the evolution of the architecture transparent to all stakeholders.
