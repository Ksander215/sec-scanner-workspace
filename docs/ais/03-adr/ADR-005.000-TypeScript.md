## 1. Context

The Adaptive Intelligence System (AIS) requires a contract language for all public interfaces: inter-module contracts (AL-002), Event Bus event types (ADR-002), Provider Abstraction interfaces (ADR-003), CLI command schemas (ADR-007), and Plugin manifests (ADR-006). These contracts must be:

**Machine-checkable**: Contracts should be validated by tools at compile time or deployment time, not only at runtime. Type mismatches, missing fields, and incompatible signatures should be caught as early as possible in the development cycle.

**Human-readable**: Developers must be able to read and understand contracts without specialised tooling. The contract language should be familiar to the development team and express intent clearly.

**Self-documenting**: A contract should document its own structure. Field names, types, and optional/required markers convey the interface semantics without a separate documentation layer (though supplementary documentation is encouraged).

**Runtime enforceable**: Contracts defined at the type level must be upheld at runtime. If a module declares that it accepts a `ConfidenceResult`, the runtime must ensure that the object received actually conforms to that shape, even if the caller is dynamically typed (e.g., a plugin written in JavaScript).

**IDE-supportable**: The contract language should integrate with modern development environments: autocomplete, go-to-definition, find-references, inline documentation, and refactoring tools.

AL-010 (TypeScript Is the Contract Language) is unambiguous: "All contracts within the AIS core are expressed in TypeScript types. Runtime is responsible for upholding what the types declare."

The alternatives considered were:

1. **JSON Schema**: Define contracts as JSON Schema documents. Rejected because JSON Schema is verbose, lacks IDE support for navigation and refactoring, and does not integrate with a programming language's type system.
2. **OpenAPI / Swagger**: Use OpenAPI specifications for interface contracts. Rejected because OpenAPI is HTTP-specific and does not cover in-process contracts, event schemas, or plugin manifests.
3. **Protocol Buffers / gRPC**: Use Protocol Buffers for schema definition. Rejected because it introduces a code-generation step, a separate schema language, and a runtime dependency. The current scale of AIS does not justify the complexity of a separate IDL.
4. **GraphQL Schema**: Use GraphQL schema definition language for contracts. Rejected because GraphQL is query-oriented and does not naturally express event schemas, internal module contracts, or plugin manifests.
5. **JSDoc / TSDoc only**: Use JSDoc comments for type documentation without TypeScript's type system. Rejected because JSDoc types are not machine-checked at compile time and do not provide the same level of safety and tooling integration.
6. **Multiple languages**: Allow each Functional Pillar to use its own contract language. Rejected because it fragments the codebase, prevents cross-pillar type checking, and violates AL-010.

## 2. Decision

**TypeScript is the contract language for all public interfaces within the AIS core.**

The following categories of artefacts are expressed as TypeScript types:

**Interface Contracts (IC-01 through IC-05)**: The public API of each core module (Adaptive Memory, Confidence Engine, Context Predictor, Notification Manager, Provider Factory) is expressed as a TypeScript interface. These are the contracts that modules agree upon and that the Event Bus coordinates through.

**Event Types**: All Event Bus event schemas (info, action, result, error, state-change) are defined as TypeScript types or interfaces. This ensures that publishers emit correctly shaped events and subscribers receive correctly typed payloads.

**Provider Interfaces**: The abstraction interfaces for LLM, Scanner, Storage, and Embedding providers are TypeScript interfaces. Provider implementations conform to these interfaces; Functional Pillars consume them through these interfaces.

**Plugin Manifest Schema**: The declarative manifest that describes a plugin's capabilities, permissions, and event subscriptions is defined as a TypeScript type. Plugin authors write manifests that conform to this schema.

**CLI Command Schemas**: The commands, arguments, options, and return types of the CLI (ADR-007) are expressed as TypeScript types, ensuring consistency between the CLI interface and the underlying API.

**Data Entities**: Core data entities (UserProfile, UserAction, ConfidenceResult, AISPrediction, AISNotification, ProviderInfo, PluginManifest, SessionContext) are defined as TypeScript types, with formal definitions in DOM-001.000 and DOM-002.000.

**Runtime enforcement**: Where TypeScript's compile-time checking is insufficient (e.g., data received from external sources, plugin inputs, configuration files), runtime validation is applied. Runtime validators (e.g., Zod, io-ts, or custom validators) ensure that data conforms to the declared TypeScript types at the point of entry into the AIS core.

## 3. Consequences

### 3.1 Positive

- **Compile-time safety**: TypeScript's type system catches mismatched interfaces, missing fields, and incompatible types at compile time. A module that tries to publish an event with the wrong shape fails during compilation, not at runtime. This reduces defects and increases developer confidence in cross-module interactions.
- **IDE support**: TypeScript has best-in-class IDE integration. Developers get autocomplete for all public interfaces, go-to-definition for event types, find-references for contract usage, and inline documentation from TSDoc comments. This accelerates development and reduces onboarding time.
- **Self-documenting contracts**: A TypeScript interface is its own documentation. The structure of `ConfidenceResult` — its fields, their types, and their optionality — is visible in the type definition. Supplementary documentation (TSDoc comments, ADR references) adds narrative, but the type itself is the primary source of truth for the interface shape.
- **Refactoring safety**: When a contract changes (e.g., a field is renamed or a method signature is updated), TypeScript's compiler identifies every location that depends on the old contract. The change can be propagated with confidence that no caller is left using the outdated interface.
- **Runtime validation alignment**: The same type definitions that drive compile-time checking can drive runtime validation. A runtime validator derived from the TypeScript type ensures that data entering the system from untrusted sources (plugins, external APIs, configuration files) conforms to the expected shape.
- **Ecosystem maturity**: TypeScript has a mature ecosystem of tooling: formatters (Prettier), linters (ESLint with TypeScript rules), bundlers (esbuild, Vite, Rollup), test frameworks (Vitest, Jest), and documentation generators (TypeDoc). This tooling supports the development workflow without bespoke solutions.

### 3.2 Negative

- **Vendor lock-in to the TypeScript ecosystem**: By choosing TypeScript as the contract language, AIS is locked into the TypeScript/JavaScript ecosystem. Switching to a different language would require rewriting all type definitions and all consuming code. This lock-in is accepted by the Architecture Council as a deliberate trade-off for the benefits of type safety and tooling.
- **Compile-time overhead**: TypeScript adds a compilation step that plain JavaScript does not require. Build times are longer. Mitigation: incremental compilation (TypeScript's `--watch` mode, project references) and fast bundlers (esbuild, Vite) minimise this overhead.
- **Type complexity ceiling**: TypeScript's type system is powerful but has limits. Highly abstract or recursive type definitions can become difficult to read and maintain. Mitigation: keep contract types pragmatic and focused. Avoid over-engineering types for edge cases that do not arise in practice.
- **Runtime type gap**: TypeScript types are erased at compile time. A `ConfidenceResult` interface compiles to a plain JavaScript object with no runtime type information. Mitigation: runtime validators (Zod, io-ts) bridge this gap for data entering from untrusted sources. For internal data flows within the AIS core (where all participants are TypeScript modules), compile-time checking is sufficient.
- **Plugin language constraint**: Plugins must interact with the AIS core through TypeScript-defined interfaces. Plugins written in other languages (Python, Rust, etc.) must use inter-process communication with JSON payloads that conform to the TypeScript-defined schemas. This adds complexity for non-TypeScript plugins but does not prevent them.

### 3.3 Neutral

- **TypeScript version**: The specific TypeScript version used by AIS is an implementation decision, not an architectural one. This ADR mandates that TypeScript is the contract language; the version is determined by the development team based on stability, feature requirements, and ecosystem compatibility.
- **Strictness level**: TypeScript's `strict` mode configuration (noImplicitAny, strictNullChecks, etc.) is an implementation decision. The Architecture Council recommends `strict` mode for maximum type safety, but the specific configuration is set at the development level.
- **Validation library**: The choice of runtime validation library (Zod, io-ts, class-validator, custom) is an implementation decision. This ADR mandates runtime validation; the specific tool is chosen at the development level.
