## 1. Context

The Adaptive Intelligence System (AIS) is composed of eight Functional Pillars (FP-01 through FP-08) that must coordinate without direct coupling. AL-008 (Events Are the Spine) mandates that cross-module coordination uses the Event Bus, and that direct method calls across module boundaries are forbidden outside the AIS Controller.

The system requires a coordination mechanism that satisfies the following constraints:

**Loose coupling**: FP-04 (Notification System) must react to confidence calculations from FP-03 without importing FP-03's code. FP-01 (Adaptive Memory) must update when the user interacts with FP-02's predictions without FP-02 knowing FP-01's internal structure. Any module should be testable in isolation with mock events, not real dependents.

**Typed communication**: Events carry structured data. A notification event, a confidence event, and a memory update event each have distinct schemas. The Event Bus must enforce type correctness so that subscribers receive only events matching their declared interest.

**Versioned evolution**: As AIS evolves, event schemas will change. New fields will be added; existing fields may be deprecated. The Event Bus must support event versioning without breaking existing subscribers that have not yet migrated to the new schema.

**Classified routing**: Events have different urgencies and trust implications. An `error` event has different routing and handling requirements than an `info` event. The Event Bus must support event classification to enable differentiated processing.

**Testability**: In testing scenarios, modules must be able to publish events and verify that the correct subscribers were notified, without standing up the full system. The Event Bus must be replaceable with a test double.

**Auditability**: Per AL-012 (Decisions Are Auditable), all cross-module coordination events should be traceable for debugging and audit purposes. The Event Bus must support event logging.

The alternatives considered were:

1. **Direct method calls**: Modules call each other's public methods directly. Rejected by AL-008 and CP-013 — this creates tight coupling and violates the "Composition over Coupling" principle.
2. **Shared state with observers**: Modules read/write a shared state object and react to changes. Rejected because it creates implicit coupling through shared state structure and makes the source of changes difficult to trace.
3. **External message broker (RabbitMQ, Kafka)**: Use an out-of-process message broker for event routing. Rejected for AIS Baseline v1.0 because the Modular Monolith (ADR-001) operates in a single process; an external broker adds operational overhead without proportional benefit at this scale. This option remains available for future consideration if the system transitions to microservices.
4. **Pub/Sub with topic strings**: Use string-based topic subscriptions. Rejected because string-based topics lack type safety and versioning, leading to runtime errors that should be caught at compile time.

---

## 2. Decision

**Adopt an Internal Event Bus as the coordination spine for all cross-module communication within AIS.**

The Event Bus is an in-process, asynchronous event dispatch mechanism with the following characteristics:

**Typed events**: Every event is a typed object (TypeScript class or interface, per ADR-005). The Event Bus enforces that publishers emit only declared event types and that subscribers declare which event types they handle.

**Versioned events**: Event types carry a version number (e.g., `AISPredictionEvent v2`). When an event schema evolves, a new version is declared. The Event Bus supports routing events to subscribers based on version compatibility. Subscribers declare the minimum version they support; events are delivered to subscribers that can handle them.

**Classified events**: Every event carries a classification from the following set:

| Classification | Description |
|----------------|-------------|
| `info` | Low-impact, informational. No action required. Logged for traceability. |
| `action` | Carries a request for execution. Triggers downstream processing. |
| `result` | Carries the outcome of an action. Completes an action-result cycle. |
| `error` | Carries an error condition. Triggers error handling flows. |
| `state-change` | Carries a state transition notification. Triggers state synchronisation. |

**No direct cross-module calls**: Direct method calls from one Functional Pillar to another are forbidden except within the AIS Controller (FP-01), which serves as the unified entry point. All other cross-Pillar communication goes through the Event Bus.

**Event logging**: The Event Bus maintains an append-only event log for auditability (AL-012). Each logged event includes timestamp, event type, classification, publisher module, and payload hash.

**Subscriber isolation**: Each subscriber processes events in its own execution context. A failing subscriber does not block or affect other subscribers of the same event.

## 3. Consequences

### 3.1 Positive

- **Loose coupling**: Modules communicate without importing each other's code. FP-03 publishes a confidence event; FP-04 subscribes to it. Neither knows the other's implementation. This satisfies CP-013 and AL-008.
- **Testability in isolation**: Each module can be tested by publishing synthetic events and asserting on the module's behaviour, without instantiating its real dependents. The Event Bus interface can be mocked or replaced with a test implementation that captures and inspects events.
- **Typed correctness**: Because events are TypeScript types (per ADR-005), compile-time checking prevents mismatched event publishers and subscribers. A module that publishes an event with the wrong shape fails at compile time, not at runtime.
- **Versioned evolution**: New event versions can be introduced without breaking existing subscribers. Subscribers declare their minimum version; the Event Bus routes accordingly. This supports the incremental evolution model described in ADR-013.
- **Auditability**: The event log provides a complete trace of cross-module coordination. For any user-visible action, the sequence of events leading to that action can be reconstructed from the log.
- **Subscriber isolation**: A failure in one subscriber does not cascade to others. The Event Bus catches errors in subscriber handlers and routes them to the error classification for separate processing.

### 3.2 Negative

- **Event ordering complexity**: In an asynchronous event system, the order in which events are processed is not guaranteed to match the order in which they were published. If FP-02 publishes two events in sequence, a subscriber might receive them out of order. Mitigation: events that require ordering carry a sequence number, and subscribers can buffer and reorder if needed.
- **Implicit flow tracing**: Unlike direct method calls, where the call stack makes control flow explicit, event-driven flow is harder to trace visually. Developers must reason about cause-and-effect across event publishers and subscribers. Mitigation: the event log and debugging tools that visualise event flows.
- **Event explosion risk**: In a highly interactive system, the number of events can grow rapidly. Each user action may trigger multiple events across multiple modules. Mitigation: event deduplication, batching, and classification-based filtering to reduce noise.
- **Debugging complexity**: Debugging an event-driven system requires following events across multiple modules, which is more complex than stepping through a synchronous call chain. Mitigation: event correlation IDs that link related events, and debug views that aggregate events by correlation ID.
- **Synchronous expectations**: Some cross-module interactions have an inherent synchronous nature (e.g., "what is the user's current confidence level?"). The Event Bus is inherently asynchronous. For synchronous queries, the pattern is: the requester publishes a query event and awaits a response event, with a timeout. This adds latency compared to a direct method call. Mitigation: the AIS Controller (FP-01) may perform synchronous reads of module state for internal coordination, as this is explicitly permitted by AL-008.

### 3.3 Neutral

- **Performance characteristics**: In-process event dispatch is fast (microseconds per event), but adds overhead compared to direct method calls (nanoseconds). For the current scale of AIS, this overhead is negligible. If performance becomes a concern, hot-path events can be optimised through direct reads within the AIS Controller's permitted scope.
- **Event Bus implementation**: The Event Bus is a core infrastructure component. Its implementation must be reliable, well-tested, and well-documented. However, the choice of specific implementation (e.g., EventEmitter, custom dispatcher, third-party library) is an implementation concern, not an architectural decision. This ADR defines the contract; the implementation is chosen at the development level (D8).
