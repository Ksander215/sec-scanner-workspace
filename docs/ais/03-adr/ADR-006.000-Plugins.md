## 1. Context

The Adaptive Intelligence System (AIS) needs extensibility beyond its core eight Functional Pillars. Extensions may come from internal teams (custom integrations, domain-specific analysis modules) or from third parties (community plugins, partner integrations). The Plugin Platform (FP-08) provides this extensibility.

The architectural decision must address the following forces:

**Extensibility without core changes**: Plugins must be able to add new functionality to AIS without modifying the core codebase. Adding a new plugin should not require recompiling, redeploying, or re-testing the AIS core. The core must remain stable while plugins evolve independently.

**Safety and isolation**: Plugins run code that is not part of the AIS core. This code may be buggy, malicious, or simply unfamiliar to the AIS team. The system must protect the core from plugin failures, plugin misbehaviour, and plugin compromise. AL-011 (Plugins Cannot Escalate) is unambiguous: "Plugins operate inside Trust Zone Z2 by default. They cannot elevate themselves, cannot read outside their declared scope, and cannot subscribe to events above their declared classification."

**Declarative intent**: Plugins must declare their capabilities, permissions, and event subscriptions in advance. The AIS core inspects this declaration before loading the plugin and can reject plugins whose declarations exceed their trust level or whose permissions are too broad.

**Versioned compatibility**: The plugin manifest and the AIS core API both evolve. The Plugin Platform must handle version mismatches gracefully: a plugin written for AIS v1.0 should fail clearly if loaded into AIS v2.0 with breaking API changes.

**No elevation path**: By design, plugins cannot gain privileges beyond what they declare. There is no mechanism for a plugin to request additional permissions at runtime, no mechanism for a plugin to access data outside its declared scope, and no mechanism for a plugin to subscribe to events above its declared classification. This is a security invariant, not a policy that can be relaxed.

**Discoverability**: Users and administrators must be able to discover available plugins, understand their capabilities, and manage their lifecycle (install, enable, disable, remove) without reading source code.

The alternatives considered were:

1. **No plugin system**: All extensibility requires changes to the AIS core. Rejected because it centralises all development on the core team and prevents the community from contributing functionality.
2. **Full API access**: Plugins can call any internal AIS API. Rejected because it violates AL-011, AL-006 (Trust Zones), and CP-005 (Local Sovereignty). Unrestricted plugin access is a security vulnerability.
3. **Dynamic code loading without sandboxing**: Plugins can load arbitrary code at runtime without isolation. Rejected because it provides no protection against plugin failures or compromise.
4. **Microservice plugins**: Plugins run as separate processes and communicate via HTTP or gRPC. Rejected for AIS Baseline v1.0 because the Modular Monolith (ADR-001) operates in-process. Out-of-process plugins add operational complexity disproportionate to current needs. This remains a future option if the plugin ecosystem requires it.

## 2. Decision

**AIS provides a Plugin Platform with declarative manifests, sandboxed execution, and no elevation path.**

The Plugin Platform has the following characteristics:

**Declarative manifest**: Every plugin is accompanied by a manifest file (PluginManifest, per ARC-001.001 §7) that declares:

- **Plugin identity**: Name, version, author, description.
- **AIS compatibility**: Minimum and maximum AIS core version required.
- **Permissions**: The specific data and operations the plugin needs. Permissions are granular (e.g., "read session memory", "publish info events", "write to reports directory") and scoped to the plugin's purpose.
- **Event subscriptions**: The specific event types and classifications the plugin subscribes to. A plugin cannot subscribe to events above its declared classification (per AL-011).
- **Entry point**: The function or module that the Plugin Host calls to initialise the plugin.

**Z2 sandbox execution**: Plugins execute inside Trust Zone Z2 (Plugin Sandbox). The sandbox provides:

- **Scoped read/write access**: The plugin can read and write only within the directories and data scopes declared in its manifest. Attempts to access data outside this scope are blocked at runtime.
- **No direct AIS internal access**: The plugin cannot import or reference AIS internal modules. All interaction with the AIS core goes through the declared permissions and event subscriptions.
- **Resource limits**: The plugin's execution is subject to resource limits (CPU time, memory allocation, network access) to prevent denial-of-service by a misbehaving plugin.

**No elevation path**: There is no mechanism for a plugin to:

- Request additional permissions at runtime beyond what its manifest declares.
- Access data outside its declared scope, even if the data is on the same file system.
- Subscribe to events above its declared classification.
- Execute code in Trust Zone Z1 (Core AIS) or Z3 (Provider Interface) directly.
- Modify AIS core state except through declared event publications and permission-scoped writes.

Any attempt to escalate is logged (AL-012), blocked, and reported as a security event.

**Plugin lifecycle**: The Plugin Host (FP-08) manages the lifecycle of each plugin:

- **Discovery**: Scan configured plugin directories for manifest files.
- **Validation**: Verify manifest schema, AIS version compatibility, and permission scope.
- **Loading**: Instantiate the plugin in the Z2 sandbox with declared permissions.
- **Activation**: Connect the plugin's event subscriptions to the Event Bus.
- **Monitoring**: Watch for resource limit violations, errors, and misbehaviour.
- **Deactivation**: Disconnect event subscriptions and terminate the plugin instance.
- **Removal**: Delete the plugin's artefacts from the plugin directory.

**Plugin result sanitisation**: When a plugin publishes an event or writes data, the Plugin Host sanitises the output through Gate G-04 (Z2 → Z1). The sanitisation includes schema validation, size limits, and content filtering. This prevents a plugin from injecting malformed data into the AIS core.

## 3. Consequences

### 3.1 Positive

- **Extensible without core changes**: New functionality is added by installing a plugin, not by modifying the AIS core. The core remains stable; plugins evolve independently. This supports CP-013 (Composition over Coupling) at the ecosystem level.
- **Sandboxed execution**: The Z2 sandbox protects the AIS core from plugin failures, misbehaviour, and compromise. A crashing plugin does not crash the AIS core. A malicious plugin cannot access data outside its declared scope.
- **Declarative transparency**: The manifest makes each plugin's intentions visible before loading. Administrators can review a plugin's permissions and event subscriptions and make informed decisions about whether to install it.
- **Security by design**: The no-elevation-path invariant is enforced at the architecture level, not at the policy level. A plugin cannot bypass this restriction through clever coding or social engineering — the sandbox mechanism physically prevents it.
- **Community enablement**: Third parties can develop and distribute plugins for AIS without access to the core codebase. The plugin manifest and the Plugin Host API define the contract that plugin authors implement against.
- **Controlled experimentation**: New features can be developed as plugins, tested in production, and later promoted to core functionality if they prove valuable. This reduces the risk of bloating the core with experimental features.

### 3.2 Negative

- **Limited plugin capability**: By design, plugins cannot access AIS internals, cannot elevate their permissions, and cannot subscribe to all events. This limits what plugins can do. A plugin that needs deep access to the AIS core cannot be implemented as a plugin; it must be proposed as a core change.
- **Sandbox overhead**: The Z2 sandbox adds runtime overhead to plugin execution. Permission checks, resource monitoring, and event sanitisation all consume CPU and memory. For lightweight plugins, this overhead is negligible; for resource-intensive plugins, it may be noticeable.
- **Manifest maintenance**: Plugin manifests must be updated when the AIS core API evolves. A plugin written for AIS v1.0 may need a manifest update for AIS v1.1. This creates a maintenance burden for plugin authors. Mitigation: the Plugin Host provides clear error messages when version mismatches are detected, and the manifest schema includes version ranges to minimise breakage.
- **Plugin debugging complexity**: Debugging a plugin requires understanding both the plugin code and the sandbox constraints. A plugin failure may be caused by the plugin code, by a permission denial, or by a resource limit. Mitigation: the Plugin Host provides detailed error reporting that distinguishes between these causes.
- **No hot reload (in baseline)**: Loading and unloading plugins at runtime without restarting AIS is not a baseline requirement. The current model requires a restart to add or remove plugins. Hot reload is deferred to a future enhancement.

### 3.3 Neutral

- **Plugin distribution**: The mechanism for distributing plugins (file-based, registry-based, package manager) is an implementation detail. This ADR defines the plugin architecture; distribution is a tooling concern.
- **Plugin authoring language**: Plugins may be written in TypeScript (preferred, for type safety with the manifest schema) or in JavaScript. Plugins in other languages require inter-process communication, which is supported but adds complexity. The Plugin Host determines the plugin's language from its manifest.
- **Plugin signing**: Cryptographic signing of plugins (to verify author identity and detect tampering) is deferred. The current model trusts the plugin directory and its access controls. Plugin signing may be added in a future baseline without architectural changes.

## 4. Compliance

This ADR satisfies the following Constitutional Principles and Architectural Laws:

| CP/AL | Relevance |
|-------|-----------|
| CP-005 — Local Sovereignty | Plugins enter the user's workspace only through consent and only to the extent declared in their manifest. |
| CP-013 — Composition over Coupling | The Plugin Platform enables composition (core + plugins) without coupling (plugins cannot access core internals). |
| AL-006 — Trust Zones Are Explicit | Plugins operate in Z2 with no access to Z0, Z1, or Z3 directly. |
| AL-011 — Plugins Cannot Escalate | This ADR is the direct operationalisation of AL-011. Plugins are sandboxed with no elevation path. |
| AL-012 — Decisions Are Auditable | All plugin load/unload events, permission denials, and escalation attempts are logged. |
| Gate G-04 (Z2 → Z1) | Plugin results are sanitised at the zone boundary before entering the AIS core. |
