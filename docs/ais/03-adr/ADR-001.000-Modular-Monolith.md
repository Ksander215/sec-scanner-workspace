## 1. Context

The Adaptive Intelligence System (AIS) requires a deployment and codebase architecture that balances simplicity of operation with the modularity needed to support eight distinct Functional Pillars (FP-01 through FP-08). The architectural decision must account for the following forces:

**Simplicity of deployment**: AIS is initially a single-user or small-team system. A distributed microservices architecture would introduce operational complexity (container orchestration, network configuration, service discovery, distributed tracing) that is disproportionate to the current scale and team size.

**Modularity of design**: CP-013 (Composition over Coupling) mandates that AIS is composed of cooperating modules with explicit boundaries. Regardless of the deployment topology, the internal architecture must enforce strong separation between Functional Pillars.

**Future scalability**: While the current scale does not demand microservices, the architecture must not preclude a future split. The transition path from monolith to distributed services must be achievable without a rewrite.

**Development velocity**: A single codebase reduces friction in cross-pillar development. Developers can navigate, build, test, and debug all Functional Pillars in a single project without managing multiple repositories, inter-service contracts, or version synchronization.

**Operational cost**: Running a single process with an in-process Event Bus eliminates the need for external message brokers, service meshes, or container orchestration platforms during the initial development and deployment phases.

The alternative architectures considered were:

1. **Distributed Microservices**: Each Functional Pillar as an independent service with its own deployment, database, and network endpoint. Rejected due to premature distribution overhead and team size mismatch.
2. **Monolithic Core with Plugin Extensions**: A tightly coupled core with extensibility only through the plugin mechanism. Rejected because it would violate CP-013 by failing to enforce internal module boundaries.
3. **Service-Oriented Architecture (SOA)**: A middle ground with a few coarse-grained services. Rejected due to unclear service boundary definitions at this stage of the programme.

---

## 2. Decision

**Adopt the Modular Monolith pattern as the deployment and codebase architecture for AIS.**

All eight Functional Pillars (FP-01 through FP-08) reside in a single codebase and execute within a single process. Modules are separated by explicit interfaces (per AL-002: Boundary by Contract) and coordinate through the Event Bus (per AL-008: Events Are the Spine). Direct cross-module method calls are forbidden outside the AIS Controller.

The split into microservices is explicitly **deferred** until evidence of need arises. Evidence of need is defined as one or more of the following measurable conditions:

- A Functional Pillar requires independent scaling that cannot be achieved through process-level optimisation.
- A Functional Pillar's deployment cadence is materially different from the rest of the system.
- Team ownership boundaries require independent deployment pipelines for specific Pillars.
- Performance profiling demonstrates that in-process communication is a bottleneck for a specific Pillar.

Until such evidence is documented in a formal ADR amendment, the Modular Monolith is the binding architecture.

## 3. Consequences

### 3.1 Positive

- **Simpler deployment**: A single binary or process deployment reduces operational complexity. No container orchestration, no service discovery, no inter-service networking configuration. Deployment is a single step: start the process.
- **Shared memory**: All modules share the same memory space, enabling high-performance in-process communication through the Event Bus and shared data structures. This eliminates serialisation/deserialisation overhead inherent in distributed systems.
- **Lower operational overhead**: No need for distributed tracing infrastructure, log aggregation across services, or inter-service authentication mechanisms during initial phases.
- **Faster development**: Developers work in a single repository with a single build system. Cross-pillar refactoring is a single commit. No need to version and publish inter-service API contracts.
- **Simpler testing**: Integration tests can exercise the full system in a single process. No need for test containers, service stubs, or contract testing between services.
- **Clear transition path**: Because modules are already separated by explicit interfaces and the Event Bus, extracting a module into a microservice requires changing the communication mechanism (in-process to network) without changing the module's logic. The interface contract remains the same.

### 3.2 Negative

- **Risk of tight coupling**: Without discipline, developers may introduce direct cross-module dependencies, bypassing the Event Bus and violating AL-008. This risk is mitigated by two controls: (a) DR-02 (Event-Driven Coordination) which explicitly forbids direct cross-FP method calls, and (b) AL-002 (Boundary by Contract) which requires all inter-module interaction to go through published, versioned contracts.
- **Single point of failure**: A process crash affects all Functional Pillars simultaneously. This is accepted at the current scale. Mitigation includes process supervision, health checks, and graceful degradation within each Pillar.
- **Resource contention**: All Pillars share CPU, memory, and I/O within a single process. A resource-intensive Pillar (e.g., a long-running LLM call in FP-06) could affect the responsiveness of other Pillars. Mitigation includes async processing, worker pools, and resource quotas at the Pillar level.
- **Technology lock-in per language**: All Pillars share the same runtime (Node.js/TypeScript, per ADR-005). If a Pillar were to benefit from a different language (e.g., a Python-based ML component), it would require an out-of-process approach or embedding, which adds complexity.

### 3.3 Neutral

- **Build times**: As the codebase grows, build times will increase. This is a natural consequence of any monolith and is managed through incremental compilation, module-level build caching, and selective testing strategies.
- **Code organisation**: The single codebase must be organised with clear directory boundaries per Functional Pillar. The project structure must make module boundaries visible and enforceable at the tooling level (e.g., lint rules preventing cross-pillar imports outside declared contracts).
