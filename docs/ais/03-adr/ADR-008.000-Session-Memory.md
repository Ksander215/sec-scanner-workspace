# ADR-008: Session Memory

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS system needs to maintain user state across the duration of an interactive session. This includes conversation history, user preferences surfaced during the session, intermediate task results, and contextual cues that inform the system's behaviour within that session window.

Several approaches were considered for managing this state:

1. **Server-side persistent storage** — Storing all session data in a database or remote store, requiring network calls on every state read/write. This introduces latency, server dependency, and operational complexity for what is fundamentally ephemeral data.

2. **In-memory only with no persistence** — Keeping state purely in process memory. This is fast but loses all data on page refresh, browser crash, or accidental navigation.

3. **Session-based memory with boundary persistence** — Holding state in memory during the active session for fast access, and persisting to local storage (browser localStorage or equivalent) at session boundaries (start, end, periodic flushes). This balances speed with durability.

The AIS operates primarily as a client-side intelligent system. Relying on server-side persistence for session state would contradict the design goal of minimising server dependency and ensuring the system remains functional even when disconnected from backend services. However, losing all session state on a crash would severely degrade user experience and trust.

Additionally, the session context must be aggregated and curated by the AIS Controller to ensure that the memory is coherent, relevant, and does not grow unbounded. Raw accumulation of every interaction would lead to noisy, low-quality context that degrades AIS reasoning over time.

## Decision

Adopt a **session-based memory model** with the following characteristics:

- **In-memory state during session:** All active session data (conversation turns, task state, user cues, preferences) is held in process memory for immediate, low-latency access by the AIS Controller and its subsystems.

- **Persistence at session boundaries:** State is flushed to local storage (browser localStorage or IndexedDB) at defined session boundaries — specifically on session start (restore), session end (explicit save), and periodic intervals (auto-flush) to mitigate data loss from unexpected termination.

- **AIS Controller as memory aggregator:** The AIS Controller is responsible for aggregating, summarising, and curating session context. It determines what is retained, what is summarised, and what is discarded as the session progresses. This ensures the memory remains coherent and relevant rather than growing into an unmanageable log.

- **Session lifecycle:** A session begins when the user initiates interaction with the AIS and ends when the user explicitly closes the session, navigates away, or a configurable timeout expires. Session data from a previous session can be restored to provide continuity.

- **No server-side dependency for memory:** The session memory model operates entirely client-side. Server-side storage may be used for backup or cross-device synchronisation in future, but is not required for core session memory functionality.

## Consequences

### Positive

- **Fast access:** In-memory state provides sub-millisecond access times for all session data, ensuring the AIS Controller and subsystems can read and write state without latency concerns.

- **No server dependency:** The system does not require a server connection to maintain session state, supporting offline and degraded-mode operation.

- **Simplified architecture:** Removing the need for a session database or server-side session store reduces infrastructure complexity and operational overhead.

- **User control:** Local storage means the user can inspect, clear, or manage their session data directly through browser tools.

- **Curated context:** The AIS Controller's aggregation role ensures session memory remains high-quality and relevant, rather than degrading into noise.

### Negative

- **Risk of data loss on crash:** If the browser or tab crashes between periodic flushes, unsaved session data may be lost. This is mitigated by periodic auto-flush (configurable interval, recommended 30-60 seconds) and save-on-significant-state-change triggers.

- **Storage limits:** Browser local storage has size limits (typically 5-10 MB for localStorage, higher for IndexedDB). Long sessions with rich data may approach these limits, requiring the AIS Controller to manage memory size proactively through summarisation and eviction.

- **No cross-device continuity:** Session memory is device-local. A user switching devices will not have access to their previous session state unless cross-device synchronisation is added later.

- **Serialization overhead:** Flushing to local storage requires serialising and deserialising session state, which adds computational overhead at flush boundaries.

## Compliance

- **CP-003 (User Control):** Session memory is stored locally, giving the user direct control over their data.
- **CP-005 (Privacy):** No session data is transmitted to servers as part of the memory model.
