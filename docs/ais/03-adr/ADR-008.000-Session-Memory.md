> **Architecture Note (TASK-AIS-002D.000):** This ADR was originally authored for a client-side browser-based deployment model. The Architecture Baseline v1.0 (ARC-001.001) subsequently adopted the **Modular Monolith** pattern (ADR-001) with **file-system storage** (ADR-004). The session persistence mechanism described below (localStorage / IndexedDB) applies to the **client-side presentation layer only** and does not govern server-side session state. Server-side session memory follows ADR-001 (in-process memory) and ADR-004 (file-based persistence at session boundaries). This ADR is retained for its session lifecycle, aggregation, and curation decisions, which remain valid regardless of deployment model.

---

## Context

The AIS system needs to maintain user state across the duration of an interactive session. This includes conversation history, user preferences surfaced during the session, intermediate task results, and contextual cues that inform the system's behaviour within that session window.

Several approaches were considered for managing this state:

1. **Server-side persistent storage** — Storing all session data in a database or remote store, requiring network calls on every state read/write. This introduces latency, server dependency, and operational complexity for what is fundamentally ephemeral data.

2. **In-memory only with no persistence** — Keeping state purely in process memory. This is fast but loses all data on process restart, crash, or accidental termination.

3. **Session-based memory with boundary persistence** — Holding state in memory during the active session for fast access, and persisting to stable storage at session boundaries (start, end, periodic flushes). This balances speed with durability. Per ADR-004, persistence uses the file system with stable, semantically meaningful paths.

Additionally, the session context must be aggregated and curated by the AIS Controller to ensure that the memory is coherent, relevant, and does not grow unbounded. Raw accumulation of every interaction would lead to noisy, low-quality context that degrades AIS reasoning over time.

---

## Decision

Adopt a **session-based memory model** with the following characteristics:

- **In-memory state during session:** All active session data (conversation turns, task state, user cues, preferences) is held in process memory for immediate, low-latency access by the AIS Controller and its subsystems.

- **Persistence at session boundaries:** State is flushed to stable storage at defined session boundaries — specifically on session start (restore), session end (explicit save), and periodic intervals (auto-flush) to mitigate data loss from unexpected termination. Per ADR-001 and ADR-004, the server-side AIS process uses file-system storage; the client-side presentation layer may use browser-local storage for UI state continuity.

- **AIS Controller as memory aggregator:** The AIS Controller is responsible for aggregating, summarising, and curating session context. It determines what is retained, what is summarised, and what is discarded as the session progresses. This ensures the memory remains coherent and relevant rather than growing into an unmanageable log.

- **Session lifecycle:** A session begins when the user initiates interaction with the AIS and ends when the user explicitly closes the session, navigates away, or a configurable timeout expires. Session data from a previous session can be restored to provide continuity.

---

## Consequences

### Positive

- **Fast access:** In-memory state provides sub-millisecond access times for all session data, ensuring the AIS Controller and subsystems can read and write state without latency concerns.

- **Curated context:** The AIS Controller's aggregation role ensures session memory remains high-quality and relevant, rather than degrading into noise.

- **Consistent with Modular Monolith:** Server-side session state follows the single-process model of ADR-001 and file-system persistence of ADR-004.

### Negative

- **Risk of data loss on crash:** If the process crashes between periodic flushes, unsaved session data may be lost. This is mitigated by periodic auto-flush (configurable interval) and save-on-significant-state-change triggers.

- **No cross-device continuity:** Session memory is device-local by default. A user switching devices will not have access to their previous session state unless cross-device synchronisation is added later.

---

## Compliance

- **CP-005 (Local Sovereignty):** Session memory is stored locally, giving the user direct control over their data.
- **CP-021 (Privacy of Profile):** No session data is transmitted to external parties without explicit consent.
- **ADR-001 (Modular Monolith):** Session memory operates within the single AIS process.
- **ADR-004 (File Storage):** Persisted session data uses file-system storage with stable paths.
