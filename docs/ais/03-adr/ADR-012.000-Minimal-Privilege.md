# ADR-012: Minimal Privilege

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS system is extensible through plugins (ADR-006) and interacts with external providers (ADR-003). Both extension points introduce code and data flows that are not under the direct control of the core system. Without a formal privilege model, a compromised or poorly designed plugin could access data or perform actions far beyond its intended scope.

Several approaches were considered:

1. **No privilege restriction:** All components have full access to the system. This maximises flexibility but creates an unacceptable security risk.

2. **Role-based access control (RBAC):** Components are assigned roles with pre-defined permission sets. This is practical but roles tend to be coarse-grained and the number of roles can grow unmanageably.

3. **Declared minimal privilege:** Every module and plugin explicitly declares the permissions it requires at initialisation time. The runtime enforces these declarations, denying any access beyond the declared scope. This is the principle of least privilege applied at the component level.

The declared minimal privilege approach was selected because it provides the strongest security guarantees while remaining practical for a plugin-based architecture.

## Decision

Adopt a **Minimal Privilege** model with the following characteristics:

- **Permission declaration at init:** Every module and plugin must declare its required permissions at initialisation time. This declaration is part of the plugin manifest (for plugins) or module configuration (for core modules).

- **Runtime enforcement:** The runtime monitors all access requests and denies any that fall outside the declared permission scope. This enforcement is implemented at the Trust Boundary gates (ADR-010, Z2 boundary).

- **Z2 default with no elevation path:** Plugins operate in Z2 (Plugin Sandbox) by default. There is no mechanism for a plugin to elevate its own privileges at runtime. If a plugin needs additional permissions, it must be reinstalled with an updated manifest and the user must explicitly approve the new permissions.

- **Permission categories:** Permissions are organised into categories: data read, data write, action execution, network access, and system configuration. Each category has granular sub-permissions.

- **User visibility:** The user can inspect any plugin or module's declared permissions through the AIS interface.

## Consequences

### Positive

- **Reduced attack surface:** By restricting each component to its declared minimum, the system limits what an attacker can achieve by compromising any single component.

- **Plugins cannot exceed their declared intent:** Even if a plugin is compromised or behaves maliciously, it cannot access data or perform actions beyond what it declared at install time.

- **Clear security audit:** The permission declarations provide a clear, auditable record of what each component is authorised to do.

### Negative

- **Requires careful permission design upfront:** Plugin developers must thoroughly analyse their permission requirements before initialisation. Under-declaring permissions causes runtime failures; over-declaring reduces security.

- **No dynamic permission adjustment:** The inability to elevate permissions at runtime means plugins cannot adapt to new requirements without reinstallation. This limits plugin flexibility.

- **Permission declaration complexity:** Designing a granular yet practical permission taxonomy requires significant upfront investment.

## Compliance

- **CP-006 (Security):** Minimal privilege is a core security mechanism.
- **CP-003 (User Control):** Users can inspect and approve permission declarations.
- **ADR-010 (Trust Boundaries):** Permission enforcement is implemented at trust boundary gates.
