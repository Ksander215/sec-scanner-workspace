# ADR-014: Domain Model Structure

**Version:** 000
**Status:** ACCEPTED
**Date:** 2025-01-01
**Owner:** AIS Architecture

---

## Context

The AIS system operates in a complex domain with multiple interacting concepts: users, sessions, tasks, plugins, providers, goals, preferences, and constitutional principles. Without a formal domain model, the system risks inconsistency in how these concepts are represented, related, and evolved.

Several approaches were considered:

1. **Ad-hoc data structures:** Define data structures as needed during implementation. This is fast initially but leads to inconsistency, duplication, and difficulty reasoning about the system.

2. **Database-first modelling:** Design the domain around database tables and relationships. This optimises for persistence but constrains the domain model to storage concerns.

3. **DDD-inspired domain model:** Adopt Domain-Driven Design concepts including bounded contexts, aggregates, value objects, domain events, and state machines. This provides a rich, formal model that captures domain complexity while maintaining clear boundaries.

The DDD-inspired approach was selected because the AIS domain is complex enough to benefit from formal modelling, and the bounded context pattern aligns naturally with the modular monolith architecture (ADR-001).

## Decision

Adopt a **DDD-inspired Domain Model Structure** with the following elements:

- **Bounded contexts:** The AIS domain is divided into bounded contexts that align with the modular architecture: Core Context (user, session, task), Provider Context (AI provider interaction), Plugin Context (plugin lifecycle and sandbox), Constitutional Context (principles, rights, constraints), and Memory Context (session and long-term memory).

- **Aggregates:** Each bounded context defines aggregates with clear consistency boundaries. For example, the User aggregate (in Core Context) owns the user's profile, goals, and preferences as a single consistency unit.

- **Value objects:** Immutable value objects represent concepts without identity, such as TrustLevel, PermissionSet, and Configuration.

- **Domain events:** Significant state changes are emitted as domain events (e.g., UserGoalChanged, PluginInstalled, SessionStarted). These events drive the event bus (ADR-002) and enable reactive behaviour.

- **State machines:** Entities with defined lifecycles use state machines to enforce valid state transitions (e.g., a Task transitions through Proposed, Approved, Executing, Completed, Failed).

- **Entity lifecycle and ownership:** Every entity has a defined lifecycle (creation, activation, deactivation, deletion), a clear owner (user, system, or provider), and invariants that must hold at all times.

- **Ubiquitous Language versioned:** The domain model's terminology (Ubiquitous Language) is versioned and documented, ensuring that all stakeholders share a common vocabulary. Changes to the language are tracked through the refinement strategy (ADR-013).

## Consequences

### Positive

- **Rich domain model:** The formal model captures domain complexity in a structured, maintainable way that supports reasoning and communication.

- **Clear boundaries:** Bounded contexts provide clear ownership and consistency boundaries, reducing coupling between modules.

- **Event-driven reactivity:** Domain events enable loose coupling between components and support the event bus architecture (ADR-002).

### Negative

- **Initial overhead in formalisation:** Defining aggregates, value objects, events, and state machines requires significant upfront investment before implementation can begin.

- **Potential over-engineering:** For simpler domains, DDD can introduce unnecessary abstraction. The AIS must be judicious about where formal modelling adds value.

- **Learning curve:** Team members must understand DDD concepts to work effectively with the domain model.

## Compliance

- **CP-018 (Documentation):** The domain model is a core part of the architectural documentation.
- **ADR-001 (Modular Monolith):** Bounded contexts align with module boundaries.
- **ADR-002 (Event Bus):** Domain events feed the event bus.
