## 1. Context

The Adaptive Intelligence System (AIS) serves its users through multiple interfaces. While the primary interaction model is proactive assistance delivered through the GUI (notifications, panels, adaptive suggestions), there are compelling use cases for a command-line interface (CLI):

**Automation and scripting**: Power users, DevOps engineers, and CI/CD pipelines need to interact with AIS programmatically. A CLI enables scripting of repetitive tasks, integration with shell workflows, and automation of AIS operations (e.g., batch confidence report generation, session memory export, plugin management).

**Headless environments**: AIS may be deployed in server-side, headless, or batch-processing contexts where no GUI is available. A CLI provides the primary — or sole — interaction mechanism in these environments.

**Developer tooling**: During development and testing, engineers need to invoke AIS capabilities from the terminal for debugging, profiling, and integration testing. A CLI provides immediate, scriptable access without starting a GUI.

**CI integration**: Continuous integration pipelines need to invoke AIS operations as build steps. A CLI with exit codes and structured output (JSON) enables CI tools to detect failures, parse results, and gate pipeline stages on AIS outputs.

**Compliance and audit**: Compliance officers may need to query AIS state, export audit logs, and generate reports from the command line. A CLI provides these capabilities without requiring GUI access to the AIS instance.

The architectural decision must address the following forces:

**API parity**: The CLI should provide access to the same capabilities as the API. If a GUI operation can trigger a confidence calculation, the CLI should be able to trigger the same calculation. Feature gaps between interfaces create user confusion and maintenance burden.

**First-class status**: The CLI is not a secondary, bolt-on interface. It is a first-class interface with its own design, testing, documentation, and release cadence. It receives the same level of attention as the GUI.

**Structured output**: For scripting and CI integration, the CLI must support structured output (JSON, optionally YAML). Human-readable output (coloured, formatted) is the default for interactive use; structured output is available via a flag.

**Exit codes**: The CLI must use standard exit codes (0 for success, non-zero for failure) so that shell scripts and CI tools can detect and handle errors programmatically.

**Type safety**: CLI command schemas (arguments, options, return types) are expressed as TypeScript types (per ADR-005), ensuring consistency between the CLI interface and the underlying API.

**Discovery**: Users must be able to discover available commands, understand their arguments, and access built-in help without external documentation. The CLI provides `--help` for every command and a top-level command listing.

The alternatives considered were:

1. **GUI only**: No CLI; all interaction through the graphical interface. Rejected because it prevents automation, scripting, and headless operation.
2. **HTTP API only**: Provide a REST or GraphQL API for programmatic access, without a dedicated CLI. Rejected because a CLI wrapper around an HTTP API is inevitable for power users; designing the CLI as a first-class interface from the start ensures a better user experience.
3. **Separate CLI project**: Develop the CLI as an independent project with its own repository and release cycle. Rejected for AIS Baseline v1.0 because the Modular Monolith (ADR-001) operates in a single codebase; a separate project adds coordination overhead. The CLI is part of the AIS codebase but is architecturally separable.

## 2. Decision

**AIS provides a Command-Line Interface (CLI) as a first-class interface that mirrors the API capabilities and supports scripting, CI integration, and headless operation.**

The CLI has the following characteristics:

**First-class interface**: The CLI is designed, tested, documented, and maintained with the same rigour as the GUI. It is not a prototype, a debug tool, or an afterthought. It is a supported user interface for all AIS capabilities.

**API parity**: Every operation available through the GUI is also available through the CLI. If a capability exists in the AIS API, the CLI exposes it. Feature gaps between the GUI and CLI are treated as defects.

**Command structure**: The CLI uses a hierarchical command structure:

```
ais <command> [subcommand] [options] [arguments]
```

Top-level commands map to Functional Pillars or operational domains. Subcommands map to specific operations within each Pillar. Options and arguments are typed and validated.

Example commands:
```
ais memory export --session <id> --format json
ais confidence calculate --context <path>
ais notify list --dismissed
ais plugin install <path-to-manifest>
ais plugin list --enabled
ais audit log --from 2026-07-01 --to 2026-07-28
ais config get autonomy-level
ais config set autonomy-level suggest
```

**Structured output**: Every command supports `--output json` (and optionally `--output yaml`) for machine-readable output. The default output is human-readable with colour and formatting. Structured output is valid, parseable JSON that conforms to the TypeScript-defined return type for the command.

**Exit codes**: Every command returns a standard exit code:

| Code | Meaning |
|------|---------|
| 0 | Success. |
| 1 | General error (invalid arguments, missing data, etc.). |
| 2 | Permission denied (insufficient autonomy level, plugin scope exceeded). |
| 3 | Provider unavailable (external provider error). |
| 4 | Timeout. |

**Built-in help**: Every command and subcommand supports `--help`, which displays the command's purpose, arguments, options, examples, and related commands. A top-level `ais help` lists all available commands.

**TypeScript-defined schemas**: CLI command arguments, options, and return types are defined as TypeScript types (per ADR-005). This ensures that the CLI's interface contract is type-checked at compile time and consistent with the underlying API.

**Session context**: The CLI operates within a session context (like the GUI). Commands can specify a session explicitly (`--session <id>`) or use the current default session. Session management commands (`ais session create`, `ais session switch`) are available for session lifecycle management.

## 3. Consequences

### 3.1 Positive

- **Automation-friendly**: Users can script AIS operations in shell scripts, Makefiles, CI/CD pipelines, and cron jobs. Batch operations (e.g., exporting all sessions, generating reports for all users) that would be tedious in the GUI become trivial in the CLI.
- **CI integration**: CI/CD pipelines can invoke AIS commands as build steps. Exit codes enable pipeline gating; structured output enables result parsing. This supports automated quality gates and compliance checks.
- **Headless operation**: AIS can be deployed and used in environments without a GUI (servers, containers, batch systems). The CLI is the primary interface in these contexts.
- **Developer productivity**: During development, engineers can invoke AIS capabilities from the terminal without switching to a GUI. This accelerates debugging, integration testing, and profiling.
- **Consistent interface contract**: Because CLI commands are defined as TypeScript types, the same type definitions drive both the CLI and the GUI. This ensures consistency and prevents the two interfaces from diverging.
- **Discoverability**: The built-in help system allows users to explore AIS capabilities interactively. New users can learn the CLI by running `ais help` and following the command hierarchy.
- **Compliance support**: Compliance officers can query AIS state, export audit logs, and generate reports from the command line. Structured output enables automated compliance checking.

### 3.2 Negative

- **Dual interface maintenance**: Maintaining both a GUI and a CLI means that every new feature must be implemented in both interfaces. This doubles the surface area for development, testing, and documentation. Mitigation: shared API layer (both GUI and CLI consume the same underlying API); CLI-specific and GUI-specific code is minimised to presentation logic only.
- **Documentation burden**: Every command must be documented in the built-in help system, in the user guide, and in the API reference. Maintaining three copies of the same information risks divergence. Mitigation: the CLI help text is the single source of truth for command documentation; other documentation references it or generates from it.
- **Design complexity**: CLI design has its own discipline: argument parsing, exit codes, signal handling, terminal colour, output formatting. These are different from GUI design concerns and require their own expertise. Mitigation: use a well-established CLI framework that handles argument parsing and output formatting, minimising bespoke CLI infrastructure.
- **Feature parity pressure**: The promise of API parity between GUI and CLI creates pressure to implement every feature in both interfaces simultaneously. This can slow down feature delivery. Mitigation: new features are implemented in the API first; both GUI and CLI consume the API. The CLI wrapper is typically simpler than the GUI implementation, so parity is usually achieved quickly.
- **Platform-specific behaviour**: Terminal behaviour (colour support, line wrapping, signal handling) varies across operating systems and terminal emulators. The CLI must handle these variations gracefully. Mitigation: use cross-platform CLI libraries that detect terminal capabilities and degrade gracefully.

### 3.3 Neutral

- **CLI framework**: The specific CLI framework (e.g., Commander.js, yargs, oclif, custom) is an implementation decision. This ADR defines the CLI's architectural characteristics; the framework is chosen at the development level.
- **Shell completion**: Tab completion for bash, zsh, and other shells is a desirable feature but is not an architectural requirement. It may be added as a development enhancement.
- **Interactive mode**: An interactive REPL mode (where the user enters commands in a persistent session without re-invoking the CLI) is deferred. The current CLI model is single-invocation: one command per process invocation. Interactive mode may be added in a future baseline.

## 4. Compliance

This ADR satisfies the following Constitutional Principles and Architectural Laws:

| CP/AL | Relevance |
|-------|-----------|
| CP-001 — Assistance Finds the User | The CLI extends assistance to terminal users and automated systems, meeting them where they work. |
| CP-005 — Local Sovereignty | The CLI respects the user's workspace and operates within declared permissions and the current autonomy level. |
| CP-020 — Accessibility by Default | The CLI is inherently accessible: keyboard-driven, screen-reader-friendly (structured output), and compatible with assistive terminal tools. |
| AL-002 — Boundary by Contract | CLI commands are defined as TypeScript types (contracts), ensuring type safety between the CLI and the API. |
| AL-010 — TypeScript Is the Contract Language | CLI command schemas are expressed as TypeScript types. |
| DR-10 — Autonomy-Level Aware | The CLI checks the current autonomy level before executing actions that affect the system or the user's workspace. |
