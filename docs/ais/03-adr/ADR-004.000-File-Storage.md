## 1. Context

The Adaptive Intelligence System (AIS) produces and consumes a wide range of persisted artefacts. These include, but are not limited to:

- **Reports**: Analysis outputs, recommendations, summaries, and audit reports generated by the Confidence Engine (FP-03) and other Pillars.
- **Evidence**: Supporting data, screenshots, log excerpts, and contextual information that underpins recommendations and decisions.
- **Memory snapshots**: Serialised state of the Adaptive Memory Engine (FP-01) for session persistence and recovery.
- **Plugin manifests**: Declarative descriptions of plugin capabilities, permissions, and event subscriptions (FP-08).
- **Audit logs**: Append-only records of state changes with side effects, as required by AL-012.
- **Configuration**: User preferences, role assignments, autonomy level settings, and notification policies.
- **Event logs**: Serialised records of Event Bus activity for post-hoc analysis and debugging.

AL-009 (File Is the Unit of Storage) is unambiguous: "All persisted artefacts (reports, evidence, memory snapshots, plugin manifests) are files with stable paths. Opaque blobs without a path are forbidden." DR-07 (File-Based Persistence) reinforces this: "All persisted artefacts are files at stable paths. No opaque blob storage."

The architectural decision must address the following forces:

**Auditability**: Every persisted artefact must be individually addressable, inspectable, and traceable. An auditor must be able to locate a specific artefact by its type, session context, and timestamp without consulting a database or opaque index.

**Human readability**: Where feasible, artefacts should be human-readable (plain text, JSON, YAML, Markdown). This supports debugging, manual inspection, and compliance review without requiring specialised tools.

**Git-friendliness**: Documentation artefacts and configuration files should be compatible with version control systems. A user should be able to commit their AIS configuration and documentation to a git repository and diff between versions.

**Stability**: Once written, an artefact's path must not change. Renaming, moving, or restructuring the storage layout breaks references and audit trails. The path structure must be designed for long-term stability.

**Path semantics**: The path to an artefact should encode meaningful metadata: the type of artefact, the session it belongs to, and the timestamp of creation. This enables path-based queries (e.g., "find all reports for session X") without a database.

**Scalability considerations**: While AIS Baseline v1.0 operates at a small scale, the file storage pattern must not create pathological performance characteristics as the number of artefacts grows. The path hierarchy must support efficient directory traversal and avoid single-directory bottlenecks.

The alternatives considered were:

1. **Database storage (SQL)**: Store all artefacts as rows in a relational database. Rejected because it requires a database engine, obscures artefact content behind SQL queries, makes human inspection difficult without tooling, and creates vendor lock-in to the database engine.
2. **Opaque blob storage (S3, blob store)**: Store artefacts as blobs keyed by an opaque identifier. Rejected by AL-009 — opaque blobs without a path are forbidden. Blobs also make human inspection difficult and path-based queries impossible.
3. **Document store (MongoDB, CouchDB)**: Store artefacts as documents in a NoSQL database. Rejected because it introduces a database dependency and does not provide the path-based, human-readable, git-friendly properties required by the architecture.
4. **In-memory only**: No persistence; all state lives in process memory. Rejected because it violates AL-012 (auditability), CP-007 (adaptive memory), and basic operational requirements for session persistence and recovery.

## 2. Decision

**All persisted artefacts in AIS are stored as files at stable, semantically meaningful paths on the file system.**

The file storage model has the following characteristics:

**One artefact, one file**: Each persisted artefact is a single file. A report is a file. A memory snapshot is a file. An audit log entry is a line in an append-only log file. Composite artefacts (e.g., a report with attachments) are represented as a directory containing the main file and its attachments.

**Stable paths**: Once an artefact is written, its path must not change. The path is the artefact's identity. If the artefact needs to be updated, a new version is written at a new path (with an updated timestamp component). The old version remains at its original path.

**Path encoding**: Paths encode the artefact type, session context, and creation timestamp. The general path pattern is:

```
<root>/
  <artefact-type>/
    <session-id>/
      <timestamp>-<identifier>.<extension>
```

For example:
```
ais-data/
  reports/
    session-2026-07-28-abc123/
      20260728-143052-confidence-report.md
      20260728-150731-context-prediction.json
  memory/
    session-2026-07-28-abc123/
      20260728-143000-snapshot.json
  audit/
    2026-07-28.log
  config/
    user-preferences.json
    role-assignments.json
```

**Human-readable formats**: Artefacts are stored in human-readable formats: JSON, YAML, Markdown, or plain text. Binary artefacts (e.g., screenshots) are stored in their native format with a metadata sidecar file in JSON.

**Append-only logs**: The audit log and event log are append-only files. New entries are appended to the end; existing entries are never modified. This supports AL-012 and prevents tampering.

**No opaque blobs**: Every stored artefact is addressable by a meaningful path. There are no artefacts stored under random identifiers, content hashes used as primary addresses, or database records without file-system correspondence.

## 3. Consequences

### 3.1 Positive

- **Auditability**: Every artefact is individually addressable by its path. An auditor, developer, or compliance officer can locate any artefact by navigating the path hierarchy — no database query required. This satisfies AL-012 and CP-015.
- **Human readability**: JSON, YAML, and Markdown files can be inspected with any text editor or terminal tool. Debugging does not require specialised database tools or deserialisation utilities. A developer can `cat` an artefact and understand its content immediately.
- **Git-friendliness**: Configuration files, reports (in Markdown), and documentation artefacts can be committed to version control. The file-based structure maps naturally to git's tree model. Diffs, blame, and history are all available through standard git commands.
- **Path-based queries**: Finding all artefacts for a session is a directory listing. Finding all reports across sessions is a recursive search by directory name. No query language, no database index, no ORM — just the file system.
- **Operational simplicity**: File storage requires no external service (no database, no blob store, no message queue). It works on any standard file system. Backup is file-system backup. Migration is file copy.
- **Tooling compatibility**: Standard Unix tools (ls, find, grep, diff, rsync) work directly on the file store. No vendor-specific tooling is needed for inspection, comparison, or transfer.
- **Latency**: File I/O is fast for the current scale of AIS. Reading and writing small files (JSON, Markdown) is orders of magnitude faster than equivalent database operations for the same data volume.

### 3.2 Negative

- **Path design discipline**: The path hierarchy must be designed carefully and locked down early. Changes to the path pattern after artefacts have been written create inconsistencies between old and new artefacts. This requires upfront investment in path schema design.
- **No built-in querying**: Advanced queries (e.g., "find all reports with confidence > 80 in the last 7 days") require parsing file contents, not just navigating paths. The file system provides structural queries (by path); semantic queries (by content) require additional tooling. Mitigation: a lightweight index or search facility can be layered on top of the file store without replacing it.
- **Scalability ceiling**: File systems have practical limits on the number of files in a single directory and the total number of files. If AIS produces millions of artefacts, directory operations may slow down. Mitigation: the path hierarchy distributes files across directories by session and date, avoiding single-directory hotspots. For extreme scale, the path pattern can be adjusted (e.g., sharding by session ID hash) without changing the file-storage principle.
- **Concurrency**: File-based storage has weaker concurrency guarantees than database transactions. Simultaneous writes to the same file may conflict. Mitigation: each artefact is written once (append-only or new-file-per-update). Concurrent writes to the audit log use file-level locking or append-only semantics that are inherently safe.
- **Schema evolution**: If the structure of an artefact type changes (e.g., a report gains a new field), old artefacts retain the old schema and new artefacts use the new schema. Consumers must handle both versions. Mitigation: artefact files include a schema version field, and consumers check this field before parsing.
- **Storage management**: Unlike a database that manages storage allocation internally, file storage requires operating-system-level storage management (disk monitoring, cleanup policies, archival). Mitigation: operational runbooks define retention policies, and a housekeeping process archives or deletes artefacts beyond their retention period.

### 3.3 Neutral

- **Root directory location**: The exact location of the file store root (`ais-data/` in the example) is a configuration parameter, not an architectural decision. It may be relative to the user's home directory, a designated data directory, or an environment-specific path.
- **File permissions**: The permission model for stored files (read/write access per user, per process, per trust zone) is an implementation detail governed by the Trust Zone model (ADR-010) and the operating system's permission system.
