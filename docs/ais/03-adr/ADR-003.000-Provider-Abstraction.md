## 1. Context

The Adaptive Intelligence System (AIS) interacts with multiple categories of external providers to deliver its core functionality. These providers include, but are not limited to:

- **LLM Providers**: Large Language Model services (e.g., OpenAI, Anthropic, local models) used for natural language generation, intent analysis, and recommendation reasoning.
- **Scanner Providers**: Code scanning, security analysis, and quality assessment tools that AIS may invoke to provide context-aware recommendations.
- **Storage Providers**: Persistent storage backends for artefacts, memory snapshots, configuration, and audit logs.
- **Embedding Providers**: Vector embedding services used for semantic search, similarity matching, and context retrieval.

CP-014 (Provider Neutrality) is unambiguous: "AIS is independent of any specific LLM provider, scanner provider, or storage provider. Providers are pluggable. Lock-in is forbidden." AL-005 (Provider behind Abstraction) operationalises this: "Every external provider (LLM, scanner, storage, embedding) sits behind an interface owned by AIS. The interface is the boundary; the provider is interchangeable."

The architectural decision must address the following forces:

**Vendor independence**: AIS must be able to switch from one LLM provider to another (e.g., from OpenAI to a local model) without changes to any Functional Pillar code. The same applies to scanner providers, storage providers, and embedding providers.

**Testing isolation**: Functional Pillars must be testable without connecting to real external providers. A test must be able to run with a mock LLM, a mock scanner, and a mock storage provider, all configured through the same mechanism used in production.

**Provider evolution**: External providers change their APIs, pricing, and availability. AIS must absorb these changes at the abstraction layer without propagating them into FP code.

**Configuration flexibility**: Different deployments of AIS may use different providers. A development environment may use a local LLM; a production environment may use a cloud LLM. The switch must be a configuration change, not a code change.

**Security scoping**: Provider credentials (API keys, tokens, certificates) must be scoped per session (per ADR-010, ADR-011) and never hard-coded in Functional Pillar code.

The alternatives considered were:

1. **Direct SDK imports**: Each Functional Pillar imports and calls the SDK of its required provider directly. Rejected by CP-014, AL-005, and DR-01 — this creates vendor lock-in and makes testing impossible without real provider credentials.
2. **Feature flags with conditional imports**: Use feature flags to select between provider SDKs at runtime. Rejected because it still couples FP code to specific SDK interfaces and proliferates conditional logic throughout the codebase.
3. **Sidecar proxy**: Deploy provider-specific proxies as sidecar processes and communicate via a generic protocol. Rejected for AIS Baseline v1.0 because the Modular Monolith (ADR-001) operates in-process; sidecar processes add operational overhead. This remains a future option if the system transitions to microservices.

## 2. Decision

**Every external provider sits behind an abstraction interface owned by AIS. No Functional Pillar may import or reference any specific provider SDK.**

The Provider Abstraction layer consists of the following components:

**Provider Interface**: For each provider category (LLM, Scanner, Storage, Embedding), AIS defines a TypeScript interface that declares the operations the system requires. For example, the LLM provider interface declares methods for text generation, intent analysis, and context reasoning — but does not specify which LLM service implements them.

**Provider Factory**: The Provider Factory (FP-06) is the single point of creation for all provider instances. It accepts a `ProviderType` and a `ProviderConfig`, and returns an object that implements the corresponding Provider Interface. The Factory handles credential resolution, connection setup, and health checking. Its public contract is IC-05 (defined in ARC-001.001 §6).

**Provider Implementation**: Each specific provider (e.g., OpenAI, Anthropic, local model) is implemented as a class that conforms to the relevant Provider Interface. These implementations are isolated in a dedicated provider layer outside the Functional Pillar code.

**Configuration-driven selection**: The choice of provider implementation is determined by configuration (environment variables, configuration files, runtime parameters), not by code imports. Switching from one LLM provider to another requires changing a configuration value and ensuring the new provider's implementation is available — no FP code changes required.

**Mock providers for testing**: For each Provider Interface, AIS provides a mock implementation that simulates provider behaviour with configurable responses. Tests use mock providers exclusively; tests that require real providers are integration tests, not unit tests.

## 3. Consequences

### 3.1 Positive

- **Full vendor independence**: No Functional Pillar is coupled to any specific provider. Switching providers requires only a configuration change and the presence of a conforming implementation. This satisfies CP-014 and AL-005.
- **Testable modules**: Every Functional Pillar can be tested with mock providers, enabling fast, reliable unit tests that do not depend on network connectivity, API availability, or provider credentials. This is essential for CI/CD pipelines.
- **Provider evolution absorption**: When a provider changes its API, only the corresponding provider implementation needs to be updated. The Provider Interface and all FP code remain unchanged. This isolates the blast radius of external changes.
- **Security isolation**: Provider credentials are managed exclusively by the Provider Factory. FP code never handles credentials directly. The Factory can enforce credential scoping per session (ADR-010, ADR-011) and rotate credentials without FP involvement.
- **New provider onboarding**: Adding a new provider (e.g., a new LLM service) requires implementing the Provider Interface and registering it with the Factory. No changes to existing FP code or existing provider implementations.
- **Configuration flexibility**: Different environments can use different providers without code branching. Development can use a local model; staging can use a cloud model; production can use a different cloud model. All managed through configuration.

### 3.2 Negative

- **Interface design burden**: The Provider Interfaces must be designed to accommodate the capabilities of all foreseeable providers. If the interface is too specific, it may not fit some providers; if too generic, it may lose type safety and convenience. Mitigation: interfaces are designed around AIS's needs (what AIS requires from a provider), not around any specific provider's capabilities.
- **Lowest common denominator risk**: Some providers offer advanced features (e.g., streaming, tool use, structured output) that others do not. The Provider Interface must decide whether to expose these features (making them optional or conditional) or omit them (limiting all providers to a common subset). Mitigation: the interface exposes core capabilities as required methods and advanced capabilities as optional extensions that FP code checks for at runtime.
- **Implementation maintenance**: Each provider requires its own implementation class. If AIS supports N LLM providers, M scanner providers, and K storage providers, the abstraction layer contains N+M+K implementation classes. This is a maintenance burden, but it is localised to the provider layer and does not affect FP code.
- **Abstraction leakage**: There is a risk that provider-specific concepts leak through the abstraction (e.g., an AIS error type that maps directly to an OpenAI error code). Mitigation: all error types, response types, and configuration types are defined by AIS, not by providers. Provider implementations translate between their native types and AIS types.
- **Performance overhead**: The abstraction layer adds a thin indirection layer. For high-throughput scenarios, this overhead is negligible, but it exists. Mitigation: the abstraction is kept thin — it translates types and delegates calls, without adding logic that would slow down the call chain.

### 3.3 Neutral

- **Provider discovery**: The mechanism for discovering available providers at runtime (e.g., dynamic loading, service registration) is an implementation detail. This ADR defines that the Provider Factory creates instances; the specific discovery mechanism is an implementation concern.
- **Provider health monitoring**: The abstraction layer may include health checking and circuit-breaking logic, but this is an implementation detail. This ADR defines the contract; operational resilience patterns are implementation concerns.
