## 0. Preamble

This document establishes the long-term strategic vision of the Adaptive Intelligence System (AIS) as a universal intelligence platform. It formalises the positioning, principles, adaptation mechanisms, and evolution roadmap that will guide AIS from its current state as a security-focused adaptive system to a platform capable of serving any user, any organisation, and any domain — without modification to its core architecture.

This document does not modify any existing architectural decision, domain model, or runtime implementation. It is a governance document that formalises what the existing architecture already enables and charts the course for its expansion.

All sections conform to the Constitutional Principles (CP-001–CP-023), Architectural Laws (AL-001–AL-012), and Architecture Decision Records (ADR-001–014).

## 1. What Is AIS? — Official Definition

**AIS (Adaptive Intelligence System) is a universal adaptive intelligence runtime platform that provides a configurable, extensible, and domain-independent foundation for intelligent assistance.**

AIS is not an AI assistant. AIS is not a chatbot. AIS is not an LLM framework. AIS is not a security tool. AIS is not a vertical application.

AIS is an **operating system for intelligence** — a runtime layer that sits between raw capability (LLMs, tools, knowledge bases, data sources) and human users, providing:

- **Context-aware reasoning** that understands what the user is doing, what they need, and how to deliver it.
- **Adaptive behaviour** that evolves with the user's patterns, preferences, and goals over time.
- **Trust-gated autonomy** that acts on behalf of the user only within explicitly defined boundaries.
- **Provider-agnostic orchestration** that abstracts away specific LLMs, scanners, tools, and services.
- **Knowledge management** that structures, indexes, versions, and retrieves domain knowledge.
- **Plugin extensibility** that allows any capability to be added without core modification.
- **Domain specialisation** that transforms the generic platform into a domain expert through configuration, not code.

The core insight is this: the Execution Engine, Tool Runtime, Memory Runtime, Knowledge Runtime, and Context Engine that have been implemented contain zero domain-specific logic. They are pure infrastructure for intelligence. The domain — whether medicine, accounting, law, engineering, research, or any other field — is supplied through Domain Packs, not embedded in the core.

### 1.1 AIS Architecture Stack

```
┌─────────────────────────────────────────┐
│              User / Organisation          │  ← Human layer
├─────────────────────────────────────────┤
│           Policy Pack                    │  ← Governance & rules
├─────────────────────────────────────────┤
│           Workflow Pack                  │  ← Process orchestration
├─────────────────────────────────────────┤
│           Tool Pack                      │  ← Domain-specific tools
├─────────────────────────────────────────┤
│           Knowledge Pack                 │  ← Domain knowledge base
├─────────────────────────────────────────┤
│           Domain Pack                    │  ← Domain ontology & rules
├─────────────────────────────────────────┤
│    Identity Layer + Preference Runtime  │  ← User model & config
├─────────────────────────────────────────┤
│           Capability Layer               │  ← Abstract capability interface
├─────────────────────────────────────────┤
│     AIS Core Runtime (Immutable)         │  ← Execution, Memory, Knowledge,
│                                          │    Context, Tool, Event Bus
├─────────────────────────────────────────┤
│        Provider Abstraction (Z3)         │  ← LLM, Scanner, Storage, Embedding
└─────────────────────────────────────────┘
```

The only layer that is fixed and immutable is the **AIS Core Runtime**. Every layer above it is configurable, replaceable, and composable.

## 2. Mission

**The mission of AIS is to provide every individual and every organisation with a personalised intelligent companion that understands their domain, adapts to their workflow, and amplifies their capabilities — regardless of their profession, industry, or technical expertise.**

AIS exists to eliminate the gap between human intent and execution. A doctor should be able to dictate a diagnosis and have AIS verify it against medical literature, prepare the treatment plan, and schedule follow-ups. An accountant should be able to describe a transaction and have AIS categorise it, generate the journal entry, and flag anomalies. A software engineer should be able to describe a feature and have AIS write the code, run the tests, and submit the pull request.

In every case, the core platform is identical. Only the Domain Packs differ.

## 3. Vision — AIS in 10 Years

A fully realised AIS in 2036 is the **universal intelligence layer** of the digital world. It is to intelligent assistance what an operating system is to computing: a platform that others build upon.

### 3.1 The Ten-Year Vision

1. **AIS Core** is a mature, battle-tested runtime that has not changed its fundamental architecture since v1.0. It is the Linux kernel of intelligence — stable, minimal, and infinitely extensible.

2. **Domain Packs** exist for every major profession and industry: medicine, law, finance, engineering, research, education, government, creative arts, and dozens more. Each is created by domain experts, validated by the community, and distributed through the Marketplace.

3. **Identity Layer** provides deep personalisation: AIS knows each user's role, skills, habits, goals, and preferences. It adapts its communication style, detail level, and autonomy to match. A surgeon gets terse, high-confidence directives. A student gets patient, explanatory guidance.

4. **Company Layer** enables organisational deployment: teams, departments, and enterprises configure AIS to enforce their policies, use their tools, and respect their hierarchies. A hospital's AIS enforces HIPAA compliance. A bank's AIS enforces regulatory reporting. A startup's AIS prioritises speed.

5. **Marketplace** is a thriving ecosystem: thousands of Domain Packs, Tool Packs, Workflow Packs, Policy Packs, Knowledge Packs, and UI Themes are available. Independent developers, consultancies, and enterprises contribute and monetise their expertise.

6. **Learning Strategy** means AIS grows with the user: a junior engineer who uses AIS for code review will find, five years later, that AIS has accumulated deep knowledge of their codebase, their design preferences, and their career trajectory. It is a lifelong companion, not a disposable tool.

7. **Capability Layer** abstracts away provider specifics: users request "analyse this document" or "generate a report" without knowing or caring whether GPT, Claude, Gemini, or a local model fulfils the request. The platform optimises for quality, cost, and speed transparently.

8. **AIS Ecosystem** is self-sustaining: the Marketplace generates revenue, the community creates content, the Core evolves through disciplined refinement, and the Governance Council ensures constitutional compliance. AIS is not a product — it is a platform that others build products upon.

## 4. Universal Platform Principles

The Universal Platform Principles (UP-001 through UP-010) are the strategic extension of the Constitutional Principles (CP). While CPs govern the internal architecture, UPs govern the platform's relationship with the outside world — its users, domains, and ecosystems.

### UP-001 — Core Is Domain-Agnostic

The AIS Core Runtime contains zero domain-specific logic. It does not know whether it is assisting a doctor, a developer, or a designer. Domain specialisation is exclusively the responsibility of Domain Packs. The Core provides the infrastructure; the Domain Pack provides the expertise.

*Traces to: CP-014 (Provider Neutrality), ADR-003 (Provider Abstraction), ARC-001.001 (FP-01..FP-08).*

### UP-002 — Core Is Profession-Agnostic

The AIS Core Runtime contains zero profession-specific logic. It does not encode medical terminology, legal frameworks, financial regulations, or engineering standards. The UserRole value object (DOM-001.000 §2.10) currently defines four roles (CEO, DevOps, Engineer, Analyst); these are examples of the role classification system, not exhaustive profession definitions. The actual profession vocabulary is supplied by the Domain Pack.

*Traces to: DOM-001.000 (DP-006 Role Determines Narrative), ARC-001.001 (DR-06 Role-Aware Output).*

### UP-003 — Specialisation Through Domain Packs

Any domain specialisation is achieved by loading a Domain Pack — a self-contained package of domain ontology, knowledge base, tools, workflows, and policies — onto the AIS Core. No Core modification is required. No recompilation is necessary. A Domain Pack is configuration, not code.

*Traces to: CP-013 (Composition over Coupling), ADR-001 (Modular Monolith), ADR-006 (Plugins).*

### UP-004 — Behaviour Through Configuration

The behaviour of AIS in any given context is determined by configuration: which Domain Pack is loaded, what policies are active, what the user's preferences are, and what the current autonomy level is. Two instances of AIS with identical Core runtimes but different configurations will behave as completely different assistants.

*Traces to: AL-007 (Autonomy Is a Spectrum), ADR-009 (Autonomy Spectrum), DOM-001.000 (DP-005 Adaptation Over Time).*

### UP-005 — Intelligence Separated from Implementation

The platform's intelligence — its reasoning, adaptation, and decision-making — is separated from its implementation details. AIS does not depend on GPT, Claude, Gemini, or any specific LLM. Intelligence is a capability provided through the Provider Abstraction layer (ADR-003). The same intelligent behaviour can be delivered by any provider that satisfies the capability interface.

*Traces to: CP-014 (Provider Neutrality), AL-005 (Provider behind Abstraction), ADR-003.000.*

### UP-006 — Full User Customisation Without Core Changes

A user or organisation can fundamentally change how AIS behaves — its communication style, domain expertise, tool set, workflow automation, policy enforcement, and user interface — entirely through Pack configuration and preference settings. The Core remains untouched. This is the ultimate expression of CP-013 (Composition over Coupling) at the platform level.

*Traces to: CP-013, CP-005 (Local Sovereignty), CP-023 (Exit Is Always Possible).*

### UP-007 — Packs Are Composable

Multiple Packs can be loaded simultaneously and composed to create hybrid capabilities. A user can load a "Legal Research" Domain Pack alongside a "Financial Analysis" Domain Pack, and AIS will integrate knowledge and tools from both. Pack composition is governed by the core's Event Bus (ADR-002) and follows the same modular composition principles as the Core itself.

*Traces to: CP-013, ADR-001, ADR-002, AL-008 (Events Are the Spine).*

### UP-008 — Packs Are Isolated

Each Pack operates within its declared scope and cannot interfere with other Packs or the Core. A Domain Pack for medicine cannot modify the behaviour of a Domain Pack for finance. Pack isolation follows the same Trust Zone principles (AL-006, ADR-010) that govern plugin isolation (AL-011, ADR-006).

*Traces to: AL-006, AL-011, ADR-006, ADR-010, ADR-012 (Minimal Privilege).*

### UP-009 — Multi-Tenancy by Design

AIS supports multiple simultaneous users, each with their own Identity, Preferences, Domain Packs, and Policies, running on a single Core instance. User data is isolated per CP-005 (Local Sovereignty) and CP-021 (Privacy of Profile). Multi-tenancy is not an afterthought — it is a design principle.

*Traces to: CP-005, CP-021, AL-004 (One Memory, One Authority).*

### UP-010 — Evolution Without Breaking

The platform evolves through incremental refinement (ADR-013). New capabilities are added as new Packs or new Core modules. Existing Packs continue to work unmodified. The versioning system (CON-001.000 CP-018, ADR-013) ensures backward compatibility. A Domain Pack written for AIS v1.0 works on AIS v2.0 unless the Core introduces a breaking change — which requires a new baseline declaration per BAS-001.000 §5.

*Traces to: CP-018 (Versioned Evolution), ADR-013, BAS-001.000.000.*

## 5. Adaptation Model

The Adaptation Model defines how AIS transforms from a generic intelligence platform into a domain-specific expert.

### 5.1 Adaptation Without Core Change

The fundamental principle is that AIS becomes a doctor, an accountant, a lawyer, a developer, an engineer, or a researcher through **loading** — not through **modification**.

The adaptation process:

1. **Load Domain Pack**: The Domain Pack injects domain ontology, terminology, knowledge structures, and domain-specific rules into the Knowledge Runtime and Context Engine.

2. **Load Knowledge Pack**: Pre-structured domain knowledge (medical literature, legal precedents, financial regulations, code patterns) is indexed and made available to the Retrieval Runtime.

3. **Load Tool Pack**: Domain-specific tools (DICOM viewer for medicine, Bloomberg API for finance, statute search for law, IDE integration for engineering) are registered with the Tool Runtime.

4. **Load Workflow Pack**: Standardised processes (diagnostic workflow, audit workflow, code review workflow) are registered with the Execution Pipeline.

5. **Load Policy Pack**: Compliance rules, data handling policies, and regulatory constraints are enforced through the Context Engine.

6. **Apply Identity**: User's role, skills, experience, and preferences configure how AIS communicates, what it suggests, and how autonomously it acts.

At no point in this process is the AIS Core modified. The entire adaptation is achieved through Pack loading and configuration.

### 5.2 Adaptation Examples

| Domain | Domain Pack | Knowledge Pack | Tool Pack | Workflow Pack | Policy Pack |
|--------|-------------|----------------|-----------|---------------|-------------|
| **Medicine** | Medical ontology, ICD codes, clinical terminology | PubMed, drug interactions, clinical guidelines | DICOM viewer, EHR integration, lab results parser | Diagnostic workflow, treatment planning, follow-up scheduling | HIPAA compliance, patient data handling, prescription verification |
| **Accounting** | Chart of accounts, tax codes, audit standards | Tax regulations, GAAP/IFRS standards, precedent rulings | ERP integration, bank statement parser, receipt OCR | Month-end close, tax filing, audit preparation | SOX compliance, data retention, multi-entity reporting |
| **Law** | Legal terminology, jurisdiction codes, case citation format | Case law database, statute library, regulatory updates | Court filing systems, contract analysis, precedent search | Case research workflow, contract review, litigation support | Client confidentiality, conflict of interest, billing compliance |
| **Software Engineering** | Code ontology, design patterns, architecture vocabulary | Codebase index, API documentation, bug database | IDE integration, CI/CD, code review tools, version control | Feature development, bug triage, release management | Code quality gates, security scanning, deployment approval |
| **Engineering** | Engineering terminology, unit systems, safety standards | Material databases, design codes, calculation references | CAD integration, simulation tools, measurement instruments | Design review workflow, safety analysis, quality control | Safety certification, regulatory compliance, document control |
| **Research** | Scientific terminology, methodology taxonomy, citation format | Paper database, dataset index, methodology references | Statistical analysis tools, experiment management, publication tools | Literature review, experiment design, peer review workflow | Data integrity, reproducibility requirements, open access compliance |

## 6. Domain Pack Architecture

### 6.1 Layer Stack

The Domain Pack Architecture defines a stack of composable layers, each with a well-defined interface. The stack flows from the immutable Core upward to the fully configured user experience.

```
Layer 7: User
    ↓ configures
Layer 6: Policy Pack
    ↓ governs
Layer 5: Workflow Pack
    ↓ orchestrates
Layer 4: Tool Pack
    ↓ enables
Layer 3: Knowledge Pack
    ↓ informs
Layer 2: Domain Pack
    ↓ specialises
Layer 1: Identity Layer + Preference Runtime
    ↓ personalises
Layer 0: AIS Core Runtime (Immutable)
```

### 6.2 Layer Interfaces

**Layer 0 — AIS Core Runtime (Immutable)**

Interface: The existing Core module contracts (IC-01 through IC-05 in ARC-001.001 §6) plus the Execution Engine, Tool Runtime, Memory Runtime, Knowledge Runtime, and Context Engine APIs.

Responsibility: Provides the runtime infrastructure — execution, memory, knowledge, context, tools, events. Contains zero domain logic.

*Governed by: CON-001.000, ARC-001.001, all ADRs.*

**Layer 1 — Identity Layer + Preference Runtime**

Interface: `IdentityProvider` — provides user identity, profile, organisation membership, team roles, skills, experience, goals, habits.

Interface: `PreferenceRuntime` — provides user-configurable preferences: communication style, language, detail level, autonomy level, speed vs. quality trade-off, security settings, model preferences, interface choices.

Responsibility: Personalises the AIS experience. Maps the generic platform to the specific human being using it. Every request from the user passes through the Identity Layer before reaching the Core.

*Governed by: This document (§8, §9). Implementation pending.*

**Layer 2 — Domain Pack**

Interface: `DomainPack` — declares domain ontology (entities, relationships, constraints), domain vocabulary, domain-specific validation rules, and domain-specific confidence calibration.

Responsibility: Transforms generic reasoning into domain-specific reasoning. When the Knowledge Runtime receives a medical Domain Pack, it structures knowledge according to medical ontology. When the Context Engine receives a legal Domain Pack, it frames predictions in legal terms.

Contents:
- `ontology.json` — Domain entity definitions and relationships
- `vocabulary.json` — Domain-specific terminology mappings
- `rules.json` — Domain validation and inference rules
- `confidence-calibration.json` — Domain-specific confidence thresholds

*Governed by: UP-003, UP-007, UP-008. Traces to: DOM-001.000, DOM-002.000 (domain modeling pattern).*

**Layer 3 — Knowledge Pack**

Interface: `KnowledgePack` — declares structured knowledge collections, documents, and fragments for loading into the Knowledge Runtime (SRC-004.000).

Responsibility: Populates the Knowledge Runtime with domain-specific knowledge that the Retrieval and Graph subsystems can query, traverse, and reason over.

Contents:
- Structured knowledge items (per KnowledgeItem type from SRC-004.000)
- Knowledge documents with metadata and versioning
- Knowledge fragments for fine-grained retrieval
- Pre-built knowledge graph with domain relations

*Governed by: UP-003. Traces to: SRC-004.000 (Knowledge Runtime), REP-013-AIS.000.*

**Layer 4 — Tool Pack**

Interface: `ToolPack` — declares domain-specific tools for registration with the Tool Runtime.

Responsibility: Extends the Tool Runtime (TASK-AIS-003C.000) with domain-specific capabilities: medical imaging viewers, financial data connectors, legal research searchers, engineering simulation interfaces.

Contents:
- Tool definitions (name, schema, parameters, permissions)
- Tool implementations or external service connectors
- Tool policies (trust zone, autonomy requirements, safety constraints)

*Governed by: UP-003. Traces to: TASK-AIS-003C.000 (Tool Runtime), ADR-006 (Plugins).*

**Layer 5 — Workflow Pack**

Interface: `WorkflowPack` — declares domain-specific workflows for the Execution Pipeline.

Responsibility: Defines repeatable multi-step processes that the Execution Pipeline (TASK-AIS-003B.000) can plan, schedule, execute, and recover from.

Contents:
- Workflow definitions (steps, dependencies, parallelisation)
- Step handlers (execution logic per step)
- Workflow policies (autonomy level per step, rollback behaviour)

*Governed by: UP-003. Traces to: TASK-AIS-003B.000 (Execution Pipeline), SRC-002.000.*

**Layer 6 — Policy Pack**

Interface: `PolicyPack` — declares governance rules that constrain AIS behaviour within the domain.

Responsibility: Enforces domain-specific constraints: regulatory compliance, data handling rules, approval workflows, audit requirements.

Contents:
- Compliance rules (data classification, retention, access control)
- Approval policies (what requires human approval, at what autonomy level)
- Audit rules (what actions must be logged, for how long)
- Boundary conditions (what AIS must never do in this domain)

*Governed by: UP-004. Traces to: AL-007 (Autonomy Spectrum), ADR-009, DOM-001.000 (DP-014).*

**Layer 7 — User**

Interface: Human user, interacting through CLI (ADR-007), GUI, or API.

Responsibility: The human operator who sets preferences, approves actions, provides feedback, and ultimately controls the system.

*Governed by: CP-023 (Exit Is Always Possible), AL-007 (Autonomy Is a Spectrum).*

### 6.3 Pack Composition Rules

1. **Pack Independence**: Each Pack is independently versioned, installable, and removable.
2. **Pack Compatibility**: Each Pack declares its minimum Core version and optional dependencies on other Packs.
3. **Pack Conflict Resolution**: When multiple Packs define conflicting rules, Policy Pack takes precedence, then Domain Pack, then user preferences.
4. **Pack Isolation**: Packs cannot modify each other's internal state. Cross-Pack communication occurs only through the Event Bus (ADR-002).
5. **Pack Validation**: All Packs are validated before loading: schema validation, dependency checking, permission scoping.

## 7. Identity Layer

The Identity Layer is a planned (not yet implemented) runtime that provides the user model for personalisation and multi-tenancy.

### 7.1 Components

| Component | Responsibility |
|-----------|----------------|
| **Identity** | Unique user identification, authentication context, session binding |
| **User Profile** | Accumulated behavioural profile (extends existing UserProfile from DOM-001.000 §2.1) |
| **Organisation** | Company, institution, or other organisational entity |
| **Team** | Sub-group within an organisation (department, unit, project team) |
| **Role** | Professional role within the organisation and domain context |
| **Persona** | Communication persona: tone, formality, humour level, verbosity |
| **Preferences** | User-configurable settings (language, detail level, autonomy, security) |
| **Habits** | Observed behavioural patterns (work schedule, tool usage, response patterns) |
| **Goals** | User-stated and inferred objectives (short-term tasks, long-term career goals) |
| **Experience** | Accumulated domain experience level and areas of expertise |
| **Skills** | Declared and demonstrated competencies |

### 7.2 Design Principles

1. **User Ownership**: All Identity data belongs to the user per CP-005 (Local Sovereignty) and CP-021 (Privacy of Profile).
2. **Separation from Core**: The Identity Layer sits above the Core (Layer 1) and does not modify Core behaviour. It configures it.
3. **Privacy by Design**: Identity data is stored in the user's sovereign space. Cross-user identity analysis is forbidden.
4. **Multi-Tenancy Ready**: The Identity Layer supports N users per Core instance with full isolation.
5. **Extended UserProfile**: The existing UserProfile entity (DOM-001.000 §2.1, 5 entities in User aggregate) forms the foundation. The Identity Layer extends it with Organisation, Team, Persona, Goals, Experience, and Skills — all stored in user-sovereign space.

*Governed by: CP-005, CP-021, AL-004, UP-009. Implementation pending future task authorisation.*

## 8. Preference Runtime

The Preference Runtime is a planned (not yet implemented) component that enables the user to control every configurable aspect of AIS behaviour.

### 8.1 Preference Dimensions

| Dimension | Description | Examples |
|-----------|-------------|---------|
| **Communication Style** | How AIS communicates with the user | Formal / casual / technical / narrative / concise |
| **Language** | Primary interaction language | English, Russian, Chinese, Arabic, etc. |
| **Detail Level** | How much detail AIS provides | Minimal / summary / standard / comprehensive / exhaustive |
| **Autonomy Level** | How much AIS acts independently | Per AL-007: L0 (Observe) through L4 (Autonomous) |
| **Speed vs. Quality** | Trade-off between response speed and output quality | Fast / balanced / thorough |
| **Security Level** | Data handling and privacy settings | Minimal / standard / enhanced / maximum |
| **Cost Awareness** | Sensitivity to provider costs | Unlimited / moderate / budget-conscious / minimal |
| **Model Preference** | Preferred provider for specific tasks | Auto-select / GPT / Claude / Gemini / local model |
| **Interface** | Primary interaction mode | CLI / GUI / API / voice |
| **Notification Style** | How AIS delivers notifications | Per CP-006 (Minimal Surface), CP-012 (Adaptive Lifetime) |
| **Proactivity** | How often AIS offers unsolicited assistance | Off / low / medium / high |
| **Feedback Verbosity** | How much AIS explains its reasoning | Silent / brief / standard / detailed |

### 8.2 Design Principles

1. **All Preferences Are User-Controlable**: Every dimension listed above is set by the user, not by the system. AIS may suggest preference values but never imposes them.
2. **Preferences Are Portable**: User preferences are stored in the user's sovereign space and can be exported and imported per ADR-011 (Data Sovereignty).
3. **Preferences Are Domain-Overridable**: A Domain Pack may suggest default preference values for its domain (e.g., a Medical Domain Pack may recommend "comprehensive" detail level), but the user can override these.
4. **Preferences Are Organisational-Overridable**: In multi-tenant deployments, an organisation may enforce minimum preference values (e.g., a bank may enforce "maximum" security level for all employees).

*Governed by: CP-005, CP-021, CP-023, AL-007, UP-004, UP-006. Implementation pending future task authorisation.*

## 9. Capability Layer

The Capability Layer defines an abstraction over provider-specific capabilities. Users request capabilities, not providers.

### 9.1 Capability Abstraction

Instead of exposing provider names (GPT, Claude, Gemini), AIS exposes **capabilities** — abstract descriptions of what the user wants to achieve.

| Capability ID | Capability Name | Description |
|--------------|----------------|-------------|
| CAP-001 | Document Analysis | Analyse, summarise, extract, and compare documents |
| CAP-002 | Search | Search across knowledge bases, documents, and external sources |
| CAP-003 | Code Generation | Write, review, refactor, and test code |
| CAP-004 | Report Creation | Generate structured reports from data and analysis |
| CAP-005 | Data Analysis | Analyse datasets, identify patterns, produce insights |
| CAP-006 | Automation | Automate repetitive tasks and multi-step workflows |
| CAP-007 | Planning | Create plans, schedules, and project roadmaps |
| CAP-008 | Translation | Translate text between languages |
| CAP-009 | Conversation | Engage in multi-turn dialogue on any topic |
| CAP-010 | Prediction | Predict outcomes based on data and patterns |
| CAP-011 | Classification | Classify, categorise, and label data |
| CAP-012 | Creative Generation | Generate creative content: text, concepts, ideas |
| CAP-013 | Reasoning | Perform logical, mathematical, and analytical reasoning |
| CAP-014 | Monitoring | Monitor systems, data, and processes for anomalies |
| CAP-015 | Orchestration | Coordinate multiple capabilities into complex workflows |

### 9.2 Provider-to-Capability Mapping

Each provider (LLM, specialised tool, external service) declares which capabilities it provides and at what quality level. The Capability Layer routes requests to the best available provider based on the user's preferences (cost, quality, speed) and the provider's declared capability profile.

This is a direct extension of the Provider Abstraction pattern (ADR-003): the Provider Interface is augmented with capability metadata, and the Provider Factory (IC-05) uses capability-based routing in addition to type-based routing.

*Governed by: CP-014, AL-005, ADR-003, UP-005. Implementation pending future task authorisation.*

## 10. Learning Strategy

The Learning Strategy defines how AIS evolves together with the user over time, within the constraints of the constitutional framework.

### 10.1 Learning Dimensions

| Dimension | Mechanism | Safety Constraint |
|-----------|-----------|-------------------|
| **Behavioural Adaptation** | AIS learns the user's patterns (reading speed, work schedule, tool preferences) and adapts its behaviour accordingly | Per DP-005: adaptation is gradual and observable |
| **Preference Refinement** | AIS suggests preference adjustments based on observed behaviour (e.g., "You consistently dismiss tips — reduce notification frequency?") | User must explicitly approve all preference changes |
| **Domain Knowledge Growth** | As the user works, AIS accumulates domain-specific context (frequently referenced documents, common tasks, domain vocabulary) in user-sovereign Knowledge Runtime space | Knowledge never shared across users per CP-021 |
| **Confidence Calibration** | AIS calibrates its confidence model based on user feedback (acceptance/rejection of suggestions, correction of predictions) | Calibration data belongs to the user per CP-005 |
| **Workflow Optimisation** | AIS learns which workflows the user executes most frequently and optimises their execution (pre-loading context, suggesting shortcuts) | Optimisation never changes workflow behaviour, only performance |
| **Skill Inference** | AIS infers the user's skill level from their interactions and adjusts its communication accordingly | Inferred skills are transparent to the user and overridable |

### 10.2 Learning Safety Rules

1. **No Cross-User Learning**: Learning data is never shared, aggregated, or analysed across users. Each user's learning model is completely isolated. Per CP-021, CP-005, ADR-011.
2. **Transparent Learning**: Every adaptation is observable and explainable. The user can see why AIS changed its behaviour and can revert any change. Per DP-005, DP-010.
3. **User-Controlled Learning**: The user can disable any learning dimension. Disabling is not penalised. Per CP-023 (Exit Is Always Possible).
4. **Gradual Adaptation**: Changes are small, incremental, and reversible. AIS never makes abrupt, large-scale behaviour changes. Per DP-005.
5. **No Manipulation**: AIS never manipulates the user's behaviour for its own benefit. Learning serves the user's goals, not the platform's metrics.
6. **Data Minimisation**: AIS collects only the data necessary for the declared learning dimensions. No covert data collection. Per CP-022 (Telemetry Is Honest).

## 11. Company Layer

The Company Layer defines how AIS supports organisational deployment beyond individual use.

### 11.1 Organisational Hierarchy

```
Organisation
    ├── Department
    │       ├── Team
    │       │       └── User
    │       └── Project
    └── Policy
            ├── Role
            ├── Permission
            └── Compliance Rule
```

### 11.2 Organisational Components

| Component | Responsibility |
|-----------|----------------|
| **Organisation** | Top-level entity representing a company, institution, or other organised group. Owns organisational policies, data, and configurations. |
| **Department** | Subdivision of an organisation (e.g., Engineering, Legal, Finance). Can inherit organisation-level policies and add department-specific ones. |
| **Team** | Working group within a department. Shared context, shared projects, shared tool configurations. |
| **Project** | Time-bounded initiative with its own Domain Pack configuration, Knowledge Pack, Tool Pack, and Workflow Pack. |
| **Role** | Organisational role definition (e.g., "Senior Engineer", "Compliance Officer"). Maps to permissions and policies. |
| **Permission** | Granular access control: what data a role can access, what tools it can use, what autonomy levels it can set. |
| **Policy** | Organisational rule enforcement: compliance requirements, data handling rules, approval workflows, audit mandates. |
| **Compliance Rule** | Domain-specific regulatory constraint (e.g., HIPAA, SOX, GDPR). Enforced through Policy Pack layer. |

### 11.3 Multi-Tenancy Model

- **Data Isolation**: Each organisation's data is completely isolated from other organisations. Per AL-004 (One Memory, One Authority) and AL-006 (Trust Zones).
- **Policy Inheritance**: Departments inherit organisation policies. Teams inherit department policies. Users inherit team policies. Any level can add stricter (but never looser) constraints.
- **Resource Sharing**: Knowledge Packs and Tool Packs can be shared within an organisation (licensed centrally) or private to a team/user.
- **Audit Trail**: All organisational actions are audited per AL-012. Audit logs are organisation-scoped and accessible to authorised roles.

*Governed by: CP-005, CP-021, AL-004, AL-006, AL-012, UP-009. Implementation pending future task authorisation.*

## 12. Marketplace Strategy

The Marketplace is the distribution and discovery channel for all Packs and extensions.

### 12.1 Marketplace Contents

| Category | Description | Examples |
|----------|-------------|---------|
| **Domain Packs** | Complete domain specialisation packages | Medical, Legal, Financial, Engineering, Research, Education |
| **Knowledge Packs** | Pre-curated knowledge collections for specific domains | Medical literature, Legal case database, Financial regulation library |
| **Tool Packs** | Domain-specific tool integrations | DICOM viewer, Bloomberg connector, GitHub integration, CAD plugin |
| **Workflow Packs** | Automated workflow templates | Diagnostic workflow, Audit workflow, Code review workflow, Compliance check |
| **Policy Packs** | Compliance and governance rule sets | HIPAA policy, SOX policy, GDPR policy, ISO 27001 policy |
| **Prompt Packs** | Curated prompt templates for specific tasks | Medical diagnosis prompts, Legal research prompts, Code review prompts |
| **UI Themes** | Visual interface customisation | Professional, minimalist, high-contrast, accessibility-focused |
| **Capability Packs** | Extended capability definitions | Specialised reasoning, domain-specific analysis, industry-specific reporting |

### 12.2 Marketplace Principles

1. **Quality Assurance**: All Marketplace items are validated before publication. Validation includes schema compliance, dependency checking, security review, and constitutional compliance.
2. **Versioning**: All Marketplace items follow the versioning system defined in ADR-013. Backward compatibility is enforced.
3. **Reviews and Ratings**: Users can rate and review Packs. Ratings inform discovery and quality signals.
4. **Monetisation**: Creators can set prices for paid Packs. Revenue sharing follows Marketplace policies.
5. **Open and Closed**: The Marketplace supports both open-source (free) and commercial (paid) Packs. The Core remains open-source regardless.
6. **Security**: All Marketplace items undergo security scanning. Items with security vulnerabilities are removed. Per AL-011, AL-012.
