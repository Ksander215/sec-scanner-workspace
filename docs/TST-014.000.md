## 1. Testing Philosophy

The Compliance Engine validates the entire AIS platform. Its own test suite must be the most rigorous in the codebase. Every rule, every subsystem, every event, and every error code is exercised with multiple test cases covering the happy path, sad path, and boundary conditions. Tests follow the existing Vitest 4.x conventions established in `src/__tests__/` with `describe/it/expect` structure and `beforeEach` for isolation.

## 3. Test Categories

### 3.1 Unit Tests (~1,400 tests)

Each subsystem is tested in isolation with fresh instances per test:
- Constructor behavior and config acceptance
- Method invocation with valid inputs
- Error paths with expected exceptions
- Edge cases: empty inputs, null, undefined, boundary values
- Immutability: Object.freeze on all returned objects
- Type safety: branded IDs, enum membership, interface conformance

### 3.2 Integration Tests (~300 tests)

Cross-subsystem interactions:
- ComplianceRuntime full lifecycle (initialize -> validate -> report -> shutdown)
- Event publishing through InProcessEventBus
- Policy evaluation delegating to RuleEngine
- All 10 validators registering into a single RuleEngine
- Report generation aggregating results from multiple validators
- Metrics accumulation across multiple validation passes

### 3.3 Contract Tests (~190 tests)

Verify all public interfaces are correctly implemented:
- IRuleEngine (11 methods)
- IPolicyEngine (7 methods)
- IReportGenerator (4 methods)
- IComplianceMetrics (6 methods)
- IComplianceRuntime (11 methods)
- All 10 IValidator interfaces
- All 11 event interfaces
- ComplianceEvent union type

## 4. Validation Testing Strategy

### 4.1 Per-Rule Testing Pattern

For each of the 40 rules, tests cover:
1. **No content** — Returns passed=true with skip note
2. **Compliant content** — Returns passed=true (positive case)
3. **Violating content** — Returns passed=false with violation(s) (negative case)
4. **Violation details** — Correct severity, enforcement level, description, evidence, recommendation
5. **Multiple violations** — Rules that can detect multiple patterns
6. **Non-applicable content** — Rules that only check certain file types (ADR files, .ts files, test files)

### 4.2 Pattern-Based Validation

Validators use regex-based content analysis. Tests verify:
- Regex correctly matches intended patterns
- Regex does not produce false positives on clean code
- Multiple patterns are independently detected
- Edge cases in regex behavior (word boundaries, case insensitivity)

### 4.3 Category Filtering

Tests verify that:
- Rules are only evaluated when their category matches the request
- Validators only produce results for their registered categories
- Cross-category requests correctly include/exclude rules
- Empty category filters evaluate all rules

## 5. Event Testing Strategy

### 5.1 Event Structure Validation

For each of the 11 event types:
- Create a valid object conforming to the interface
- Verify all required fields are present and correctly typed
- Verify readonly constraints (through interface compliance)
- Verify metadata is present

### 5.2 Event Publishing

For events published by subsystems:
- Event is published to InProcessEventBus on correct operation
- Event is not published when eventBus is null
- Event combines domain event fields (eventId, sequence, aggregateId, etc.)
- Subscriber isolation: failing handler does not block publisher

### 5.3 Event Union Type

- All 10 member types are assignable to ComplianceEvent union
- Type narrowing works correctly via eventType discriminator

- Event type strings follow the `compliance.*` naming convention

## 6. Error Testing Strategy

### 6.1 Error Hierarchy

```
ComplianceError (base)
  ├── RuleNotFoundError
  ├── RuleAlreadyRegisteredError
  ├── RuleEvaluationError
  ├── RuleEvaluationTimeoutError
  ├── RuleLimitExceededError
  ├── PolicyNotFoundError
  ├── PolicyAlreadyRegisteredError
  ├── PolicyLimitExceededError
  ├── ValidationError
  ├── ValidationTimeoutError
  ├── BlockingViolationError
  ├── ComplianceRuntimeError
  ├── ComplianceNotInitializedError
  ├── ReportGenerationError
  └── ViolationNotFoundError
```

### 6.2 Per-Error Tests

For each error class:
- Extends ComplianceError (instanceof chain)
- Extends Error (native JavaScript)
- Has correct `.name` property
- Has correct `.code` property
- Has specific properties (ruleId, policyId, targetPath, violationIds)
- Context is frozen (Object.freeze)
- Timestamp is a valid ISO-8601 string
- Message includes relevant identifiers

## 7. Configuration Testing

### 7.1 DefaultComplianceRuntimeConfig

- All nested config objects are present
- All score weights sum to 1.0
- All values are frozen (Object.freeze)
- Mutation attempts throw TypeError

### 7.2 Config Pass-Through

- ComplianceRuntime passes sub-configs to subsystems
- Custom configs override defaults correctly
- Missing config sections use defaults
