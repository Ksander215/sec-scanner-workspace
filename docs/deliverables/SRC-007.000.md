## Key Design Decisions

1. **Dual FSM Architecture** — The workflow runtime employs two separate finite state machines: a *Workflow FSM* governing the top-level instance lifecycle (7 states: `idle → running → paused → completing → completed / failed / cancelled`) and a *Stage FSM* governing individual stage execution (8 states including `pending`, `skipped`, and `compensating`). This separation enables independent reasoning about workflow-level and stage-level concerns.

2. **Branded Type Identifiers** — All entity IDs (`WorkflowDefinitionId`, `WorkflowInstanceId`, `StageId`, etc.) use TypeScript branded types to prevent accidental cross-entity ID misuse at compile time without runtime overhead.

3. **Discriminated Union Events** — Domain events use a string literal `type` discriminator field with a union type (`WorkflowEvent`), enabling exhaustive pattern matching and ensuring no event type is silently dropped by handlers.

4. **Five-Scope Variable Hierarchy** — Variables resolve across five nested scopes (global → workflow → stage → iteration → step) with explicit merge strategies (`override`, `merge`, `prepend`, `append`) rather than simple overwriting, allowing downstream stages to access accumulated context without mutation of upstream data.

5. **Compensation-First Error Handling** — Rather than relying solely on retry loops, the runtime implements a structured compensation engine with five discrete actions (`undo`, `retry`, `compensate`, `notify`, `log`). Compensations are registered declaratively during definition and executed in reverse topological order on failure.

6. **Policy Engine Extensibility** — The policy subsystem is built on a handler registration model where five default policies (timeout, retry, concurrency, notification, dead-letter) are pre-registered but can be replaced or extended at runtime without modifying the core scheduler or transition engine.

7. **In-Memory Storage with Interface Abstraction** — The default storage adapter is in-memory for zero-dependency development, but all persistence is accessed through a `WorkflowStoragePort` interface, enabling drop-in replacement with SQLite, PostgreSQL, or external stores without touching orchestration logic.

## Integration Points

The Workflow Runtime integrates with the following runtimes and subsystems within the platform:

| Runtime / Subsystem | Integration Method | Description |
|--------------------|--------------------|-------------|
| **Agent Runtime** | Event bus (publish/subscribe) | Workflow stages can invoke agent executions and receive `AgentCompleted` / `AgentFailed` events back into the workflow FSM |
| **Tool Runtime** | Synchronous adapter via `TransitionEngine` | Stage guards and conditions may evaluate tool availability and invoke tool calls as part of stage execution |
| **Memory Runtime** | Variable scope bridge | The five-scope variable manager reads from and writes to the Memory Runtime's key-value store for persistent cross-workflow context |
| **Event Bus (Platform)** | `WorkflowEvent` emission | All 15 domain events are published to the platform-wide event bus for audit, monitoring, and cross-runtime reaction |
| **Policy Engine (Platform)** | Handler registration | The 5 default policy handlers conform to the platform policy interface and can be augmented with organization-specific policies |
| **Observability / Tracing** | `WorkflowTrace` export | Execution traces are structured as OpenTelemetry-compatible spans and exported to the platform tracing pipeline |
| **Metrics Collector** | `WorkflowMetrics` adapter | Counter-based metrics (durations, counts, error rates) are pushed to the platform metrics aggregation service |
| **Storage Abstraction** | `WorkflowStoragePort` | The persistence interface is designed to be fulfilled by the platform's Data Access layer (SQLite default, extensible) |
