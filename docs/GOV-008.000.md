## 2. Purpose of This Document

This document updates the Architecture Governance framework to incorporate the **Immutable Principles** defined in the AIS Constitution (PHI-001.000), the Value Creation Model (PHI-002.000), the Constraint Optimization Model (PHI-003.000), and the Company Playbook (PHI-004.000).

Governance is the mechanism through which principles become enforceable. Without governance, the Constitution is aspirational. With governance, the Constitution is operational.

## 5. Runtime Requirements

### 5.1 Mandatory Runtime Questions

Every Runtime in the AIS platform must be able to answer the following questions. These questions become part of the Runtime's public API contract.

| Question ID | Question | Return Type | Fallback |
|---|---|---|---|
| GOV-RQ-001 | What currently constrains the user? | `ConstraintReport | 'Unknown'` | `'Unknown'` |
| GOV-RQ-002 | What value does this Runtime create? | `ValueMetricsReport` | Must always return a report; zero-value dimensions are valid |
| GOV-RQ-003 | What can be improved? | `ImprovementSuggestion[]` | Empty array (no suggestions is valid) |
| GOV-RQ-004 | How is the result measured? | `MeasurementPlan` | Must return a plan; if measurement is not yet possible, explain why |

**Critical rule:** If a Runtime cannot answer any of these questions, it **must return "Unknown"** — never fabricate an answer. Fabrication violates PHI-CV-001 (Truth).

### 5.2 Runtime Governance Interface

Every Runtime must implement the following governance interface:

```typescript
interface RuntimeGovernanceContract {
  /**
   * GOV-RQ-001: What currently constrains the user
   * (Per PHI-UC-001, PHI-003.000)
   */
  getConstraintReport(): ConstraintReport | 'Unknown';

  /**
   * GOV-RQ-002: What value does this Runtime create
   * (Per PHI-UC-002, PHI-002.000)
   */
  getValueMetrics(): ValueMetricsReport;

  /**
   * GOV-RQ-003: What can be improved
   * (Per PHI-UC-004, PHI-003.000)
   */
  getImprovementSuggestions(): ImprovementSuggestion[];

  /**
   * GOV-RQ-004: How is the result measured
   * (Per PHI-UC-012, PHI-002.000)
   */
  getMeasurementPlan(): MeasurementPlan;
}
```

## 6. AI Requirements

### 6.1 Cognitive Runtime Recommendation Chain

Before issuing any recommendation, the Cognitive Runtime **must** traverse the following chain. A recommendation that skips any step is invalid.

```
GOV-AI-STEP-1: GOAL
    “What is the user trying to achieve?”
    → Identifies or infers the user's current goal.
    → If goal is ambiguous, ask for clarification before proceeding.
    ↓
GOV-AI-STEP-2: VALUE
    “What value would this recommendation create?”
    → Maps the potential recommendation to PHI-002.000 value dimensions.
    → Estimates the magnitude of value creation.
    → If value cannot be articulated, do not recommend.
    ↓
GOV-AI-STEP-3: CONSTRAINT
    “What constraint is limiting the user?”
    → Applies PHI-003.000 constraint detection.
    → Identifies the specific bottleneck the recommendation would address.
    → If no constraint is identified, reconsider whether a recommendation is needed.
    ↓
GOV-AI-STEP-4: ROOT CAUSE
    “Why does this constraint exist?”
    → Applies PHI-UC-011 (Root Cause Principle).
    → Minimum: Five Whys analysis.
    → If root cause is unclear, present the analysis as a hypothesis, not a conclusion.
    ↓
GOV-AI-STEP-5: RECOMMENDATION
    “Based on the above analysis, what should the user consider?”
    → The recommendation is the output of the analysis, not the starting point.
    → Multiple options should be provided when appropriate, with trade-offs explained.
    → Each option must reference which constraint it addresses and what value it creates.
    ↓
GOV-AI-STEP-6: EXPECTED IMPACT
    “What should happen if the user follows this recommendation?”
    → Predicts the outcome in measurable terms (PHI-002.000 value dimensions).
    → Includes confidence level for the prediction.
    → Explicitly states what could go wrong (PHI-CV-001: Truth).
    ↓
GOV-AI-STEP-7: MEASUREMENT
    “How will we know if the recommendation was effective?”
    → Defines the measurement that would validate or invalidate the recommendation.
    → Suggests a follow-up check timeframe.
    → If the recommendation's effect cannot be measured, acknowledge this limitation.
```

### 6.2 AI Output Requirements

Every AI-generated output must include:

1. **Confidence level** — how certain the AI is about the output (never 100% unless provable).
2. **Reasoning chain** — the steps that led to the conclusion (per GOV-AI-STEP-1 through STEP-7 above).
3. **Value articulation** — what value the output creates for the user (per PHI-002.000).
4. **Constraint addressed** — which user constraint this output helps resolve (per PHI-003.000).
5. **Fallback** — what the user should do if the output is incorrect or unhelpful.

## 7. Personal Intelligence Runtime Requirements

### 7.1 Constraint Detection Scope

The Personal Intelligence Runtime is obligated to help users identify **bottlenecks** (constraints) in the following domains:

| Domain | GOV-PI-ID | Constraint Examples | Detection Method |
|---|---|---|---|
| **Life** | GOV-PI-001 | Time allocation, energy management, relationship investment | Pattern analysis over time |
| **Work** | GOV-PI-002 | Task prioritization, meeting load, deep work availability | Workflow pattern analysis |
| **Learning** | GOV-PI-003 | Study consistency, depth of engagement, knowledge retention | Learning curve analysis |
| **Habits** | GOV-PI-004 | Trigger patterns, consistency, environmental factors | Behavioral pattern detection |
| **Health** | GOV-PI-005 | Activity patterns, sleep quality, stress indicators | Correlation analysis |
| **Finances** | GOV-PI-006 | Spending patterns, subscription accumulation, savings rate | Financial pattern tracking |
| **Projects** | GOV-PI-007 | Scope stability, milestone achievement, dependency management | Project health metrics |

### 7.2 Constraint Communication Rules

1. **Present, don't prescribe.** The Personal Intelligence Runtime presents observations and patterns. It never diagnoses or prescribes. The user decides whether a pattern is a problem and what to do about it (PHI-CV-010: Autonomy).
2. **Evidence required.** Every constraint observation must include the specific evidence that supports it (PHI-UC-012: Evidence Based Decisions).
3. **Humility required.** If the evidence is weak or the pattern is unclear, say so. "Unknown" is always an acceptable answer (PHI-CV-001: Truth).
4. **User control required.** The user can disable constraint detection for any domain at any time (PHI-CV-010: Autonomy).

## 8. Experience Runtime Requirements

### 8.1 Value-Centric Measurement

The Experience Runtime must evaluate not only user satisfaction (traditional UX metric) but also **value growth** (PHI-002.000). This means:

| Traditional Metric | Value Metric | Why It Matters |
|---|---|---|
| Satisfaction score (1-5) | Value growth rate (per-session) | Satisfaction without growth means the product entertains but does not help |
| Task completion rate | Goal achievement rate | Completing tasks without achieving goals is busywork |
| Time on platform | Value per interaction | More time does not mean more value; we want high value density |
| Feature adoption rate | Value dimension improvement | Using features is not the goal; improving value dimensions is |
| Net Promoter Score | User growth rate | Recommending AIS is good; growing because of AIS is better |

### 8.2 Experience Governance Interface

The Experience Runtime must implement:

```typescript
interface ExperienceGovernanceContract extends RuntimeGovernanceContract {
  /**
   * Measures not just satisfaction but value growth
   * (Per PHI-UC-005, PHI-002.000)
   */
  getValueGrowthTrend(): {
    dimension: string;
    trend: 'improving' | 'stable' | 'declining' | 'unknown';
    confidence: number;
    period: { start: timestamp; end: timestamp };
  }[];

  /**
   * Identifies experiences that create negative value
   * (Per PHI-CV-001, PHI-002.000 §6)
   */
  getNegativeValueExperiences(): {
    description: string;
    valueImpact: number;
    evidence: string[];
    suggestedFix: string;
  }[];
}
```

## 11. Capability Pack Requirements

Future **Capability Packs** (extensible modules that add domain-specific capabilities to AIS) must comply with the following governance requirements:

### 11.1 Capability Pack Constitutionality

Every Capability Pack must:

1. **Reference the Constitution** — the pack's manifest must explicitly state which Core Values and Universal Principles are most relevant to its domain.
2. **Define value dimensions** — the pack must articulate which PHI-002.000 value dimensions it affects and how.
3. **Implement governance interface** — the pack must implement `RuntimeGovernanceContract` (§5.2).
4. **Support offline operation** — the pack must work without cloud connectivity (PHI-UC-006: Local First) or explicitly document why cloud is required.
5. **Respect user autonomy** — the pack must never make decisions for the user or bypass human judgment (PHI-UC-009).

### 11.2 Capability Pack Review Process

Before a Capability Pack is released, it must pass:

1. **Constitutionality review** — does the pack violate any Blocking principle?
2. **Value review** — does the pack create measurable value per PHI-002.000?
3. **Privacy review** — does the pack handle user data in compliance with PHI-CV-005?
4. **Simplicity review** — does the pack follow PHI-CV-003 and PHI-UC-010?
5. **Constraint review** — does the pack create new constraints or help resolve existing ones?
