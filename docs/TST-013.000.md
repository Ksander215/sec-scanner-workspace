## 3. Test Infrastructure

### 3.1 Mock Provider SDK

All 15 test files use `MockProviderSDK` as the test double for provider interactions. The mock supports:

- **Configurable response text** — `response?: string` (default: `'Mock response'`)
- **Configurable latency** — `latencyMs?: number` (default: `10ms`)
- **Configurable failure rate** — `failRate?: number` (default: `0`)
- **Configurable error message** — `errorMessage?: string`
- **Full `ProviderSDK` interface** — `execute()`, `stream()`, `health()`, `models()`, `embeddings()`, `tokenize()`, `detokenize()`
- **Initialization guard** — throws if `execute()` called before `initialize()`
- **Deterministic embeddings** — 128-dim vectors based on text length
- **Word-by-word streaming** — splits response on spaces, yields individual chunks

### 3.2 Dependency Injection in Tests

Each subsystem is tested in isolation. The `ExecutionEngine` test creates the engine with mock function references:

```typescript
const engine = new ExecutionEngine(config, {
  getProviderSDK: mockGetSDK,
  getModel: mockGetModel,
  shouldRetry: mockShouldRetry,
  getRetryDelay: mockGetDelay,
  getNextProvider: mockGetNext,
  // ... other deps with no-op defaults
});
```

This pattern allows testing each subsystem independently without instantiating the full `AIProviderRuntime`.

### 3.3 Event Bus in Tests

Tests that verify event publishing create a mock event bus that captures published events:

```typescript
const published: DomainEventBase[] = [];
const mockBus = { publish: (e: DomainEventBase) => { published.push(e); } } as unknown as InProcessEventBus;
```

### 3.4 Error Hierarchy Testing

The 33 error classes are tested via `instanceof` chains and structured detail fields. Every error class is verified to:
- Extend `AIProviderError` (which extends `Error`)
- Carry correct error codes
- Include structured detail objects
- Format messages correctly

## 5. Stress Test Notes

### 5.1 Concurrent Execution

The `ExecutionEngine` enforces `maxConcurrentExecutions` (default: 10). The test suite verifies:
- Exact limit enforcement — the 11th concurrent request throws `ConcurrentExecutionLimitError`
- Status cleanup after completion/failure — `active` map is pruned correctly

### 5.2 Retry Storm

The `RetryEngine` test suite exercises all 4 backoff strategies across multiple attempts:
- **Fixed**: constant delay regardless of attempt number
- **Linear**: `initialDelay * attempt`
- **Exponential**: `initialDelay * 2^(attempt-1)`, capped at `maxDelayMs`
- **ExponentialJitter**: exponential with randomization (bounds verified statistically)

Max retry exhaustion is tested with `defaultMaxRetries: 3` — the 4th attempt throws `RetryExhaustedError`.

### 5.3 Failover Chain Exhaustion

The `FailoverEngine` tests verify:
- Sequential fallback through chain entries
- Chain exhaustion after `maxFailovers` (default: 3)
- `FailoverExhaustedError` when no more providers available
- `NoFailoverChainError` when no chain registered for an execution

### 5.4 Cache Eviction

The `CacheEngine` tests verify:
- TTL expiry triggers `CacheEvictedEvent`
- Max entries enforcement (default: 1000)
- Stats accuracy under rapid get/set/delete cycles

### 5.5 Token Budget Enforcement

The `TokenManager` tests verify:
- Warn event fires at 80% budget consumption
- Block (error) fires at 95% budget consumption
- Exact accounting across all 6 token types
- Multiple account isolation
