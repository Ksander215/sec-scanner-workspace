## 2. Purpose of This Document

This document provides the **formal model for identifying, measuring, and resolving constraints** across the AIS platform. It is the operational implementation of **PHI-UC-001 (Constraint First Principle)** from the AIS Constitution.

The model is based on the **Theory of Constraints** (ToC) as formulated by Eliyahu M. Goldratt in "The Goal" (1984) and subsequent works. ToC states that every system has at least one constraint, and that system-wide improvement is achieved only by improving the constraint. Optimizing non-constrained components is waste.

This document applies ToC at four levels: the AIS platform itself, each individual Runtime, the AI systems within AIS, and the user's own life and work.

## 3. Core Concepts

### 3.1 What Is a Constraint?

A **constraint** is any factor that limits the system from achieving higher performance relative to its goal.

In the context of AIS:

- **Platform-level constraint:** The single component or subsystem that currently limits the value AIS can deliver to users. Example: if the Memory Runtime's retrieval accuracy is the bottleneck that prevents users from finding their knowledge, it is the constraint.
- **Runtime-level constraint:** Within a specific Runtime, the component that limits that Runtime's performance. Example: if the Cognitive Runtime's recommendation latency is too high, it limits the user's ability to get timely assistance.
- **AI-level constraint:** A limitation in the AI models or processing pipeline that limits the quality of AI assistance. Example: if context window size prevents AIS from considering enough history, that is an AI constraint.
- **User-level constraint:** A bottleneck in the user's life, work, or learning that limits their growth. Example: if a user's decision-making process is limited by poor information organization, that is a user constraint that AIS should help identify and address.

### 3.2 Constraint vs. Symptom

A critical distinction from PHI-UC-011 (Root Cause Principle):

- **Symptom:** "Users are spending too much time searching for information."
- **Constraint:** "The Knowledge Runtime's semantic search relevance score is 0.34, below the 0.6 threshold."

Symptoms are what users experience. Constraints are the systemic causes that produce symptoms. AIS must always operate on constraints, not symptoms. Fixing the search UI (symptom) without fixing search relevance (constraint) may improve perception temporarily but will not solve the problem.

### 3.3 Constraint Taxonomy

| Type | Description | Example |
|---|---|---|
| **Capacity** | A component cannot handle the current load | Memory Runtime cannot index documents fast enough for real-time updates |
| **Quality** | A component's output quality is insufficient | Cognitive Runtime recommendations have a relevance score below threshold |
| **Latency** | A component takes too long to respond | AI Provider Runtime execution time exceeds 5 seconds |
| **Accuracy** | A component produces incorrect results | Token Manager's estimation error exceeds 20% |
| **Coverage** | A component does not handle all required cases | Workflow Runtime does not support parallel decision branches |
| **Usability** | A component's output is correct but not usable | Context Manager produces relevant context but in an unstructured format |
| **Knowledge** | The system lacks necessary information | AIS does not know enough about the user's domain to provide useful recommendations |
| **Behavioral** | The user has a behavioral pattern that limits their effectiveness | The user consistently skips the review step in their decision process |

## 4. The Constraint Optimization Cycle

### 4.1 The Five-Step Focusing Process (FOCUS)

Based on Goldratt's Five Focusing Steps, adapted for AIS:

```
COM-STEP-1: IDENTIFY the system's constraint
     ↓
COM-STEP-2: EXPLOIT the constraint (maximize its utilization)
     ↓
COM-STEP-3: SUBORDINATE everything else to the constraint
     ↓
COM-STEP-4: ELEVATE the constraint (increase its capacity)
     ↓
COM-STEP-5: REPEAT — if the constraint has shifted, return to step 1
```

#### COM-STEP-1: Identify the Constraint

**Goal → Measure → Detect.**

1. **Define the system's goal** (per PHI-002.000, the goal is value creation).
2. **Measure current throughput** (value delivery rate, in value-dimension units per time period).
3. **Identify the component** where work is piling up, quality is lowest, or latency is highest — that is the constraint.

**Runtime obligation:** Every Runtime must be able to answer: "What currently limits this Runtime's value output?" If it cannot answer, it must return **"Unknown"** and flag the need for measurement infrastructure.

#### COM-STEP-2: Exploit the Constraint

Ensure the constraint is working at **maximum effective capacity**. This means:

- No idle time on the constraint resource.
- No wasted effort on the constraint (e.g., reprocessing, redundant work).
- The constraint is doing only what it does best — all other work is offloaded.

**Example:** If the AI Provider Runtime's execution latency is the constraint, ensure that every execution request is meaningful (no duplicate calls, no unnecessary re-executions, caching is maximized).

#### COM-STEP-3: Subordinate Everything Else

Non-constraint components must be adjusted to **support the constraint**, not to optimize themselves:

- Non-constraint components should produce **no more than the constraint can absorb**. Producing excess creates waste (work-in-progress inventory that the constraint cannot process).
- Non-constraint components should **never optimize locally** in ways that increase load on the constraint.

**Example:** If the Memory Runtime's retrieval speed is the constraint, the Knowledge Runtime should not index more knowledge than the Memory Runtime can retrieve. Adding more knowledge that cannot be found is waste.

#### COM-STEP-4: Elevate the Constraint

If exploiting and subordinating are insufficient to meet the goal, **invest in increasing the constraint's capacity**:

- Add resources to the constrained component.
- Redesign the constrained component for higher throughput.
- Replace the constrained component with a fundamentally different approach.

**Example:** If the AI Provider Runtime's context window size is the constraint, and exploitation (better context selection) and subordination (reducing unnecessary context) are insufficient, elevate by integrating models with larger context windows.

#### COM-STEP-5: Repeat

After elevating the constraint, one of two things happens:

1. **The constraint breaks** and a new constraint emerges elsewhere. Return to COM-STEP-1.
2. **The constraint remains** and further elevation is needed. Evaluate whether the system's goal needs adjustment or whether different elevation strategies are required.

This cycle **never ends**. Per PHI-UC-004 (Continuous Improvement), constraint optimization is a perpetual process.

## 5. Constraint Detection at Each Level

### 5.1 Platform Level

**Who:** Platform Integration Runtime (per SRC-011.000)

**How:**
- Aggregate value metrics from all Runtimes (per PHI-002.000 §4.1, Macro level).
- Identify the Runtime contributing the least value per unit of resource consumed.
- Analyze cross-Runtime dependencies: is one Runtime's constraint causing bottlenecks in others?
- The constraint is the Runtime (or cross-Runtime interaction) that most limits total platform value.

**Reporting:** Platform must report: current constraint, evidence for identification, exploitation status, subordination actions taken, and elevation plans.

### 5.2 Runtime Level

**Who:** Each individual Runtime

**How:**
- Measure the Runtime's own value output against its value potential.
- Profile the Runtime's internal components: identify which internal subsystem is the bottleneck.
- Track queue depths, processing times, error rates, and quality scores for each internal component.
- The constraint is the internal component that most limits the Runtime's value output.

**Reporting:** Each Runtime must expose a `getConstraintReport()` method:

```typescript
interface ConstraintReport {
  runtimeId: string;
  constraint: {
    component: string;
    type: ConstraintType;    // from §3.3 taxonomy
    description: string;
    evidence: string[];
    impactOnValue: number;   // estimated value lost per time period
    status: 'identified' | 'exploiting' | 'subordinating' | 'elevating' | 'resolved';
  };
  previousConstraint?: {
    component: string;
    resolvedAt: timestamp;
    resolutionMethod: string;
    valueImpact: number;     // value gained by resolving it
  };
}
```

### 5.3 AI Level

**Who:** AI Provider Runtime (per TASK-AIS-006A.000, SRC-013.000)

**How:**
- Monitor model performance metrics: accuracy, relevance, latency, token efficiency.
- Compare performance across providers to identify which provider/model is the constraint.
- Analyze the AI pipeline: is the constraint in the model, the context selection, the prompt construction, or the output processing?
- Track failover frequency — frequent failovers indicate a provider-level constraint.

**Reporting:** The AI Provider Runtime's Metrics Runtime reports constraint information as part of its standard metrics output.

### 5.4 User Level

**Who:** Personal Intelligence Runtime (per TASK-AIS-005B.000)

**How:**
- Analyze the user's activity patterns, goal progress, and value metrics over time.
- Identify recurring patterns that limit the user's growth: procrastination loops, knowledge gaps, decision avoidance, over-optimization, context switching.
- Compare the user's trajectory against their own goals and against anonymized cohort benchmarks.
- The constraint is the behavioral, knowledge, or environmental factor most limiting the user's value growth.

**Domains for constraint detection:**

| Domain | Example Constraints |
|---|---|
| **Life** | Time management, sleep patterns, relationship maintenance, health habits |
| **Work** | Task prioritization, meeting overload, context switching, knowledge silos |
| **Learning** | Inconsistent study patterns, surface-level engagement, lack of spaced repetition |
| **Habits** | Procrastination triggers, environmental distractions, willpower depletion |
| **Health** | Sedentary patterns, stress accumulation, sleep deprivation |
| **Finances** | Impulse spending, lack of tracking, subscription creep |
| **Projects** | Scope creep, unclear milestones, dependency bottlenecks |

**Important:** User-level constraints must be presented as **observations**, not diagnoses. AIS suggests: "I notice you typically delay decisions involving financial trade-offs for an average of 8 days. This may be limiting your goal of 'Reduce financial decision debt.' Would you like to explore this further?" It never prescribes: "You have a decision avoidance problem. Here is a 7-step program."

## 6. Constraint Lifecycle

Every constraint follows a lifecycle from detection to resolution:

```
       COM-LC-1           COM-LC-2           COM-LC-3
  GOAL Definition → MEASUREMENT → CONSTRAINT
  (What are we     (Baseline &     DETECTION
   trying to        real-time        (Where is the
   improve?)        metrics)         bottleneck?)
       │                  │                  │
       ▼                  ▼                  ▼
                         COM-LC-4           COM-LC-5
                  ROOT CAUSE → OPTIMIZATION
                  ANALYSIS    (Exploit →
                  (Why does   Subordinate →
                   this         Elevate)
                   exist?)          │
                         │              │
                         ▼              ▼
                                       COM-LC-6
                                VALIDATION
                                (Did value
                                 increase?)
                                       │
                              ┌────────┴────────┐
                              ▼                  ▼
                         COM-LC-7           COM-LC-8
                         CONSTRAINT         REPEAT
                         RESOLVED          (New constraint
                         (Document &        emerges)
                          move on)          Return to LC-1
```

### 6.1 Lifecycle Stages

| Stage | ID | Description | Exit Criteria |
|---|---|---|---|
| Goal Definition | COM-LC-1 | Clearly define what we are trying to improve, in value terms | Goal is articulated in at least one PHI-002.000 value dimension |
| Measurement | COM-LC-2 | Establish baseline metrics and real-time monitoring | Metrics pipeline is collecting relevant data |
| Constraint Detection | COM-LC-3 | Identify the specific component or factor that is the bottleneck | Constraint is identified with supporting evidence |
| Root Cause Analysis | COM-LC-4 | Determine why this constraint exists (Five Whys minimum) | Root cause is identified and documented |
| Optimization | COM-LC-5 | Apply the Focusing Process (Exploit → Subordinate → Elevate) | Constraint's impact on value is reduced by measurable amount |
| Validation | COM-LC-6 | Confirm that value actually increased as a result of the optimization | Value metrics show improvement attributable to the optimization |
| Constraint Resolved | COM-LC-7 | Document the resolution and its impact for future reference | Resolution is documented with evidence |
| Repeat | COM-LC-8 | Return to stage 1 — a new constraint has emerged | New constraint is identified |

### 6.2 Mandatory Documentation

Every constraint optimization cycle must produce a **Constraint Resolution Record**:

```typescript
interface ConstraintResolutionRecord {
  id: string;
  constraintId: string;
  goal: string;                    // What value dimension was targeted
  measurement: {
    baseline: number;              // Value before optimization
    afterOptimization: number;     // Value after optimization
    delta: number;                 // Improvement
    confidence: number;            // How certain we are this is causation, not correlation
  };
  rootCause: string;               // Why the constraint existed
  optimizationSteps: string[];     // What was done (Exploit/Subordinate/Elevate)
  evidence: string[];              // Supporting data
  resolvedAt: timestamp;
  nextConstraint: string;          // What emerged as the new constraint
}
```

## 7. Constraint-Aware Decision Making

When any architectural or product decision is made, the following questions must be answered:

### COM-DEC-001: What is the current constraint?
If the decision-maker cannot identify the current system constraint, the decision is deferred until the constraint is identified.

### COM-DEC-002: Does this decision affect the constraint?
If yes: the decision must be evaluated in terms of its impact on constraint throughput.
If no: the decision must be evaluated in terms of whether it will create a new constraint or worsen an existing one.

### COM-DEC-003: Does this decision add capacity to a non-constraint?
Adding capacity to a non-constrained component is waste unless there is evidence that the constraint is about to shift. Decision must include: "We believe the constraint will shift to X because of Y evidence. Therefore, pre-investing in Z is justified."

### COM-DEC-004: What is the expected value impact?
Per PHI-002.000, every decision must articulate its expected impact on value. For constraint-related decisions, this means: "By resolving constraint X, we expect to increase value dimension Y by Z amount, because evidence E supports this projection."

## 8. Integration with AI Provider Runtime

The AI Provider Runtime (TASK-AIS-006A.000) implements constraint optimization at the AI level:

| AI Provider Subsystem | Constraint Role |
|---|---|
| **Provider Registry** | Tracks which providers are available and their current capacity |
| **Model Registry** | Tracks which models offer which capabilities — identifies capability gaps |
| **Execution Engine** | The execution pipeline itself may be a constraint (latency, throughput) |
| **Retry Engine** | Frequent retries indicate a provider-level constraint |
| **Failover Engine** | Frequent failovers indicate provider reliability is a constraint |
| **Parallel Engine** | Parallel execution elevates throughput constraints by using multiple providers |
| **Cache Engine** | Caching exploits the constraint by reducing redundant work |
| **Token Manager** | Token budget management prevents context window from becoming a constraint |
| **Cost Engine** | Cost tracking ensures that cost does not become a constraint |
| **Metrics Runtime** | Provides the measurement infrastructure for constraint detection |
| **Trace Runtime** | Provides the evidence chain for root cause analysis |
