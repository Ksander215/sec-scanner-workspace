## 2. Scope

This manifest documents the **Platform Integration Layer** — the coordinator that unites all 8 existing domain Runtimes into a single working AIS platform.

### 2.1 Mandate

- Unite 8 domain Runtimes (Memory, Knowledge, Identity, Capability, Workflow, Cognitive, Experience, Desktop) into a single, cohesive AIS platform via the Platform Integration Layer.
- All prior Runtime architectures are **immutable** — only integration is permitted. No domain Runtime internals may be modified to accommodate the integration layer.
- The integrator (PlatformRuntime and its subsystems) acts **solely as a coordinator**: it discovers, validates, registers, initializes, and activates each Runtime, but does not alter their internal behavior.

### 2.2 Design Principle

The Platform Integration Layer follows a **facade pattern**. Each domain Runtime operates independently and exposes its capabilities through a `RuntimeContract` interface. The Platform does not know or care about the internals of any Runtime — it only knows the contract.

### 2.3 Exclusions

This manifest does not cover:
- Individual domain Runtime internals (each has its own SRC manifest)
- UI/UX layer implementation details
- External API gateway configuration
- Deployment and CI/CD pipeline specifics

## 4. Runtime Bridge Contracts

The file `runtime-bridges.ts` provides **8 bridge factory functions** that adapt existing domain Runtimes into the `RuntimeContract` interface expected by the `BootstrapEngine`.

### 4.1 Generic Bridge Factory

| Function | Signature |
|---|---|
| `createRuntimeBridge` | `(options: RuntimeBridgeOptions) → RuntimeContract` |

The generic bridge accepts options for id, name, version, description, dependencies, instance reference, health check function, and lifecycle callbacks (`onInitialize`, `onActivate`, `onShutdown`). It provides safe no-op defaults for all optional callbacks and health checks.

### 4.2 Domain-Specific Bridges

Each domain-specific bridge wraps a real Runtime instance and performs the following integration tasks:

1. **Registers the runtime instance** as a singleton in the DI container (`container.registerSingleton()`)
2. **Registers a health check function** in the Platform Health Monitor (`healthMonitor.registerCheck()`)
3. **Publishes lifecycle events** to the Event Hub (`eventHub.publish()`)
4. **Delegates to real lifecycle methods** on the wrapped runtime (`initialize()`, `start()`, `stop()`, `shutdown()`, `dispose()`)

| # | Bridge Factory | Runtime ID | Dependencies | Real Lifecycle Methods Called |
|---|---|---|---|---|
| 1 | `createMemoryRuntimeBridge` | `memory-runtime` | *(none — root)* | `getStats()`, `dispose()` |
| 2 | `createKnowledgeRuntimeBridge` | `knowledge-runtime` | `memory-runtime` | `getStats()`, `dispose()` |
| 3 | `createIdentityRuntimeBridge` | `identity-runtime` | `memory-runtime` | `initialize()`, `start()`, `stop()`, `shutdown()`, `dispose()`, `getStats()` |
| 4 | `createCapabilityRuntimeBridge` | `capability-runtime` | `memory-runtime`, `identity-runtime` | `initialize()`, `start()`, `stop()`, `shutdown()`, `dispose()`, `getMetrics()` |
| 5 | `createWorkflowRuntimeBridge` | `workflow-runtime` | `memory-runtime`, `knowledge-runtime` | `getMetrics()`, `listDefinitions()`, `dispose()` |
| 6 | `createCognitiveRuntimeBridge` | `cognitive-runtime` | `memory-runtime`, `knowledge-runtime`, `identity-runtime` | `initialize()`, `start()`, `shutdown()` |
| 7 | `createExperienceRuntimeBridge` | `experience-runtime` | `memory-runtime`, `identity-runtime`, `cognitive-runtime` | `initialize()`, `start()`, `stop()`, `shutdown()` |
| 8 | `createDesktopRuntimeBridge` | `desktop-foundation` | `memory-runtime`, `knowledge-runtime`, `identity-runtime`, `cognitive-runtime`, `experience-runtime` | `initialize()`, `start()`, `stop()`, `shutdown()` |

### 4.3 Bridge Integration Points

Each bridge hooks into the platform through the `PlatformContext`:

- **DI Container** — Runtime registered as singleton for cross-runtime dependency injection
- **Health Monitor** — Health check function registered for periodic monitoring
- **Event Hub** — Lifecycle events published (`runtime.<name>.initialized`, `runtime.<name>.activated`, `runtime.<name>.shutdown`)

## 5. Startup Order

The platform follows a deterministic startup order governed by the dependency graph resolved by the `DependencyResolver`. The `BootstrapEngine` executes the following sequence:

```
Platform  →  Bootstrap  →  Configuration  →  Registry  →  Memory  →  Knowledge
→  Identity  →  Capability  →  Workflow  →  Cognitive  →  Experience
→  Desktop  →  Ready
```

### 5.1 Phase Detail

| Step | Phase | Action |
|---|---|---|
| 1 | **Platform** | `PlatformRuntime` constructor instantiates all subsystems, wires DI, starts health auto-check |
| 2 | **Bootstrap** | `PlatformRuntime.start()` sets state to `Discovering`, constructs `PlatformContext`, delegates to `BootstrapEngine.bootstrap()` |
| 3 | **Discovery** | Collects all `RuntimeContract` instances, creates `RuntimeDescriptor` objects |
| 4 | **Validation** | Resolves DAG, performs security checks (version, dependencies, cycles) |
| 5 | **Registration** | Registers all descriptors in the `RuntimeRegistry` |
| 6 | **Configuration** | Configuration layers loaded (Default → Environment → User → Override) |
| 7 | **Memory** | `memory-runtime` initialized first (root node — no dependencies) |
| 8 | **Knowledge** | `knowledge-runtime` initialized (depends on memory) |
| 9 | **Identity** | `identity-runtime` initialized and activated (depends on memory) |
| 10 | **Capability** | `capability-runtime` initialized and activated (depends on memory, identity) |
| 11 | **Workflow** | `workflow-runtime` initialized (depends on memory, knowledge) |
| 12 | **Cognitive** | `cognitive-runtime` initialized and activated (depends on memory, knowledge, identity) |
| 13 | **Experience** | `experience-runtime` initialized and activated (depends on memory, identity, cognitive) |
| 14 | **Desktop** | `desktop-foundation` initialized and activated (depends on all prior runtimes) |
| 15 | **Ready** | Platform state set to `Ready`, scheduler started, `platform.ready` event published |

> **Note:** The exact topological order may vary slightly depending on the dependency graph, but the DAG guarantees that all dependencies of a given Runtime are initialized before it.

## 6. Shutdown Sequence

The platform follows an orderly shutdown sequence designed to ensure data integrity and resource cleanup:

```
ShutdownRequested  →  Flush  →  Persist  →  Release  →  Stopped
```

### 6.1 Shutdown Steps

| Step | Action | Detail |
|---|---|---|
| 1 | **ShutdownRequested** | `PlatformRuntime.stop()` sets state to `ShuttingDown`, publishes `platform.shutdown.requested` event |
| 2 | **Flush** | Metrics flushed (`platform.shutdown.initiated` recorded) |
| 3 | **Scheduler Stop** | `scheduler.stop()` called first — prevents new background tasks from being scheduled or executed |
| 4 | **Runtime Shutdown** | `bootstrapEngine.shutdownAll()` shuts down all runtimes in **reverse** initialization order (Desktop → Experience → Cognitive → Workflow → Capability → Identity → Knowledge → Memory) |
| 5 | **Release** | `healthMonitor.stopAutoCheck()` — stops periodic health checking |
| 6 | **Stopped** | Platform state set to `Stopped`, metrics recorded (`platform.stopped`), `platform.stopped` event published |

### 6.2 Error Resilience

Individual runtime shutdown failures are caught and logged but **do not prevent** subsequent runtimes from being shut down. This ensures maximum data preservation even when a runtime is in a degraded state.

## 7. Dependency Graph (DAG)

The platform's dependency graph forms a directed acyclic graph (DAG) rooted at the Memory Runtime. All edges represent "depends on" relationships.

```
memory-runtime (root)
├── knowledge-runtime
│   └── workflow-runtime
├── identity-runtime
│   ├── capability-runtime
│   └── cognitive-runtime
│       └── experience-runtime
│           └── desktop-foundation
└── (capability-runtime also depends on identity-runtime)
```

### 7.1 Formal Dependency List

| Runtime | Depends On |
|---|---|
| `memory-runtime` | *(none — root)* |
| `knowledge-runtime` | `memory-runtime` |
| `identity-runtime` | `memory-runtime` |
| `capability-runtime` | `memory-runtime`, `identity-runtime` |
| `workflow-runtime` | `memory-runtime`, `knowledge-runtime` |
| `cognitive-runtime` | `memory-runtime`, `knowledge-runtime`, `identity-runtime` |
| `experience-runtime` | `memory-runtime`, `identity-runtime`, `cognitive-runtime` |
| `desktop-foundation` | `memory-runtime`, `knowledge-runtime`, `identity-runtime`, `cognitive-runtime`, `experience-runtime` |

### 7.2 Topological Order

The resolved topological order (via Kahn's algorithm) produces a valid initialization sequence. One valid ordering:

```
memory-runtime → knowledge-runtime → identity-runtime → workflow-runtime
→ capability-runtime → cognitive-runtime → experience-runtime → desktop-foundation
```

### 7.3 Cycle Detection

The `DependencyResolver` performs DFS-based cycle detection before topological sort. If a cycle is found, a `DependencyCycleError` is thrown with the full cycle path. This is a fatal error that prevents platform startup.

## 8. Security

The `BootstrapEngine` performs security validation during the **Validation** phase (when `enableSecurityValidation` is `true`, which is the default).

### 8.1 Validation Rules

| Rule | Condition | Error |
|---|---|---|
| **Version Check** | Runtime version is `undefined` or `'0.0.0'` | `SecurityValidationError` with reason `INVALID_VERSION` |
| **Dependency Resolution** | Runtime declares a dependency that does not match any registered runtime ID | `SecurityValidationError` with reason `UNRESOLVED_DEPENDENCY` |
| **Cycle Detection** | Dependency graph contains a cycle (any node reachable from itself) | `DependencyCycleError` with `cyclePath` |

### 8.2 Security Error Hierarchy

```
PlatformError
├── SecurityValidationError  (code: SECURITY_VALIDATION_ERROR)
├── DependencyCycleError     (code: DEPENDENCY_CYCLE)
├── BootstrapError           (code: BOOTSTRAP_ERROR)
└── RuntimeRegistrationError  (code: RUNTIME_REGISTRATION_ERROR)
```

### 8.3 Blocking Behavior

All security validation errors are **blocking** — they throw immediately and prevent further bootstrap progress. This is intentional: a platform with unresolved dependencies or cyclic dependencies cannot function correctly.

## 9. Recovery

The platform implements graceful degradation and retry mechanisms to maximize availability.

### 9.1 Initialization Retry

| Parameter | Default | Description |
|---|---|---|
| `maxInitializationRetries` | `2` | Maximum number of retry attempts per runtime |
| `initializationRetryDelayMs` | `200` | Delay between retry attempts (fixed, not exponential) |

If a runtime fails to initialize, the `BootstrapEngine` retries up to `maxInitializationRetries` times with a fixed delay. Each failure is recorded via `metrics.increment(runtime.<id>.initFailure)`.

### 9.2 Graceful Degradation

| Runtime Type | Failure Behavior |
|---|---|
| **Required Runtime** | Listed in `failedRuntimes`, overall `BootstrapResult.success = false` |
| **Non-required Runtime** | Listed in `degradedRuntimes`, overall `BootstrapResult.success = true` |

Required runtime IDs are configured via `BootstrapConfig.requiredRuntimeIds`. If a required runtime fails after all retries, the entire bootstrap is marked as failed. Non-required runtimes are marked as degraded, and the platform continues without them.

### 9.3 No Full Platform Crash

Individual runtime failures **never** crash the entire platform. The platform always produces a `BootstrapResult` indicating which runtimes succeeded, which failed, and which degraded.

### 9.4 Command Bus Retry Policy

The `CommandBus` supports a configurable retry policy with exponential backoff:

| Parameter | Default | Description |
|---|---|---|
| `maxRetries` | `0` | Number of retries for failed command dispatches |
| `baseDelayMs` | `100` | Initial delay before first retry |
| `maxDelayMs` | `5000` | Maximum delay cap |
| `backoffMultiplier` | `2` | Exponential multiplier per attempt |

Delay formula: `min(baseDelayMs * backoffMultiplier^(attempt-1), maxDelayMs)`

### 13.2 Architectural Principles

1. **Immutability** — All interface properties are `readonly`; all returned data structures are `Object.freeze()`'d where practical

## Appendix B: Platform Context Injection

Every domain Runtime receives a `PlatformContext` object during initialization and activation. This context provides access to all platform subsystems:

```typescript
interface PlatformContext {
  readonly eventHub: EventHub;
  readonly commandBus: CommandBus;
  readonly queryBus: QueryBus;
  readonly configuration: ConfigurationRuntime;
  readonly registry: RuntimeRegistry;
  readonly container: ServiceContainer;
  readonly scheduler: Scheduler;
  readonly healthMonitor: HealthMonitor;
  readonly metrics: MetricsAggregator;
  readonly diagnostics: PlatformDiagnostics;
}
```

This context is constructed by the `PlatformRuntime` and passed to the `BootstrapEngine`, which in turn passes it to each `RuntimeContract.initialize()` and `RuntimeContract.activate()` call.
