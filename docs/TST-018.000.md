## 3. Категории тестов

### 3.1 Модульные тесты по подсистемам

Каждая подсистема тестируется по 6 обязательным категориям:

1. **Позитивные сценарии** — Все публичные методы с валидными параметрами, проверка корректных возвращаемых значений и изменений состояния.
2. **Сценарии ошибок** — Превышение лимитов, отсутствие сущности, неверные переходы состояний, несовпадение типов.
3. **Тесты фильтрации** — list() со всеми комбинациями фильтров (одиночный, множественный, пустой, отсутствующий).
4. **Тесты подсчёта** — Точность count() до и после операций.
5. **Генерация событий** — publishEvent вызывается с корректным eventType, classification и полями данных.
6. **Граничные случаи** — Пустое состояние, дублирующие операции, невалидные идентификаторы, предельные значения.

### 3.2 Тесты типов и каркаса

- **Функции брендирования** (30 тестов): Все 15 brand-функций создают корректные брендированные идентификаторы.
- **Значения перечислений** (120+ тестов): Все 20 перечислений содержат ожидаемые элементы с корректными строковыми значениями.
- **Иерархия ошибок** (100+ тестов): Все 25+ классов ошибок наследуют SolutionBuilderError с корректным code и name.
- **Объединение событий** (10 тестов): SolutionBuilderEvent принимает все 23 формы событий.
- **Замороженная конфигурация** (40 тестов): DefaultSolutionBuilderConfig и все 14 подконфигураций являются Object.frozen.
- **Интерфейсы контрактов** (4 теста): Все 15 классов реализаций реализуют свои интерфейсы.

### 3.3 Тесты оркестратора SolutionRuntime

- Переходы состояний: Uninitialized -> Ready -> Stopped
- Initialize создаёт все 14 подсистем
- Shutdown выполняет корректный переход

- getMetrics возвращает все 11 полей SolutionBuilderMetrics

- Обработка двойной инициализации

## 6. Валидация иерархии ошибок

Все 25+ классов ошибок проверены на:
- Наследование от `SolutionBuilderError` (который наследует `Error`)
- Корректное свойство `name`, совпадающее с именем класса
- Корректное свойство `code`, совпадающее с константой кода ошибки
- Замороженный объект `context`
- Строка `timestamp` в формате ISO-8601

Дополнительно проверены специфичные свойства: `goalId` у InvalidGoalError, `solutionId` у NoValueProofError и OptimizationWithoutValueError, `fromState`/`toState` у LifecycleTransitionError, `field` у ManifestValidationError, `capabilityName` у MissingCapabilityError.

## 7. Валидация генерации событий

Все методы, генерирующие события, протестированы на:
- `mockEventBus.publish` вызывается ровно один раз (или корректное количество раз)
- Событие имеет `eventType`, совпадающий с ожидаемой строкой доменного события
- Событие имеет `classification` из перечисления `EventClassification`
- Событие имеет `timestamp` как строку ISO-8601
- Событие имеет `metadata` как замороженный объект
- Событие имеет `eventId` (UUID), `sequence`, `aggregateId`, `aggregateType`, `version`

## 8. Тесты соответствия принципам

- **PHI-001**: SolutionManifest требует указания expectedValue; NoValueProofError блокирует решения без доказательства ценности
- **PHI-003**: SolutionValidator предоставляет 6 количественных оценок по категориям; SolutionBuilderMetrics агрегирует 11 KPI
- **PHI-005**: OptimizationWithoutValueError существует для решений, которые оптимизируют без создания ценности
- **PHI-007**: Цифровая подпись в SolutionManifest; NoValueProofError требует доказательства эффективности

| ID | Описание | Серьёзность | Статус |

Примечание: BUG-SB-001 является косметической проблемой в errors.ts, где свойство name устанавливается конструктором. Оно не влияет на функциональность, поскольку error.code уникально идентифицирует ошибку.
