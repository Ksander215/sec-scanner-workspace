## Зависимости от продуктовых документов

Этот документ переводит Product Layer в архитектурные требования. Все архитектурные утверждения должны быть прослеживаемы до конкретных продуктовых документов:

- **Product Vision** — определяет, зачем существует AIS и какова его ценность
- **Product Principles** (13 принципов: §3.1–§3.13) — ограничивают архитектурные решения
- **Product Architecture Decisions** (D1–D10) — фиксируют фундаментальные продуктовые выборы
- **Capability Map** — определяет 11 capabilities и их отношения
- **MVP Definition** — определяет 8 MVP-possible capabilities и 3 Post-MVP
- **Architecture Model Specification** — определяет центральную сущность платформы
- **Architecture Knowledge Specification** — определяет границу между фактами и пониманием
- **Architecture Evolution Specification** — определяет временное измерение архитектуры
- **Organization Adaptation Specification** — определяет контекстный слой
- **AI Assistance Specification** — определяет роль AI в платформе
- **Security Analysis Specification** — определяет архитектуру анализа безопасности
- **Dependency Analysis Specification** — определяет архитектуру анализа зависимостей
- Все остальные спецификации capabilities — контекстные зависимости

## 1. Purpose

Настоящий документ является **первым документом Architecture Layer** платформы AIS. Его назначение — перевести продуктовые требования, зафиксированные в Product Layer, в архитектурные требования, определяющие, как система должна быть структурирована. Он отвечает на ключевой вопрос: **«Как Product Layer должен быть отражён в системной архитектуре?»**

Этот документ **не является спецификацией реализации**. Он не содержит описания конкретных технологий, фреймворков, баз данных, форматов данных, API или паттернов программирования. Архитектура Layer занимает промежуточное положение между Product Layer (что и зачем) и Implementation Layer (как именно). Здесь определяется, **какие архитектурные сущности должны существовать, как они соотносятся друг с другом, какие потоки информации между ними протекают и какие границы непроницаемы**.

Необходимость такого документа обусловлена фундаментальным разрывом между продуктовым описанием и технической реализацией. Product Layer описывает *что* система делает для пользователя и *почему*. Он фиксирует ценности, принципы и решения на уровне продукта. Однако продуктыый слой не говорит, *как система должна быть структурирована внутренне*, чтобы обеспечить выполнение этих требований. Без промежуточного архитектурного слоя возникает риск: реализация может технически работать, но нарушать продуктовые принципы неявно — потому что никто не перевёл принципы в архитектурные ограничения.

Пример. Принцип «Model Before Analyze» (Product Principles, §3.2) означает, что анализ всегда проводится поверх модели. Но без архитектурного определения, что такое «модель» как сущность, чем она отличается от данных, которые генерирует Discovery, и как анализ получает к ней доступ, реализатор может построить систему, где анализ технически работает, но фактически игнорирует модель — потому что архитектурная граница не была формализована.

Цель данного документа — устранить этот разрыв. Каждый архитектурный принцип, определённый здесь, прослеживается до конкретного продуктового документа. Каждая граница обоснована продуктовым решением. Каждая связь между архитектурными областями обоснована отношениями между capabilities в Capability Map.

Документ определяет концептуальную архитектуру AIS как набор взаимосвязанных областей с явными границами, правилами взаимодействия и иерархией зависимостей. Он фиксирует, какие области являются центральными (Architecture Model), какие являются обогащающими (Analysis), какие являются интерпретирующими (AI, Knowledge), какие являются презентационными (Visualization, Reports), и какие являются процессами, а не постоянными сущностями (Discovery).

Впоследствии Implementation Layer будет строиться **строго поверх** этого документа. Любое архитектурное решение на уровне реализации должно быть прослеживаемо до конкретного утверждения Architecture Foundation Specification. Если реализация требует архитектурного решения, не описанного здесь — это сигнал, что Architecture Layer нуждается в расширении, а не в том, что реализация может действовать автономно.

## 2. Architectural Definition

### 2.1 Что такое архитектура для AIS

В контексте AIS «архитектура» означает **структуру единого пространства архитектурного понимания программного проекта**. AIS — это не набор независимых анализаторов, каждый из которых производит собственный результат. AIS — это **единая платформа архитектурного понимания**, где все capabilities работают поверх общей модели и обогащают её.

Это определение является архитектурным следствием Product Architecture Decisions. Decision 8 («AIS развивается как единая платформа, а не набор отдельных инструментов») устанавливает, что платформа предоставляет единое пространство для всех типов анализа, связанных через архитектурную модель. Decision 1 («AIS строит архитектурную модель до любого анализа») устанавливает приоритет: модель существует до анализа и является его основой. Decision 2 («Все результаты всегда привязываются к архитектурной модели») устанавливает обязательность привязки: ни один результат анализа не существует вне модели.

### 2.2 Архитектурная модель как структурный центр

**Architecture Model — это структурный центр платформы AIS.** Это не один из компонентов системы — это центральная сущность, вокруг которой строится вся архитектура. Все capabilities являются либо **обогащениями** модели (анализ, добавляющий данные к компонентам модели), либо **проекциями** модели (визуализация, отчёты, AI-ответы), либо **контекстными слоями** (Organization Adaptation, добавляющий интерпретативный контекст к модели).

Это архитектурное решение является следствием целой цепочки продуктовых документов. Architecture Model Specification (§1) определяет: «Без модели ни одна из возможностей не создаёт уникальной ценности — они становятся ещё одним набором отдельных инструментов». Product Architecture Decisions, D10 устанавливает: «Любая новая возможность должна усиливать архитектурную модель». Capability Map (§3) показывает, что Architecture Modeling находится в центре дерева возможностей, и все остальные capabilities логически зависят от него.

С архитектурной точки зрения это означает, что Architecture Model является **единственным источником структурной правды** о проекте. Если факт о проекте не отражён в модели — он не доступен ни для анализа, ни для визуализации, ни для AI, ни для отчётов. Это не означает, что модель хранит всё; это означает, что всё, что используется другими capabilities, должно пройти через модель.

### 2.3 Capabilities как виды и обогащения модели

Каждая capability платформы рассматривается архитектурно как один из трёх типов:

**Вид (view) модели.** Capability читает модель и представляет её в определённой форме. Примеры: Visualization представляет модель визуально; Reports представляют модель в виде структурированного документа; AI Assistance интерпретирует модель в ответ на вопрос пользователя. Виды не изменяют модель — они являются чистыми проекциями.

**Обогащение модели.** Capability анализирует проект и записывает результаты в модель, привязывая их к компонентам. Примеры: Security Analysis привязывает уязвимости к компонентам модели; Dependency Analysis привязывает данные о зависимостях к компонентам модели. Обогащения увеличивают полноту модели, но не заменяют её структуру.

**Контекстный слой.** Capability предоставляет контекст, влияющий на интерпретацию модели, но не изменяющий фактическое содержание модели. Пример: Organization Adaptation добавляет организационный контекст, который влияет на то, как AI и анализ интерпретируют результаты, но не изменяет сами архитектурные факты.

### 2.4 AIS как единое пространство, а не конгломерат

Архитектурное следствие Decision 8 — AIS не является конгломератом независимых модулей. Модули не обмениваются данными напрямую между собой. Все обмены происходят через Architecture Model. Security Analysis не общается с Dependency Analysis напрямую — оба читают и пишут в модель. AI Assistance не получает данные от Security Analysis напрямую — он читает результаты безопасности из модели.

Это создаёт строгую звёздную топологию: модель в центре, все capabilities на периферии. Каждый capability взаимодействует только с моделью. Это обеспечивает:
- Единообразие: все данные о проекте существуют в одном месте.
- Согласованность: conflicting данные между capabilities невозможны, потому что все работают с одной моделью.
- Независимость: capabilities могут развиваться и добавляться независимо, потому что взаимодействие происходит через стандартный интерфейс модели.
- Прослеживаемость: любой результат может быть прослежен до его источника через модель.

## 3. Architecture Goals

Архитектурные цели AIS выведены из Product Layer. Каждая цель прослеживается до конкретных продуктовых документов и принципов. Цели упорядочены по приоритету: выше — более фундаментальные.

### 3.1 Единое архитектурное понимание (Unified Architectural Understanding)

**Суть:** Все capabilities платформы работают поверх единой архитектурной модели. Не существует параллельных моделей, дублирующих данных или независимых анализаторов с собственным представлением о системе.

**Источник:** Product Architecture Decisions, D8 («AIS развивается как единая платформа, а не набор отдельных инструментов»); Product Vision, §3 («Единая модель проекта»); Product Principles, §3.12 («Composable, Not Monolithic»).

**Архитектурное следствие:** Звёздная топология с Architecture Model в центре. Все capabilities взаимодействуют через модель. Никакой прямой обмен данными между capabilities не допускается на архитектурном уровне.

### 3.2 Модель до анализа (Model Before Analysis)

**Суть:** Архитектурная модель должна существовать до выполнения любого анализа. Анализ обогащает модель, но не создаёт её. Без модели анализ не имеет архитектурного контекста и, следовательно, не создаёт ценности, отличающей AIS от существующих инструментов.

**Источник:** Product Architecture Decisions, D1 («AIS строит архитектурную модель до любого анализа»); Product Principles, §3.2 («Model Before Analyze»).

**Архитектурное следствие:** Discovery → Model → Analysis является обязательной последовательностью. Analysis capabilities не могут быть выполнены до того, как Architecture Model достигнет минимального состояния готовности. Результаты анализа, полученные до построения модели, не представляются пользователю.

### 3.3 AI как интерпретатор, а не владелец (AI as Interpreter, Not Owner)

**Суть:** AI является конечным потребителем в цепочке ценности. AI читает все данные платформы и интерпретирует их для пользователя, но не пишет ничего в Architecture Model напрямую. AI-ответы являются эфемерным текстом, а не постоянным знанием.

**Источник:** Product Architecture Decisions, D3 («AI никогда не заменяет разработчика»); Product Principles, §3.6 («AI Assists, Not Replaces»); Product Principles, §3.7 («Safe Evolution»); AI Assistance Specification.

**Архитектурное следствие:** AI имеет только READ-ONLY доступ к Architecture Model и всем другим архитектурным областям. AI не может создавать, модифицировать или удалять элементы модели. AI-ответы существуют только в момент взаимодействия с пользователем и не сохраняются как Knowledge без явной валидации пользователем.

### 3.4 Контекст важнее правил (Context Over Rules)

**Суть:** Организационный контекст влияет на интерпретацию архитектурных фактов, но не изменяет сами факты. Граница между фактами и интерпретациями непроницаема на архитектурном уровне.

**Источник:** Product Architecture Decisions, D5 («Контекст важнее правил»); Product Principles, §3.11 («Context Over Rules»); Organization Adaptation Specification.

**Архитектурное следствие:** Organization Adaptation является cross-cutting контекстным слоем, а не движком правил. Организационный контекст записывается в элемент модели («организационный контекст»), но архитектурные факты (компоненты, связи, зависимости) не изменяются под влиянием организационного контекста.

### 3.5 Объяснимость каждого вывода (Full Explainability)

**Суть:** Каждый архитектурный вывод, представленный пользователю, должен быть прослежен до исходных данных модели. Не существует «магических» заключений.

**Источник:** Product Architecture Decisions, D4 («Все рекомендации должны объясняться»); Product Principles, §3.1 («Explain Before Recommend»); Product Principles, §3.5 («Every Recommendation Has Reason»); Product Principles, §3.9 («Transparent Analysis»).

**Архитектурное следствие:** Каждое обогащение модели (анализ) должно сохранять информацию об источнике данных, на которых оно основано. Каждый AI-ответ должен иметь возможность показать, какие элементы модели были использованы для его формирования. Цепочка «модель → данные → вывод → рекомендация» должна быть полностью прослеживаема.

### 3.6 Знания накапливаются, не пересчитываются (Knowledge Accumulates)

**Суть:** Состояния архитектурной модели и накопленные знания сохраняются между сессиями. Переоткрытие известных фактов — это трата ресурсов.

**Источник:** Product Architecture Decisions, D7 («Знания проекта постоянно накапливаются»); Product Principles, §3.4 («Knowledge Never Lost»); Product Principles, §3.8 («Continuous Understanding»); Knowledge Persistence capability.

**Архитектурное следствие:** Architecture Model является stateful-сущностью с историей состояний. Каждое обновление модели не заменяет предыдущее состояние, а создаёт новое. Переход между состояниями должен быть доступен для анализа эволюции.

### 3.7 Минимальные предположения о проекте (Minimal Assumptions)

**Суть:** Архитектура платформы делает минимальные предположения о структуре анализируемого проекта. Платформа адаптируется к проекту, а не требует от проекта адаптироваться к ней.

**Источник:** Product Principles, §3.13 («Minimal Assumptions»); Project Discovery Specification; Architecture Model Specification, §8.6 («Независимость от технологий»).

**Архитектурное следствие:** Architecture Model является technology-agnostic. Смена языка программирования, фреймворка или инструмента анализа не должна требовать перестройки модели. Discovery должен работать с существующими артефактами проекта без специальных конфигурационных файлов.

### 3.8 Понимание важнее количества проблем (Understanding Over Volume)

**Суть:** Цель платформы — обеспечить понимание системы, а не максимизировать количество обнаруженных проблем. Поиск проблем — это средство, а не цель.

**Источник:** Product Architecture Decisions, D9 («Продукт ориентирован на понимание системы, а не только поиск ошибок»); Product Vision, §3.

**Архитектурное следствие:** Architecture Model не оптимизирован для максимизации количества findings. Модель оптимизирована для полноты структурного понимания. Каждый finding привязан к компоненту модели и объяснён в контексте (D2, D4), что естественным образом ограничивает шум.

### 3.9 Новые возможности усиливают модель (Capabilities Strengthen Model)

**Суть:** Каждая новая capability должна обогащать Architecture Model новыми данными, связями или контекстом. Capability, которая не усиливает модель, не добавляется.

**Источник:** Product Architecture Decisions, D10 («Любая новая возможность должна усиливать архитектурную модель»); Product Decision Framework, §6.1.

**Архитектурное следствие:** Добавление новой capability требует архитектурного обоснования её вклада в модель. Если capability создаёт параллельную структуру данных — она отклоняется на архитектурном уровне. Если capability работает с данными, не привязанными к модели — она отклоняется.

### 3.10 Факт неделим, интерпретация контекстуальна (Fact is Universal, Interpretation is Contextual)

**Суть:** Архитектурные факты существуют объективно и не зависят от организационного контекста. Одна и та же архитектура может получать разные интерпретации в разных организационных контекстах — и это правильно.

**Источник:** Architecture Model Specification, §8.7 («Адаптивность»); Organization Adaptation Specification, §2.5; Product Principles, §3.11 («Context Over Rules»).

**Архитектурное следствие:** Architecture Model содержит два типа данных: структурные факты (объективные, неизменяемые контекстом) и контекст (субъективный, зависящий от организации). Граница между ними непроницаема: контекст не может изменить факт.

## 4. Conceptual Architecture Model

### 4.1 Структура областей

Концептуальная архитектура AIS определяется как набор областей с определёнными отношениями между ними. Каждая область имеет свою роль, свои правила взаимодействия и своё место в иерархии зависимостей.

```
Project Artifacts
       ↓
  [Discovery] ← процесс, не постоянная область
       ↓
[Architecture Model] ← ЦЕНТРАЛЬНАЯ СУЩНОСТЬ, единый источник структурной правды
       ↓
  ┌────┼────┬────┬────┐
  │    │    │    │    │
[Sec] [Dep] [Vis] [OA]  ← MVP: Анализ и Контекст
  │    │              │
  └────┴──────────────┘
       ↓ (модель обогащается результатами анализа)
[Architecture Knowledge] ← слой понимания (Post-MVP, Stage 2)
       ↓
[Architecture Evolution] ← временное измерение (Post-MVP, Stage 2)
       ↓
[Change Impact Assessment] ← требует Knowledge + Evolution (Post-MVP)
       ↓
[Technical Debt Tracking] ← требует всё вышеперечисленное (Post-MVP)
       ↓
[AI Assistance] ← читает всё, ничего не пишет в модель
       ↓
  ┌────┴────┐
[Reports] [Viz] ← чистые проекции, только чтение
```

### 4.2 Project Artifacts — входной слой

**Роль:** Project Artifacts представляют собой совокупность файлов, конфигураций, репозиториев и других артефактов программного проекта, которые являются входными данными для AIS. Это не часть архитектуры AIS — это внешняя среда, с которой платформа взаимодействует.

Артефакты проекта включают исходный код, конфигурационные файлы, манифесты зависимостей, инфраструктурные описания, документацию и любые другие файлы, из которых можно извлечь информацию о структуре проекта. Project Artifacts являются **source of truth** для Discovery — именно из них Discovery извлекает первичное понимание структуры проекта.

Артефакты проекта **не хранятся** в Architecture Model. Модель хранит знание о структуре проекта, а не сам код (Architecture Model Specification, §5.1). Исходный код остаётся в системе контроля версий. Это архитектурное решение обеспечивает: модель не дублирует репозиторий; объём модели ограничен структурным знанием, а не сырыми данными.

### 4.3 Discovery — процесс, не область

**Роль:** Discovery является **процессом**, который принимает Project Artifacts на вход и производит начальное состояние Architecture Model на выходе. Discovery **не является** постоянной архитектурной областью — он не имеет собственного хранилища, не сохраняет промежуточное состояние и не создаёт параллельной модели.

Discovery выполняет следующие функции:
- Определяет тип проекта (язык, фреймворк, структура).
- Обнаруживает основные компоненты и их взаимосвязи.
- Извлекает информацию о зависимостях.
- Формирует первичное представление, достаточное для создания начальной Architecture Model.

Discovery выполняется **до** создания модели и формирует данные для её создания. Повторный запуск Discovery **уточняет** существующую модель, а не заменяет её. Это критически важное архитектурное свойство: модель накапливается (Product Architecture Decisions, D7), и Discovery является одним из механизмов её обновления.

Discovery **не имеет AI-компонента** на продуктовом уровне. Это архитектурное следствие принципа «Model Before Analyze» — AI интерпретирует модель, а Discovery создаёт данные для модели. AI без модели бесполезен (AI Assistance Specification), и привлечение AI к Discovery означало бы попытку интерпретировать данные до создания структуры для интерпретации.

Discovery **не выполняет анализ** (Security, Dependency и т.д.). Это архитектурное следствие принципа «Composable, Not Monolithic» (Product Principles, §3.12) и Decision 1. Если Discovery выполнял бы анализ, он нарушал бы границу между созданием модели и её обогащением, что привело бы к монолитному процессу, противоречащему архитектурным принципам.

**Поток данных:** Project Artifacts → Discovery → Architecture Model (ENRICHES — создаёт/обновляет начальное состояние модели).

### 4.4 Architecture Model — центральная сущность

**Роль:** Architecture Model является **центральной сущностью** платформы и **единым источником структурной правды** о проекте. Это не «одна из capabilities» — это фундамент, на котором строится вся архитектура AIS. Все остальные области являются либо обогащениями модели, либо её проекциями, либо контекстными слоями.

Architecture Model содержит:
- **Компоненты системы** — модули, сервисы, библиотеки, подсистемы, описанные с точки зрения их роли в архитектуре (Architecture Model Specification, §4.1).
- **Связи между компонентами** — вызовы, обмен данными, общие зависимости с направлением и типом (Architecture Model Specification, §4.2).
- **Зависимости** — прямые и транзитивные, внутренние и внешние, с контекстом их использования и рисков (Architecture Model Specification, §4.3).
- **Слои и границы** — архитектурные слои и границы между подсистемами, нарушения которых выделяются как проблемы (Architecture Model Specification, §4.4).
- **Результаты анализа** — привязанные к компонентам уязвимости, проблемы зависимостей, метрики качества, архитектурные аномалии (Architecture Model Specification, §4.5).
- **Организационный контекст** — настройки, специфичные для организации (Architecture Model Specification, §4.8).

Architecture Model **не содержит:** исходный код, историю коммитов, бизнес-логику, данные пользователей, документацию проекта (Architecture Model Specification, §5).

Architecture Model является **technology-agnostic** — она описывает архитектуру проекта, а не технологии реализации (Architecture Model Specification, §8.6). Это означает, что смена языка или фреймворка не требует перестройки модели.

Architecture Model является **stateful** — она хранит историю своих состояний (Architecture Model Specification, §4.7; Product Architecture Decisions, D7). Каждое обновление модели создаёт новое состояние, а не перезаписывает предыдущее. Это позволяет анализировать эволюцию архитектуры.

### 4.5 Security Analysis — обогащение модели данными о безопасности

**Роль:** Security Analysis читает Architecture Model, выполняет анализ безопасности (через интеграцию с внешними сканирующими инструментами) и записывает результаты в модель, привязывая их к компонентам. Это **обогащение модели**, а не параллельная модель безопасности.

Security Analysis привязывает к компонентам модели:
- Обнаруженные уязвимости с классификацией по серьёзности.
- Конфигурационные проблемы безопасности.
- Цепочки атак, построенные на основе связей модели.
- Риск-оценки с учётом архитектурного контекста.

Без Architecture Model Security Analysis — это просто список уязвимостей без понимания реального риска (Product Architecture Decisions, D6). С моделью — уязвимость становится точкой на архитектурной карте с пониманием того, какие данные под угрозой и через какие пути атакующий может до них добраться.

Security Analysis входит в MVP и является одним из ключевых создателей ценности платформы.

### 4.6 Dependency Analysis — обогащение модели данными о зависимостях

**Роль:** Dependency Analysis читает Architecture Model, анализирует зависимости между компонентами и записывает данные о зависимостях в модель, привязывая их к компонентам. Это **обогащение модели** графом зависимостей.

Dependency Analysis привязывает к компонентам модели:
- Полный граф зависимостей (прямые и транзитивные).
- Проблемные паттерны: циклические, избыточные, рискованные зависимости.
- Критические точки отказа.
- Информацию об устаревших и небезопасных зависимостях.

Без Architecture Model Dependency Analysis — это граф без понимания роли зависимостей в архитектуре (Capability Map, §3). С моделью — каждая зависимость имеет контекст: почему она существует, как используется, какие риски несёт.

Dependency Analysis входит в MVP и неотделим от архитектурного понимания.

### 4.7 Visualization — проекция модели

**Роль:** Visualization читает Architecture Model и представляет её в визуальной форме. Это **чистая проекция** — она только читает модель и не записывает в неё ничего. Visualization не кэширует собственное состояние — она всегда работает с текущим состоянием модели.

Visualization входит в MVP и делает Architecture Model доступной для визуального восприятия и навигации.

### 4.8 Organization Adaptation — контекстный слой

**Роль:** OA является **cross-cutting контекстным слоем**, который предоставляет организационный контекст для интерпретации модели. OA не является анализатором и не создаёт параллельной модели. OA записывает контекст в элемент модели («организационный контекст»), влияя на интерпретацию, но не изменяя архитектурные факты.

OA входит в MVP и обеспечивает выполнение принципа «Context Over Rules» (Product Principles, §3.11).

### 4.9 Architecture Knowledge — слой понимания (Post-MVP, Stage 2)

**Роль:** Architecture Knowledge является слоем **накопленного понимания**, который отвечает на вопрос «Почему?». Knowledge обогащает Model интерпретациями, причинами решений, историческим контекстом и развивающимся пониманием. Knowledge не изменяет структуру Model — он добавляет измерение смысла к существующим фактам.

Knowledge является Post-MVP capability, требующей стабильной модели и достаточного объёма накопленных данных для формирования осмысленного понимания (Capability Map, §5).

### 4.10 Architecture Evolution — временное измерение (Post-MVP, Stage 2)

**Роль:** Architecture Evolution является **временным измерением** архитектуры. Оно отвечает на вопрос «Как изменилось?» и требует множества состояний Architecture Model для сравнения. Evolution наблюдателен — он фиксирует, что изменилось, но не объясняет, почему (объяснение — это задача Knowledge).

Evolution является Post-MVP capability (Capability Map, §5).

### 4.11 Change Impact Assessment — требует Knowledge + Evolution (Post-MVP)

**Роль:** CIA оценивает последствия планируемых изменений, определяя затронутые компоненты, возможные риски и регрессии. Для полноценной работы CIA требует накопленных Knowledge (чтобы понимать причины связей) и Evolution (чтобы видеть исторические паттерны изменений).

CIA является Post-MVP capability (Capability Map, §5).

### 4.12 Technical Debt Tracking — требует всё вышеперечисленное (Post-MVP)

**Роль:** Technical Debt Tracking отслеживает накопление технического долга с привязкой к компонентам архитектуры. Для полноценной работы требует стабильной модели, накопленных Knowledge, Evolution для отслеживания тенденций, и CIA для понимания влияния долга.

Technical Debt Tracking является Post-MVP capability (Capability Map, §5).

### 4.13 AI Assistance — финальный интерпретатор

**Роль:** AI Assistance является **конечным потребителем** в цепочке ценности. AI читает Architecture Model (приоритет 1), Knowledge (приоритет 2), Evolution (приоритет 3), все результаты анализа, OA контекст и вопрос пользователя. AI производит интерпретацию в виде текстового ответа или рекомендации. AI **не пишет** ничего в Architecture Model напрямую.

AI входит в MVP и является ключевым отличием платформы от существующих инструментов.

### 4.14 Report Generation — проекция модели

**Роль:** Report Generation читает Architecture Model и формирует структурированные отчёты для внешнего использования. Это **чистая проекция** — отчёты являются срезами модели в момент генерации. Отчёты не обновляются автоматически — каждый отчёт является самостоятельным артефактом.

Report Generation входит в MVP как минимальный формат доставки результатов.

## 5. Model / Knowledge / Evolution Boundary

Граница между Architecture Model, Architecture Knowledge и Architecture Evolution является **критической** для архитектуры AIS. Нарушение этой границы означает подмену одного типа данных другим, что ведёт к искажению понимания и нарушению продуктовых принципов. Данный раздел определяет явные границы и правила взаимодействия между тремя областями.

### 5.1 Architecture Model — «Что существует?»

**Определение:** Architecture Model отвечает на вопрос **«Что существует?»** — он содержит структурные факты о программном проекте. Компоненты, связи, зависимости, слои, границы, результаты анализа, привязанные к компонентам. Model — это technology-independent описание того, *как устроена система*.

**Свойства Model:**
- Факты Model объективны. Компонент X зависит от компонента Y — это факт, не зависящий от интерпретации. Model не содержит мнений, оценок или причин.
- Model является technology-agnostic. Смена языка программирования или фреймворка не меняет архитектурный факт (Architecture Model Specification, §8.6).
- Model не содержит «почему». Model знает, что зависимость существует, но не знает, почему она была создана. Причины — это область Knowledge.
- Model является **единственным источником структурной правды**. Если факт не в модели — он не доступен для анализа, визуализации или AI.

**Граница:** Model facts are immutable by Knowledge. Knowledge может интерпретировать факты Model, объяснять их, связывать между собой, но не может изменять сами факты. Если Knowledge утверждает, что «компонент A не должен зависеть от компонента B» — это интерпретация, которая записывается в Knowledge, а не изменение Model. Факт зависимости остаётся в Model как факт.

**Следствие:** Model без Knowledge — это точный снимок системы, но мёртвый. Он показывает, что существует, но не объясняет, почему. Это полезно, но недостаточно для осознанного принятия решений (Architecture Knowledge Specification, §1).

### 5.2 Architecture Knowledge — «Что мы понимаем об этом?»

**Определение:** Architecture Knowledge отвечает на вопрос **«Что мы понимаем об этом?»** — он содержит интерпретации, причины решений, контекст компромиссов, подтверждённые и опровергнутые утверждения, исторические объяснения. Knowledge обогащает Model, но не изменяет её структуру.

**Свойства Knowledge:**
- Knowledge субъективен в том смысле, что он отражает понимание, которое может уточняться с появлением новых данных. Но Knowledge не является произвольным — он основан на фактах Model и результатах анализа.
- Knowledge включает причины. Знание о том, *почему* зависимость была создана, *почему* граница проведена здесь, *почему* использована конкретная библиотека — это Knowledge, а не Model.
- Knowledge включает контекст компромиссов. Знание о том, что команда осознанно допускает циклическую зависимость внутри слоя — это Knowledge, который влияет на интерпретацию Model.
- Knowledge уточняется без потери истории. Предыдущее понимание сохраняется как этап развития (Architecture Knowledge Specification, §5.9).

**Граница:** Knowledge is validated understanding, not AI output. AI-ответ является эфемерным текстом. Он становится Knowledge только после явной валидации пользователем. AI может предложить интерпретацию, но только человек может превратить её в Knowledge. Это архитектурное следствие Product Architecture Decisions, D3 («AI никогда не заменяет разработчика») и принципа «AI Assists, Not Replaces» (Product Principles, §3.6).

**Следствие:** Knowledge без Model — это интерпретации без предмета. Knowledge объясняет факты Model, но без Model у объяснений нет основы. Knowledge существует *для* Model, а не *вместо* Model.

### 5.3 Architecture Evolution — «Как это изменилось?»

**Определение:** Architecture Evolution отвечает на вопрос **«Как это понимание и система изменялись?»** — он содержит временное измерение, сравнения состояний, тренды и паттерны изменения. Evolution требует множества состояний Model для сравнения.

**Свойства Evolution:**
- Evolution наблюдателен. Он фиксирует, *что* изменилось между состояниями Model, но не объясняет, *почему* (объяснение причин изменений — это Knowledge). Если компонент X был добавлен между состояниями S1 и S2 — это факт Evolution. Почему он был добавлен — это Knowledge.
- Evolution требует Model states over time. Без истории состояний Model невозможно построить Evolution. Это определяет Evolution как Post-MVP capability (Capability Map, §5).
- Evolution обнаруживает паттерны. Рост связанности, деградация модульности, накопление долгов в определённых компонентах — это паттерны, которые видны при сравнении состояний.

**Граница:** Evolution is observational (what changed), not causal (why changed — that's Knowledge). Этот раздел обязанностей является архитектурно необходимым: если Evolution объясняет причины изменений, он подменяет Knowledge. Если Knowledge фиксирует только причины без наблюдения изменений, он лишается эмпирической основы. Разделение позволяет каждой области развиваться независимо.

**Следствие:** Evolution без Model — невозможен. Evolution без Knowledge — это хронология без понимания. Полноценная ценность Evolution проявляется только в комбинации с Knowledge.

### 5.4 Сводная матрица границ

| Критерий | Architecture Model | Architecture Knowledge | Architecture Evolution |
|---|---|---|---|
| **Отвечает на вопрос** | «Что существует?» | «Что мы понимаем?» | «Как изменилось?» |
| **Тип данных** | Структурные факты | Интерпретации и причины | Временные наблюдения |
| **Объективность** | Объективны (не зависят от контекста) | Основаны на фактах, но содержат интерпретацию | Объективны (наблюдения) |
| **Статус в MVP** | Центральная сущность (Must Have) | Post-MVP, Stage 2 | Post-MVP, Stage 2 |
| **Может изменять Model?** | — (это и есть Model) | Нет, только интерпретирует | Нет, только наблюдает |
| **Может изменять Knowledge?** | Нет | — (это и есть Knowledge) | Нет, предоставляет данные |
| **Источник данных** | Discovery, Analysis | Model + Analysis + User | Model states over time |
| **Кто создаёт** | Discovery (начальное), Analysis (обогащение) | Пользователь (валидация), платформа (автоматическое) | Платформа (наблюдение) |
| **AI может писать напрямую?** | Нет | Нет | Нет |

### 5.5 AI output как отдельная категория

Важный архитектурный принцип: **AI output — это отдельная категория данных, которая не является ни Model, ни Knowledge, ни Evolution.** AI output является эфемерным текстом, который существует только в момент взаимодействия с пользователем.

AI output может **стать** Knowledge, но только через явную валидацию пользователем. Архитектурно это означает:
- AI generates interpretation → User validates → Becomes Knowledge
- AI generates interpretation → User rejects → Disappears
- AI generates interpretation → User ignores → Never becomes anything

Эта граница является архитектурным следствием Product Architecture Decisions, D3 (AI никогда не заменяет разработчика) и принципиального разделения между автоматической интерпретацией и валидированным знанием. Без этой границы AI-ответы могли бы автоматически загрязнять Knowledge недостоверными или контекстуально неверными интерпретациями.

## 6. Discovery Boundary

### 6.1 Discovery как процесс

Discovery является **процессом**, который преобразует Project Artifacts в начальное состояние Architecture Model. Архитектурно Discovery — это не постоянная область с собственным хранилищем, не capability с собственным API, и не отдельная модель. Discovery — это **транзитный процесс**: он принимает артефакты на вход, производит данные для Model на выходе, и не сохраняет промежуточное состояние.

Это архитектурное следствие нескольких продуктовых принципов. Принцип «Composable, Not Monolithic» (Product Principles, §3.12) требует, чтобы Discovery не поглощал другие capabilities. Decision 1 («AIS строит архитектурную модель до любого анализа») требует, чтобы Discovery создавал данные для Model, а не заменял Model. Capability Map (§3) фиксирует логическую зависимость: Project Discovery → Architecture Modeling.

### 6.2 Discovery не является постоянной областью

Discovery **не сохраняет** собственное состояние. Результаты Discovery — это данные, которые **непосредственно поступают** в Architecture Model. Если Discovery обнаруживает 15 компонентов, эти 15 компонентов становятся элементами Architecture Model. Discovery не имеет отдельного списка «обнаруженных, но ещё не добавленных в модель» компонентов.

Это архитектурное правило имеет важные следствия:
- Повторный запуск Discovery **уточняет** существующую Model, а не создаёт новую. Компоненты, обнаруженные повторно, обновляются. Новые компоненты добавляются. Удалённые компоненты отмечаются.
- Если Model уже содержит данные от Security Analysis или Dependency Analysis, повторный запуск Discovery **не удаляет** эти данные. Discovery работает только со структурными данными (компоненты, связи, слои), а результаты анализа остаются привязанными к компонентам.

### 6.3 Discovery не создаёт параллельную модель

Архитектурно запрещено существование «Discovery Model» — отдельной модели, создаваемой Discovery, которая затем «сливается» с Architecture Model. Это нарушало бы принцип единого источника правды и создавало риск расхождения между двумя моделями.

Единственная модель — Architecture Model. Discovery является одним из механизмов её создания и обновления.

### 6.4 Discovery не содержит AI

На продуктовом уровне Discovery **не имеет AI-компонента**. Это архитектурное следствие принципа «Model Before Analyze»: AI интерпретирует модель (AI Assistance Specification), а Discovery создаёт данные для модели. AI без модели — это «generic chatbot, explicitly useless» (AI Assistance Specification). Привлечение AI к Discovery означало бы попытку интерпретировать данные до создания структуры для интерпретации, что является архитектурно бессмысленным.

### 6.5 Discovery не выполняет анализ

Discovery **не может** выполнять функции Security Analysis, Dependency Analysis или любого другого типа анализа. Это архитектурное следствие принципа «Composable, Not Monolithic» (Product Principles, §3.12) и Decision 1. Если Discovery выполнял бы анализ, он нарушал бы границу между созданием модели и её обогащением, что привело бы к монолитному процессу.

Discovery обнаруживает структуру. Analysis интерпретирует структуру. Это два разных архитектурных процесса с разными целями, разными входами и разными выходами.

### 6.6 Re-running Discovery

Повторный запуск Discovery является архитектурно корректной операцией, но с определёнными ограничениями:

- Повторный запуск **уточняет** Model, но **не заменяет** её. (Product Architecture Decisions, D7)
- Повторный запуск не затрагивает результаты Analysis, привязанные к компонентам.
- Если компонент, обнаруженный ранее, отсутствует в повторном Discovery — это фиксируется как изменение в Model, но не приводит к каскадному удалению результатов Analysis.

## 7. Analysis Layer

### 7.1 Архитектурная роль анализа

Analysis Layer состоит из capabilities, которые **читают Architecture Model, выполняют специализированный анализ, и записывают результаты обратно в Model, привязывая их к компонентам**. Каждая analysis capability является обогащением Model, а не параллельной моделью.

Архитектурные правила Analysis Layer являются следствием Product Architecture Decisions:
- D1: Модель строится до анализа.
- D2: Результаты всегда привязаны к модели.
- D6: Безопасность анализируется вместе с архитектурой.
- D8: Единая платформа, не набор инструментов.

### 7.2 Security Analysis

**Роль:** Security Analysis — это capability создания **понимания безопасности** проекта. Читает Architecture Model, выполняет анализ безопасности (через интеграцию с внешними инструментами: nmap, nuclei, ZAP, semgrep, trivy и др.), и записывает данные о безопасности в Architecture Model, привязывая их к компонентам.

**Что привязывается к Model:**
- Обнаруженные уязвимости (CVE, CWE) с классификацией.
- Конфигурационные проблемы безопасности.
- Цепочки атак (attack paths), построенные на основе связей Model.
- Оценки рисков с учётом архитектурного контекста.

**Что производит:** Картина рисков безопасности, привязанная к архитектуре. Пользователь видит не список уязвимостей, а понимание того, какие данные под угрозой, через какие пути атакующий может добраться до критических активов, и почему конкретная уязвимость опасна в контексте данной архитектуры.

**Ключевые правила:**
- Каждый security finding привязан к конкретному компоненту Model.
- Без привязки к Model finding не представляется пользователю.
- Security Analysis не создаёт отдельную «security model».
- Security Analysis не изменяет структурные факты Model (компоненты, связи).

**Статус:** MVP.

### 7.3 Dependency Analysis

**Роль:** Dependency Analysis — это capability создания **понимания зависимостей** проекта. Читает Architecture Model, анализирует зависимости между компонентами, и записывает данные о зависимостях в Architecture Model, привязывая их к компонентам.

**Что привязывается к Model:**
- Полный граф зависимостей (прямые и транзитивные).
- Циклические зависимости.
- Избыточные зависимости.
- Рискованные зависимости (устаревшие, небезопасные).
- Точки концентрации зависимостей.

**Что производит:** Понимание связанности системы. Пользователь видит не список зависимостей, а понимание того, как компоненты связаны, какие связи проблемные, и что произойдёт, если связь изменится или исчезнет.

**Ключевые правила:**
- Каждая dependency finding привязана к конкретному компоненту Model.
- Без привязки к Model finding не представляется пользователю.
- Dependency Analysis не создаёт отдельную «dependency model».
- Dependency Analysis не изменяет структурные факты Model.

**Статус:** MVP.

### 7.4 Правила для всех анализов

Следующие архитектурные правила применяются ко всем analysis capabilities — как MVP, так и Post-MVP:

**1. Каждый анализ читает Model, produces findings bound to Model components.** Никакие результаты анализа не существуют «вне модели». Это архитектурное следствие D2.

**2. Никакой анализ не может создать параллельную модель.** Если analysis capability создаёт собственную структуру данных, не привязанную к Model — это архитектурное нарушение. Все данные должны быть обогащением Model.

**3. Результаты анализа — это обогащение Model, никогда — замена.** Analysis может добавлять данные к компонентам Model, но не может удалять компоненты, изменять связи или перестраивать структуру. Структурные изменения — это задача Discovery и ручных корректировок.

**4. AI интерпретирует результаты анализа, но не заменяет анализ.** AI может объяснить, почему обнаруженная уязвимость критична в данном контексте. Но AI не выполняет сам сканирование безопасности. AI не обнаруживает зависимости. AI не создаёт findings — он интерпретирует findings, созданные analysis capabilities.

### 7.5 Post-MVP анализы

**Change Impact Assessment (Post-MVP).** CIA оценивает последствия планируемых изменений. Для полноценной работы требует:
- Текущей Architecture Model (для определения затронутых компонентов).
- Architecture Knowledge (для понимания причин связей и контекста).
- Architecture Evolution (для анализа исторических паттернов изменений).

Архитектурная роль CIA — прогнозирование. CIA читает Model + Knowledge + Evolution, использует граф зависимостей и исторические данные для оценки влияния, и производит прогноз, привязанный к компонентам Model.

**Technical Debt Tracking (Post-MVP).** Отслеживает накопление технического долга. Для полноценной работы требует:
- Architecture Model (для привязки долга к компонентам).
- Architecture Knowledge (для понимания причин возникновения долга).
- Architecture Evolution (для отслеживания динамики долга).
- CIA (для понимания влияния долга на систему).
- Security Analysis и Dependency Analysis (для комплексной картины долга).

Архитектурная роль TDT — накопительная оценка. TDT читает все вышеперечисленные области, synthesizes данные о долге, и записывает агрегированные данные о долге в Model, привязывая их к компонентам.

## 8. AI Layer

### 8.1 AI как финальный потребитель

AI Assistance является **финальным потребителем** в ценностной цепи AIS. Архитектурно это означает, что AI располагается **после всех других областей** и читает их результаты, но не является источником данных для любой из них.

Ценностная цепь:
```
Project Artifacts → Discovery → Model → Analysis → Knowledge → Evolution → AI → User
```

AI не участвует в Discovery (нет AI в Discovery). AI не участвует в Analysis (AI интерпретирует результаты, но не создаёт findings). AI не участвует в Knowledge accumulation (AI output становится Knowledge только после валидации пользователем). AI не участвует в Evolution observation.

### 8.2 Что читает AI

AI Assistance читает следующие данные, в порядке приоритета:

**Приоритет 1: Architecture Model.** Структурные факты о проекте — компоненты, связи, зависимости, слои. Это основа для любого ответа. Без Model AI работает с общими знаниями и становится «generic chatbot, explicitly useless» (AI Assistance Specification).

**Приоритет 2: Architecture Knowledge.** Накопленное понимание — причины решений, контекст компромиссов, исторические объяснения. Knowledge позволяет AI отвечать на вопросы «почему», а не только «что».

**Приоритет 3: Architecture Evolution.** Временное измерение — как система изменилась, тренды, паттерны. Evolution позволяет AI отвечать на вопросы об эволюции и тенденциях.

**Приоритет 4: Результаты анализа.** Security findings, dependency findings — данные, привязанные к Model компонентам. AI интерпретирует эти данные в контексте конкретного вопроса пользователя.

**Приоритет 5: Organization Context.** Организационные стандарты, политики, допустимые компромиссы. AI учитывает контекст организации при формировании рекомендаций.

**Приоритет 6: Вопрос пользователя.** Intent, контекст вопроса, предыдущие взаимодействия. AI адаптирует ответ к конкретной потребности пользователя.

### 8.3 Что пишет AI

**AI не пишет ничего в Architecture Model напрямую.** Это архитектурное ограничение, являющееся следствием Product Architecture Decisions, D3 и принципа «AI Assists, Not Replaces».

AI пишет:
- **Эфемерный текст** — ответы на вопросы, рекомендации, объяснения. Этот текст существует только в момент взаимодействия с пользователем.
- AI не сохраняет свои ответы как постоянные данные.
- AI не создаёт новые компоненты в Model.
- AI не изменяет существующие компоненты в Model.
- AI не привязывает findings к компонентам (это задача Analysis).
- AI не создаёт Knowledge напрямую (только через валидацию пользователем).

### 8.4 AI output → Knowledge transition

AI output может **стать** Architecture Knowledge, но только через явную валидацию пользователем:

```
AI generates interpretation
       ↓
User reads and evaluates
       ↓
  ┌────┴────┐
  │         │
Validated  Rejected
  │         │
  ↓         ↓
Becomes    Disappears
Knowledge  (no trace)
```

Архитектурно это означает, что существует **явный переход** между эфемерным AI output и постоянным Knowledge. Этот переход контролируется пользователем, а не платформой. Без этого перехода AI output остаётся эфемерным и не влияет на накопленное знание.

### 8.5 AI не владеет моделью, знаниями или анализом

AI является **интерпретатором**, а не **владельцем**. Это фундаментальное архитектурное разделение:

- AI не владеет Architecture Model — AI читает Model.
- AI не владеет Architecture Knowledge — AI читает Knowledge.
- AI не владеет результатами Analysis — AI интерпретирует Analysis results.
- AI не принимает решения — AI предоставляет информацию для принятия решений (D3).
- AI ≠ Source of Truth — Architecture Model является единственным источником правды.

### 8.6 AI без Model = generic chatbot

Это архитектурное утверждение является прямым следствием AI Assistance Specification. AI Assistance, работающий без Architecture Model, не отличается от любого другого AI-ассистента (copilot, chatgpt). Он может объяснить, что такое циклическая зависимость, но не может сказать, какие циклические зависимости существуют в *данном* проекте.

Разница между AIS AI и generic AI:
- **Generic AI:** «Циклические зависимости — это плохо, потому что...»
- **AIS AI:** «В вашем проекте существует циклическая зависимость между модулями AuthService и PaymentProcessor, которая создаёт риск при развёртывании, потому что...»

Вторая форма возможна только потому, что AI читает Architecture Model конкретного проекта.

## 9. Organization Context Layer

### 9.1 OA как cross-cutting контекстный слой

Organization Adaptation (OA) является **cross-cutting контекстным слоем**, который обеспечивает интерпретацию архитектурных фактов в контексте конкретной организации. OA не является анализатором, не является движком правил, и не является отдельной моделью. OA — это слой контекста, который влияет на то, как *другие capabilities* интерпретируют данные.

Архитектурно OA является cross-cutting: он влияет на Security Analysis, Dependency Analysis, AI Assistance, Knowledge accumulation и Report Generation. Но OA не изменяет Architecture Model напрямую — он записывает контекст в элемент модели («организационный контекст»).

Это архитектурное следствие:
- Product Principles, §3.11 («Context Over Rules»).
- Product Architecture Decisions, D5 («Контекст важнее правил»).
- Organization Adaptation Specification.

### 9.2 OA записывает в элемент Model

OA **записывает** организационный контекст в элемент Architecture Model (Architecture Model Specification, §4.8). Этот контекст включает:
- Архитектурные стандарты организации.
- Security policies.
- Приоритеты.
- Допустимые компромиссы.
- Отраслевые стандарты.

Запись контекста в Model обеспечивает:
- Единое хранение — контекст доступен всем capabilities через Model.
- Прослеживаемость — изменения контекста видны в истории Model.
- Согласованность — все capabilities работают с одним и тем же контекстом.

### 9.3 Граница «Факт vs. Интерпретация» — НЕПРОНИЦАЕМА

Архитектурная граница между архитектурными фактами и организационным контекстом является **непроницаемой**. Это означает:

- Организационный контекст **не может изменять** архитектурные факты. Если в Model зафиксировано, что компонент A зависит от компонента B, этот факт остаётся независимо от того, считает ли организация эту зависимость допустимой.
- Организационный контекст **влияет на интерпретацию** фактов. Та же зависимость между A и B может быть:
  - В финансовой компании: «Нарушение стандарта изоляции слоёв. Риск: высокий.»
  - В стартапе-прототипе: «Допустимый компромисс на текущем этапе. Рекомендуется устранить к Q3.»

**Факт одинаковый. Интерпретация различается.** Граница между ними непроницаема.

Это архитектурное правило является критически важным. Если бы организационный контекст мог изменять архитектурные факты, AIS превращался бы в инструмент, который показывает то, что организация *хочет видеть*, а не то, что *существует*. Это подрывало бы доверие к платформе и противоречило бы принципу «Transparent Analysis» (Product Principles, §3.9).

### 9.4 OA предоставляет контекст AI и Analysis

OA предоставляет организационный контекст двум типам потребителей:

**Analysis capabilities** (Security, Dependency) — используют OA для адаптации интерпретации результатов. Security Analysis выделяет нарушения mandatory policies отдельно от нарушений recommended practices. Dependency Analysis учитывает допустимые компромиссы при оценке рисков.

**AI Assistance** — использует OA для формирования рекомендаций, учитывающих контекст организации. AI формулирует рекомендации в терминах, релевантных для конкретной организации.

В обоих случаях OA предоставляет *контекст*, а не *правила*. Разница фундаментальная (Organization Adaptation Specification, §2.4):
- **Rules engine:** «Если циклическая зависимость → ошибка» (абсолютно, бинарно).
- **OA:** «В данной организации циклическая зависимость внутри слоя считается допустимым компромиссом, а между слоями — нарушением стандарта» (контекстуально).

### 9.5 OA без Model = контекст без предмета

OA без Architecture Model частично существует (пользователь может ввести организационный контекст), но **бесполезен**. Контекст без предмета интерпретации — это конфигурация без системы. OA требует Model как обязательный prerequisite для создания ценности.

Это определяет порядок: Model создаётся первым (Discovery → Model), OA настраивается после (или параллельно), но OA без Model не создаёт архитектурного понимания.

### 9.6 OA как форма Knowledge

Architecture Knowledge Specification (§9.11) определяет OA как форму Knowledge — «набор интерпретативных утверждений, которые организация считает релевантными для оценки архитектуры». Это означает, что OA контекст является частью накопленного понимания, а не внешней конфигурацией.

Архитектурно это означает:
- OA контекст может уточняться со временем (как Knowledge).
- OA контекст может быть переосмыслен (как Knowledge).
- OA контекст имеет историю изменений (как Knowledge).
- OA контекст объясним (как Knowledge — пользователь может понять, почему данное правило/стандарт существует).

## 10. Presentation Layer

### 10.1 Visualization и Report Generation как чистые проекции

Presentation Layer состоит из двух capabilities: Visualization и Report Generation. Обе являются **чистыми проекциями** Architecture Model — они только читают Model и производят представления для пользователя. Ни одна из них не пишет обратно в Model. Ни одна из них не является источником правды.

Архитектурно Presentation Layer является **последним звеном** перед пользователем (вместе с AI Assistance). Порядок:

```
Model → Analysis enriches Model → Presentation reads Model → User
Model → Analysis enriches Model → AI reads Model → User
```

Presentation Layer является следствием Product Principles, §3.9 («Transparent Analysis»): каждый вывод должен быть прослежен до исходных данных. Presentation не создаёт новых данных — она делает существующие данные доступными для восприятия.

### 10.2 Visualization

**Роль:** Visualization читает Architecture Model и представляет её в интерактивной визуальной форме. Пользователь может исследовать структуру проекта, навигировать по компонентам и связям, фильтровать по аспектам (только зависимости, только безопасность).

**Ключевые архитектурные правила:**
- Visualization **не кэширует** собственное состояние. Визуализация всегда работает с текущим состоянием Model. Это архитектурное следствие принципа «Continuous Understanding» (Product Principles, §3.8) — устаревшая визуализация создаёт ложную уверенность.
- Visualization **не может** стать источником правды. Если визуализация показывает что-то, чего нет в Model — это архитектурная ошибка.
- Visualization **не пишет** в Model. Визуализация — это чистая проекция.
- Visualization может читать OA контекст для адаптации отображения, но OA контекст влияет на визуализацию, а не на Model.

**Статус:** MVP.

### 10.3 Report Generation

**Роль:** Report Generation читает Architecture Model и формирует структурированные отчёты для внешнего использования. Отчёты являются **срезами Model в момент генерации** — они фиксируют состояние Model на определённый момент времени.

**Ключевые архитектурные правила:**
- Отчёты **не обновляются автоматически**. Каждый отчёт является самостоятельным артефактом, созданным в определённый момент. Если Model изменилась после генерации отчёта, отчёт не обновляется — пользователь должен сгенерировать новый отчёт.
- Отчёты являются **самодостаточными артефактами** для потребления вне платформы. Отчёт содержит всю необходимую информацию из Model в момент генерации и не требует доступа к платформе для интерпретации.
- Отчёты **не могут** стать источником правды. Отчёт — это срез Model, а не самостоятельное знание. Если отчёт противоречит текущему состоянию Model — Model имеет приоритет.
- Отчёты **не пишут** в Model. Генерация отчёта не изменяет Model.

**Статус:** MVP.

### 10.4 Чтение OA контекста

Presentation Layer может читать OA контекст для адаптации:
- Visualization может выделять компоненты, нарушающие организационные стандарты, другим цветом.
- Reports могут включать раздел «Соответствие стандартам организации» на основе OA контекста.

Но OA контекст влияет только на **отображение**, а не на **содержание** Model. Это согласуется с принципом непроницаемости границы «Факт vs. Интерпретация» (раздел 9.3).

## 11. Unified Context Model

### 11.1 Определение

**Unified Context Model** — это концептуальная модель контекста, который AIS предоставляет всем downstream capabilities. Unified Context объединяет:

1. **Architecture Model** — структурные факты (компоненты, связи, зависимости, слои).
2. **Architecture Knowledge** — накопленное понимание (причины, контекст, интерпретации).
3. **Architecture Evolution** — временной контекст (история состояний, тренды, паттерны).
4. **Organization Context** — интерпретативная линза организации (стандарты, политики, компромиссы).
5. **Analysis Results** — результаты специализированных анализов (security findings, dependency findings, impact assessments, debt evaluations).
6. **User Question/Intent** — что пользователь хочет понять (вопрос, контекст взаимодействия, предыдущие вопросы).
7. **Uncertainty** — явные неизвесты (что модель не знает, где данные неполны, где анализ не проводился).
8. **Historical Context** — прошлые состояния, прошлые решения, прошлые интерпретации.

### 11.2 Зачем нужен Unified Context

Без Unified Context каждая capability работала бы с неполным набором данных. AI без Knowledge может ответить «что», но не «почему». AI без OA может дать универсальную рекомендацию, которая не применима в контексте организации. AI без Uncertainty может дать уверенный ответ там, где данных недостаточно.

Unified Context гарантирует, что любая downstream capability получает максимально полный контекст для формирования ответа. Это архитектурная реализация принципа «Explain Before Recommend» (Product Principles, §3.1) и «Context Over Rules» (Product Principles, §3.11).

### 11.3 Иерархия контекста

Unified Context имеет иерархию приоритетов. Не все элементы контекста доступны для всех capabilities на всех стадиях зрелости:

**MVP Context (Stage 1):**
- Architecture Model (обязательный, центральный)
- Analysis Results: Security + Dependency (обязательные для MVP)
- Organization Context (обязательный для MVP)
- User Question/Intent (обязательный для AI)
- Uncertainty (желательный)

**Post-MVP Context (Stage 2):**
- Architecture Knowledge (добавляется)
- Architecture Evolution (добавляется)
- CIA Results (добавляются)
- Historical Context (расширяется)

**Long-term Context (Stage 3+):**
- Tech Debt Results (добавляются)
- Evolution Trends (расширяются)
- Cross-project Context (добавляется)

### 11.4 Uncertainty как явный элемент контекста

Uncertainty является **явным элементом** Unified Context. Это архитектурное следствие принципа «Transparent Analysis» (Product Principles, §3.9). Платформа должна явно указывать, где данных недостаточно, где анализ не проводился, где Model неполна.

Uncertainty включает:
- Компоненты, для которых нет данных анализа (анализ ещё не проводился).
- Области Model, где данные устарели (последнее обновление было давно).
- Вопросы, на которые AI не может ответить с достаточной уверенностью.
- Компромиссы, принятые при построении Model (где точность была пожертвована в favour полноты).

Uncertainty не является недостатком — это свойство honest system. Система, которая скрывает свою неопределённость, создаёт ложную уверенность. Система, которая явно показывает неопределённость, зарабатывает доверие (Product Principles, §6 — Product Philosophy: «Доверие зарабатывается прозрачностью»).

### 11.5 User Intent как элемент контекста

User Question/Intent является частью контекста, потому что один и тот же Architecture Model может требовать разных интерпретаций для разных вопросов:

- Вопрос «покажи все уязвимости» требует Security Analysis + Model.
- Вопрос «почему модуль X зависит от Y» требует Knowledge + Model + Dependency Analysis.
- Вопрос «как архитектура изменилась за последний месяц» требует Evolution + Model.

User Intent определяет, какие элементы контекста приоритетны для конкретного ответа. AI Assistance использует Intent для маршрутизации к соответствующим элементам Unified Context.

## 12. Information Flow

### 12.1 Определение потоков

Информационные потоки AIS определяют направления движения данных между архитектурными областями. Каждый поток классифицирован по типу взаимодействия:

- **READ-ONLY** — область читает данные, но не записывает ничего.
- **ENRICHES** — область читает данные, выполняет обработку и записывает результаты обратно.
- **VALIDATES** — область проверяет корректность данных.
- **INTERPRETS** — область читает данные и производит интерпретацию для пользователя.
- **PRESENTS** — область читает данные и производит представление (визуальное или текстовое).

### 12.2 Input Flow: Project → Discovery → Model

**Классификация:** ENRICHES

**Направление:**
```
Project Artifacts → [Discovery process] → Architecture Model
```

**Описание:** Project Artifacts являются входными данными для процесса Discovery. Discovery извлекает структурную информацию из артефактов и создаёт/обновляет Architecture Model. Discovery enriches Model структурными данными: компонентами, связями, слоями.

**Правила:**
- Discovery является единственным источником структурных данных для Model (наряду с ручными корректировками).
- Discovery не удаляет данные, созданные другими capabilities (Analysis results привязанные к компонентам сохраняются).
- Повторный запуск Discovery уточняет Model, но не заменяет её.

**Источник:** Product Architecture Decisions, D1 (Model Before Analysis); Product Principles, §3.4 (Knowledge Never Lost); Project Discovery Specification.

### 12.3 Analysis Flow: Model → Analysis → Model

**Классификация:** ENRICHES (findings bound to model)

**Направление:**
```
Architecture Model → [Security Analysis] → Architecture Model (security findings)
Architecture Model → [Dependency Analysis] → Architecture Model (dependency findings)
```

**Описание:** Analysis capabilities читают Architecture Model, выполняют специализированный анализ, и записывают результаты обратно в Model, привязывая их к компонентам. Каждый finding связан с конкретным компонентом Model.

**Правила:**
- Каждый finding привязан к компоненту Model.
- Без привязки к Model finding не представляется пользователю.
- Analysis не создаёт параллельную модель.
- Analysis enriches Model, но не заменяет её структуру.

**Источник:** Product Architecture Decisions, D1, D2, D6, D8; Security Analysis Specification; Dependency Analysis Specification.

### 12.4 Knowledge Flow: Model + Analysis → Knowledge

**Классификация:** ENRICHES

**Направление:**
```
Architecture Model + Analysis Results → [Knowledge accumulation] → Architecture Knowledge
```

**Описание:** Knowledge накапливается на основе Model и результатов Analysis. Knowledge enriches понимание системы, добавляя интерпретации, причины и контекст. Knowledge не изменяет структуру Model — он добавляет измерение смысла.

**Правила:**
- Knowledge основан на фактах Model, но содержит интерпретации.
- Knowledge может быть создан пользователем (валидация AI output, ручные заметки).
- Knowledge уточняется без потери истории.
- AI output становится Knowledge только после валидации пользователем.

**Источник:** Architecture Knowledge Specification; Product Architecture Decisions, D7; Product Principles, §3.4.

### 12.5 Evolution Flow: Model states → Evolution

**Классификация:** READ-ONLY (observation)

**Направление:**
```
Architecture Model states (over time) → [Evolution observation] → Architecture Evolution
```

**Описание:** Evolution читает последовательность состояний Architecture Model и производит наблюдения о том, что изменилось. Evolution не изменяет Model и не объясняет причины изменений — он фиксирует наблюдения.

**Правила:**
- Evolution observational — он фиксирует *что* изменилось, не *почему*.
- Evolution требует множества состояний Model (поэтому Post-MVP).
- Evolution не является причиной Knowledge, но предоставляет данные для Knowledge.

**Источник:** Architecture Evolution Specification; Capability Map (Post-MVP).

### 12.6 AI Flow: Everything → AI → User

**Классификация:** INTERPRETS

**Направление:**
```
Model + Knowledge + Evolution + Analysis + OA + User Intent → [AI Assistance] → User
```

**Описание:** AI Assistance читает все доступные данные из Unified Context и производит интерпретацию в виде текстового ответа или рекомендации. AI является финальным интерпретатором в цепочке ценности.

**Правила:**
- AI читает все, но пишет ничего в Model.
- AI output является эфемерным текстом.
- AI output становится Knowledge только после валидации пользователем.
- AI без Model = generic chatbot.
- AI не является источником правды.

**Источник:** AI Assistance Specification; Product Architecture Decisions, D3; Product Principles, §3.6.

### 12.7 Presentation Flow: Model → Viz/Reports

**Классификация:** PRESENTS (read-only)

**Направление:**
```
Architecture Model → [Visualization] → User (visual)
Architecture Model → [Report Generation] → User (document)
```

**Описание:** Presentation capabilities читают Architecture Model и производят представления для пользователя. Visualization создаёт интерактивные визуальные представления. Reports создают структурированные документы.

**Правила:**
- Presentation только читает Model.
- Presentation не кэширует собственное состояние (Visualization).
- Reports являются срезами Model в момент генерации, не обновляются автоматически.
- Presentation может читать OA контекст для адаптации отображения.

**Источник:** Visualization Specification; Report Generation Specification; Product Principles, §3.9.

### 12.8 OA Flow: User → OA → Model context element

**Классификация:** ENRICHES (adds interpretation layer)

**Направление:**
```
User input → [Organization Adaptation] → Architecture Model (organizational context element)
```

**Описание:** Пользователь вводит организационный контекст (стандарты, политики, компромиссы). OA записывает этот контекст в элемент Model («организационный контекст»). Контекст влияет на интерпретацию данных Model другими capabilities, но не изменяет архитектурные факты.

**Правила:**
- OA записывает контекст в Model, а не в отдельное хранилище.
- OA контекст не может изменять архитектурные факты.
- Граница «Факт vs. Интерпретация» непроницаема.
- OA является формой Knowledge (Architecture Knowledge Specification, §9.11).

**Источник:** Organization Adaptation Specification; Product Principles, §3.11; Product Architecture Decisions, D5.

### 12.9 Сводная таблица потоков

| Поток | Направление | Классификация | MVP/Post-MVP |
|---|---|---|---|
| Input Flow | Project → Discovery → Model | ENRICHES | MVP |
| Analysis Flow (Security) | Model → Security → Model | ENRICHES | MVP |
| Analysis Flow (Dependency) | Model → Dependency → Model | ENRICHES | MVP |
| Knowledge Flow | Model + Analysis → Knowledge | ENRICHES | Post-MVP |
| Evolution Flow | Model states → Evolution | READ-ONLY | Post-MVP |
| CIA Flow | Model + Knowledge + Evolution → CIA → Model | ENRICHES | Post-MVP |
| Tech Debt Flow | All above → TDT → Model | ENRICHES | Post-MVP |
| AI Flow | Everything → AI → User | INTERPRETS | MVP |
| Visualization Flow | Model → Viz → User | PRESENTS | MVP |
| Report Flow | Model → Reports → User | PRESENTS | MVP |
| OA Flow | User → OA → Model context | ENRICHES | MVP |

### 12.10 Критические правила потоков

**1. Нет обратных потоков от Presentation к Model.** Visualization и Reports только читают Model. Пользователь может взаимодействовать с визуализацией (навигация, фильтрация), но это взаимодействие не записывается в Model.

**2. Нет прямых потоков между Analysis capabilities.** Security Analysis не общается с Dependency Analysis напрямую. Обе читают и пишут в Model. Если Security Analysis нуждается в данных о зависимостях — он читает их из Model, а не из Dependency Analysis.

**3. AI не может инициировать потоки.** AI не может запустить Discovery, Analysis, или любой другой процесс. AI только читает существующие данные и интерпретирует их. Инициирование процессов — это задача пользователя.

**4. OA контекст влияет на интерпретацию, но не на данные.** OA Flow записывает контекст в Model, но архитектурные факты (компоненты, связи) не изменяются. Это непроницаемая граница.

## 13. Ownership Matrix

Матрица владения данными определяет, какой домен создаёт, потребляет, производит и модифицирует данные. Ключевое правило: **никакого перекрытия владения**. Каждый домен имеет чёткую, непересекающуюся зону ответственности.

| Домен | Владеет (какие данные создаёт и за что отвечает) | Потребляет (что читает) | Производит (что выдаёт) | Может изменять Source of Truth? |
|---|---|---|---|---|
| **Discovery** | Сырые данные проекта: структура файлов, конфигурации, метаданные обнаруженных артефактов | Файловая система проекта, конфигурации сборки | Структурированные данные для Model: компоненты, модули, файлы, связи | Нет. Discovery поставляет данные в Model, но не владеет архитектурной структурой |
| **Architecture Model** | Структурные факты архитектуры: компоненты, модули, связи, слои, интерфейсы. Единый Source of Truth | Данные от Discovery, результаты анализов (bound results), контекст от OA | Структурированную архитектурную модель для всех потребителей | **Да, эксклюзивно.** Model — единственный домен, который является Source of Truth для архитектурной структуры |
| **Architecture Knowledge** | Валидированное понимание: паттерны, интерпретации, обоснования решений, контекстные объяснения | Model (факты), результаты анализов, OA контекст, эволюционные данные | Обогащённое понимание архитектуры, интерпретации для AI и пользователей | Нет. Knowledge потребляет Model, но не модифицирует её |
| **Architecture Evolution** | Историю состояний Model: снимки, дельты, временные метки, эволюционные связи | Model (текущее и предыдущие состояния) | Временную линию архитектуры, данные для Change Impact Assessment | Нет. Evolution фиксирует состояния Model, не изменяя их |
| **Security Analysis** | Результаты анализа безопасности, привязанные к элементам Model | Model (компоненты, зависимости, связи), OA контекст (стандарты безопасности) | Security-аннотации на элементах Model, отчёты об уязвимостях | Нет. Пишет результаты в Model как аннотации, но не модифицирует архитектурные факты |
| **Dependency Analysis** | Результаты анализа зависимостей, привязанные к элементам Model | Model (компоненты, модули), данные о внешних зависимостях | Dependency-аннотации на элементах Model, карты зависимостей | Нет. Пишет результаты в Model как аннотации, но не модифицирует архитектурные факты |
| **Change Impact Assessment** | Оценки влияния изменений: затронутые компоненты, цепочки влияния, риски | Model (текущая и предыдущая версия), Evolution (история изменений) | Impact-отчёты, рекомендации по порядку изменений | Нет. Читает Model и Evolution, выдаёт оценки |
| **Technical Debt Tracking** | Реестр технического долга: записи о долге, оценка серьёзности, приоритеты | Model (текущее состояние), все результаты анализов, Evolution (тренды) | Записи технического долга, привязанные к элементам Model, тренды деградации | Нет. Пишет записи о долге, но не модифицирует архитектурные факты |
| **AI Assistance** | **Ничего постоянно.** AI не владеет данными. Временные сессии интерпретации уничтожаются | Всё: Model, Knowledge, Evolution, результаты анализов, OA контекст | Интерпретации, объяснения, рекомендации для пользователя | **Нет, никогда.** AI принципиально не может писать в Model, Knowledge или любой другой Source of Truth |
| **Visualization** | **Ничего.** Visualization не хранит данные | Model (для отображения), результаты анализов (для визуализации) | Визуальные представления (графы, диаграммы, дашборды) | Нет. Visualization — окно в Model, не хранит собственное представление |
| **Report Generation** | **Ничего.** Reports — временные снимки | Model (текущее состояние), результаты анализов, Knowledge (интерпретации) | Отчёты (документы, экспорты) как point-in-time снимки | Нет. Reports — производные снимки, не влияют на Source of Truth |
| **Organization Adaptation** | Организационный контекст: стандарты, приоритеты, принятые компромиссы, политические ограничения | Пользовательский ввод, Model (для контекстуализации) | Контекстные элементы, записываемые в Model как метаданные | Нет. OA записывает контекст в Model, но не модифицирует архитектурные факты |

### 13.1 Ключевые правила матрицы владения

**Правило 1: Один Source of Truth.** Architecture Model — единственный домен, который является Source of Truth. Все остальные домены либо поставляют данные в Model, либо читают из неё.

**Правило 2: AI владеет ничем.** AI Assistance не имеет постоянного хранилища. Все интерпретации — временные. Это архитектурное ограничение, а не ограничение реализации.

**Правило 3: Presentation не хранит.** Visualization и Report Generation принципиально не хранят данные. Они — окна в Model и её производные.

**Правило 4: Knowledge != Model.** Knowledge владеет *пониманием*, Model владеет *фактами*. Граница непроницаема.

**Правило 5: Анализ аннотирует, не создаёт.** Security Analysis и Dependency Analysis создают результаты (аннотации), которые привязаны к элементам Model, но не заменяют Model.

**Правило 6: Evolution фиксирует, не модифицирует.** Architecture Evolution хранит историю состояний Model, но не может изменить ни одно из них.

## 14. Capability Dependency Architecture

Детальная архитектура зависимостей для всех 11 capabilities. Определяет позицию каждой capability в цепочке зависимостей и её отношения с ключевыми архитектурными сущностями.

### 14.1 Project Discovery

| Параметр | Значение |
|---|---|
| **Архитектурный вход** | Файловая система проекта, конфигурации сборки, метаданные |
| **Архитектурный выход** | Структурированные данные о проекте для загрузки в Model |
| **Позиция в цепочке зависимостей** | Источник данных (первая позиция) |
| **Отношение с Model** | Записывает (writes): поставляет компоненты, модули, связи в Model |
| **Отношение с Knowledge** | Нет (Discovery не взаимодействует с Knowledge) |
| **Отношение с Evolution** | Нет (Discovery не взаимодействует с Evolution) |
| **Отношение с AI** | Предоставляет данные (provides data): AI может читать результаты Discovery через Model |
| **Может существовать самостоятельно?** | ДА (источник данных, не зависит от других capabilities) |
| **Может стать отдельным Source of Truth?** | НЕТ (Discovery поставляет данные, но не является архитектурным Source of Truth) |

## 15. MVP Architecture Boundary

Определение архитектурных границ для MVP (Stage 1), Post-MVP (Stage 2) и долгосрочной перспективы (Stage 3+).

### 15.1 MVP (Stage 1)

**Включённые capabilities:**
- Project Discovery
- Architecture Modeling
- Security Analysis
- Dependency Analysis
- AI Assistance
- Report Generation
- Visualization
- Organization Adaptation

**Архитектурные требования MVP:**

**AM-1: Model — единый Source of Truth.** Architecture Model является единственным постоянным хранилищем архитектурной информации. Все результаты анализа привязаны к Model.

**AM-2: Персистентность Model между сессиями.** Model должен сохранять состояние между сессиями пользователя (MVP Checklist, пункт 16). Это базовая персистентность (save/load), а не полная система версионирования.

**AM-3: Все результаты анализа привязаны к Model.** Security Analysis и Dependency Analysis записывают результаты как аннотации на элементах Model. Отдельного хранилища результатов нет.

**AM-4: AI читает, не пишет.** AI Assistance получает доступ к Model и результатам анализов, но принципиально не может модифицировать какие-либо данные. AI — интерпретатор, не источник.

**AM-5: Visualization — окно в Model.** Visualization отображает данные Model. В MVP — статическая или минимально интерактивная визуализация. Навигация (Should Have, не Must Have).

**AM-6: Reports — временные снимки.** Report Generation создаёт point-in-time снимки Model и результатов анализа. Отчёты не являются постоянным хранилищем.

**AM-7: OA — базовый организационный контекст.** Organization Adaptation предоставляет базовый контекст: приоритеты, стандарты, принятые компромиссы. Не является корпоративной платформой политик.

### 15.2 Три условия стабилизации (неблокирующие, для Architecture Layer)

Эти условия определяют границы, в которых Architecture Layer принимает решение о конкретном уровне реализации.

**Стабилизация 1: Уровень интерактивности Visualization.**
- **MVP:** Статическая визуализация с опциональной навигацией (Should Have, не Must Have).
- **Граница принятия решения:** Architecture Layer определяет конкретный уровень интерактивности (какие элементы интерактивны, какие — нет).
- **Критерий:** Если добавление интерактивности требует отдельной модели данных — это нарушает инвариант I9. Интерактивность должна работать поверх Model.

**Стабилизация 2: Персистентность Model.**
- **MVP:** Базовая персистентность состояния Model (save/load). Сохранение и восстановление текущего состояния между сессиями.
- **Post-MVP:** Полная Knowledge Persistence — история, сравнение, эволюция (Stage 2).
- **Граница принятия решения:** Architecture Layer определяет подход к реализации (формат хранения, гранулярность сохранения).
- **Критерий:** Персистентность MVP не должна требовать архитектурных решений, которые ограничат Stage 2.

**Стабилизация 3: Scope Organization Adaptation в MVP.**
- **MVP:** Базовый организационный контекст — приоритеты, стандарты, принятые компромиссы.
- **НЕ входит в MVP:** Корпоративная платформа политик, сложная система согласования компромиссов, интеграция с внешними системами управления.
- **Граница принятия решения:** Architecture Layer определяет конкретные параметры OA в MVP (какие поля, какой формат, как хранится).
- **Критерий:** OA MVP должен быть расширяем до полноценного OA без изменения архитектуры Model.

### 15.3 Post-MVP (Stage 2)

**Добавляемые capabilities:**
- Knowledge Persistence (расширение Architecture Knowledge)
- Change Impact Assessment
- Architecture Evolution (расширение Architecture Evolution)
- Enhanced AI с историческим контекстом

**Архитектурные изменения:**
- Knowledge получает персистентность и становится полноценным слоем понимания.
- Evolution начинает фиксировать состояния Model и обеспечивает временное измерение.
- Change Impact Assessment использует Evolution для анализа влияния изменений.
- AI получает доступ к историческому контексту через Knowledge и Evolution.

### 15.4 Long-term (Stage 3+)

**Добавляемые capabilities:**
- Technical Debt Tracking
- Командные функции (multi-user, collaboration)
- Multi-project поддержка

**Архитектурные изменения:**
- Technical Debt Tracking интегрируется как высокоуровневый анализатор, потребляющий Model, все результаты анализов и Evolution.
- Многопользовательская работа требует пересмотра Model с точки зрения параллельного доступа.
- Multi-project требует расширения Model для поддержки нескольких проектов с возможностью кросс-проектного анализа.

## 16. Architecture Invariants

Обязательные архитектурные инварианты — правила, нарушение которых недопустимо на любом этапе разработки. Каждый инвариант имеет источник в Product Layer, архитектурное следствие и последствия нарушения.

### I1 — Model Before Analysis

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D1 (Architecture Model is the single source of truth for architectural structure) |
| **Архитектурное следствие** | Любой анализ требует наличия Model. Discovery должен завершить построение Model до начала любого анализа. Нет пути от файлов напрямую к анализу. |
| **Последствие нарушения** | Анализ работает с неполными или несогласованными данными. Результаты невозможно привязать к Model. Появляются параллельные модели (anti-pattern #1). Система теряет единое представление об архитектуре. |

### I2 — Results Bound to Model

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D2 (All analysis results are bound to the model) |
| **Архитектурное следствие** | Результаты Security Analysis, Dependency Analysis и других анализаторов хранятся как аннотации на элементах Model. Отдельного хранилища результатов анализа не существует. |
| **Последствие нарушения** | Результаты анализа отрываются от архитектурного контекста. Невозможно понять, к какому компоненту относится уязвимость. Появляется отдельный Source of Truth для аналитики (anti-pattern #3). |

### I3 — One Architectural Understanding

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D8 (There is one architectural understanding, not separate ones per capability) |
| **Архитектурное следствие** | Knowledge — единый слой понимания. Нет «security-понимания», «dependency-понимания» и т.д. Все интерпретации converge в единое Knowledge. |
| **Последствие нарушения** | Разрозненные интерпретации создают противоречивое понимание. Пользователь получает разные объяснения от разных capabilities. AI не может предоставить согласованную картину. |

### I4 — No Capability-Specific Source of Truth

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | Следствие из D1, D2, D8 (системное требование) |
| **Архитектурное следствие** | Ни одна capability не может создать собственный Source of Truth. Все данные, которые capability хочет сохранить, должны быть привязаны к Model или к Knowledge. |
| **Последствие нарушения** | Появление изолированных хранилищ данных. Capability-специфичные модели. Невозможность кросс-capability анализа. Деградация в набор изолированных инструментов. |

### I5 — AI Does Not Replace Analysis

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D3 (AI assists but does not replace analysis) |
| **Архитектурное следствие** | AI не выполняет анализ вместо анализаторов. AI интерпретирует результаты анализа, но не генерирует их. Если Security Analysis не обнаружил уязвимость — AI не может «додумать» её. |
| **Последствие нарушения** | AI генерирует результаты, не основанные на фактическом анализе. Результаты ненадёжны. Анализаторы становятся избыточными. Пользователь теряет возможность верифицировать результаты. |

### I6 — AI Does Not Own Decisions

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D3 (AI assists but does not replace analysis); D4 (Recommendations must include context and reasoning) |
| **Архитектурное следствие** | AI не принимает архитектурные решения. AI предлагает варианты с обоснованием, но финальное решение всегда за пользователем. AI не может модифицировать Model на основе своих рекомендаций. |
| **Последствие нарушения** | AI становится de facto архитектором системы. Пользователь теряет контроль. Автоматические изменения Model без верификации. Риски неконтролируемой эволюции архитектуры. |

### I7 — Knowledge Does Not Equal AI Output

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | Следствие из D7 (Knowledge persists and evolves), D3 (AI assists) |
| **Архитектурное следствие** | Knowledge — это валидированное, структурированное понимание. AI Output — это временная интерпретация. Knowledge переживает AI-сессии. AI Output уничтожается после сессии. |
| **Последствие нарушения** | Потеря накопленного понимания при смене AI-сессии. Невозможность построения долгосрочного архитектурного знания. AI-зависимость: без AI нет понимания. |

### I8 — Evolution Does Not Destroy History

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D7 (Architecture knowledge persists and evolves over time) |
| **Архитектурное следствие** | При обновлении Model предыдущие состояния сохраняются в Evolution. Никакая операция не может удалить или перезаписать исторические данные. Эволюция — добавление, не замена. |
| **Последствие нарушения** | Невозможность анализа трендов. Потеря контекста прошлых решений. Change Impact Assessment становится невозможным. Невозможность отката к предыдущему состоянию. |

### I9 — Presentation Does Not Modify Understanding

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | Следствие из D2, принцип разделения Presentation и Data |
| **Архитектурное следствие** | Visualization и Report Generation не могут модифицировать Model, Knowledge или любые другие данные. Они — чистые потребители. Навигация, фильтрация, интерактивные элементы — всё это работает поверх Model, не изменяя её. |
| **Последствие нарушения** | Visualization хранит собственное представление (anti-pattern #4). Синхронизация между визуализацией и Model. Противоречивые представления у разных пользователей. |

### I10 — Organization Context Is Context, Not Absolute Truth

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D5 (Organization-specific context is advisory, not authoritative) |
| **Архитектурное следствие** | OA контекст влияет на интерпретацию, но не на факты. OA приоритеты могут указывать, на что обратить внимание, но не могут скрыть архитектурный факт. Стандарты OA — рекомендации, не обязательные правила. |
| **Последствие нарушения** | OA становится правилами (anti-pattern #6). Организационный контекст подавляет объективный анализ. Неприемлемые компромиссы скрываются, а не документируются. |

### I11 — Every Recommendation Has Context

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | D4 (Recommendations must include context and reasoning) |
| **Архитектурное следствие** | Любая рекомендация (от AI или от анализатора) должна содержать: (1) контекст — на основе каких данных сформирована, (2) обоснование — почему именно эта рекомендация, (3) уровень уверенности — насколько надёжна. |
| **Последствие нарушения** | Рекомендации без контекста не различимы от мнений. Пользователь не может оценить надёжность рекомендации. Невозможность верификации. Слепое доверие к рекомендациям. |

### I12 — Uncertainty Must Remain Visible

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | P9 (Uncertainty must remain visible and not be hidden behind confidence) |
| **Архитектурное следствие** | Все данные в Model и Knowledge должны явно отмечать уровень неопределённости. Если Discovery не может определить тип компонента — это должно быть видно. Если анализ неполный — это должно быть отмечено. |
| **Последствие нарушения** | Ложная уверенность. Пользователь принимает решения на основе неполных данных, считая их полными. Скрытые риски. Невозможность приоритизации по уровню неопределённости. |

### I13 — Architecture Remains Technology Independent

| Параметр | Значение |
|---|---|
| **Источник в Product Layer** | P13 (Architecture should be technology-independent at the conceptual level) |
| **Архитектурное следствие** | Концептуальная архитектура AIS (разделы 1–22 этого документа) не зависит от конкретных технологий реализации. Model, Knowledge, Evolution — концептуальные сущности, не привязанные к конкретным базам данных или фреймворкам. |
| **Последствие нарушения** | Привязка к конкретной технологии на концептуальном уровне. Невозможность смены стека. Ограничение эволюции платформы. Vendor lock-in на архитектурном уровне. |

## 17. Anti-Patterns

Запрещённые архитектурные паттерны — схемы, которые кажутся разумными, но ведут к нарушению продуктовых принципов и решений. Каждый anti-pattern включает описание, нарушаемые принципы/решения и способ обнаружения.

### 17.1 Independent Analyzer Architecture

**Описание:** Каждый анализатор (Security, Dependency, и т.д.) создаёт и поддерживает собственную модель анализируемой системы. Анализаторы работают независимо, каждый со своим представлением об архитектуре.

**Нарушаемые принципы и решения:**
- **D1** (Model is single source of truth) — множественные модели вместо одной.
- **D2** (Results bound to model) — результаты привязаны к capability-специфичным моделям.
- **D8** (One architectural understanding) — каждое capability имеет своё понимание.

**Как обнаружить:**
- Наличие отдельных схем данных для каждого анализатора.
- Невозможность задать кросс-аналитический запрос (например, «найди все компоненты с security-уязвимостями и устаревшими зависимостями»).
- Дублирование сущностей (компонент существует в нескольких моделях).
- Разные представления одного компонента в разных анализаторах.

### 17.2 AI-Centric Architecture

**Описание:** AI становится центральным элементом системы. AI не просто интерпретирует, а генерирует архитектурную модель, результаты анализа, рекомендации. Все данные проходят через AI.

**Нарушаемые принципы и решения:**
- **D3** (AI assists, does not replace analysis) — AI заменяет анализаторы.
- **D5** (Organization context is advisory) — AI может генерировать «организационные нормы» на основе обучающих данных.

**Как обнаружить:**
- AI имеет доступ на запись к Model, Knowledge или другим Source of Truth.
- Результаты анализа недоступны без AI (невозможно получить «сырые» результаты).
- AI генерирует архитектурные факты (компоненты, связи) без верификации.
- Пользователь не может проверить, что именно проанализировано, а что «придумано» AI.

### 17.3 Report-Centric Architecture

**Описание:** Отчёты становятся постоянным хранилищем архитектурной информации. Пользователи работают с отчётами как с основным источником данных, а не с Model.

**Нарушаемые принципы и решения:**
- **D2** (Results bound to model) — отчёты становятся отдельным хранилищем.
- **D7** (Knowledge persists) — отчёты заменяют Knowledge как механизм сохранения понимания.

**Как обнаружить:**
- Отчёты хранятся как постоянные сущности с идентификаторами.
- Пользователи запрашивают данные из отчётов, а не из Model.
- Отчёты содержат информацию, отсутствующую в Model.
- Отчёты обновляются при изменениях (отчёт как живой документ, а не снимок).

### 17.4 Visualization-Centric Architecture

**Описание:** Visualization хранит собственное представление об архитектуре. Визуальные элементы (layout, позиционирование, стили) влияют на то, как архитектура понимается системой.

**Нарушаемые принципы и решения:**
- **D2** (Results bound to model) — визуализация создаёт параллельную модель.

**Как обнаружить:**
- Visualization имеет собственную модель данных.
- Изменения в визуализации (перетаскивание, группировка) сохраняются как архитектурные факты.
- Разные визуализации показывают разные архитектурные структуры.
- Layout-информация используется в анализе.

### 17.5 Knowledge-as-Database

**Описание:** Architecture Knowledge редуцируется до простого хранилища данных без структуры. Знания записываются как плоские записи без связей, контекста и иерархии.

**Нарушаемые принципы и решения:**
- **P4** (Architecture knowledge is structured) — знания не структурированы.
- **D7** (Knowledge persists and evolves) — без структуры невозможно эволюционировать.

**Как обнаружить:**
- Knowledge хранится как набор записей без связей между ними.
- Невозможно проследить эволюцию понимания.
- Знания не привязаны к элементам Model.
- Отсутствует различие между фактами (Model) и пониманием (Knowledge).

### 17.6 Rules-as-Architecture

**Описание:** Organization Adaptation превращается в движок правил. Организационный контекст кодируется как жёсткие правила, которые автоматически фильтруют или модифицируют архитектурные данные.

**Нарушаемые принципы и решения:**
- **D5** (Organization context is advisory, not authoritative) — контекст становится обязательным.
- **P11** (Compromises must be documented, not hidden) — правила скрывают компромиссы.

**Как обнаружить:**
- OA содержит логику фильтрации (скрывает компоненты, не соответствующие стандартам).
- OA правила модифицируют Model или результаты анализа.
- Невозможно увидеть данные, не соответствующие OA правилам.
- OA является «чёрным ящиком» с недокументированными правилами.

### 17.7 Analysis-Before-Model

**Описание:** Анализ начинается напрямую из файлов проекта, без предварительного построения Architecture Model. Анализаторы читают исходный код и генерируют результаты без единой модели.

**Нарушаемые принципы и решения:**
- **D1** (Model is single source of truth) — Model не создаётся или является необязательным.
- **P2** (Architecture model is built from project, not created manually) — процесс нарушен: модель не строится.

**Как обнаружить:**
- Анализаторы принимают файлы/директории как вход, а не Model.
- Результаты анализа не привязаны к элементам Model.
- Невозможно запустить анализ повторно на обновлённой Model.
- Discovery и анализ — один процесс, без промежуточного Model.

### 17.8 Autonomous-Decision Architecture

**Описание:** AI принимает архитектурные решения автоматически. На основе анализа AI модифицирует Model, создаёт рекомендации, которые автоматически применяются, или блокирует операции.

**Нарушаемые принципы и решения:**
- **D3** (AI assists, does not replace analysis) — AI заменяет человека в принятии решений.
- **P6** (User retains control over architectural decisions) — пользователь теряет контроль.

**Как обнаружить:**
- AI имеет доступ на запись к Model или другим Source of Truth.
- AI инициирует процессы (запуск анализа, модификация Model).
- Рекомендации AI применяются автоматически без подтверждения пользователя.
- Пользователь не может отклонить решение AI.

## 18. Product Decision Alignment (D1–D10)

Трассировка каждого продуктового решения D1–D10 на архитектурный уровень: импликация, механизм соблюдения, потенциальный конфликт и его разрешение.

### D1 — Architecture Model is the single source of truth for architectural structure

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Architecture Model — единый источник истины для архитектурной структуры |
| **Архитектурная импликация** | Все capabilities читают из Model и пишут в Model (или не пишут вообще). Нет параллельных моделей. Model — центральный узел архитектуры. |
| **Механизм соблюдения** | (1) Model — единственная сущность с правом записи архитектурных фактов. (2) Анализаторы записывают только аннотации. (3) AI — read-only. (4) Visualization и Reports — read-only. |
| **Потенциальный конфликт** | Performance: все capabilities обращаются к единому Model, что может создать bottleneck. |
| **Разрешение** | Кэширование для чтения (не модифицирует Model). Асинхронная запись аннотаций. Оптимизация на уровне реализации, а не архитектуры. |

### D2 — All analysis results are bound to the model

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Все результаты анализа привязаны к модели |
| **Архитектурная импликация** | Результаты Security Analysis, Dependency Analysis хранятся как аннотации на элементах Model. Нет отдельного хранилища для результатов анализа. |
| **Механизм соблюдения** | (1) Schema Model включает слот для аннотаций каждого типа анализа. (2) Анализаторы получают reference на элемент Model и записывают аннотацию. (3) Нет API для записи результатов вне Model. |
| **Потенциальный конфликт** | Model раздувается от аннотаций. Гибридные результаты (security + dependency) не имеют очевидного места. |
| **Разрешение** | Аннотации хранятся отдельно от структуры (но привязаны к ней). Кросс-аналитические результаты привязаны к общему элементу Model. |

### D3 — AI assists but does not replace analysis

| Параметр | Значение |
|---|---|
| **Утверждение решения** | AI помогает, но не заменяет анализ |
| **Архитектурная импликация** | AI — терминальный потребитель. AI не может инициировать процессы, не может писать в Source of Truth. AI интерпретирует существующие данные. |
| **Механизм соблюдения** | (1) AI API — read-only для всех источников данных. (2) AI Output не сохраняется как часть Model или Knowledge. (3) Анализаторы работают независимо от AI. |
| **Потенциальный конфликт** | Пользователь ожидает, что AI «сам найдёт проблемы» (инициирует анализ). |
| **Разрешение** | AI может рекомендовать запуск анализа, но инициирует его пользователь. AI может описать, какой анализ запустить, но не запускает его самостоятельно. |

### D4 — Recommendations must include context and reasoning

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Рекомендации должны включать контекст и обоснование |
| **Архитектурная импликация** | Все рекомендательные outputs (AI, анализаторы) имеют обязательную структуру: контекст (исходные данные), обоснование (почему), уверенность (насколько надёжно). |
| **Механизм соблюдения** | (1) Schema для рекомендаций включает обязательные поля: context, reasoning, confidence. (2) Валидация на уровне API: рекомендация без контекста отвергается. |
| **Потенциальный конфликт** | Увеличение объёма данных для каждой рекомендации. |
| **Разрешение** | Контекст и обоснование — сжатые ссылки на элементы Model, а не дублирование данных. Уверенность — числовой показатель. |

### D5 — Organization-specific context is advisory, not authoritative

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Организационный контекст является рекомендательным, не авторитетным |
| **Архитектурная импликация** | OA контекст не может модифицировать архитектурные факты. OA не может фильтровать или скрывать данные. OA влияет на интерпретацию, не на данные. |
| **Механизм соблюдения** | (1) OA записывает контекст в Model как метаданные (отдельный слой). (2) Архитектурные факты и OA контекст — непроницаемая граница. (3) OA не имеет доступа к модификации фактов. |
| **Потенциальный конфликт** | Пользователи хотят «автоматически применять стандарты» (фильтровать нестандартные компоненты). |
| **Разрешение** | OA может помечать компоненты как «не соответствующие стандарту», но не скрывать их. Фильтрация — на уровне Presentation (Visualization/Reports), не на уровне данных. |

### D6 — Tool manages architectural knowledge, not just data

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Инструмент управляет архитектурными знаниями, а не только данными |
| **Архитектурная импликация** | Система хранит не только факты (Model), но и понимание (Knowledge). Knowledge — отдельный слой с собственной структурой и жизненным циклом. |
| **Механизм соблюдения** | (1) Knowledge — отдельная сущность с собственным schema. (2) Knowledge потребляет Model, но не является Model. (3) Knowledge обогащается через анализ и Evolution. |
| **Потенциальный конфликт** | Граница между фактами (Model) и пониманием (Knowledge) может размываться. |
| **Разрешение** | Чёткое разделение: Model — что обнаружено, Knowledge — что это значит. Граница определена в Architecture Knowledge Specification. |

### D7 — Architecture knowledge persists and evolves over time

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Архитектурные знания сохраняются и развиваются с течением времени |
| **Архитектурная импликация** | Knowledge и Model имеют временное измерение. Предыдущие состояния сохраняются. Эволюция — добавление, не замена. |
| **Механизм соблюдения** | (1) Evolution фиксирует состояния Model. (2) Knowledge версионируется. (3) Никакая операция не удаляет исторические данные (инвариант I8). |
| **Потенциальный конфликт** | Объём данных растёт бесконтрольно. |
| **Разрешение** | Политика хранения (retention policy) на уровне реализации. Архитектурно — все данные сохраняются, но реализация может архивировать старые состояния. |

### D8 — There is one architectural understanding, not separate ones per capability

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Существует одно архитектурное понимание, а не раздельные для каждой capability |
| **Архитектурная импликация** | Knowledge — единый слой. Нет capability-специфичных подсистем понимания. Все интерпретации converge в единое Knowledge. |
| **Механизм соблюдения** | (1) Knowledge — единая сущность. (2) Все capabilities пишут в Knowledge через единый API. (3) Нет «Security Knowledge», «Dependency Knowledge» и т.д. |
| **Потенциальный конфликт** | Разные capabilities имеют разные модели понимания (security видит риски, dependency видит связи). |
| **Разрешение** | Knowledge поддерживает разные *аспекты* понимания, но в единой структуре. Аспекты — не отдельные хранилища, а разные проекции единого Knowledge. |

### D9 — Discovery and analysis can be run independently

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Discovery и анализ могут запускаться независимо |
| **Архитектурная импликация** | Discovery, Security Analysis, Dependency Analysis — независимые процессы. Каждый может быть запущен отдельно. Но анализ требует наличия Model (инвариант I1). |
| **Механизм соблюдения** | (1) Каждый анализатор — отдельный процесс с собственным API. (2) Анализаторы проверяют наличие Model перед запуском. (3) Discovery можно перезапустить без потери результатов анализа. |
| **Потенциальный конфликт** | Независимый запуск может привести к несогласованным результатам (Model обновлён, а анализ — нет). |
| **Разрешение** | Явное указание устаревших результатов (stale markers). Пользователь видит, какие результаты актуальны, а какие — нет. |

### D10 — User retains full control over all architectural decisions

| Параметр | Значение |
|---|---|
| **Утверждение решения** | Пользователь сохраняет полный контроль над всеми архитектурными решениями |
| **Архитектурная импликация** | Система не принимает решений автоматически. Все изменения Model инициируются пользователем или явным действием (Discovery, анализ). AI не может модифицировать данные. |
| **Механизм соблюдения** | (1) Нет автоматических модификаций Model без явного действия пользователя. (2) AI — read-only. (3) Все изменения логируются и обратимы. |
| **Потенциальный конфликт** | Пользователь может не знать, что нужно сделать (ожидает, что система подскажет). |
| **Разрешение** | AI может рекомендовать действия, но не выполнять их. Система может предлагать следующий шаг, но пользователь принимает решение. |

## 19. Product Principles Alignment

Трассировка каждого из 13 продуктовых принципов (§3.1–§3.13) на архитектурные требования.

### 19.1 §3.1 — Единое представление об архитектуре

| Параметр | Значение |
|---|---|
| **Название принципа** | Единое представление об архитектуре (Single Architectural Representation) |
| **Архитектурное требование** | Architecture Model — единая структура, содержащая все архитектурные факты. Все capabilities работают с одной и той же моделью. |
| **Как архитектура это обеспечивает** | (1) Model — единственный Source of Truth для архитектурной структуры (D1). (2) Все анализаторы привязывают результаты к Model (D2). (3) Knowledge — единый слой понимания (D8). (4) Инвариант I4 запрещает capability-специфичные Source of Truth. |

### 19.2 §3.2 — Автоматическое построение модели

| Параметр | Значение |
|---|---|
| **Название принципа** | Автоматическое построение модели (Automatic Model Construction) |
| **Архитектурное требование** | Discovery автоматически строит Model из файлов проекта. Model не создаётся вручную. |
| **Как архитектура это обеспечивает** | (1) Discovery — отдельная capability, ответственная за автоматическое построение Model. (2) Model строится из фактических артефактов проекта. (3) Инвариант I1 обеспечивает, что Model строится до анализа. |

### 19.3 §3.3 — AI как помощник, не заменитель

| Параметр | Значение |
|---|---|
| **Название принципа** | AI как помощник, не заменитель (AI as Assistant) |
| **Архитектурное требование** | AI — терминальный потребитель. AI не может писать в Source of Truth, не может инициировать процессы, не может заменять анализаторы. |
| **Как архитектура это обеспечивает** | (1) Инвариант I5: AI Does Not Replace Analysis. (2) Инвариант I6: AI Does Not Own Decisions. (3) AI Flow — только INTERPRETS. (4) Anti-pattern #2 (AI-Centric) и #8 (Autonomous-Decision) запрещены. |

### 19.4 §3.4 — Структурированные знания

| Параметр | Значение |
|---|---|
| **Название принципа** | Структурированные знания (Structured Knowledge) |
| **Архитектурное требование** | Knowledge имеет собственную структуру, отличную от Model. Знания организованы, связаны с элементами Model и между собой. |
| **Как архитектура это обеспечивает** | (1) Knowledge — отдельный домен с собственной зоной владения (раздел 13). (2) Knowledge потребляет Model, но не является Model. (3) Инвариант I7: Knowledge ≠ AI Output. (4) Anti-pattern #5 (Knowledge-as-Database) запрещён. |

### 19.5 §3.5 — Рекомендации с контекстом

| Параметр | Значение |
|---|---|
| **Название принципа** | Рекомендации с контекстом (Contextual Recommendations) |
| **Архитектурное требование** | Все рекомендации имеют обязательную структуру: контекст, обоснование, уровень уверенности. |
| **Как архитектура это обеспечивает** | (1) D4 определяет обязательные компоненты рекомендаций. (2) Инвариант I11: Every Recommendation Has Context. (3) AI Output включает ссылки на исходные данные в Model. |

### 19.6 §3.6 — Пользовательский контроль

| Параметр | Значение |
|---|---|
| **Название принципа** | Пользовательский контроль (User Control) |
| **Архитектурное требование** | Пользователь инициирует все действия. Нет автоматических модификаций. AI не может действовать от имени пользователя. |
| **Как архитектура это обеспечивает** | (1) D10: пользователь сохраняет полный контроль. (2) Инвариант I6: AI Does Not Own Decisions. (3) AI не может инициировать потоки (правило потока #3, раздел 12.10). (4) Anti-pattern #8 (Autonomous-Decision) запрещён. |

### 19.7 §3.7 — Устойчивость к неполным данным

| Параметр | Значение |
|---|---|
| **Название принципа** | Устойчивость к неполным данным (Robustness to Incomplete Data) |
| **Архитектурное требование** | Система работает с неполным Model. Отсутствие данных не блокирует анализ. Неопределённость явно отмечена. |
| **Как архитектура это обеспечивает** | (1) Model поддерживает частичное заполнение (не все поля обязательны). (2) Инвариант I12: Uncertainty Must Remain Visible. (3) Анализаторы работают с доступными данными, помечая отсутствующие. (4) Knowledge учитывает уровень полноты данных. |

### 19.8 §3.8 — Эволюция без потери

| Параметр | Значение |
|---|---|
| **Название принципа** | Эволюция без потери (Evolution Without Loss) |
| **Архитектурное требование** | Обновления Model не уничтожают предыдущие состояния. История сохраняется и доступна для анализа. |
| **Как архитектура это обеспечивает** | (1) D7: Knowledge persists and evolves. (2) Инвариант I8: Evolution Does Not Destroy History. (3) Evolution — наблюдатель, не модификатор. (4) Architecture Evolution — отдельный домен с правом только на чтение Model. |

### 19.9 §3.9 — Понятное представление

| Параметр | Значение |
|---|---|
| **Название принципа** | Понятное представление (Clear Presentation) |
| **Архитектурное требование** | Visualization и Reports — окна в Model. Представление не искажает данные, не создаёт собственное понимание. |
| **Как архитектура это обеспечивает** | (1) Инвариант I9: Presentation Does Not Modify Understanding. (2) Visualization и Reports — read-only потребители. (3) Anti-pattern #4 (Visualization-Centric) запрещён. (4) Reports — временные снимки, не постоянное хранилище. |

### 19.10 §3.10 — Опасность перегрузки информацией

| Параметр | Значение |
|---|---|
| **Название принципа** | Опасность перегрузки информацией (Information Overload Risk) |
| **Архитектурное требование** | Архитектура поддерживает фильтрацию и приоритизацию на уровне Presentation, не на уровне данных. Model содержит все данные, Presentation показывает релевантное. |
| **Как архитектура это обеспечивает** | (1) Model содержит полную информацию (никаких фильтров на уровне данных). (2) Visualization и Reports могут фильтровать и приоритизировать. (3) OA контекст помогает приоритизировать (но не фильтровать на уровне данных). (4) AI помогает выделять релевантное. |

### 19.11 §3.11 — Документированные компромиссы

| Параметр | Значение |
|---|---|
| **Название принципа** | Документированные компромиссы (Documented Compromises) |
| **Архитектурное требование** | OA контекст документирует принятые компромиссы, а не скрывает их. Компромиссы видны в Model и влияют на интерпретацию. |
| **Как архитектура это обеспечивает** | (1) D5: OA контекст рекомендателен, не авторитетен. (2) Инвариант I10: OA контекст — контекст, не абсолютная истина. (3) Anti-pattern #6 (Rules-as-Architecture) запрещён. (4) OA записывает контекст в Model как метаданные, не модифицируя факты. |

### 19.12 §3.12 — Измеримый прогресс

| Параметр | Значение |
|---|---|
| **Название принципа** | Измеримый прогресс (Measurable Progress) |
| **Архитектурное требование** | Архитектура поддерживает измеримость: количество компонентов, покрытия анализом, технического долга, эволюции. |
| **Как архитектура это обеспечивает** | (1) Model содержит все данные для измерений. (2) Evolution обеспечивает историческое сравнение. (3) Reports генерируют измеримые метрики. (4) Technical Debt Tracking (Stage 3) обеспечивает тренды. |

### 19.13 §3.13 — Технологическая независимость

| Параметр | Значение |
|---|---|
| **Название принципа** | Технологическая независимость (Technology Independence) |
| **Архитектурное требование** | Концептуальная архитектура не привязана к конкретным технологиям. Model, Knowledge, Evolution — абстрактные сущности. |
| **Как архитектура это обеспечивает** | (1) Инвариант I13: Architecture Remains Technology Independent. (2) Документ описывает концепции, не реализации. (3) Implementation Layer может выбрать любую технологию, не нарушая архитектуру. |

## 20. Quality Criteria

Критерии качества архитектуры AIS. Каждый критерий определяет ожидаемое свойство архитектуры и может быть использован для валидации на этапах проектирования и реализации.

### QC-1: Продуктовые возможности остаются единой системой

**Критерий:** Capabilities не изолированы. Система работает как единое целое, а не как набор отдельных инструментов.

**Проверка:** Удаление любой capability (кроме Discovery и Model) не разрушает остальные. Удаление Discovery делает Model пустым. Удаление Model делает все остальные capabilities неработоспособными.

### QC-2: Architecture Model остаётся центральной структурой

**Критерий:** Model — центральный узел. Все данные проходят через Model или привязаны к нему.

**Проверка:** Ни один архитектурный факт не существует вне Model. Все результаты анализа привязаны к элементам Model.

### QC-3: Знания не теряются

**Критерий:** Knowledge сохраняется между сессиями. Накопленное понимание не теряется при перезапуске.

**Проверка:** Knowledge существует после завершения AI-сессии. Knowledge эволюционирует с обновлениями Model.

### QC-4: Эволюция сохраняет контекст

**Критерий:** Обновления Model не теряют предыдущий контекст. История доступна для анализа.

**Проверка:** Предыдущие состояния Model доступны. Change Impact Assessment может сравнивать состояния.

### QC-5: Анализ не дублирует Model

**Критерий:** Результаты анализа не содержат дубликатов данных Model. Анализ добавляет, не дублирует.

**Проверка:** Аннотации анализа содержат только новые данные (уровень риска, тип зависимости), не переписывая существующие факты Model.

### QC-6: AI не является Source of Truth

**Критерий:** AI не владеет данными постоянно. AI не может писать в Source of Truth.

**Проверка:** Перезапуск AI-сессии не теряет данных. AI Output не сохраняется как часть Model или Knowledge. AI не имеет API для записи.

### QC-7: Presentation не создаёт отдельную модель

**Критерий:** Visualization и Reports не хранят собственное представление об архитектуре.

**Проверка:** Закрытие Visualization не теряет данных. Reports — одноразовые снимки. Нет «визуальной модели» как отдельной сущности.

### QC-8: OA не является движком правил

**Критерий:** Organization Adaptation не содержит жёстких правил, фильтрующих или модифицирующих данные.

**Проверка:** OA контекст не скрывает архитектурные факты. Все данные видны независимо от OA настроек. OA влияет на интерпретацию, не на данные.

### QC-9: MVP остаётся простым

**Критерий:** MVP реализует минимально необходимую архитектуру. Нет «на будущее» компонентов.

**Проверка:** MVP содержит только 8 capabilities. Persistence — базовая (save/load). Knowledge Persistence — Stage 2. Technical Debt Tracking — Stage 3.

### QC-10: Нет циклического владения

**Критерий:** В Ownership Matrix нет циклов. Владение направлено acyclic.

**Проверка:** Граф владения (кто владеет чем) — DAG. Нет домена A, владеющего данными домена B, который владеет данными домена A.

### QC-11: Нет изоляции capabilities

**Критерий:** Capabilities взаимодействуют через Model. Нет прямых связей между анализаторами.

**Проверка:** Security Analysis не общается с Dependency Analysis напрямую. Все взаимодействия идут через Model. Если capability A нуждается в данных capability B — он читает их из Model.

### QC-12: Нет технологической привязки на концептуальном уровне

**Критерий:** Концептуальная архитектура не зависит от конкретных технологий.

**Проверка:** Документ Architecture Foundation не содержит ссылок на конкретные базы данных, фреймворки или библиотеки. Implementation Layer может выбрать любую технологию.

## 21. Open Questions

Открытые вопросы, разделённые по категориям. Вопросы отмечают области, требующие уточнения на соответствующих уровнях.

### 21.1 Product Questions

Вопросы о Product Layer, требующие уточнения:

1. **PQ-1: Гранулярность Model.** Какой уровень детализации компонента является минимально достаточным для MVP? Файл? Класс? Функция? Product Layer определяет «component», но не конкретизирует.

2. **PQ-2: Конфликты OA контекста.** Как разрешать конфликты между разными OA-стандартами (например, стандарт безопасности требует шифрование, а стандарт производительности запрещает его из-за overhead)?

3. **PQ-3: Порог для Knowledge.** Когда интерпретация становится «знанием»? Мгновенно после анализа или после верификации пользователем?

4. **PQ-4: Обновление Model.** Может ли пользователь вручную корректировать Model (добавлять компоненты, связи), или Model — только результат Discovery?

5. **PQ-5: Мультипроектная граница.** В каком Stage начинается поддержка мультипроектного анализа? Stage 3 или позже?

### 21.2 Architecture Questions

Архитектурные решения, отложенные до фазы реализации:

1. **AQ-1: Формат хранения Model.** Graph database? Relational? Document store? Решение — для Implementation Layer.

2. **AQ-2: Механизм привязки аннотаций.** Как именно аннотации анализа привязываются к элементам Model? Встроенные поля? Отдельная таблица? Решение — для Implementation Layer.

3. **AQ-3: Гранулярность персистентности MVP.** Полное сохранение Model или инкрементальное? Решение — для Architecture Layer при проектировании MVP.

4. **AQ-4: API границы capabilities.** REST? GraphQL? Внутрипроцессные вызовы? Решение — для Implementation Layer.

5. **AQ-5: Стратегия кэширования.** Как кэшировать данные Model для Visualization и Reports? Решение — для Implementation Layer.

### 21.3 UX Questions

Решения о пользовательском опыте:

1. **UXQ-1: Уровень интерактивности Visualization в MVP.** Статические изображения? Интерактивный граф с навигацией? Решение — Architecture Layer определяет границу (раздел 15.2, Стабилизация 1).

2. **UXQ-2: Формат отчётов в MVP.** PDF? Markdown? HTML? Интерактивный дашборд? Решение — для UX Layer.

3. **UXQ-3: Представление неопределённости.** Как визуально отображать уровень неопределённости компонента? Цвет? Иконка? Текстовая пометка? Решение — для UX Layer.

4. **UXQ-4: Процесс ввода OA контекста.** Форма? Файл конфигурации? Интерактивный диалог? Решение — для UX Layer.

### 21.4 Implementation Questions

Выбор технологий — все отложены:

1. **IQ-1: Выбор базы данных для Model.** Решение — для Implementation Layer.

2. **IQ-2: Выбор AI провайдера.** OpenAI? Anthropic? Local model? Решение — для Implementation Layer.

3. **IQ-3: Фреймворк для Visualization.** D3.js? React Flow? Другой? Решение — для Implementation Layer.

4. **IQ-4: Стратегия парсинга для Discovery.** AST-based? Regex? Plugin-based? Решение — для Implementation Layer.

5. **IQ-5: Язык реализации.** TypeScript? Python? Решение — для Implementation Layer.

### 21.5 Future Decisions

Решения для последующих стадий:

1. **FD-1: Multi-user collaboration.** Как обрабатывать параллельный доступ к Model? Оптимистичные блокировки? Pessimistic? Решение — Stage 3+.

2. **FD-2: Cross-project analysis.** Как объединять модели нескольких проектов? Общая Model? Отдельные Models с маппингом? Решение — Stage 3+.

3. **FD-3: Plugin architecture для анализаторов.** Нужна ли возможность подключать сторонние анализаторы? Решение — Stage 3+.

4. **FD-4: Knowledge sharing между проектами.** Может ли Knowledge одного проекта использоваться в другом? Решение — Stage 3+.

5. **FD-5: Automation pipeline.** Нужна ли автоматизация (CI/CD integration, scheduled analysis)? Решение — Stage 3+.
