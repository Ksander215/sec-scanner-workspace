## 2. Overview

The Architecture Compliance & Governance Engine is the runtime enforcement layer that operationalizes the principles defined in the AIS Constitution (PHI-001.000), the Value Creation Model (PHI-002.000), the Constraint Optimization Model (PHI-003.000), and the Company Playbook (PHI-004.000) through the governance framework established in GOV-008.000.

Without the Compliance Engine, governance is aspirational — principles exist as documentation but are not systematically enforced. With the Compliance Engine, every architectural decision, code change, runtime interaction, and API call is validated against a formalized rule registry of 40 rules across 10 categories. The engine produces quantifiable compliance scores, emits structured violation events, and provides a dashboard API for real-time governance visibility.

The Compliance Engine is the mechanism through which the Constitution becomes operational.

### 2.1 Mandate

- Every Runtime interaction must pass through at least one compliance validator before execution.
- Violations are classified by severity (Critical, High, Medium, Low, Info) and enforcement level (Blocking, Advisory, Informational).
- Blocking violations prevent the action from proceeding; Advisory violations emit warnings but allow execution.
- The engine operates as an event-driven middleware layer — it never directly modifies Runtime behavior, only observes and governs.
- All compliance state is queryable through the `IComplianceRuntime` public API.

### 2.2 Design Principles

1. **Non-Invasive** — The Compliance Engine observes and validates; it never mutates Runtime state or intercept return values. Runtimes are unaware of the engine's presence.
2. **Rule-Driven** — All governance logic is expressed as declarative rules in the Rule Registry. Validators execute rules; they do not contain embedded policy.
3. **Event-Sourced** — Every validation result is emitted as a domain event. Downstream consumers (dashboards, alerting, audit trails) react to events.
4. **Composable** — Validators are composed into pipelines. Each subsystem can register its own validator chain. New rule categories can be added without modifying existing validators.
5. **Traceable** — Every violation links back to the source document (PHI-001.000 §6, GOV-008.000 §3, etc.) and the specific principle or governance rule that was violated.

### 3.2 Subsystem Responsibilities

The Compliance Engine comprises **15 subsystems**, each with a single responsibility:

1. **Rule Registry** — Stores and retrieves the canonical set of 40 rules. Supports rule lookup by ID, category, severity, and enforcement level.
2. **Rule Evaluator** — Evaluates a single rule against a compliance context, producing a `RuleEvaluationResult` (pass/fail/skip with evidence).
3. **Architecture Validator** — Validates module boundaries, dependency direction constraints, and architectural layer invariants.
4. **Runtime Validator** — Validates that Runtime implementations satisfy the `RuntimeGovernanceContract` (GOV-008.000 §5.2).
5. **Capability Validator** — Validates Capability Packs against constitutionality requirements (GOV-008.000 §11.1).
6. **Documentation Validator** — Validates documentation completeness, currency, and cross-reference integrity.
7. **Traceability Validator** — Validates that every decision is traceable to a source principle and evidence chain.
8. **Validation Validator** — Validates input/output contracts, type safety, and interface conformance.
9. **Constraint Validator** — Validates that constraint-first analysis (PHI-UC-001) has been performed before optimization actions.
10. **Privacy Validator** — Validates that privacy levels (PHI-CV-005, PHI-UC-006) are correctly enforced across all data flows.
11. **Security Validator** — Validates security boundaries, access control, and data handling policies.
12. **Quality Validator** — Validates code quality, design simplicity (PHI-CV-003, PHI-UC-010), and maintainability metrics.
13. **Score Calculator** — Computes weighted compliance scores from aggregated rule evaluation results.
14. **Event Bus** — Publishes compliance events (violations, score changes, threshold breaches) to downstream consumers.
15. **Metrics** — Accumulates counters and gauges for compliance monitoring: rules evaluated, violations by category, score trends.

### 5.2 Rule ID Naming Convention

All rule IDs follow the pattern:

```
{CATEGORY_PREFIX}-{THREE_DIGIT_SEQUENCE}
```

Examples: `ARCH-001`, `RUN-003`, `PRIV-002`, `QUAL-003`

Rule IDs are globally unique and immutable. Once a rule ID is assigned, it is never reused even if the rule is deprecated.

### 5.3 Severity Levels

| Severity | Description | Default Action |
|---|---|---|
| **Critical** | Violates a Blocking principle (PHI-001.000). System integrity at risk. | Immediate block + alert + event |
| **High** | Significant deviation from governance framework. Action required within current sprint. | Block + event + warning |
| **Medium** | Moderate deviation. Requires documentation of justification if not remediated. | Advisory + event |
| **Low** | Minor deviation. Tracked for trend analysis. | Informational + event |
| **Info** | Informational observation. No violation; recorded for audit trail. | Event only |

### 5.4 Enforcement Levels

| Level | Behavior |
|---|---|
| **Blocking** | The action is prevented from proceeding. The caller receives a `ComplianceViolationError` with the rule ID, evidence, and remediation guidance. |
| **Advisory** | A warning is emitted. The action proceeds, but the violation is recorded. Repeated advisory violations without justification trigger a governance review. |
| **Informational** | The observation is recorded. No action is taken. Used for trend analysis and audit trails. |

## 7. Event Types

The Compliance Engine emits **11 domain event types** through the `ComplianceEventBus`. All events are immutable value objects.

| # | Event Name | Interface | Description |
|---|---|---|---|
| 1 | `RuleEvaluated` | `RuleEvaluatedEvent` | A single rule was evaluated; includes rule ID, result (pass/fail/skip), evidence, and context |
| 2 | `ViolationDetected` | `ViolationDetectedEvent` | A rule evaluation resulted in a failure; includes rule ID, severity, enforcement level, and remediation guidance |
| 3 | `ViolationBlocked` | `ViolationBlockedEvent` | A Blocking violation prevented an action from proceeding; includes the blocked action and rule references |
| 4 | `ScoreCalculated` | `ScoreCalculatedEvent` | A compliance score was computed; includes overall score, category scores, and evaluation window |
| 5 | `ThresholdBreached` | `ThresholdBreachedEvent` | A compliance score fell below a configured threshold; includes threshold value and current score |
| 6 | `GovernanceReviewTriggered` | `GovernanceReviewTriggeredEvent` | Repeated advisory violations triggered a governance review; includes violation history |
| 7 | `RuleRegistered` | `RuleRegisteredEvent` | A new rule was added to the registry |
| 8 | `RuleDeprecated` | `RuleDeprecatedEvent` | A rule was deprecated (no longer enforced but retained for history) |
| 9 | `ValidatorPipelineExecuted` | `ValidatorPipelineExecutedEvent` | A validator pipeline completed execution; includes pipeline ID and aggregate results |
| 10 | `ComplianceSnapshotGenerated` | `ComplianceSnapshotGeneratedEvent` | A point-in-time compliance snapshot was generated for reporting |
| 11 | `ConfigurationChanged` | `ConfigurationChangedEvent` | Compliance engine configuration was modified; includes previous and new values |

### 7.1 Event Discriminated Union

All events are united under the `ComplianceEvent` discriminated union:


## 8. Configuration

### 8.1 DefaultComplianceRuntimeConfig Structure

```typescript
interface ComplianceRuntimeConfig {
  /** Enable/disable the compliance engine entirely */
  enabled: boolean;

  /** Event bus configuration */
  eventBus: {
    maxListeners: number;
    enableEventLogging: boolean;
  };

  /** Scoring configuration */
  scoring: {
    /** Weight per category (must sum to 1.0) */
    categoryWeights: Record<RuleCategory, number>;
    /** Thresholds for score-based alerts */
    thresholds: {
      critical: number;  // Default: 0.50
      warning: number;   // Default: 0.75
      healthy: number;   // Default: 0.90
    };
    /** Scoring window (number of evaluations) */
    windowSize: number;  // Default: 100
  };

  /** Validator configuration */
  validators: {
    /** Enable/disable individual validators */
    enabledValidators: RuleCategory[];
    /** Maximum concurrent validator pipelines */
    maxConcurrentPipelines: number;  // Default: 4
    /** Timeout per validation in milliseconds */
    validationTimeoutMs: number;  // Default: 5000
  };

  /** Metrics configuration */
  metrics: {
    /** Enable metrics collection */
    enabled: boolean;  // Default: true
    /** Metrics aggregation interval in milliseconds */
    aggregationIntervalMs: number;  // Default: 60000
  };
}
```

## 9. Public API (Dashboard)

The Compliance Engine exposes its capabilities through the `IComplianceRuntime` interface. This is the public contract for dashboard consumers, monitoring systems, and integration points.

```typescript
interface IComplianceRuntime {
  // --- Lifecycle ---

  /** Initialize the compliance engine with optional config overrides */
  initialize(config?: Partial<ComplianceRuntimeConfig>): Promise<void>;

  /** Shut down the compliance engine gracefully */
  shutdown(): Promise<void>;

  // --- Validation ---

  /** Validate a context against a specific rule */
  evaluateRule(ruleId: string, context: RuleContext): Promise<RuleEvaluationResult>;

  /** Validate a context against all rules in a category */
  evaluateCategory(category: RuleCategory, context: RuleContext): Promise<RuleEvaluationResult[]>;

  /** Validate a context against all enabled validators (full pipeline) */
  evaluateAll(context: RuleContext): Promise<ComplianceReport>;

  // --- Scoring ---

  /** Get the current overall compliance score */
  getCurrentScore(): ComplianceScore;

  /** Get compliance scores broken down by category */
  getCategoryScores(): Record<RuleCategory, number>;

  /** Get a compliance snapshot for reporting */
  getSnapshot(): ComplianceSnapshot;

  // --- Rule Registry ---

  /** Get a rule by ID */
  getRule(ruleId: string): ComplianceRule | undefined;

  /** Get all rules in a category */
  getRulesByCategory(category: RuleCategory): ComplianceRule[];

  /** Get all registered rules */
  getAllRules(): ComplianceRule[];

  // --- Violations ---

  /** Get recent violations, optionally filtered by category and severity */
  getViolations(filter?: {
    category?: RuleCategory;
    severity?: RuleSeverity;
    since?: Date;
    limit?: number;
  }): ComplianceViolation[];

  /** Get violation count by category */
  getViolationCounts(): Record<RuleCategory, number>;

  // --- Events ---

  /** Subscribe to compliance events */
  on<T extends ComplianceEvent['type']>(
    eventType: T,
    handler: (event: Extract<ComplianceEvent, { type: T }>) => void
  ): () => void;  // Returns unsubscribe function

  // --- Health ---

  /** Get engine health status */
  getHealth(): {
    status: 'healthy' | 'degraded' | 'unhealthy';
    lastEvaluationTime: Date | null;
    totalEvaluations: number;
    activeValidators: number;
  };
}
```

## 10. Integration Points

The Compliance Engine connects to other platform Runtimes through event-driven, non-invasive integration points. It never imports Runtime code directly; instead, it observes events published by Runtimes and evaluates compliance.

### 10.1 Integration Matrix

| Integration Target | Direction | Mechanism | Description |
|---|---|---|---|
| **Platform Runtime** | Bidirectional | Event subscription + health reporting | Subscribes to platform lifecycle events; reports compliance health to platform's health registry. The Platform Runtime provides `publishEvent`, `getConfiguration`, and `getHealth` via `PlatformRuntimeContract`. |
| **Personal Runtime** | Inbound (observes) | Event subscription | Subscribes to personal intelligence events to validate constraint detection compliance (GOV-008.000 §7). Monitors that constraint observations include evidence and respect user autonomy (PHI-CV-010). |
| **Cognitive Runtime** | Inbound (observes) | Event subscription | Subscribes to recommendation events to validate the 7-step recommendation chain (GOV-008.000 §6.1). Validates that every recommendation includes confidence, reasoning, value articulation, and constraint reference (GOV-008.000 §6.2). |
| **Workflow Runtime** | Inbound (observes) | Event subscription | Subscribes to workflow execution events to validate that automation respects user autonomy and does not bypass human judgment (PHI-UC-009). |
| **AI Provider Runtime** | Inbound (observes) | Event subscription + privacy contract | Subscribes to AI provider execution events to validate privacy level enforcement (PRIV-001, PRIV-002, PRIV-003) and security boundary compliance (SEC-001 through SEC-004). Uses `PrivacyLevel` from AI-PR types. |
| **Event Hub** | Outbound (publishes) | Event publication | Publishes all 11 compliance event types to the platform Event Hub for consumption by dashboards, alerting systems, and audit trails. |
| **Metrics** | Outbound (publishes) | Metrics facade | Exposes compliance counters and gauges through the platform metrics system: rules evaluated/sec, violations by category, score trend, validator latency. |
| **Trace** | Bidirectional | Trace correlation | Correlates compliance violations with distributed traces. Each violation includes a `traceId` linking it to the execution trace in the AI Provider Runtime's `TraceRuntime`. Enables root-cause analysis of violations. |

### 10.3 Integration Contracts

The Compliance Engine defines the following integration contracts for Runtime consumers:

```typescript
interface ComplianceRuntimeContract {
  /** Evaluate compliance for a given context */
  evaluate(context: RuleContext): Promise<ComplianceReport>;

  /** Get current compliance score */
  getScore(): ComplianceScore;
```
