# AIS — Capability Map

Единая карта возможностей платформы. Отвечает на вопрос «Что умеет платформа?», а не «Как это реализовано?».

---

## 1. Capability Tree

```
Platform
├── Project Discovery
├── Architecture Modeling
├── Security Analysis
├── Dependency Analysis
├── Change Impact Assessment
├── Knowledge Persistence
├── Technical Debt Tracking
├── AI Assistance
├── Report Generation

```

## 2. Capability Description

### 2.1 Project Discovery

**Назначение:** Автоматическое обнаружение и первичное понимание структуры подключаемого проекта без ручной настройки.

**Какую проблему решает:** Подключение нового проекта к аналитической платформе обычно требует ручного описания архитектуры, конфигурации правил и указания точек входа. Это создаёт барьер внедрения и задерживает получение первой ценности. Команды теряют время на настройку вместо того, чтобы сразу получать результаты анализа.

**Кто использует:** Developer, Tech Lead, Architect.

**Результат:** Пользователь подключает проект (указывая репозиторий), платформа автоматически определяет его тип, структуру, основные компоненты и точки входа. Первичная архитектурная модель доступна без ручного вмешательства.

---

### 2.2 Architecture Modeling

**Назначение:** Построение и поддержание целостной архитектурной модели проекта — графа компонентов, их связей, слоёв и границ.

**Какую проблему решает:** Архитектура существует в головах людей и теряется с их уходом. Формальная документация устаревает. Ни один инструмент не даёт связанной картины: что из чего состоит, как компоненты взаимодействуют, где границы ответственности. Без модели все последующие анализы проводятся вслепую.

**Кто использует:** Developer, Tech Lead, Architect, CTO.

**Результат:** Пользователь получает интерактивную архитектурную модель проекта, которая отражает компоненты, их взаимосвязи и слоёвую структуру. Модель обновляется при изменениях проекта и доступна для навигации и запросов.

---

### 2.3 Security Analysis

**Назначение:** Систематическое выявление уязвимостей и оценка рисков безопасности с привязкой к архитектурной модели проекта.

**Какую проблему решает:** Инструменты сканирования безопасности генерируют списки уязвимостей без привязки к архитектуре. Сервисный инженер видит «уязвимость в компоненте X», но не понимает, какие данные под угрозой и через какие пути атакующий может до них добраться. Без архитектурного контекста приоритизация уязвимостей невозможна.

**Кто использует:** Developer, Security Engineer, Tech Lead, CTO.

**Результат:** Пользователь получает результаты сканирования безопасности, привязанные к компонентам архитектурной модели. Уязвимости связаны с зависимостями, позиционированием в архитектуре и историей изменений. Видны цепочки атак — пути от возможной точки входа к критическим активам.

---

### 2.4 Dependency Analysis

**Назначение:** Построение полного графа зависимостей проекта и выявление проблемных паттернов — циклических, избыточных и рискованных связей.

**Какую проблему решает:** С ростом проекта карта зависимостей становится непостижимой для человека. Циклические зависимости создают непредсказуемое поведение при изменениях. Избыточные зависимости увеличивают поверхность атаки. Рискованные зависимости (устаревшие, небезопасные) создают скрытые угрозы. Без полного графа зависимостей каждое изменение — это лотерея.

**Кто использует:** Developer, Tech Lead, Architect.

**Результат:** Пользователь получает полный граф зависимостей проекта с выделением проблемных зон. Видны циклы, избыточные связи, устаревшие зависимости. Каждая проблема привязана к конкретному компоненту архитектуры.

---

### 2.5 Change Impact Assessment

**Назначение:** Оценка последствий планируемых изменений до их применения — какие компоненты затронуты, какие риски возникают, что может регрессировать.

**Какую проблему решает:** Разработчик не может предсказать все последствия изменения в сложной системе. Локально правильное решение может нарушить работу удалённого компонента через непредвиденную зависимость. Это ведёт к регрессиям, которые обнаруживаются в продакшене, когда исправление стоит на порядок дороже предотвращения.

**Кто использует:** Developer, Tech Lead, Architect.

**Результат:** Перед внесением изменения пользователь видит список затронутых компонентов, оценку рисков и возможные регрессии. Это информационная оценка, а не запрет — решение остаётся за пользователем.

---

### 2.6 Knowledge Persistence

**Назначение:** Сохранение и накопление знаний о проекте — архитектурных решений, причин изменений, контекста проблем — с возможностью обращения к любому предыдущему состоянию.

**Какую проблему решает:** Знания о проекте существуют только в головах людей и теряются при их уходе. Архитектурные решения принимаются, но причины не фиксируются. Через полгода никто не помнит, почему модуль X устроен именно так. Новые участники тратят месяцы на воссоздание контекста, который уже существовал.

**Кто использует:** Developer, Tech Lead, Architect, CTO.

**Результат:** Пользователь может обратиться к истории состояний архитектурной модели, сравнить текущее состояние с любым предыдущим и понять эволюцию проекта. Знания сохраняются между сессиями и доступны всей команде.

---

### 2.7 Technical Debt Tracking

**Назначение:** Отслеживание накопления технического долга с привязкой к конкретным компонентам архитектуры и приоритизацией по влиянию на систему.

**Какую проблему решает:** Технический долг растёт незаметно до тех пор, пока не становится критическим. Никто не знает точный объём долга, его распределение по компонентам и влияние на способность развиваться. Рефакторинг планируется интуитивно, а не на основе данных.

**Кто использует:** Tech Lead, Architect, CTO.

**Результат:** Пользователь видит карту технического долга проекта, привязанную к компонентам архитектуры. Долг приоритизирован по влиянию на систему. Связан с конкретными архитектурными решениями и историей изменений.

---

### 2.8 AI Assistance

**Назначение:** Ответы на вопросы о проекте в естественной форме с привязкой к архитектурной модели. Объяснимые рекомендации по обнаруженным проблемам.

**Какую проблему решает:** Получить ответ на вопрос «какие компоненты затронет изменение модуля X» требует ручного трассирования зависимостей. Вопрос «почему эта зависимость существует» может потребовать heures git history. Общий AI-ассистент не знает контекста конкретного проекта и даёт общие ответы. Платформа отвечает на основе реальной модели проекта.

**Кто использует:** Developer, Tech Lead, Architect, Security Engineer.

**Результат:** Пользователь задаёт вопросы о проекте в естественной форме и получает ответы, основанные на архитектурной модели. Каждая рекомендация содержит объяснение: что обнаружено, почему это проблема, что можно сделать. Рекомендации не содержат общих шаблонов — они привязаны к конкретному контексту проекта.

---

### 2.9 Report Generation

**Назначение:** Автоматическая генерация отчётов о состоянии проекта в нескольких форматах для различных аудиторий.

**Какую проблему решает:** Подготовка отчётов о состоянии проекта (для руководства, для аудита, для команды) требует ручного сбора данных из нескольких источников. Процесс трудоёмок, результаты быстро устаревают, а разные отчёты могут противоречить друг другу, поскольку основаны на разных срезах данных.

**Кто использует:** Developer, Tech Lead, Architect, Security Engineer, CTO.

**Результат:** Пользователь получает отчёты, сгенерированные на основе единой архитектурной модели. Отчёты адаптированы к аудитории: от детальных технических отчётов для инженеров до высокоуровневых сводок для руководства.

---

### 2.10 Visualization

**Назначение:** Интерактивная визуализация архитектурной модели, зависимостей, цепочек атак и эволюции проекта.

**Какую проблему решает:** Понять архитектуру проекта по текстовому описанию или списку компонентов невозможно. Человек воспринимает визуальную информацию значительно эффективнее текстовой. Без визуализации архитектурная модель остаётся абстракцией, недоступной для быстрого понимания.

**Кто использует:** Developer, Tech Lead, Architect, Security Engineer, CTO.

**Результат:** Пользователь получает интерактивную визуализацию архитектуры, зависимостей и результатов анализа. Навигация по графу от высокого уровня к деталям. Возможность фильтрации и выделения специфических аспектов (только зависимости, только безопасность, только эволюция).

---

### 2.11 Organization Adaptation

**Назначение:** Настройка платформы на контекст конкретной организации — приоритеты безопасности, стандарты кодирования, архитектурные принципы, допустимые компромиссы.

**Какую проблему решает:** Универсальные правила анализа не учитывают реальный контекст организации. То, что является критическим нарушением для банка, может быть допустимым компромиссом для стартапа. Без адаптации платформа генерирует шум — рекомендации, которые команда игнорирует, потому что они не применимы к её ситуации.

**Кто использует:** Architect, Tech Lead, CTO.

**Результат:** Пользователь настраивает платформу под стандарты и приоритеты своей организации. Результаты анализа и рекомендации адаптируются к этому контексту. Платформа учитывает осознанные компромиссы команды и не выдаёт рекомендации, противоречащие им без явного указания причины.

## 3. Capability Relationships

```
Project Discovery
      ↓
Architecture Modeling ←──────┐
      ↓                      │
      ├──→ Security Analysis  │
      ├──→ Dependency Analysis│
      └──→ Visualization     │
                             │
Knowledge Persistence ←─────┘
      ↓
Change Impact Assessment
      ↓
Technical Debt Tracking
      ↓
AI Assistance
      ↓
Report Generation

Organization Adaptation ───→ (влияет на все аналитические возможности)
```

**Логические зависимости:**

- **Project Discovery → Architecture Modeling.** Невозможно построить архитектурную модель без первичного понимания структуры проекта. Обнаружение компонентов и их связей — prerequisite для моделирования.

- **Architecture Modeling → Security Analysis.** Результаты сканирования безопасности получают смысл только будучи привязанными к архитектурной модели. Без модели уязвимость — строка в отчёте; с моделью — понимание риска.

- **Architecture Modeling → Dependency Analysis.** Граф зависимостей строится поверх архитектурной модели. Зависимости между компонентами имеют смысл только в контексте архитектурных границ.

- **Architecture Modeling → Visualization.** Визуализация отображает архитектурную модель. Без модели нечего визуализировать.

- **Architecture Modeling → Knowledge Persistence.** Knowledge Persistence хранит состояния архитектурной модели. Без модели нечего сохранять.

- **Knowledge Persistence → Change Impact Assessment.** Оценка влияния изменений опирается на накопленную историю состояний модели. Без истории оценка ограничена текущим срезом.

- **Change Impact Assessment → Technical Debt Tracking.** Технический долг отслеживается через накопление изменений и их последствий. Без оценки влияния невозможно определить, какие изменения создали долг.

- **Technical Debt Tracking → AI Assistance.** AI-ассистент использует данные о техническом долге для формирования рекомендаций. Без этих данных рекомендации лишены контекста.

- **AI Assistance → Report Generation.** Отчёты включают рекомендации и объяснения, которые формирует AI-ассистент.

- **Organization Adaptation → все аналитические возможности.** Контекст организации влияет на то, как Security Analysis, Dependency Analysis, Technical Debt Tracking и AI Assistance интерпретируют результаты и формируют рекомендации.

## 5. MVP Capabilities

### MVP

Возможности, обязательные для первой версии. Они обеспечивают полный цикл: от подключения проекта до получения объяснимых рекомендаций.

| Capability | Обоснование включения в MVP |
|---|---|
| Project Discovery | Без неё невозможно начать работу с платформой |
| Architecture Modeling | Основа всех последующих анализов |
| Security Analysis | Ключевая ценность для целевой аудитории |
| Dependency Analysis | Неотделима от архитектурного понимания |
| AI Assistance | Объяснимые рекомендации — ключевое отличие от конкурентов |
| Report Generation | Минимальный формат доставки результатов |
| Visualization | Без визуализации архитектурная модель недоступна для восприятия |
| Organization Adaptation | Без адаптации платформа генерирует нерелевантные рекомендации |

### Post-MVP

Возможности, которые появятся после стабилизации MVP. Они усиливают ценность, но не являются критическими для первого запуска.

| Capability | Обоснование отложения |
|---|---|
| Knowledge Persistence | Требует стабильной архитектурной модели и достаточного объёма истории изменений. В MVP модель строится, но полный цикл сохранения и сравнения состояний — следующая ступень |
| Technical Debt Tracking | Требует накопленной истории изменений и стабильной модели. В MVP отдельные проблемы выявляются, но системное отслеживание долга — post-MVP |
| Change Impact Assessment | Требует накопленной истории и устойчивой модели зависимостей. В MVP оценка ограничена текущим срезом |

### Long-term

Направления развития, требующие значительной зрелости платформы.

| Capability | Обоснование |
|---|---|
| Knowledge Persistence (эволюция) | Переход от хранения истории к прогнозированию на её основе |
| Change Impact Assessment (прогнозирование) | Оценка влияния на основе исторических паттернов, а не только текущего среза |
| Technical Debt Tracking (приоритизация) | Автоматическая приоритизация долга на основе влияния на бизнес-критические пути |

## 6. Future Expansion

Направления расширения возможностей платформы без привязки к конкретным технологиям и срокам.

### 6.1 Углублённый AI-анализ

Переход от ответов на вопросы к проактивному анализу. Платформа не ждёт запроса, а самостоятельно выявляет значимые изменения в архитектуре и привлекает к ним внимание. Включает: выявление паттернов деградации на ранних стадиях, сравнение архитектуры с отраслевыми практиками, автоматическое формирование гипотез о причинах проблем.

### 6.2 Корпоративные функции

Расширение для работы в крупных организациях: управление несколькими проектами и их взаимодействиями, роль-based доступ к результатам анализа, соответствие отраслевым стандартам и регуляциям, интеграция с корпоративными системами управления.

### 6.3 Расширение типов анализа

Подключение новых аналитических горизонтов: анализ производительности (определение узких мест через архитектурную модель), анализ доступности (оценка точек отказа и отказоустойчивости), анализ соответствия стандартам (проверка соблюдения архитектурных принципов).

### 6.4 Кооперативное использование

Функции для совместной работы команды: общее пространство архитектурных знаний, обсуждение和建议 в контексте конкретных компонентов, совместное принятие архитектурных решений с фиксацией контекста.

### 6.5 Экосистема интеграций

Интеграция с процессами разработки: обратная связь в процессе ревью кода, встраивание в процесс планирования изменений, связь с системами мониторинга для привязки runtime-поведения к архитектурной модели.
