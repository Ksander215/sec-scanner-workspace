# AIS — Report Generation Specification

Полное продуктовое описание capability Report Generation: как AIS превращает накопленное архитектурное понимание, результаты анализов и рекомендации в артефакты, пригодные для использования за пределами платформы.

---

## 1. Purpose

Report Generation существует для того, чтобы знания, накопленные внутри платформы, могли быть использованы за её пределами. Архитектурная модель, результаты анализов безопасности и зависимостей, рекомендации AI-ассистента, накопленная история изменений — всё это существует внутри AIS и создаёт ценность при взаимодействии пользователя с платформой. Но принятие технических решений происходит не только перед экраном платформы. Решения обсуждаются на встречах, обосновываются перед руководством, передаются новым участникам команды, включаются в планирование спринтов. Во всех этих ситуациях пользователь нуждается в артефакте, который несёт архитектурное понимание вне контекста платформы.

Без Report Generation ценность AIS ограничена моментом непосредственного взаимодействия. Пользователь, который хочет поделиться результатами анализа с командой, вынужден пересказывать их, делать скриншоты или собирать фрагменты вручную. Это разрушает связность знания: объяснимая рекомендация, которая внутри платформы связана с компонентом модели, цепочкой атак и историческим контекстом, превращается в изолированное утверждение. Report Generation сохраняет эту связность при переносе знания за пределы платформы.

Проблема, которую решает Report Generation, формулируется так: подготовка отчётов о состоянии проекта требует ручного сбора данных из нескольких источников, процесс трудоёмок, результаты быстро устаревают, а разные отчёты могут противоречить друг другу, поскольку основаны на разных срезах данных. Report Generation решает эту проблему, создавая отчёты на основе единой архитектурной модели — единого источника истины о проекте. Каждый отчёт отражает согласованное состояние всех аспектов проекта: архитектуры, безопасности, зависимостей, знаний.

Report Generation — это не отдельный инструмент создания документов. Это продолжение архитектурной модели в форме, пригодной для доставки. Отчёт является срезом модели, а не самостоятельным артефактом. Это ключевое отличие: если бы AIS генерировала отчёты из отдельных источников данных, каждый отчёт мог бы противоречить другому. Поскольку все отчёты создаются из единой модели, они по определению согласованы.

---

## 2. Definition

**Report Generation** — capability AIS, которая создаёт структурированные артефакты, отражающие состояние архитектурной модели, результаты анализов и накопленные знания проекта в форме, пригодной для использования за пределами платформы.

Отчёт в контексте AIS — это не документ в общепринятом смысле. Это проекция архитектурной модели на конкретную аудиторию и конкретную цель. Проекция означает, что отчёт не содержит новых данных — он отражает данные модели, отобранные и структурированные для конкретного потребителя. Модель остаётся единственным источником истины; отчёт — её представление в момент создания.

Что делает Report Generation на продуктовом уровне:

- **Выбирает срез модели.** Архитектурная модель содержит все данные о проекте. Отчёт отражает тот срез, который релевантен для конкретной цели и аудитории. Технический отчёт для разработчиков содержит детали компонентов и связей. Сводный отчёт для руководства содержит высокоуровневые метрики и ключевые риски. Один и тот же проект, одна и та же модель — разные проекции.

- **Сохраняет связность.** Результаты анализов внутри платформы связаны через архитектурную модель: уязвимость привязана к компоненту, компонент — к зависимостям, зависимости — к истории изменений. Report Generation сохраняет эту связность в отчёте. Пользователь отчёта видит не изолированные данные, а связанные фрагменты единой картины.

- **Адаптирует к аудитории.** Разные аудитории нуждаются в разной информации и разной глубине. Разработчику нужны детали уязвимостей и конкретные рекомендации. Руководству нужны сводные метрики и оценка рисков. Report Generation адаптирует содержание, глубину и язык отчёта к тому, кто его будет читать.

- **Фиксирует момент времени.** Отчёт отражает состояние модели на момент создания. Это не ограничение, а свойство: каждый отчёт привязан к конкретному состоянию архитектуры, что позволяет сравнивать отчёты между собой и отслеживать эволюцию. Отчёт — это зафиксированный срез живой модели.

- **Обеспечивает самодостаточность.** Отчёт содержит всю информацию, необходимую для понимания без доступа к платформе. Читатель отчёта не должен догадываться, что скрывается за сокращением или термином. Каждый элемент отчёта объяснён в контексте проекта. Это приложение принципа «Explain Before Recommend» (Product Principles, 3.1) к форме доставки.

## 3. Report Types

### 3.1 Architecture Overview Report

**Назначение:** Предоставить целостную картину архитектуры проекта — компоненты, их взаимосвязи, слои и границы.

**Аудитория:** Developer, Tech Lead, Architect.

**Содержание:** Структура архитектурной модели: компоненты и их роли, связи между компонентами, выявленные слои и границы, точки входа. Краткое описание каждого компонента, основанное на данных модели. Области неопределённости, которые платформа не смогла разрешить. Общее резюме архитектурного здоровья проекта.

**Ценность:** Позволяет быстро получить или восстановить понимание архитектуры проекта. Полезен при онбординге новых участников, при передаче проекта между командами, при подготовке к архитектурному ревью.

---

### 3.2 Security Analysis Report

**Назначение:** Предоставить полную картину безопасности проекта в архитектурном контексте.

**Аудитория:** Developer, Security Engineer, Tech Lead.

**Содержание:** Обнаруженные уязвимости с привязкой к компонентам архитектуры. Оценка рисков каждой уязвимости с учётом позиции компонента в архитектуре и его связей. Цепочки атак — пути от возможных точек входа к критическим активам. Рекомендации по устранению с объяснениями. История изменения состояния безопасности (если доступна).

**Ценность:** Позволяет приоритизировать работу по безопасности на основе реального влияния уязвимостей на архитектуру, а не на формальных критериях严重程度. Заменяет разрозненные отчёты различных сканеров единым связным документом.

---

### 3.3 Dependency Analysis Report

**Назначение:** Предоставить полную картину зависимостей проекта с выделением проблемных зон.

**Аудитория:** Developer, Tech Lead, Architect.

**Содержание:** Граф зависимостей проекта. Выделенные проблемные паттерны: циклические зависимости, избыточные связи, устаревшие или рискованные внешние зависимости. Привязка каждой проблемы к конкретным компонентам архитектуры. Оценка влияния проблемных зависимостей на систему в целом. Рекомендации по улучшению.

**Ценность:** Позволяет увидеть полную карту зависимостей и понять, какие из них создают наибольшие риски. Полезен при планировании рефакторинга и при оценке влияния изменений.

---

### 3.4 Executive Summary Report

**Назначение:** Предоставить руководству высокоуровневую картину технического состояния проекта без погружения в технические детали.

**Аудитория:** CTO, Engineering Manager, Tech Lead (для представления руководству).

**Содержание:** Сводные метрики архитектурного здоровья. Ключевые риски с оценкой влияния на бизнес. Тренды эволюции архитектуры (если доступна история). Сравнение с предыдущим отчётом (если доступно). Приоритизированные рекомендации на уровне действий. Объём технического долга и его распределение.

**Ценность:** Позволяет руководству принимать стратегические решения на основе объективных данных о техническом состоянии. Исключает необходимость «переводить» технические данные на язык бизнеса — отчёт уже структурирован для этого.

---

### 3.5 Change Impact Report

**Назначение:** Зафиксировать оценку влияния конкретного изменения или набора изменений на архитектуру проекта.

**Аудитория:** Developer, Tech Lead, Architect.

**Содержание:** Описание оцениваемого изменения. Список затронутых компонентов с указанием характера влияния. Оценка рисков, связанных с изменением. Возможные регрессии. Рекомендации по проверке и тестированию. Сравнение состояния «до» и «после» (если доступно).

**Ценность:** Является артефактом, который можно приложить к pull request, обсудить на code review или использовать при планировании. Фиксирует оценку влияния для последующей верификации.

---

### 3.6 Technical Debt Report

**Назначение:** Предоставить полную картину технического долга проекта с привязкой к компонентам архитектуры.

**Аудитория:** Tech Lead, Architect, CTO.

**Содержание:** Карта технического долга, привязанная к компонентам. Приоритизация долга по влиянию на систему. Связь долгов с конкретными архитектурными решениями и историей изменений. Тренды накопления долга. Рекомендации по приоритизации устранения.

**Ценность:** Обеспечивает объективную основу для планирования рефакторинга. Позволяет обосновать приоритизации перед руководством.

---

## 4. Report Properties

### 4.1 Основан на архитектурной модели

Каждый отчёт создаётся из архитектурной модели проекта. Отчёт не содержит данных, отсутствующих в модели. Если данные в модели неполны, отчёт явно указывает на это. Это приложение принципа «Model Before Analyze» (Product Principles, 3.2) к форме доставки: нельзя создать отчёт о том, что не смоделировано.

Это свойство гарантирует согласованность: поскольку все отчёты создаются из единого источника, два отчёта о разных аспектах одного проекта не могут противоречить друг другу. Уязвимость, указанная в Security Analysis Report, и компонент, указанный в Architecture Overview Report, описывают одну и ту же архитектуру.

### 4.2 Самодостаточен

Отчёт содержит всю информацию, необходимую для понимания без доступа к платформе. Каждый термин, сокращение и показатель объяснён в контексте проекта. Если отчёт ссылается на компонент, он содержит достаточно информации о компоненте для понимания его роли. Если отчёт указывает на уязвимость, он объясняет, почему она является проблемой в контексте данного проекта.

Самодостаточность не означает, что отчёт содержит все данные модели. Она означает, что содержащаяся в отчёте информация понятна без дополнительных источников. Это приложение принципа «Explain Before Recommend» (Product Principles, 3.1).

### 4.3 Привязан к моменту времени

Каждый отчёт фиксирует состояние модели на момент создания. Отчёт содержит указание: когда он был создан, на каком состоянии модели основан и насколько это состояние актуально по отношению к текущему моменту. Если с момента создания отчёта проект существенно изменился, платформа явно указывает на это при просмотре отчёта.

Это свойство позволяет сравнивать отчёты между собой и отслеживать эволюцию. Отчёт — не живой документ, а зафиксированный срез. Это согласуется с принципом «Continuous Understanding» (Product Principles, 3.8): актуальность модели поддерживается обновлением, но исторические срезы сохраняются.

### 4.4 Адаптирован к аудитории

Содержание, глубина и язык отчёта адаптированы к аудитории, для которой он создан. Executive Summary Report не содержит терминов, понятных только инженерам. Technical Debt Report не содержит рекомендаций, применимых только к руководству. Адаптация — это не упрощение, а выбор релевантного среза модели.

Адаптация обеспечивает принцип «Developer First» (Product Principles, 3.10): отчёт создаётся для того, кто его читает, а не для того, кто его генерирует. Каждый тип отчёта проходит проверку на релевантность для заявленной аудитории.

### 4.5 Содержит объяснимые рекомендации

Каждая рекомендация в отчёте следует формату: наблюдение (что обнаружено), анализ (почему это проблема), влияние (на что влияет), рекомендация (что можно сделать). Это приложение принципа «Every Recommendation Has Reason» (Product Principles, 3.5). Рекомендация без объяснения не включается в отчёт.

Объяснимость в отчёте особенно важна, потому что читатель не может задать дополнительный вопрос платформе. В отличие от интерактивного взаимодействия с AI-ассистентом, где пользователь может уточнить, отчёт должен содержать всё необходимое объяснение самостоятельно.

### 4.6 Обозначает границы уверенности

Отчёт явно различает то, что платформа знает уверенно, и то, что является предположением или неполным знанием. Области неопределённости, выявленные при Discovery или в процессе анализа, сохраняются в отчёте с указанием степени уверенности. Это приложение принципа «Transparent Analysis» (Product Principles, 3.9).

Читатель отчёта должен понимать, какие выводы опираются на полные данные, а какие — на неполные. Это предотвращает ложную уверенность и позволяет принять осознанное решение о доверии к конкретному выводу.

## 5. User Journey

### 5.1 Пользователь работает с платформой

Пользователь подключил проект, получил архитектурную модель, провёл анализы, исследовал результаты через визуализацию и AI-ассистента. Накопленное понимание существует внутри платформы и доступно при взаимодействии.

### 5.2 Возникает потребность в артефакте

Пользователю необходимо поделиться результатами с кем-то, кто не имеет доступа к платформе: с коллегой, с руководством, с командой на встрече. Или пользователю необходимо зафиксировать текущее состояние для будущего сравнения. В обоих случаях нужен артефакт, который существует отдельно от платформы.

### 5.3 Пользователь выбирает тип отчёта

Платформа предлагает типы отчётов, релевантные для текущего состояния проекта и аудитории. Пользователь выбирает подходящий тип. Выбор основан на том, для кого предназначен отчёт и какая информация нужна.

### 5.4 Платформа генерирует отчёт

Отчёт создаётся на основе текущего состояния архитектурной модели. Процесс генерации не требует от пользователя дополнительных действий — все данные уже доступны в модели. Пользователь может видеть прогресс генерации.

### 5.5 Пользователь получает отчёт

Отчёт доступен для просмотра, скачивания и передачи. Пользователь может проверить, что отчёт содержит ожидаемую информацию и корректно отражает состояние проекта.

### 5.6 Отчёт используется за пределами платформы

Отчёт передается аудитории, для которой он создан. Читатель получает связную картину состояния проекта без необходимости иметь доступ к платформе. Рекомендации понятны без дополнительных объяснений. Если читатель имеет доступ к платформе, он может использовать отчёт как отправную точку для более глубокого исследования.

## 6. User Value

### 6.1 Developer

**Проблема:** Разработчику необходимо обосновать изменения перед командой или руководством. Он проводит анализ влияния внутри платформы, но при обсуждении вынужден пересказывать результаты устно или собирать фрагменты из разных источников. Картинка, которую он передает, неполна и не связна.

**Как помогает Report Generation:** Разработчик генерирует Change Impact Report или Security Analysis Report, который содержит все необходимые данные в связной форме. Отчёт можно приложить к pull request или отправить коллегам. Рекомендации уже объяснены — не нужно пересказывать контекст.

**Результат:** Обоснование изменений на основе данных, а не пересказа. Экономия времени на подготовку к обсуждениям.

---

### 6.2 Tech Lead

**Проблема:** Tech Lead нуждается в регулярных отчётах о состоянии проекта для команды и руководства. Подготовка таких отчётов вручную занимает время и не всегда объективна. Разные отчёты могут противоречить друг другу, потому что основаны на разных срезах данных.

**Как помогает Report Generation:** Tech Lead генерирует отчёты нужного типа на основе единой модели. Executive Summary Report для руководства, Technical Debt Report для планирования, Architecture Overview Report для новых участников. Все отчёты согласованы, потому что основаны на одной модели.

**Результат:** Объективные, согласованные отчёты для всех аудиторий. Экономия времени на подготовку отчётов. Единая основа для обсуждений.

---

### 6.3 Architect

**Проблема:** Архитектору необходимо фиксировать архитектурные решения и их обоснования. Формальная документация устаревает, а неформальная существует только в обсуждениях. При оценке эволюции архитектуры нет зафиксированных срезов для сравнения.

**Как помогает Report Generation:** Архитектор генерирует Architecture Overview Report на ключевых этапах эволюции проекта. Сравнение отчётов показывает, как архитектура изменялась. Каждый отчёт фиксирует моментальное состояние модели, создавая историю эволюции в форме, пригодной для анализа.

**Результат:** Зафиксированная история архитектурной эволюции. Объективная основа для оценки архитектурных решений.

---

### 6.4 Security Engineer

**Проблема:** Security Engineer должен представлять результаты безопасности команде и руководству. Отчёты различных сканеров не связаны между собой и не привязаны к архитектуре. Приоритизация уязвимостей объясняется отдельно, а не вытекает из единой картины.

**Как помогает Report Generation:** Security Analysis Report объединяет результаты всех сканирований в единый документ с привязкой к архитектуре. Приоритизация обоснована позициями компонентов в архитектуре и цепочками атак. Отчёт самодостаточен — читатель понимает, почему каждая уязвимость имеет указанный приоритет.

**Результат:** Единый, связный отчёт по безопасности вместо набора разрозненных результатов. Обоснованная приоритизация, которую можно представить руководству.

---

### 6.5 CTO

**Проблема:** CTO нуждается в объективной картине технического состояния проектов организации. Сводки от команд разрозненны, форматы различаются, уровни детализации не сопоставимы. Принятие стратегических решений опирается на субъективные оценки.

**Как помогает Report Generation:** Executive Summary Report для каждого проекта создаёт единый формат представления технического состояния. CTO получает сопоставимые отчёты от разных команд, что позволяет сравнивать проекты и принимать решения на основе данных. При многократной генерации отчётов CTO видит тренды.

**Результат:** Объективная, сопоставимая картина технического состояния организации. Основание для стратегических решений.

---

## 7. Relationship with Architecture Model

### 7.1 Отчёт — это проекция модели

Архитектурная модель является единственным источником данных для отчёта (Architecture Model Specification). Отчёт не создаёт новых данных и не добавляет собственную интерпретацию. Он выбирает, структурирует и форматирует данные модели для конкретной аудитории и цели. Если в модели нет данных о каком-то аспекте проекта, отчёт не может его содержать.

Это отношение аналогично отношению чертежа и здания. Чертёж (отчёт) отражает здание (модель) с определённой точки зрения и в определённом масштабе. Разные чертежи одного здания не противоречат друг другу, потому что отражают одно и то же здание. Так же и разные отчёты одного проекта не противоречат друг другу, потому что отражают одну и ту же модель.

### 7.2 Качество отчёта определяется качеством модели

Report Generation не может компенсировать неполноту или неточность модели. Если архитектурная модель неполна, отчёт будет неполным. Если данные модели устарели, отчёт будет отражать устаревшее состояние. Это не ограничение Report Generation, а свойство: отчёт честно отражает то, что знает модель.

Это означает, что инвестиции в качество модели (более глубокий Discovery, более точный анализ) напрямую улучшают качество отчётов. Report Generation усиливает ценность качественной модели, создавая дополнительные точки её использования.

### 7.3 Отчёт не заменяет модель

Отчёт — это срез модели в определённый момент. Модель продолжает развиваться после создания отчёта. Обратное неверно: отчёт не обновляется при изменении модели. Для получения актуального состояния пользователь создаёт новый отчёт.

Это разделение намеренно. Попытка сделать отчёт «живым» документом, синхронизированным с моделью, создала бы путаницу: читатель не знал бы, какую версию данных он видит. Зафиксированный отчёт с явным указанием момента создания более честен и полезен.

---

## 8. Relationship with Knowledge

### 8.1 Отчёт delivers знания за пределы платформы

Architecture Knowledge Specification определяет знания как понимание «что это означает и что мы знаем об этом». Report Generation является механизмом доставки этого понимания за пределы платформы. Знания, накопленные в модели, становятся доступны тем, кто не взаимодействует с платформой напрямую.

### 8.2 Отчёт сохраняет контекст знаний

Знания о проекте имеют контекст: почему компонент устроен именно так, какое решение привело к текущему состоянию, какие альтернативы рассматривались. Report Generation сохраняет этот контекст в отчёте, а не только сухие данные. Рекомендации содержат причины, проблемы содержат объяснения, решения содержат контекст их принятия.

### 8.3 Исторические отчёты — часть знаний

Серия отчётов, созданных в разные моменты времени, является формой фиксации знаний об эволюции проекта. Это не заменяет Architecture Evolution, но дополняет его: эволюция видна не только через платформу, но и через сравнение зафиксированных отчётов.

---

## 9. Relationship with AI Assistance

### 9.1 AI Assistance создаёт объяснения, Report Generation их доставляет

AI Assistance Specification определяет, что каждая рекомендация содержит объяснение. Report Generation использует эти объяснения как содержимое отчёта. AI-ассистент формулирует объяснение в интерактивном режиме; Report Generation формулирует его для автономного чтения. Формулировки могут отличаться (автономное чтение требует более полного контекста), но суть остаётся той же.

### 9.2 Отчёт не является ответом AI-ассистента

AI-ассистент отвечает на конкретный вопрос пользователя в контексте диалога. Отчёт — это структурированный артефакт, отражающий состояние модели. Отличие принципиальное: диалог с AI-ассистентом подразумевает возможность уточнения, а отчёт должен быть самодостаточным. Отчёт содержит больше контекста, чем типичный ответ AI-ассистента, потому что не предполагает обратной связи.

## 10. Relationship with Other Capabilities

### 10.1 Project Discovery

Результаты Discovery (тип проекта, обнаруженные компоненты, технологический контекст) являются частью архитектурной модели и, следовательно, доступны в отчётах. Architecture Overview Report опирается на данные Discovery для описания структуры проекта.

### 10.2 Security Analysis

Security Analysis Report является прямым представлением результатов Security Analysis в форме отчёта. Уязвимости, цепочки атак и оценки рисков, привязанные к модели, отображаются в отчёте с сохранением связности.

### 10.3 Dependency Analysis

Dependency Analysis Report является прямым представлением результатов Dependency Analysis. Проблемные паттерны зависимостей, привязанные к компонентам модели, отображаются в отчёте.

### 10.4 Change Impact Assessment

Change Impact Report фиксирует результаты оценки влияния изменений. Затронутые компоненты, риски и возможные регрессии, определённые Change Impact Assessment, отображаются в отчёте.

### 10.5 Technical Debt Tracking

Technical Debt Report является прямым представлением результатов Technical Debt Tracking. Карта долга, привязанная к компонентам, отображается в отчёте с приоритизацией.

### 10.6 Architecture Evolution

Исторические отчёты, созданные в разные моменты, позволяют видеть эволюцию проекта. Это не заменяет Architecture Evolution (который отслеживает переходы между состояниями модели), но является дополнительным способом фиксации эволюции.

### 10.7 Organization Adaptation

Настройки организации (приоритеты, стандарты, допустимые компромиссы) влияют на то, какие данные и рекомендации включаются в отчёт и как они интерпретируются. Отчёт для банка и отчёт для стартапа, основанные на одной и той же модели, будут отличаться акцентами и приоритетами.

## 11. What Report Generation Does NOT Do

### 11.1 Не создаёт новые данные

Report Generation не проводит анализ, не сканирует проект и не генерирует новые выводы. Она отражает данные, уже существующие в архитектурной модели. Если данных недостаточно для качественного отчёта, это сигнал о необходимости улучшить модель, а не о необходимости расширить Report Generation.

### 11.2 Не заменяет взаимодействие с платформой

Отчёт — это артефакт для использования за пределами платформы, а не замена интерактивного взаимодействия. Пользователь, который имеет доступ к платформе, получает больше ценности от прямого взаимодействия: навигация по модели, вопросы AI-ассистенту, детальное исследование компонентов. Отчёт является дополнением, а не заменой.

### 11.3 Не обновляется автоматически

Созданный отчёт фиксирует состояние модели на момент создания. Он не обновляется при изменении проекта или модели. Для получения актуального состояния создаётся новый отчёт. Это намеренное решение: автоматическое обновление отчётов создавало бы путаницу относительно того, какая версия данных перед читателем.

### 11.4 Не является инструментом редактирования

Report Generation создаёт отчёты, но не предоставляет средства их редактирования. Пользователь не может модифицировать содержание отчёта внутри платформы. Если пользователю нужна модификация, он может создать новый отчёт с другими параметрами или экспортировать данные для внешнего редактирования.

### 11.5 Не генерирует код

Отчёт может содержать рекомендации, но не содержит генерируемого кода. Это приложение принципа «AI Assists, Not Replaces» (Product Principles, 3.6) и решения D3 (AI никогда не заменяет разработчика) из Product Architecture Decisions. Рекомендации описывают, что можно сделать, но не предоставляют готовый код для копирования.

### 11.6 Не является системой управления документами

Report Generation создаёт отчёты, но не управляет их жизненным циклом: не контролирует версии, не отслеживает распространение, не управляет доступом. Управление документами — это отдельная задача, которая может решаться внешними инструментами.

## 12. Design Principles

### 12.1 Модель — единственный источник истины

Все данные в отчёте берутся из архитектурной модели. Report Generation не имеет собственных данных и не генерирует собственных выводов. Это гарантирует согласованность между отчётами и между отчётами и платформой.

### 12.2 Самодостаточность отчёта

Отчёт должен быть понятен без доступа к платформе. Каждый элемент отчёта содержит достаточно контекста для понимания. Читатель не должен догадываться о терминах, сокращениях или пропущенных связях.

### 12.3 Честность относительно границ знания

Отчёт явно указывает, что известно, а что нет. Области неопределённости не скрываются. Степень уверенности в выводах обозначена. Это создаёт доверие к отчёту и позволяет читателю принять осознанное решение о доверии к конкретным выводам.

### 12.4 Адаптация без искажения

Отчёт адаптируется к аудитории, но не искажает данные. Адаптация означает выбор релевантного среза и подходящего уровня детализации, а не изменение выводов. Один и тот же факт может быть описан разным языком для разных аудиторий, но факт остаётся тем же.

### 12.5 Минимально достаточная глубина

Отчёт содержит достаточно информации для понимания, но не перегружен деталями. Уровень детализации соответствует типу отчёта и аудитории. Избыточная детализация затрудняет восприятие и противоречит принципу «Developer First» (Product Principles, 3.10).

### 12.6 Воспроизводимость

Один и тот же отчёт, созданный из одного и того же состояния модели, даёт один и тот же результат. Воспроизводимость обеспечивает доверие: пользователь может убедиться, что отчёт объективно отражает модель.

## 13. Success Criteria

### 13.1 Отчёт используется для принятия решений

Report Generation считается успешной, если на основе отчёта принято хотя бы одно техническое решение. Это напрямую связано с North Star Metric (Product Success Metrics, раздел 2): осознанные решения, принятые с использованием AIS. Отчёт является формой доставки данных для таких решений.

### 13.2 Отчёт понятен без доступа к платформе

Report Generation считается успешной, если читатель отчёта, не имеющий доступа к платформе, понимает его содержание и может действовать на его основе. Это проверяется на целевых аудиториях каждого типа отчёта.

### 13.3 Отчёты согласованы между собой

Report Generation считается успешной, если два отчёта разного типа, созданные из одного состояния модели, не противоречат друг другу. Это следствие свойства «основан на архитектурной модели» (раздел 4.1).

### 13.4 Отчёт экономит время пользователя

Report Generation считается успешной, если время создания отчёта значительно меньше времени, которое пользователь потратил бы на ручную подготовку аналогичного артефакта. Экономия времени — прямое приложение принципа «Developer First».

### 13.5 Рекомендации в отчёте привели к действию

Связано с первичной метрикой «Доля рекомендаций, приведших к действию» (Product Success Metrics, 3.3). Рекомендации, доставленные через отчёт, должны приводить к действиям с той же частотой, что и рекомендации, доставленные через интерактивное взаимодействие с платформой.

## 14. MVP / Roadmap Boundary

### MVP Must Have

- Architecture Overview Report — базовое представление архитектуры
- Security Analysis Report — результаты безопасности с привязкой к модели
- Dependency Analysis Report — граф зависимостей с проблемными зонами
- Один формат вывода (достаточно для первичной ценности)
- Самодостаточность отчёта (понятен без доступа к платформе)

MVP Must Have обеспечивают минимальный цикл доставки: пользователь получает отчёт, отражающий ключевые результаты анализа, и может использовать его вне платформы.

### MVP Should Have

- Executive Summary Report — высокоуровневая сводка для руководства
- Выбор уровня детализации при генерации
- Указание степени актуальности данных в отчёте

### Post-MVP

- Change Impact Report — фиксация оценки влияния изменений
- Technical Debt Report — карта технического долга
- Сравнение с предыдущим отчётом
- Множественные форматы вывода
- Шаблоны отчётов, настраиваемые организацией

### Long-term

- Автоматическая генерация отчётов по расписанию
- Интеграция с процессами разработки (приложение к pull request)
- Настраиваемые шаблоны для разных типов проектов

Report Generation в MVP фокусируется на базовой доставке результатов. Сравнение отчётов, расширенные типы и автоматизация — последующие этапы, требующие зрелой модели и стабильных анализов.

## 15. Metrics

Report Generation связана со следующими метриками из Product Success Metrics:

**North Star Metric** (раздел 2): Количество осознанных решений, принятых с использованием AIS. Отчёты являются одним из каналов доставки данных для таких решений.

**Доля объяснимых рекомендаций** (раздел 3.2): Все рекомендации в отчётах должны быть объяснимыми. Эта метрика применяется к отчётам в той же мере, как и к интерактивному взаимодействию.

**Доля рекомендаций, приведших к действию** (раздел 3.3): Рекомендации в отчётах должны приводить к действиям. Если доля для отчётов значительно ниже, чем для интерактивного взаимодействия, это сигнал о проблеме доставки.

**Количество сгенерированных отчётов** (раздел 4.3): Вторичная метрика. Показывает частоту использования Report Generation, но не отражает качество. Рост количества отчётов при падении качества — негативный сигнал.

## 16. Architectural Integrity Check

### 16.1 Как Report Generation использует Architecture Model?

Report Generation читает данные из архитектурной модели и форматирует их в виде отчёта. Модель является единственным источником данных. Report Generation не имеет собственного хранилища данных.

### 16.2 Что Report Generation добавляет к модели или Knowledge?

Report Generation не добавляет данные к модели. Она создаёт артефакт (отчёт), который является проекцией модели. Однако исторические отчёты становятся частью знаний организации о проекте: они фиксируют состояния модели в определённые моменты.

### 16.3 Как Report Generation связана с Evolution?

Серия отчётов, созданных в разные моменты, отражает эволюцию проекта. Это не заменяет Architecture Evolution, но дополняет его, предоставляя форму фиксации эволюции, доступную за пределами платформы.

### 16.4 Как Report Generation взаимодействует с другими capabilities?

Report Generation является последним звеном в цепочке создания ценности: анализы создают данные, AI Assistance формулирует объяснения, Report Generation доставляет всё это пользователю в виде артефакта. Report Generation потребляет результаты всех предыдущих capabilities и не влияет на их работу.

### 16.5 Что теряется, если убрать единый контекст?

Без единого контекста архитектурной модели отчёты превращаются в набор разрозненных документов: отчёт по безопасности от одного инструмента, отчёт по зависимостям от другого, архитектурное описание — третьего. Связность теряется, противоречия становятся неизбежными, приоритизация — субъективной.

### 16.6 Усиливает ли Report Generation центральную идею AIS?

Да. Центральная идея AIS — создание и поддержание архитектурного понимания. Report Generation расширяет доступность этого понимания за пределы платформы. Без отчётов понимание заперто внутри платформы; с отчётами оно становится доступным для всех, кто принимает решения о проекте.

## 17. Cross-Document Audit

### 17.1 Product Vision

Report Generation усиливает направление «Объяснимые рекомендации» — рекомендации доставляются в форме, пригодной для использования вне платформы. Также усиливает «Сохранение архитектурных знаний» — отчёты фиксируют знания в переносимой форме. Не противоречит Vision.

### 17.2 Product Principles

- **Explain Before Recommend (3.1):** Соблюдается. Рекомендации в отчётах содержат объяснения.
- **Model Before Analyze (3.2):** Соблюдается. Отчёты создаются из модели.
- **Architecture Over Files (3.3):** Соблюдается. Отчёты оперируют архитектурными понятиями.
- **Knowledge Never Lost (3.4):** Усиливается. Отчёты фиксируют знания.
- **Continuous Understanding (3.8):** Поддерживается. Актуальность отчётов привязана к актуальности модели.

## 20. Verification Checklist

- [ ] Отчёт создаётся из архитектурной модели без дополнительных источников данных
- [ ] Отчёт самодостаточен: понятен без доступа к платформе
- [ ] Отчёт содержит объяснимые рекомендации (наблюдение, анализ, влияние, рекомендация)
- [ ] Отчёт явно указывает области неопределённости
- [ ] Отчёт привязан к моменту создания (указана дата и состояние модели)
- [ ] Разные типы отчётов из одной модели не противоречат друг другу
- [ ] Отчёт адаптирован к заявленной аудитории
- [ ] Отчёт не содержит генерируемого кода
- [ ] Отчёт не содержит автоматических рекомендаций без объяснения
- [ ] Рекомендации в отчёте привели к действию (измеряется метрикой)
- [ ] Отчёт экономит время пользователя по сравнению с ручной подготовкой
- [ ] Генерация отчёта не требует настройки от пользователя
