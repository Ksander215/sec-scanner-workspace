## 1. Purpose

Security Analysis существует для того, чтобы превращать разрозненные сведения о безопасности программной системы в **целостное понимание её реального риска**.

Обычный подход отвечает на вопрос:

> «Какие уязвимости обнаружены?»

AIS должен отвечать на более важный вопрос:

> **«Как устроен риск этой системы, почему он возникает, как связанные с ним компоненты могут быть использованы для атаки, к чему это может привести и насколько это важно для бизнеса?»**

Security Analysis рассматривает безопасность не изолированно от архитектуры, а **в контексте архитектурной модели, зависимостей, изменений, накопленного знания и организационного контекста**.

Цель анализа — не максимизировать количество найденных проблем.

Цель — обеспечить **максимально полезное понимание реального security risk**.

---

# 2. Definition

### Security Analysis

Security Analysis — это способность AIS исследовать состояние безопасности программной системы через её архитектурный контекст и формировать связанное представление:

**Risk → Component → Dependency → Attack Path → Consequence → Business Impact**

Security Analysis объединяет:

* обнаруженные security-проблемы;
* архитектурные компоненты;
* зависимости между компонентами;
* точки входа;
* потенциальные пути эксплуатации;
* связанные риски;
* возможные последствия;
* изменения архитектуры;
* накопленное знание;
* организационный контекст.

Таким образом, отдельная уязвимость рассматривается не как самостоятельный объект, а как **элемент более крупной системы риска**.

---

# 3. What Security Analysis Is NOT

Security Analysis не является:

### 3.1. Простым vulnerability scanner

Список CVE или других findings сам по себе не является достаточным результатом.

### 3.2. Соревнованием по количеству найденных проблем

Количество findings не является показателем качества понимания безопасности.

### 3.3. Отдельным security-продуктом вне AIS

Security Analysis не должен существовать как независимый инструмент, который игнорирует архитектурную модель.

### 3.4. Автоматическим исправлением

AIS может объяснять и рекомендовать, но не должен самостоятельно принимать критические решения об изменении системы.

### 3.5. Гарантией безопасности

Security Analysis не может утверждать, что система полностью безопасна.

### 3.6. Только техническим отчётом

Техническая глубина необходима, но конечная ценность должна быть понятна человеку, принимающему решение.

### 3.7. Только бизнес-оценкой

Business impact без технического доказательства также недостаточен.

# 4. Core Security Model

Security Analysis должен рассматривать безопасность как систему связанных объектов.

Минимальная смысловая цепочка:

**Asset → Entry Point → Component → Dependency → Weakness → Attack Path → Consequence → Business Impact**

Не каждая проблема будет содержать все элементы цепочки.

Но при наличии достаточного контекста AIS должен стремиться устанавливать такие связи.

---

## 4.1. Security Finding

Security Finding — наблюдение или обнаруженная проблема, имеющая отношение к безопасности.

Finding должен рассматриваться в контексте:

* где находится проблема;
* какой компонент затронут;
* откуда он доступен;
* от чего зависит;
* какие другие компоненты зависят от него;
* возможно ли развитие атаки;
* какие последствия возможны.

---

## 4.2. Risk

Risk — не просто наличие технической проблемы.

Risk определяется сочетанием:

* проблемы;
* возможности её эксплуатации;
* архитектурного контекста;
* затронутых активов;
* возможного пути атаки;
* потенциальных последствий;
* бизнес-значимости.

Поэтому:

> **Finding ≠ Risk**

Одна техническая проблема может иметь:

* низкий реальный риск;
* высокий реальный риск;
* неизвестный риск при недостатке контекста.

---

## 4.3. Attack Path

Attack Path — связанная последовательность элементов системы, которая показывает потенциальное развитие атаки.

Например:

**External Entry Point → Public API → Vulnerable Service → Privileged Dependency → Sensitive Asset**

Ценность Attack Path заключается не в визуализации самой цепочки, а в объяснении:

* откуда начинается атака;
* какие компоненты затрагиваются;
* почему связь между ними важна;
* где находится ключевая точка риска;
* к какому результату может привести успешная эксплуатация.

---

## 4.4. Consequence

Consequence описывает технический результат успешной эксплуатации.

Например:

* получение доступа;
* раскрытие данных;
* изменение данных;
* выполнение нежелательных действий;
* компрометация компонента;
* распространение атаки;
* нарушение доступности.

---

## 4.5. Business Impact

Business Impact переводит техническое последствие в значение для организации.

В зависимости от контекста это может быть:

* потеря или раскрытие критичных данных;
* нарушение работы продукта;
* финансовый ущерб;
* нарушение обязательств;
* репутационный ущерб;
* остановка критического процесса;
* компрометация других систем.

Business Impact не должен выдумываться при отсутствии достаточного контекста.

При недостатке информации AIS должен явно обозначать неопределённость.

---

# 5. Security Analysis Dimensions

Security Analysis должен рассматривать минимум следующие измерения.

## 5.1. Exposure

Насколько компонент или ресурс доступен потенциальному атакующему.

## 5.2. Vulnerability

Какая техническая проблема или слабость существует.

## 5.3. Exploitability

Насколько реалистична эксплуатация проблемы с учётом доступного контекста.

## 5.4. Dependency

Какие зависимости усиливают или уменьшают риск.

## 5.5. Attack Propagation

Как потенциальная атака может распространяться через систему.

## 5.6. Critical Assets

Какие важные ресурсы могут быть затронуты.

## 5.7. Consequence

Что произойдёт при успешной эксплуатации.

## 5.8. Business Impact

Как техническое последствие может повлиять на организацию.

## 5.9. Change Context

Как недавние или планируемые изменения влияют на security risk.

## 5.10. Historical Context

Изменялся ли данный риск ранее и как организация на него реагировала.

# 6. Security Analysis Lifecycle

Security Analysis развивается вместе с архитектурным пониманием системы.

### Stage 1 — Security Discovery

Определение доступной информации о security-состоянии системы.

Результат:

> «Что нам известно о безопасности?»

---

### Stage 2 — Contextualization

Привязка security information к архитектурной модели.

Результат:

> «Где именно находится проблема?»

---

### Stage 3 — Relationship Analysis

Определение зависимостей между security-проблемами и компонентами системы.

Результат:

> «С чем связана проблема?»

---

### Stage 4 — Attack Path Analysis

Определение потенциальных путей развития атаки.

Результат:

> «Как проблема может превратиться в атаку?»

---

### Stage 5 — Consequence Analysis

Определение технических последствий.

Результат:

> «Что произойдёт при успешной эксплуатации?»

---

### Stage 6 — Business Risk Interpretation

Связывание технических последствий с бизнес-контекстом.

Результат:

> «Почему это важно для бизнеса?»

---

### Stage 7 — Recommendation

Формирование объяснимых рекомендаций.

Результат:

> «Что имеет смысл сделать и почему?»

---

### Stage 8 — Continuous Re-analysis

Повторный анализ после изменений.

Результат:

> «Что изменилось в security risk и почему?»

---

# 7. Relationship with Architecture Model

Security Analysis **не существует отдельно от Architecture Model**.

Architecture Model отвечает:

> **«Как устроена система?»**

Security Analysis отвечает:

> **«Что эта структура означает с точки зрения безопасности?»**

Модель предоставляет:

* компоненты;
* связи;
* зависимости;
* границы;
* точки взаимодействия;
* контекст.

Security Analysis добавляет:

* security findings;
* риски;
* attack paths;
* последствия;
* security knowledge;
* рекомендации.

Таким образом:

> **Architecture Model = structural context**
> **Security Analysis = security understanding of that context**

Без архитектурного контекста Security Analysis теряет значительную часть своей ценности.

---

# 8. Relationship with Architecture Knowledge

Security Analysis создаёт и обогащает Architecture Knowledge.

Каждый значимый security finding должен по возможности становиться частью накопленного понимания системы.

Например:

**Finding**

→ связан с компонентом

→ компонент является частью критического процесса

→ имеет внешний entry point

→ зависит от другого компонента

→ уже имел похожую проблему

→ предыдущая рекомендация была отклонена

→ текущий риск отличается от исторического

Это превращает единичное security-событие в **накопленное знание о безопасности архитектуры**.

Security Knowledge должно сохранять не только:

> «Проблема была обнаружена»

но и:

> «Почему она важна, как она связана с системой и какое решение было принято».

---

# 9. Relationship with Architecture Evolution

Security risk не является статическим.

Изменение архитектуры может:

* устранить риск;
* создать новый риск;
* изменить вероятность эксплуатации;
* изменить attack path;
* открыть новый entry point;
* изменить criticality компонента;
* расширить последствия существующей проблемы.

Поэтому Security Analysis должен учитывать Evolution.

Для одного и того же finding необходимо уметь понимать:

**Before → Change → After**

и отвечать:

> «Как изменение системы повлияло на security risk?»

---

# 10. Relationship with Change Impact Assessment

Change Impact Assessment отвечает:

> «Что изменится, если мы внесём изменение?»

Security Analysis добавляет security dimension:

> **«Какие security consequences может вызвать это изменение?»**

Например:

изменение компонента

→ новые зависимости

→ новый external exposure

→ изменение attack path

→ увеличение criticality

→ изменение business impact.

Таким образом, Security Analysis и Change Impact Assessment должны усиливать друг друга, а не существовать как два независимых инструмента.

---

# 11. Security Analysis Output

Основной результат должен представлять **единую картину риска**, а не набор несвязанных списков.

Минимальные смысловые уровни:

### Level 1 — Executive View

Для руководителя бизнеса:

* наиболее существенные риски;
* потенциальные последствия;
* затронутые критические области;
* приоритет;
* степень уверенности;
* что требует решения.

Главный вопрос:

> **«Что может серьёзно повлиять на бизнес?»**

---

### Level 2 — Risk View

Для руководителей технических направлений:

* risk;
* affected components;
* exposure;
* dependencies;
* attack paths;
* consequences;
* business impact;
* confidence.

Главный вопрос:

> **«Почему этот риск имеет такой приоритет?»**

---

### Level 3 — Technical View

Для Security Engineer, Architect и разработчиков:

* конкретный finding;
* техническое доказательство;
* affected component;
* relationships;
* dependency context;
* attack path;
* exploitation assumptions;
* supporting evidence;
* historical context;
* recommendation rationale.

Главный вопрос:

> **«Как технически формируется этот риск?»**

---

# 12. Risk Prioritization

AIS не должен автоматически считать:

> «Высокая техническая severity = высокий бизнес-риск».

Приоритет должен учитывать контекст.

Минимальная логика:

**Technical Severity + Exposure + Exploitability + Architecture Context + Asset Criticality + Consequence + Business Context**

При отсутствии информации отдельный фактор должен считаться **неизвестным**, а не автоматически благоприятным.

---

## 12.1. Confidence

Каждый существенный вывод должен иметь степень уверенности.

Например:

* High confidence;
* Medium confidence;
* Low confidence;
* Unknown.

Confidence должен отражать качество имеющихся доказательств, а не субъективную уверенность AI.

---

# 13. Explainability

Каждый существенный security conclusion должен отвечать минимум на четыре вопроса:

### What?

Что обнаружено?

### Where?

Где это находится?

### Why?

Почему это важно?

### What happens?

К чему это может привести?

Для рекомендаций добавляется:

### Why this action?

Почему предлагается именно это действие?

---

# 14. Evidence

Security Analysis должен отделять:

**Fact**

от

**Inference**

от

**Recommendation**

Пример:

**Fact:** компонент доступен извне.

**Fact:** компонент имеет известную security weakness.

**Inference:** существует потенциальный путь к внутреннему компоненту.

**Inference:** успешная эксплуатация может затронуть чувствительный ресурс.

**Recommendation:** устранить или уменьшить exposure.

Это необходимо для сохранения доверия пользователя.

---

# 15. Handling Uncertainty

AIS не должен превращать отсутствие информации в утверждение.

Если невозможно доказать:

* наличие attack path;
* возможность эксплуатации;
* business impact;
* criticality;
* relationship между компонентами;

система должна сообщить:

> **что известно, чего не известно и какая дополнительная информация необходима.**

Особенно важно для руководителя бизнеса:

**Unknown ≠ Safe**

и

**Potential ≠ Confirmed**

---

# 16. Recommendations

Security recommendations должны быть:

* объяснимыми;
* связанными с конкретным риском;
* связанными с архитектурным контекстом;
* пропорциональными риску;
* проверяемыми;
* приоритизированными.

Каждая рекомендация должна отвечать:

1. Что предлагается изменить?
2. Какой риск это уменьшает?
3. Почему изменение должно помочь?
4. Какие части системы затронуты?
5. Какие возможные trade-offs существуют?
6. Что останется неизвестным после изменения?

---

# 17. What Security Analysis Must NOT Do

Security Analysis не должен:

1. максимизировать количество findings;
2. скрывать uncertainty;
3. выдавать предположение за факт;
4. считать severity равной business risk;
5. игнорировать архитектурный контекст;
6. рассматривать уязвимости независимо от зависимостей;
7. автоматически исправлять систему;
8. выдавать необъяснимые рекомендации;
9. уничтожать исторический security context;
10. заменять человеческое решение;
11. обещать абсолютную безопасность;
12. превращаться в отдельный продукт внутри AIS.

# 18. User Value

## 18.1. Business Leader

### Problem

Руководитель бизнеса обычно получает технические security-отчёты, но не понимает:

* какой риск действительно важен;
* что может произойти;
* какие риски связаны между собой;
* что требует немедленного решения;
* насколько проблема влияет на бизнес.

### AIS provides

AIS переводит технический security analysis в структурированную картину риска.

### Result

Руководитель получает возможность принимать решения на основании:

**Risk → Consequence → Business Impact → Priority**

при сохранении доступа к техническому обоснованию.

---

## 18.2. Developer

Получает понимание:

* где находится проблема;
* почему она важна;
* какие зависимости затронуты;
* какое изменение может устранить риск.

---

## 18.3. Tech Lead

Получает:

* приоритетную карту security risk;
* архитектурный контекст;
* влияние изменений;
* объяснение причин приоритета.

---

## 18.4. Architect

Получает возможность:

* исследовать архитектурные security weaknesses;
* проверять attack paths;
* анализировать systemic risks;
* оценивать security consequences архитектурных решений.

---

## 18.5. Security Engineer

Получает глубокий технический контекст:

* findings;
* relationships;
* dependencies;
* attack paths;
* evidence;
* historical knowledge;
* recommendations.

---

# 19. Business Value

Security Analysis создаёт ценность не количеством обнаруженных проблем.

Ценность возникает благодаря способности ответить:

> **«Какие security-проблемы действительно важны для нашей системы и почему?»**

Это позволяет:

* сокращать шум;
* концентрировать ресурсы на существенных рисках;
* быстрее принимать решения;
* связывать security с архитектурой;
* видеть systemic risks;
* понимать последствия изменений;
* сохранять security knowledge внутри организации.

| Security Analysis        | формирует security understanding                  |

# 21. Design Principles

### 21.1. Context Before Severity

Контекст важнее голого severity score.

### 21.2. Risk Over Findings

Ценность определяется пониманием риска, а не количеством findings.

### 21.3. Architecture Before Interpretation

Security findings должны интерпретироваться в архитектурном контексте.

### 21.4. Evidence Before Conclusion

Вывод должен опираться на доступные факты и явно обозначенные предположения.

### 21.5. Unknown Must Remain Unknown

Недостаток данных не должен превращаться в ложную уверенность.

### 21.6. Business Impact Requires Context

Business impact нельзя достоверно определить без соответствующего организационного контекста.

### 21.7. Every Recommendation Has a Reason

Ни одна существенная рекомендация не должна существовать без объяснения.

### 21.8. Security Evolves with Architecture

Изменение архитектуры должно приводить к переоценке security understanding.

### 21.9. History Must Be Preserved

Security decisions, risks и изменения понимания не должны исчезать бесследно.

### 21.10. AI Assists, Human Decides

AIS помогает понять риск, но окончательное решение остаётся за человеком.

---

# 22. Success Criteria

Security Analysis считается успешным, если:

### 22.1. Contextual Understanding

Пользователь видит не только findings, но и их архитектурный контекст.

### 22.2. Attack Understanding

Для существенных рисков система способна объяснить потенциальные attack paths.

### 22.3. Consequence Understanding

Пользователь понимает возможные технические последствия.

### 22.4. Business Understanding

Руководитель может понять, почему риск важен для бизнеса.

### 22.5. Explainability

Существенные выводы имеют понятное обоснование.

### 22.6. Evidence Separation

Факты, выводы и рекомендации не смешиваются.

### 22.7. Uncertainty Transparency

Недостаток информации явно обозначается.

### 22.8. Contextual Prioritization

Приоритет учитывает архитектурный и бизнес-контекст.

### 22.9. Change Awareness

После изменения системы security understanding может быть переоценено.

### 22.10. Decision Support

Результат анализа помогает человеку принять техническое или бизнес-решение.

---

# 23. MVP Boundary

Security Analysis в MVP должен оставаться сфокусированным.

### Must Have

* security findings;
* привязка findings к архитектурной модели;
* contextual risk;
* severity;
* affected components;
* dependencies;
* explainable recommendations;
* distinction between facts and conclusions;
* basic uncertainty indication.

### Should Have

* attack path representation;
* consequence analysis;
* change-aware security analysis.

### Post-MVP

* глубокий business impact modeling;
* исторический security intelligence;
* advanced attack-path reasoning;
* organization-wide security knowledge;
* cross-project risk correlation.

---

# 24. Out of Scope

Следующие возможности не являются частью данной спецификации:

1. гарантирование полной безопасности;
2. автономное исправление кода;
3. автономное изменение production-систем;
4. автоматическое принятие security decisions;
5. замена Security Engineer;
6. замена CISO;
7. самостоятельная юридическая интерпретация compliance requirements;
8. создание универсальной threat model без контекста;
9. автоматическое утверждение security risk;
10. скрытие uncertainty ради простоты;
11. отдельная независимая security-модель;
12. превращение AIS в набор независимых security tools;
13. раскрытие чувствительных данных без соответствующего контекста;
14. использование AI-вывода как доказанного факта;
15. абсолютная классификация business impact без организационного контекста.

---

# 25. Product Definition

Security Analysis в AIS — это не механизм поиска максимального количества уязвимостей.

Это механизм превращения технических security observations в **объяснимое понимание риска всей системы**.

Итоговая цепочка:

**Security Finding**

↓

**Architectural Context**

↓

**Dependencies**

↓

**Attack Path**

↓

**Technical Consequence**

↓

**Business Impact**

↓

**Risk Priority**

↓

**Explainable Recommendation**

↓

**Human Decision**

Именно эта цепочка превращает Security Analysis из очередного vulnerability analyzer в часть **платформы архитектурного понимания программных систем**.
