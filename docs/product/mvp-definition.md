# AIS — MVP Definition

Документ определяет минимально жизнеспособную версию платформы: что обязательно должно быть готово к первому публичному релизу, что сознательно исключается и по каким критериям оценивается готовность.

---

## 1. Purpose of MVP

MVP существует для того, чтобы подтвердить центральную гипотезу продукта: **команда принимает лучшие технические решения, когда имеет доступ к целостной архитектурной модели проекта с привязанными результатами анализа**.

MVP решает конкретную проблему: разработчик подключает проект и за разумное время получает архитектурную модель с результатами анализа безопасности и зависимостей, каждая проблема объяснена в контексте архитектуры. Без этого продукта разработчик либо не имеет этой информации, либо собирает её вручную из нескольких инструментов.

MVP не пытается решить всё сразу. Первая версия сфокусирована на одном сценарии: **подключение проекта, получение понимания и устранение обнаруженных проблем**. Командная работа, корпоративные функции, интеграции с процессами и расширенная аналитика — всё это требует устойчивой базы, которую создаёт MVP.

---

## 2. Target Customer

### 2.1 Tech Lead небольшой команды (3–10 человек)

**Основные боли:** Не может объективно показать команде состояние архитектуры. Новые участники тратят недели на вникание. Технический долг растёт, но невозможно приоритизировать его без данных. Результаты сканирования безопасности существуют отдельно от понимания архитектуры.

**Почему подходит для первой версии:** Tech Lead мотивирован улучшить командные процессы. Он принимает решения о том, какие инструменты использовать, и может внедрить платформу для всей команды без согласования на уровне организации. Ему нужны объективные данные для обоснования рефакторинга и приоритизации.

### 2.2 Solo Developer (опытный, работает со сложными проектами)

**Основные боли:** Не видит полную картину зависимостей. Непредвиденные регрессии из-за непонимания влияния изменений. Нет коллег, у которых можно спросить об архитектуре. Результаты анализа безопасности не привязаны к контексту проекта.

**Почему подходит для первой версии:** Solo Developer полностью контролирует выбор инструментов. Он немедленно получает ценность: понимание архитектуры проекта, которое раньше было недоступно без команды. Барьер внедрения минимален — один человек, один проект.

### 2.3 Startup-команда (до 20 человек, быстрый рост кодовой базы)

**Основные боли:** Кодовая база растёт быстрее, чем команда может её понимать. Архитектурные решения принимаются в спешке и не документируются. Новые сотрудники приходят быстрее, чем передаются знания. Инциденты безопасности обнаруживаются постфактум.

**Почему подходит для первой версии:** Стартапы чувствительны к техническим проблемам, но не имеют ресурсов на ручное поддержание документации. Им нужен инструмент, который даёт понимание автоматически. Быстрый рост кодовой базы делает проблему острой.

## 3. MVP Goals

### 3.1 Построить архитектурную модель подключённого проекта

Пользователь подключает проект и получает целостную архитектурную модель: компоненты, их взаимосвязи и слоёвую структуру. Модель создаётся автоматически, без ручного описания.

### 3.2 Выявить и объяснить проблемы безопасности

Платформа находит уязвимости и привязывает их к компонентам архитектурной модели. Каждая проблема объяснена: что обнаружено, на что влияет, почему это опасно в контексте данного проекта.

### 3.3 Показать зависимости и их проблемы

Пользователь видит полный граф зависимостей проекта с выделением проблемных зон — циклических, избыточных и рискованных связей.

### 3.4 Предоставить объяснимые рекомендации

Для каждой обнаруженной проблемы платформа даёт рекомендацию с контекстом: почему проблема существует, на что она влияет, какие варианты решения.

### 3.5 Визуализировать архитектуру

Архитектурная модель доступна для визуального восприятия и навигации. Пользователь может исследовать структуру проекта интерактивно.

### 3.6 Создать отчёт о состоянии проекта

Пользователь может сгенерировать отчёт, отражающий архитектуру, обнаруженные проблемы и рекомендации. Отчёт пригоден для использования внутри команды.

---

## 4. MVP Scope

### Must Have

Без этих возможностей MVP не выполняет свою цель.

| Возможность | Почему Must Have |
|---|---|
| Подключение проекта (Project Discovery) | Без этого невозможно начать работу. Пользователь должен иметь возможность указать проект и получить результат. |
| Построение архитектурной модели | Это основа всех последующих анализов. Без модели остальные результаты лишены контекста. |
| Анализ безопасности с привязкой к модели | Ключевая ценность для целевого клиента. Без привязки к модели — это просто ещё один сканер. |
| Анализ зависимостей | Неотделим от архитектурного понимания. Без графа зависимостей модель неполна. |
| Объяснимые рекомендации | Фундаментальное отличие от конкурентов. Без объяснений рекомендации не выполняют принцип "Explain Before Recommend". |
| Визуализация архитектуры | Без визуализации модель остаётся абстракцией, недоступной для быстрого понимания. |
| Генерация отчёта | Минимальный формат доставки результатов. Без отчёта результаты не могут быть использованы вне платформы. |
| Адаптация под организацию | Без адаптации платформа генерирует нерелевантные рекомендации, что нарушает принцип "Context Over Rules". |

### Should Have

Желательные возможности, которые значительно усиливают ценность, но не блокируют первый релиз.

| Возможность | Почему Should Have |
|---|---|
| Оценка влияния изменений | Значительно усиливает ценность, но требует устойчивой модели и графа зависимостей. Может быть добавлена после стабилизации базового анализа. |
| Навигация по архитектурной модели | Улучшает использование визуализации, но базовая визуализация без навигации уже даёт ценность. |

### Nice to Have

Улучшения, которые не влияют на ценность MVP.

| Возможность | Почему Nice to Have |
|---|---|
| Сравнение состояний модели | Полезно для понимания эволюции, но не требуется для первого использования. |
| Множественные форматы отчётов | Один формат отчёта достаточен для MVP. |
| Детальная настройка визуализации | Базовая визуализация достаточна для первого релиза. |

---

## 5. Explicitly Out of Scope

Следующие возможности сознательно не входят в MVP. Они не забыты — они требуют зрелой базы, которую создаёт MVP.

### 5.1 Генерация кода

Платформа рекомендует, но не генерирует код. Это принципиальное ограничение (принцип "AI Assists, Not Replaces"), а не временное.

### 5.2 Автоматическое исправление проблем

Платформа предоставляет рекомендации, но не применяет их автоматически. Это принципиальное ограничение.

### 5.3 Интеграция с CI/CD

Требует стабильного API и проверенной модели. Интеграция возможна только после того, как платформа надёжно работает в ручном режиме.

### 5.4 Командная аналитика и совместная работа

Требует системы авторизации, управления доступом и многопользовательского взаимодействия. Это отдельный этап развития.

### 5.5 Корпоративные функции

Роль-based доступ, SSO, аудит-логи, соответствие отраслевым стандартам — всё это требует зрелой платформы и отдельной разработки.

### 5.6 Облачная совместная работа в реальном времени

Требует инфраструктуры реального времени и системы синхронизации. Это долгосрочное развитие.

### 5.7 Управление техническим долгом с приоритизацией

Требует накопленной истории изменений и устойчивой модели. В MVP отдельные проблемы выявляются, но системное отслеживание долга с приоритизацией — следующая ступень.

### 5.8 Прогнозирование влияния на основе истории

Требует значительного объёма исторических данных. Невозможно без длительного периода накопления.

### 5.9 Marketplace плагинов

Требует стабильной архитектуры расширения, системы версионирования и инфраструктуры распространения.

### 5.10 Мобильный доступ и desktop-приложение

MVP доступен через веб-интерфейс. Другие форматы — последующее развитие.

## 6. User Workflow

Полный путь пользователя в MVP:

```
Подключение проекта
        ↓
Автоматическое обнаружение структуры
        ↓
Построение архитектурной модели
        ↓
Анализ безопасности и зависимостей
        ↓
Визуализация архитектуры и проблем
        ↓
Объяснимые рекомендации
        ↓
Пользователь устраняет проблему
        ↓
Повторный анализ
        ↓
Обновление модели
        ↓
Генерация отчёта
```

**Подключение проекта.** Пользователь указывает проект. Платформа автоматически определяет его тип и структуру. Никакой ручной настройки не требуется.

**Обнаружение и моделирование.** Платформа анализирует проект, строит архитектурную модель и запускает анализ безопасности и зависимостей.

**Визуализация и рекомендации.** Пользователь видит архитектурную модель с привязанными результатами анализа. Каждая проблема объяснена. Каждая рекомендация содержит контекст.

**Устранение и повторный анализ.** Пользователь устраняет проблему, повторно запускает анализ и видит обновлённое состояние модели.

**Отчёт.** Пользователь генерирует отчёт о текущем состоянии проекта для использования внутри команды.

---

## 7. Success Criteria

MVP считается успешным, если:

### 7.1 Пользователь понимает архитектуру своего проекта

Пользователь, подключивший проект, может назвать основные компоненты, их взаимосвязи и проблемные места. Это понимание получено через платформу, а не через ручной анализ.

### 7.2 Пользователь находит проблемы, которые не знал ранее

По крайней мере одна обнаруженная платформой проблема является новой для пользователя. Это подтверждает, что платформа предоставляет информацию, недоступную без неё.

### 7.3 Пользователь понимает причины проблем

Для каждой обнаруженной проблемы пользователь может объяснить, почему она существует и на что влияет, опираясь на рекомендации платформы.

### 7.4 Пользователь может оценить влияние изменений

Пользователь может определить, какие компоненты затронет изменение, используя информацию о зависимостях, предоставленную платформой.

### 7.5 Пользователь возвращается к платформе повторно

После первого использования пользователь возвращается к платформе для анализа новых изменений. Это подтверждает, что платформа предоставляет регулярную ценность, а не разовое любопытство.

### 7.6 Результаты применимы к реальным решениям

Пользователь принимает на основе результатов платформы конкретные действия: устраняет уязвимость, рефакторит зависимость, пересматривает архитектурное решение.

## 8. Release Readiness Checklist

### Проект

1. Проект импортируется и начинается анализ без ручной настройки
2. Платформа корректно обрабатывает проекты различной структуры
3. Платформа сообщает о прогрессе анализа
4. Ошибки анализа не приводят к потере данных
5. Пользователь видит, когда анализ завершён и результаты готовы

### Архитектурная модель

6. Архитектурная модель строится автоматически
7. Модель отражает реальные компоненты и связи проекта
8. Модель доступна для визуального восприятия
9. Визуализация позволяет ориентироваться в структуре проекта
10. Модель обновляется при повторном анализе

### Анализ

11. Результаты анализа безопасности привязаны к компонентам модели
12. Результаты анализа зависимостей привязаны к компонентам модели
13. Каждая обнаруженная проблема содержит объяснение
14. Объяснения понятны без знания внутреннего устройства платформы
15. Рекомендации содержат варианты действий

### Надёжность

16. Платформа не теряет данные о проекте между сессиями
17. Ошибки обрабатываются корректно, без потери контекста
18. Платформа информирует о проблемах анализа, не скрывает их
19. Результаты воспроизводимы: повторный анализ даёт сопоставимые результаты

### Пользовательский опыт

20. Пользователь может выполнить полный путь от подключения до отчёта без помощи
21. Интерфейс понятен разработчику без обучения
22. Время от подключения проекта до первых результатов приемлемо
23. Отчёт генерируется и содержит полезную информацию
24. Платформа работает без постоянного подключения к интернету (локальный режим)

### Ценность

25. Пользователь находит хотя бы одну ранее неизвестную проблему
26. Пользователь понимает причины обнаруженных проблем
27. Пользователь может связать рекомендацию с конкретным местом в проекте

## 9. First Commercial Version

Первый коммерческий релиз возможен, когда выполнены все условия Release Readiness Checklist и подтверждены следующие критерии:

**Стабильность.** Платформа обрабатывает проекты целевого клиента без критических ошибок. Результаты воспроизводимы и корректны. Потеря данных исключена.

**Ценность подтверждена.** Не менее 5 целевых пользователей успешно выполнили полный путь и подтвердили, что платформа предоставила ценность, недоступную без неё.

**Обратная связь интегрирована.** Результаты тестирования с целевыми клиентами привели к улучшениям, которые делают продукт пригодным для широкой аудитории.

**Минимальная адаптация.** Платформа позволяет настроить приоритеты и стандарты организации, что подтверждает принцип "Context Over Rules".

**Доставка результатов.** Пользователь может получить результаты в виде, пригодном для использования вне платформы (отчёт).

Первый коммерческий релиз — это не дата, а состояние продукта. Когда эти критерии выполнены, продукт готов к продаже.

## 10. What Makes MVP Valuable

MVP ценнее существующего набора отдельных инструментов даже в первой версии по трём причинам.

**Во-первых, единый контекст.** Сегодня разработчик, которому нужна полная картина проекта, использует сканер безопасности для уязвимостей, анализатор зависимостей для графа связей и собственную память для архитектуры. Эти три источника не связаны. Уязвимость в отчёте сканера — это строка текста. В AIS та же уязвимость — это точка на архитектурной модели с пониманием того, какие данные под угрозой и через какие пути атакующий может до них добраться. Разница между списком и пониманием — это разница между данными и знанием.

**Во-вторых, объяснимость.** Существующие инструменты сообщают о проблемах, но не объясняют их в контексте проекта. Статический анализатор говорит «высокая цикломатическая сложность», но не говорит, что этот метод является единственной точкой доступа к критическому компоненту, и именно поэтому его сложность рискованна. AIS объясняет проблемы в контексте архитектуры, превращая формальное предупреждение в осмысленную рекомендацию.

**Во-третьих, накопление знаний.** Ни один существующий инструмент не накапливает знание о проекте между запусками. Каждый запуск начинается с нуля. AIS сохраняет архитектурную модель и обновляет её, создавая эффект роста: чем дольше платформа работает с проектом, тем лучше она его понимает. Даже в MVP этот эффект присутствует, потому что модель сохраняется между сессиями и обновляется при повторных анализах.
