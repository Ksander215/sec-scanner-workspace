## §1. Главная задача

Создать систему доказательства продуктовой и коммерческой ценности AIS до полноценной реализации MVP.

Этот документ определяет:

- что именно AIS должен доказать на реальных пользователях;
- какие гипотезы необходимо проверить;
- какие пользователи должны участвовать;
- какие реальные задачи они должны выполнять;
- какие данные необходимо собирать;
- как отличать мнение пользователя от объективного evidence;
- как переводить evidence из E0/E1 в E2/E3;
- как проверять отличие AIS от generic AI + существующих инструментов;
- как определить MVP value и повторную ценность;
- как проверить willingness to pay;
- какие условия позволяют перейти к полноценной реализации MVP;
- какие результаты должны приводить к изменению продукта;
- какие результаты являются основанием остановить или изменить направление.

**Главный принцип:** Не доказывать, что AIS хорошо спроектирован. Доказать, что AIS решает реальную проблему пользователя лучше существующих способов и создаёт ценность, ради которой пользователь готов использовать продукт повторно и потенциально платить.

## §3. Главный вопрос

> Как мы можем доказать, что AIS нужен реальному пользователю до того, как потратим значительные ресурсы на полноценную реализацию MVP?

Второй вопрос:

> Какие наблюдаемые evidence позволят нам уверенно изменить Commercial Score с текущих 3.0/5.0?

Ответ на оба вопроса: через систему task-based validation с реальными пользователями, выполняющими реальные задачи на реальных проектах, с измеримыми результатами и чётким разделением observation от opinion.

## §4. Validation Philosophy

### Не является достаточным evidence

| Утверждение | Почему недостаточно |
|---|---|
| «Идея нравится» | Не требует действия |
| «Интересный продукт» | Не привязан к задаче |
| «Я бы попробовал» | Обещание, не поведение |
| «Это звучит полезно» | Вежливость, не commitment |
| Количество положительных ответов в опросе | Опрос измеряет мнение, не поведение |
| Субъективное мнение команды | Confirmation bias (§33) |
| Мнение одного пользователя | Selection bias, insufficient sample |
| Generic praise («Круто!») | Не содержит информации о конкретной ценности |

### Более сильное evidence

| Evidence | Почему сильнее |
|---|---|
| Пользователь самостоятельно выполняет задачу | Поведение, не мнение |
| Пользователь использует AIS для решения задачи | Adoption через действие |
| AIS сокращает путь к пониманию | Измеримое преимущество |
| Пользователь обнаруживает ранее неизвестную информацию | Concrete value |
| Пользователь использует AIS повторно | Retention через поведение |
| Пользователь возвращается к AIS для новой задачи | Repeat value |
| Пользователь предпочитает AIS альтернативному workflow | Preference через выбор |
| Пользователь готов выделить бюджет или обсуждать покупку | Commercial signal (E4) |

## §5. Evidence Maturity Model

### E0 — Assumption

**Определение:** Предположение команды без внешнего подтверждения.

**Примеры из commercial-reassessment-001:** Willingness to pay, pricing model, time-to-value, retention rate, category acceptance.

**Как повысить:** Провести user interview, наблюдать реальное поведение.

### E1 — Expert / Internal Evidence

**Определение:** Логически обоснованное утверждение, подтверждённое внутренним анализом, domain expertise или архитектурными документами. Не основано на наблюдении реального поведения внешних пользователей.

**Примеры из commercial-reassessment-001:** Problem exists (общеизвестна в индустрии), AI is not a wrapper (архитектурно доказано), quality architecture is differentiator.

**Как повысить:** Наблюдать реального пользователя при выполнении реальной задачи.

### E2 — User Evidence

**Определение:** Наблюдение реального (внешнего) пользователя при выполнении реальной задачи на реальном проекте. Пользователь не является членом команды AIS.

**Минимальные критерии для E2:"

- Пользователь — не член команды AIS
- Задача — реальная (не придуманная для демо)
- Проект — реальный (не toy example)
- Наблюдение — структурированное (сценарий, критерии, фиксация результатов)
- Результат — задокументирован (evidence grade, finding, confidence)

**Как повысить:** Повторное наблюдение, multiple users, measurable improvement.

### E3 — Behavioral / Repeated Evidence

**Определение:** Повторяющееся поведение, наблюдаемое у одного или нескольких пользователей.

**Критерии:"

- Повторное использование (≥2 сессий у одного пользователя)
- Самостоятельный возврат (без приглашения команды AIS)
- Выполнение нескольких разных задач
- Предпочтение AIS при наличии альтернативы
- Measurable improvement (время, полнота, качество)

**Как повысить:** Commercial signal (бюджет, пилот, покупка).

### E4 — Commercial Evidence

**Определение:** Реальное коммерческое действие.

**Критерии (в порядке возрастания силы):"

1. Запрос на доступ после окончания validation
2. Запрос на pilot для команды
3. Готовность обсудить pricing
4. Бюджетный разговор (allocation of budget)
5. Paid pilot
6. Purchase

**E4 не является обязательным для первого validation gate.** Product Documents не требуют коммерческой транзакции для начала MVP.

## §6. Validation Hypotheses

### H1 — Problem

> У целевых пользователей действительно существует проблема понимания сложных систем, и она возникает достаточно часто, чтобы оправдывать отдельный продукт.

**Current Evidence:** E1 (commercial-reassessment-001 §5, User Personas)

**Target Evidence:** E2 (наблюдение реального пользователя, сталкивающегося с проблемой)

**Validation method:** Структурированное интервью (§34) с последующим наблюдением за workflow.

### H2 — Frequency

> Проблема возникает достаточно часто, чтобы пользователь помнил о ней и искал решение.

**Current Evidence:** E1 («ежедневно» для Tech Lead, «несколько раз в неделю» для Developer — из User Personas, не подтверждено наблюдением)

**Target Evidence:** E2 (пользователь описывает конкретный недавний случай)

**Validation method:** Интервью: «Когда в последний раз вы сталкивались с этой проблемой? Расскажите конкретно.»

### H3 — AIS Value

> AIS сокращает усилия, необходимые для понимания системы, по сравнению с текущим workflow.

**Current Evidence:** E1 (архитектурная ценностная цепочка обоснована)

**Target Evidence:** E2 (измеренное сокращение времени или повышение полноты понимания)

**Validation method:** Scenario-based comparison (§9, §10). Baseline workflow vs AIS workflow на одной и той же задаче.

### H4 — Context Advantage

> Архитектурный контекст AIS создаёт ценность сверх generic AI.

**Current Evidence:** E1 (AI Assistance specification: 9 источников контекста, Context-First principle)

**Target Evidence:** E2 (пользователь получает более полный/точный ответ через AIS, чем через generic AI с тем же вопросом)

**Validation method:** AI Wrapper Test (§11) + Context Advantage Test (§12).

### H5 — Model Advantage

> Architecture Model улучшает качество понимания по сравнению с отсутствием модели.

**Current Evidence:** E1 (D1: Model Before Analysis, Foundation specification)

**Target Evidence:** E2 (пользователь находит информацию через Model, которую не нашёл бы без неё)

**Validation method:** Scenario A (Understand) + Scenario H (Unknown System). Сравнение с и без Model.

### H6 — Knowledge Advantage

> Накопленное Knowledge повышает полезность AIS при повторном использовании.

**Current Evidence:** E1 (Principle: Knowledge Never Lost, Knowledge specification)

**Target Evidence:** E3 (пользователь возвращается и получает более точный/полный ответ, чем в первый раз)

**Validation method:** Repeat session observation. Сравнение quality первого и второго взаимодействия.

**Ограничение MVP:** В MVP Knowledge минимальна (session-level, accepted trade-off AT-1 из Readiness spec). Полная проверка H6 требует Stage 2+.

### H7 — Evolution Advantage

> Исторический контекст создаёт дополнительную ценность.

**Current Evidence:** E1 (Evolution specification: 7 стадий зрелости)

**Target Evidence:** E3 (пользователь использует исторический контекст для принятия решения)

**Ограничение:** Evolution отсутствует в MVP. H7 **не проверяется** в рамках MVP validation. Отложена до Stage 2.

### H8 — Integrated Understanding

> Комбинация Model + Knowledge + Analysis создаёт ценность, которую сложнее получить через набор независимых инструментов.

**Current Evidence:** E1 (§11 Unified Understanding Advantage в commercial-reassessment)

**Target Evidence:** E2 (пользователь решает задачу через AIS, которую не может решить с той же полнотой через комбинацию инструментов)

**Validation method:** Competitive Substitution Test (§27).

### H9 — Trust

> Explainability и traceability повышают доверие к результатам.

**Current Evidence:** E1 (D4: All Recommendations Explained, Trust Architecture из Interaction spec)

**Target Evidence:** E2 (пользователь проверяет evidence, использует recommendation, задаёт уточняющие вопросы — поведенческие сигналы доверия из §17)

**Validation method:** Trust Validation (§17). Наблюдение за поведением, не за высказываниями.

### H10 — Repeat Value

> После первого использования пользователь имеет причину вернуться.

**Current Evidence:** E1 (Learning Loop, Knowledge Accumulates, Product Roadmap Stage 2 criteria)

**Target Evidence:** E3 (пользователь возвращается самостоятельно для новой задачи)

**Validation method:** Предложить пользователям вернуться через 3–7 дней. Наблюдать, кто вернулся и зачем.

### H11 — Differentiation

> AIS не воспринимается просто как UI над generic AI.

**Current Evidence:** E1 (AI Wrapper Test architectural, AI Writes NOTHING invariant)

**Target Evidence:** E2 (пользователь описывает AIS как отличающийся от ChatGPT/Copilot без подсказки)

**Validation method:** AI Wrapper Test (§11). Вопрос: «Если бы у вас не было AIS, как бы вы решили эту задачу?»

### H12 — Commercial Value

> Для части пользователей ценность потенциально достаточно велика для коммерческого использования.

**Current Evidence:** E0 (no data)

**Target Evidence:** E3 (повторное использование) + E4 (commercial signal)

**Validation method:** Commercial Validation (§26). Наблюдение за коммерческими сигналами.

Каждая роль имеет свою проблему, свой workflow и свою мотивацию. Developer и CTO могут описывать одну и ту же систему совершенно по-разному. Validation должен учитывать эти различия.

## §8. User ≠ Buyer

### Разделение ролей в процессе покупки

| Роль | Кто | Что делает в процессе покупки |
|---|---|---|
| **User** | Developer, Tech Lead, Architect, Security Engineer | Использует продукт, формирует мнение о ценности |
| **Champion** | Tech Lead, Architect (внутренний promoter) | Активно продвигает AIS внутри организации |
| **Technical Evaluator** | Architect, Senior Developer | Оценивает техническое качество и интеграцию |
| **Decision Maker** | Tech Lead (команда <10), CTO/EM (организация) | Принимает решение о покупке/пилоте |
| **Economic Buyer** | CTO, EM, иногда Tech Lead с бюджетом | Выделяет бюджет, подписывает договор |

### Правило

Человек, которому нравится AIS, **не является** покупателем. Лiking ≠ buying. Validation должен разделять:

- «Мне нравится использовать AIS» (user signal, E2–E3)
- «Я хочу, чтобы моя команда использовала AIS» (champion signal, E3)
- «Я готов обсудить бюджет» (buyer signal, E4)

## §9. Validation Scenarios

### Scenario A — Understand

**Задача:** Пользователь получает незнакомый компонент и должен понять: назначение, связи, зависимости, потенциальные проблемы.

**Формат:** Пользователь выбирает реальный компонент из своего проекта (не toy). Работает с ним через AIS.

**Измеряемые результаты:**

- Время до рабочего понимания (§14)
- Полнота найденных зависимостей
- Количество ранее неизвестных фактов
- Сравнение с baseline (как пользователь решал бы это обычно)

### Scenario B — Dependency

**Задача:** «Что зависит от X?»

**Формат:** Пользователь выбирает реальный компонент X из своего проекта. Через AIS определяет все зависимости. Через baseline workflow делает то же самое.

**Измеряемые результаты:**

- Полнота списка зависимостей (AIS vs baseline)
- Время выполнения
- Понимание критичности каждой зависимости
- Наличие объяснения (зачем зависимость существует)

### Scenario C — Change Impact

**Задача:** «Что произойдёт, если изменить X?»

**Формат:** Пользователь планирует реальное изменение. Через AIS оценивает влияние. Через baseline — своё обычное оценивание.

**Измеряемые результаты:**

- Количество затронутых компонентов (AIS vs baseline)
- Обнаруженные неочевидные последствия
- Уверенность в оценке
- Решение: продолжить/отменить/модифицировать изменение

**Ограничение MVP:** Change Impact Assessment — базовый (Should Have). Проверяется через композицию Dependency Analysis + AI Assistance.

### Scenario D — Security

**Задача:** Пользователь получает реальный security finding и должен понять: почему важен, что затронуто, какой риск.

**Формат:** Пользователь выбирает реальный finding из своего проекта (из сканера). Через AIS получает архитектурный контекст. Без AIS — свою обычную интерпретацию.

**Измеряемые результаты:**

- Изменилась ли оценка приоритета (formal severity → реальный приоритет)
- Были ли обнаружены дополнительные затронутые компоненты
- Понимание бизнес-последствий
- Решение: исправить сейчас/отложить/принять риск

### Scenario E — Technical Debt

**Задача:** «Какой technical debt наиболее важен для текущей задачи?»

**Формат:** Пользователь работает над реальной задачей. Через AIS определяет релевантный технический долг.

**Ограничение MVP:** Technical Debt Tracking — Post-MVP (Stage 2–3). В MVP проверяется через композицию: Model + Dependency Analysis + AI Assistance.

### Scenario F — Evolution

**Задача:** «Почему система стала такой?»

**Ограничение:** Evolution отсутствует в MVP. Scenario F **не выполняется** в рамках MVP validation. Отложен до Stage 2.

### Scenario G — Architecture Decision

**Задача:** Пользователь сравнивает возможные варианты изменения.

**Формат:** Пользователь имеет реальное архитектурное решение, которое нужно принять. Через AIS получает контекст для сравнения вариантов.

**Измеряемые результаты:**

- Количество учтённых факторов (AIS vs baseline)
- Обнаруженные компромиссы
- Уверенность в решении
- Изменение решения после получения контекста

### Scenario H — Unknown System

**Задача:** Пользователь впервые сталкивается с проектом и должен получить working understanding.

**Формат:** Пользователь подключает реальный проект, который не видел ранее (возможно, open-source проект аналогичного домена). Через AIS получает Architecture Overview.

**Измеряемые результаты:**

- Время до рабочего понимания
- Полнота понимания структуры
- Количество обнаруженных проблем
- Сравнение с baseline (как пользователь обычно погружается в новый проект)

## §10. Baseline Comparison

### Метод

Каждый validation scenario, где применимо, выполняется дважды:

1. **Baseline workflow:** Пользователь решает задачу своим обычным способом (IDE, инструменты, коллеги, документация)
2. **AIS workflow:** Пользователь решает ту же задачу через AIS

Порядок (сначала baseline или сначала AIS) чередуется между пользователями для устранения order bias.

### Правила

- **Не предполагать**, что AIS быстрее. Измерять фактическую разницу.
- **Не помогать** пользователю при baseline workflow больше, чем обычно.
- **Не помогать** пользователю при AIS workflow больше, чем предполагает product design.
- **Фиксировать** время, полноту, уверенность, решение для обоих workflow.

### Формат фиксации

| Параметр | Baseline | AIS | Разница | Примечание |
|---|---|---|---|---|
| Время (мин) | | | | |
| Полнота (1–5) | | | | |
| Уверенность (1–5) | | | | |
| Решение | | | | |
| Неизвестные факты | | | | |
| Изменение решения | — | Да/Нет | — | Только для AIS |

## §11. AI Wrapper Test

### Вопрос

> Может ли пользователь получить примерно такой же результат, используя generic AI (ChatGPT, Claude) и предоставив ему доступный контекст вручную?

### Метод

Для каждого сценария (где применимо):

1. Пользователь решает задачу через AIS.
2. Пользователь решает ту же задачу через generic AI. Пользователь сам решает, какой контекст предоставить.
3. Фиксируются результаты обоих подходов.

### Критерии оценки

| Результат | Interpretation |
|---|---|
| «Generic AI дал сопоставимый результат без существенной потери ценности» | **Серьёзный differentiation risk.** Зафиксировать как critical finding. |
| «Generic AI дал частичный результат, AIS дал более полный/точный» | **Differentiation подтверждена.** Зафиксировать конкретные различия. |
| «Generic AI не смог решить задачу» | **Strong differentiation.** Но проверить: задача ли реальна. |

### Важное правило

Если ответ «Да, практически без потери ценности» — это **не провал AIS**, а evidence, что differentiation weaker, чем предполагалось. Это должно привести к Product Decision (§21): Investigate или Reframe.

## §12. Context Advantage Test

### Метод

Отдельная проверка для гипотезы H4 (Context Advantage).

**Generic AI condition:** Пользователь предоставляет контекст вручную (копирует код, описывает структуру, даёт дополнительные данные).

**AIS condition:** Контекст уже является частью архитектурного понимания проекта.

### Измеряемые параметры

| Параметр | Generic AI | AIS | Критерий преимущества |
|---|---|---|---|
| Полнота ответа | | | AIS > Generic по количеству релевантных фактов |
| Релевантность | | | AIS более специфичен для проекта |
| Consistency | | | AIS не противоречит известным фактам о проекте |
| Historical context | | | AIS ссылается на эволюцию (если доступно) |
| Traceability | | | AIS указывает источник каждого утверждения |
| Объяснимость | | | AIS объясняет причину, не только вывод |

### Правило

Преимущество AIS должно быть **наблюдаемым и конкретным**, а не утверждением команды. Если пользователь говорит: «Оба ответа примерно одинаковые» — это evidence, что context advantage недостаточен.

## §13. Quality of Understanding

### Что оценивать

Не измерять исключительно «правильный ли ответ AI?».

Оценивать:

| Критерий | Определение | Как измерять |
|---|---|---|
| Usefulness | Ответ помог выполнить задачу | Пользователь использовал информацию для действия |
| Completeness | Все релевантные аспекты покрыты | Пользователь не нуждался в дополнительном поиске |
| Context Relevance | Ответ привязан к конкретному проекту | Отсутствие generic рекомендаций |
| Traceability | Можно проследить до исходных данных | Пользователь может проверить источник |
| Uncertainty Visibility | AIS указывает, где не уверен | Пользователь видит границы понимания |
| Decision Usefulness | Ответ помог принять решение | Пользователь принял решение на основе ответа |
| Ability to Verify | Пользователь может проверить ответ | Пользователь независимым образом подтвердил/опроверг |

## §14. Time-to-Understanding

### Определение

> Сколько времени пользователю требуется, чтобы получить достаточное понимание для выполнения конкретной задачи?

### Привязка к Product Success Metrics

Эта метрика напрямую связана с существующей метрикой «Скорость получения понимания» (Product Success Metrics, 3.1): *время от подключения до ответа на архитектурный вопрос*.

**Time-to-Understanding** расширяет эту метрику для validation: время от начала задачи до момента, когда пользователь заявляет, что у него достаточно понимания для её выполнения.

### Формат

| Задача | Baseline (мин) | AIS (мин) | Разница | Пользовательская оценка достаточности |
|---|---|---|---|---|

### Не vanity metric

Time-to-Understanding измеряется только в контексте конкретной задачи. Отдельное «среднее время» без привязки к задаче — vanity metric.

## §15. Decision Quality

### Принцип

AIS должен помогать принимать **более информированные решения**, не только более быстрые.

### Наблюдаемые признаки улучшенного решения

| Признак | Как наблюдать |
|---|---|
| Пользователь обнаружил relevant dependency | Задал вопрос, получил ответ, учёл в решении |
| Пользователь обнаружил security implication | Изменил приоритет findings после получения контекста |
| Пользователь заметил architectural trade-off | Обсудил компромисс, который не видел без AIS |
| Пользователь смог проверить recommendation | Самостоятельно проверил evidence, указанный AIS |
| Пользователь изменил решение после получения контекста | Описал: «Я собирался сделать X, но после AIS понял, что лучше Y» |

### Правило

Не утверждать автоматически, что решение стало лучше. Фиксировать:

- Первоначальное намерение (до AIS)
- Информация, полученная через AIS
- Итоговое решение
- Обоснование изменения (или отсутствия изменения)

## §16. Explainability Validation

### Вопрос

> Может ли пользователь понять, почему AIS дал такой вывод?

### Метод

После каждого AIS-ответа задать пользователю:

1. «Почему AIS дал именно этот вывод?» — если пользователь может объяснить своими словами → explainability работает.
2. «Где AIS берёт эту информацию?» — если пользователь может указать на модель/компонент/зависимость → traceability работает.
3. «Вы уверены, что этот вывод правильный?» — если пользователь может обосновать уверенность/неуверенность → trust architecture работает.

### Negative signal

Если пользователь говорит: «Я просто должен поверить AI» — это **negative signal** для H9 (Trust). Зафиксировать и классифицировать как finding.

### Оценка

| Элемент explainability | Доступен пользователю? | Evidence |
|---|---|---|
| Evidence (исходные данные) | | |
| Context (проектный контекст) | | |
| Model relationship (связь с моделью) | | |
| Knowledge (накопленное понимание) | | |
| Dependencies (зависимости) | | |
| Uncertainty (границы уверенности) | | |
| Recommendation reasoning (причина рекомендации) | | |

## §17. Trust Validation

### Принцип

Доверие измеряется через **поведение**, не через эмоциональную оценку.

### Поведенческие сигналы доверия

| Сигнал | Поведение | Evidence Grade |
|---|---|---|
| Проверяет источник | Пользователь кликает/переходит к исходным данным | E2 |
| Использует recommendation | Пользователь выполняет действие на основе рекомендации | E2 |
| Задаёт уточняющий вопрос | Пользователь хочет больше контекста, не отвергает | E2 |
| Самостоятельно проверяет evidence | Пользователь верифицирует вне AIS | E2–E3 |
| Возвращается к AIS | Пользователь приходит снова для новой задачи | E3 |

### Non-signals (не являются доказательством доверия)

- «Мне нравится» (opinion, не behaviour)
- «Круто» (generic praise)
- «Полезно» (vague)
- Согласие с очевидным выводом

## §18. Uncertainty Validation

### Вопрос

> Как пользователь воспринимает «Недостаточно данных для уверенного ответа»?

### Метод

Создать ситуации, где AIS должен указать на неопределённость (например, неполная модель, конфликтующие данные).

Наблюдать:

| Реакция пользователя | Interpretation |
|---|---|
| Оценил прозрачность положительно | Uncertainty повышает доверие (positive signal) |
| Предпочёл бы уверенный (даже если неточный) ответ | Uncertainty снижает perceived value (negative signal, но не failure) |
| Использовал неопределённость для дальнейшего расследования | Uncertainty как инструмент (strong positive) |
| Проигнорировал неопределённость | Neutral — пользователь не оценил этот аспект |

### Правило

Прозрачная uncertainty **не является failure**. Это архитектурное свойство (No False Certainty invariant). Если пользователи систематически предпочитают ложную уверенность — это finding для Product Decision, не для отказа от принципа.

## §19. Feedback Collection

### Соответствие Quality & Feedback Architecture

Feedback собирается в соответствии с существующей Quality & Feedback Architecture (TASK-ARCH-QUALITY-001):

### Разделение типов

| Тип | Определение | Превращается в Knowledge? |
|---|---|---|
| Opinion | «Мне нравится / не нравится» | Нет — это opinion, не observation |
| Observation | «Пользователь сделал X» | Нет — требует contextualization и validation |
| Correction | «Это неправильно, правильно Y» | Нет — через Signal Lifecycle (§8 Quality spec) |
| Confirmation | «Да, это верно» | Нет — через Signal Lifecycle |
| Rejection | «Нет, это не полезно» | Нет — Rejection ≠ Error (Quality spec) |
| Decision | «Я решил сделать X» | Нет — Decision ≠ Knowledge |
| Quality Signal | Наблюдение, требующее интерпретации | Нет — Signal Is Not Truth (I-2) |

### Правило

Feedback **никогда автоматически** не превращается в Knowledge. Это нарушает инвариант I-2 (Signal Is Not Truth) и I-4 (Feedback Does Not Mutate Model).

## §20. Product Learning Loop

### Цикл

```
User Interaction
       ↓
Observation (что пользователь сделал/сказал)
       ↓
Evidence (классификация по E0–E4)
       ↓
Validation (проверка на bias, сравнение с гипотезой)
       ↓
Finding (что мы узнали)
       ↓
Product Decision (Keep / Improve / Simplify / Remove / Reframe / Investigate / Defer)
       ↓
Product Change (модификация Product Layer, Architecture Layer, или Specification)
       ↓
Re-validation (повторная проверка после изменения)
```

### Главное правило

> Validation не заканчивается отчётом. Его результат должен улучшать AIS.

Каждый significant finding проходит через Product Decision (§21) и приводит к конкретному изменению или осознанному решению не менять.

---

## §21. Evidence → Product Improvement

### Возможные решения

| Решение | Когда применять | Пример |
|---|---|---|
| **Keep** | Evidence подтверждает гипотезу | Пользователь действительно использует Model для понимания |
| **Improve** | Гипотеза подтверждена, но execution слабый | Пользователь находит ценность, но UI мешает |
| **Simplify** | Пользователь путается в сложности | Слишком много шагов для простой задачи |
| **Remove** | Гипотеза не подтверждена | Пользователь не использует capability |
| **Reframe** | Проблема подтверждена, но формулировка неверна | Пользователь ищет не «понимание», а «обоснование для руководства» |
| **Investigate** | Неожиданный результат | Пользователь использует AIS неожиданным образом |
| **Defer** | Проблема реальна, но не приоритетна для MVP | CTO-ценность подтверждена, но MVP target — Tech Lead |

### Запрещённый паттерн

> «Пользователь не понял → добавим ещё функций»

Сначала искать root cause. Почему не понял? Недостаточный explainability? Неправильный intent resolution? Слишком сложный interface? Неполная модель?

---

## §22. Feature Factory Protection

### Запрет

> Validation не должна использоваться для оправдания добавления функций без доказанной проблемы.

### Когда пользователь просит feature

| Вопрос | Зачем |
|---|---|
| Какую проблему она решает? | Понять root cause, не symptom |
| Существует ли уже capability для этой проблемы? | Проверить Capability Map |
| Почему текущий workflow недостаточен? | Понять limitation |
| Сколько пользователей имеют эту проблему? | Оценить распространённость |
| Влияет ли она на core value? | Решить: core improvement или feature creep |

### Правило

Если < 30% пользователей запрашивают одну и ту же feature — это **не** evidence для добавления. Это individual preference.

## §23. MVP Value Validation

### Core loop для проверки

```
Discover → Model → Understand → Analyze → Explain → Decide
```

Этот loop — минимальная цепочка ценности, которую должен продемонстрировать MVP.

### Что необходимо проверить

| Элемент loop | Как проверяется | Минимальный evidence |
|---|---|---|
| Discover | Scenario H (Unknown System) | Проект подключён, структура обнаружена |
| Model | Scenario A (Understand) | Модель содержит компоненты и связи |
| Understand | Scenario A + B | Пользователь может описать систему |
| Analyze | Scenario D (Security) + B (Dependency) | Findings привязаны к модели |
| Explain | Scenario D + G | Пользователь понимает почему |
| Decide | Scenario C + G | Пользователь принимает решение на основе AIS |

### AI не рассматривается отдельно от loop

AI Assistance — механизм доступа к пониманию (terminal consumer, INV-A3), не отдельный product. Validation проверяет AI как часть loop, не изолированно.

## §24. Validation Gates

### Gate 1 — Problem Validated

**Вопрос:** Есть реальная повторяющаяся проблема?

| Критерий | Требование |
|---|---|
| Required Evidence | ≥5 пользователей из целевых ролей описали конкретный случай проблемы в последние 30 дней |
| Minimum Confidence | Medium (≥3/5 пользователей подтверждают frequency ≥ еженедельно) |
| **Pass** | Problem подтверждена у ≥4/5 пользователей, frequency достаточна |
| **Fail** | < 2/5 пользователей подтверждают проблему ИЛИ frequency < ежемесячно |
| **Inconclusive** | 2–3/5 подтверждают ИЛИ mixed frequency |

### Gate 2 — Value Validated

**Вопрос:** AIS действительно помогает решить задачу?

| Критерий | Требование |
|---|---|
| Required Evidence | ≥3 пользователя выполнили ≥1 scenario с измеримым результатом (AIS vs baseline) |
| Minimum Confidence | Medium (≥2/3 показали улучшение хотя бы по одному параметру) |
| **Pass** | ≥3/3 пользователей нашли ценность в AIS для хотя бы одной задачи |
| **Fail** | Ни один пользователь не нашёл измеримого преимущества |
| **Inconclusive** | 1–2/3 нашли ценность, результаты mixed |

### Gate 3 — Differentiation Validated

**Вопрос:** Ценность не сводится к generic AI?

| Критерий | Требование |
|---|---|
| Required Evidence | AI Wrapper Test (§11) проведён ≥3 раз с разными пользователями |
| Minimum Confidence | Medium (≥2/3 пользователей нашли AIS полезнее, чем generic AI) |
| **Pass** | Большинство пользователей нашли конкретное преимущество AIS над generic AI |
| **Fail** | Большинство: «Generic AI достаточно» |
| **Inconclusive** | Mixed результаты, no clear pattern |

### Gate 4 — Repeat Value Validated

**Вопрос:** Пользователь имеет причину вернуться?

| Критерий | Требование |
|---|---|
| Required Evidence | ≥3 пользователя вернулись для новой задачи (без приглашения) через 3–7 дней |
| Minimum Confidence | Low–Medium (даже 1 repeat — significant signal на этом этапе) |
| **Pass** | ≥2/5 предложенных пользователей вернулись самостоятельно |
| **Fail** | Ни один пользователь не вернулся |
| **Inconclusive** | 1 пользователь вернулся |

### Gate 5 — Commercial Signal

**Вопрос:** Существует observable commercial intent?

| Критерий | Требование |
|---|---|
| Required Evidence | Любой из: запрос на доступ, запрос на pilot, готовность обсудить pricing, бюджетный разговор |
| Minimum Confidence | Low (даже 1 commercial signal — significant на этом этапе) |
| **Pass** | ≥1 пользователь проявил коммерческий интерес (E3–E4) |
| **Fail** | Ни один коммерческий сигнал за весь период validation |
| **Inconclusive** | Пользователи выражают интерес, но не предпринимают действий |

### Gate summary

| Gate | Evidence Required | Pass Threshold | Current E-level Target |
|---|---|---|---|
| 1. Problem | 5+ users, interviews | 4/5 confirm | E1 → E2 |
| 2. Value | 3+ users, scenarios | 3/3 find value | E1 → E2 |
| 3. Differentiation | 3+ AI Wrapper tests | 2/3 prefer AIS | E1 → E2 |
| 4. Repeat | 3+ users, 3–7 days | 2/5 return | E1 → E3 |
| 5. Commercial | 1+ signal | 1+ signal | E0 → E3/E4 |

## §25. Failure Criteria

### Условия для остановки или пересмотра

| # | Условие | Interpretation | Действие |
|---|---|---|---|
| F1 | Проблема оказывается редкой (< ежемесячно для большинства) | H2 не подтверждена | PAUSE — переоценить targeting |
| F2 | Пользователь не использует AIS после первого опыта | H10 не подтверждена | INVESTIGATE — почему? UX? Ценность? |
| F3 | Generic AI решает задачу с тем же качеством | H4, H11 не подтверждены | REFRAME — что уникального в AIS? |
| F4 | Пользователю не нужен persistent context | H6, H8 под вопросом | INVESTIGATE — достаточно ли one-shot анализа? |
| F5 | Architecture Model не создаёт observable value | H5 не подтверждена | PAUSE — фундаментальное предположение |
| F6 | Explainability не влияет на trust | H9 не подтверждена | INVESTIGATE — нужна ли объяснимость? |
| F7 | Пользователи не воспринимают AIS как отдельную ценность | H8, H11 не подтверждены | PAUSE — category problem |
| F8 | Нет повторного использования | H10 не подтверждена | INVESTIGATE — нет причин вернуться? |
| F9 | Commercial value полностью отсутствует (ни один сигнал) | H12 не подтверждена | PAUSE — пересмотреть commercial hypothesis |
| F10 | Все 5 personas описывают одинаковую проблему одинаково | Selection bias suspected | INVESTIGATE — расширить sample |

### Правило

Не считать failure один негативный отзыв. Failure — это **паттерн**, наблюдаемый у большинства пользователей.

## §26. Commercial Validation

### Observable evidence (по возрастанию силы)

| Уровень | Evidence | Evidence Grade | Пример |
|---|---|---|---|
| 1 | Interest (задает вопросы о AIS после сессии) | E2 | «Как я могу получить доступ?» |
| 2 | Request for access (хочет продолжить использовать) | E2–E3 | «Можно ли мне ещё попользоваться?» |
| 3 | Request for pilot (хочет попробовать с командой) | E3 | «Могу ли я показать это команде?» |
| 4 | Repeated usage (возвращается самостоятельно) | E3 | Пользователь пришёл через 3 дня с новой задачей |
| 5 | Willingness to discuss pricing | E3–E4 | «Сколько это стоит?» |
| 6 | Budget conversation | E4 | «Мне нужно обсудить бюджет с руководством» |
| 7 | Paid pilot | E4 | Организация платит за пилотный период |
| 8 | Purchase | E4 | Подписка/лицензия приобретена |

### Правило

Не придумывать revenue forecasts. Не прогнозировать conversion rates. Фиксировать только observable evidence.

## §27. Competitive Substitution

### Три уровня проверки

**Level 1 — Generic AI:**
Пользователь использует ChatGPT/Claude с ручным предоставлением контекста.

**Level 2 — Generic AI + IDE/tooling:**
Пользователь использует AI + IDE (VS Code) + existing tools (dependency-cruiser, sonarqube).

**Level 3 — Набор специализированных инструментов + AI:**
Пользователь использует optimal combination: IDE + GitHub + security scanner + dependency tool + documentation + generic AI.

### Главный вопрос

> Что AIS делает настолько лучше или иначе, что пользователь предпочитает единый AIS workflow?

### Метод

Для каждого уровня:

1. Пользователь решает задачу через комбинацию инструментов.
2. Пользователь решает ту же задачу через AIS.
3. Фиксируются: время, полнота, понимание, решение.

### Ожидание (не assumption)

На Level 3 пользователь может достичь **большей части** ценности. Ключевой вопрос: **стоит ли разница в усилиях?** Если пользователь тратит 2 часа на комбинацию инструментов vs 15 минут на AIS — это evidence. Если разница минимальна — это тоже evidence.

## §28. Commercial Score Reassessment Trigger

### Принцип

Следующая коммерческая оценка запускается **не по завершении очередной спецификации**, а по достижению evidence threshold.

### Threshold для запуска reassessment

| Критерий | Minimum | Current | Gap |
|---|---|---|---|
| Validated scenarios (E2+) | 5 | 0 | 5 |
| Разных пользователей (E2+) | 5 | 0 | 5 |
| Повторных interactions (E3+) | 3 | 0 | 3 |
| E2 evidence | ≥5 утверждений | 0 | 5 |
| E3 evidence | ≥2 утверждения | 0 | 2 |
| E4 evidence | Любой | 0 | 1 (optional) |
| Commercial signals | ≥1 | 0 | 1 |

### Правило

Если после достижения threshold Commercial Score остаётся 3.0/5.0 — это тоже valuable information. Это означает, что архитектурная зрелость не переводится в продуктовую ценность.

## §29. Evidence Distribution

### Текущий vs Target

| Evidence | Current | Target (post-validation) | Обоснование target |
|---|---|---|---|
| E0 | 40% (10 утверждений) | ≤20% | Минимум 8 утверждений должны перейти на E1+ через validation |
| E1 | 60% (15 утверждений) | ≤40% | Минимум 5 должны перейти на E2 через observation |
| E2 | 0% | ≥30% | Минимум 8 утверждений должны достичь E2 |
| E3 | 0% | ≥10% | Минимум 3 утверждения должны достичь E3 (repeat behaviour) |
| E4 | 0% | Optional | Не является обязательным для первого validation cycle |

### Обоснование процентов

- E0 → E1: Interview data (5–10 пользователей) должно перевести 5+ утверждений с «assumption» на «reasoned hypothesis with user confirmation».
- E1 → E2: Scenario-based observation должно перевести 5+ утверждений на «observed behaviour».
- E2 → E3: Repeat sessions должны перевести 2–3 утверждения на «repeated behaviour».
- E4: Не target, а bonus. Любой E4 — strong positive signal.

## §32. Sample Strategy

### Принцип

> На раннем этапе цель — качественно обнаружить закономерность, а не доказать рынок статистически.

### Minimum sample

| Этап | Minimum | Maximum | Обоснование |
|---|---|---|---|
| Interviews (Gate 1) | 5 | 10 | Достаточно для pattern detection |
| Scenario validation (Gate 2–3) | 3 | 7 | Достаточно для value signal |
| Repeat validation (Gate 4) | 3 (из предыдущих) | 5 | Все, кто прошёл сценарии |

### Кого НЕ включать

- Членов команды AIS
- Только друзей/знакомых
- Только техническую команду (одной компании)
- Только людей, уже заинтересованных в AIS (pre-bias)

### Как искать

- Open-source сообщества (contributors сложных проектов)
- Технические конференции/meetups
- Профессиональные сети (LinkedIn, technical communities)
- Рефералы от начальных участников (но не более 1/3 от sample)

## §33. Validation Bias

### Типы bias и защита

| Bias | Определение | Защита |
|---|---|---|
| **Confirmation bias** | Склонность искать подтверждение своей гипотезы | Чёткие fail criteria (§25). Фиксировать negative results. |
| **Founder bias** | Команда убеждена в ценности продукта | Валидация внешними пользователями, не командой. |
| **Selection bias** | Выбор «удобных» пользователей | Строгие exclusion criteria (§32). |
| **Leading questions** | Вопросы, подталкивающие к нужному ответу | Интервью правила (§34). |
| **Demo effect** | Пользователь впечатлён демо, не продуктом | Real tasks, real projects, не toy examples. |
| **Novelty effect** | Пользователю нравится новизна, не ценность | Repeat validation (Gate 4) через 3–7 дней. |
| **AI enthusiasm bias** | Пользователь восторжен от AI как технологии | AI Wrapper Test (§11). Сравнение с generic AI. |

## §34. Interview Rules

### Запрещённые вопросы

- «Хотели бы вы пользоваться AIS?»
- «Нравится ли вам наша идея?»
- «Не думаете ли вы, что это было бы полезно?»
- «Вы бы за это заплатили?» (без контекста конкретной ценности)

### Предпочтительные вопросы

| Вместо... | Спросить... |
|---|---|
| «У вас есть проблема с пониманием архитектуры?» | «Расскажите, как вы разбираетесь в архитектуре проекта, к которому только присоединились?» |
| «AIS помог бы вам?» | «Когда в последний раз вы потратили много времени на поиск информации о проекте? Что вы сделали?» |
| «Вам нравятся наши возможности?» | «Какие инструменты вы сейчас используете для понимания зависимостей? Где они вас ограничивают?» |
| «Сколько вы бы заплатили?» | «Какие инструменты для вашей работы ваша компания покупает? Как решается вопрос бюджета?» |

### Фокус интервью

Выяснять:

1. Как пользователь решает проблему сейчас?
2. Когда проблема возникла последний раз?
3. Что конкретно он сделал?
4. Сколько времени это заняло?
5. Какие инструменты использовал?
6. Где возникли сложности?
7. Что было результатом?
8. Что он сделал бы иначе, если бы мог?

## §35. Observation Over Opinion

### Правило конфликта

При конфликте:

> «Мне нравится AIS» (opinion)

vs.

> Пользователь не возвращается к AIS (observation)

**Приоритет отдаётся наблюдаемому поведению.**

### Иерархия evidence

1. **Поведение** (action) — высший приоритет
2. **Наблюдение** (observable result) — высокий приоритет
3. **Обоснованное мнение** (reasoned opinion) — средний приоритет
4. **Необоснованное мнение** (generic praise) — низкий приоритет
5. **Предполагаемое мнение** («возможно, им понравилось») — не является evidence

## §37. Decision Framework Alignment

### Проверка через Product Decision Framework

| Evaluation Criterion | Проверка | Соответствие |
|---|---|---|
| Customer Value | Validation проверяет реальную ценность | ✓ — это цель спецификации |
| Strategic Fit | Validation через Product Vision | ✓ — проверяет hypothesis из Vision |
| Product Principles | Validation не нарушает 13 принципов | ✓ — особенно D3 (AI Assists), D10 (Strengthen Model) |

| Simplicity | Validation не требует complexity | ✓ — minimum viable approach |

### Rejection Criteria (из Decision Framework)

- Validation НЕ является complexity without value — каждая проверка привязана к гипотезе.
- Validation НЕ существует только для маркетинга — все данные внутренние, для product improvement.
- Validation НЕ копирует конкурентов — фокус на уникальной ценности AIS.

## §38. Architecture Alignment

### Проверка D1–D10 реальным поведением

| Decision | Что проверяется в validation | Как |
|---|---|---|
| D1: Model Before Analysis | Пользователь получает анализ только после/через модель | Scenario A, H: Model строится до Security/Dependency анализа |
| D2: Results Bound to Model | Все findings привязаны к компонентам модели | Scenario D, B: findings ссылаются на Model elements |
| D3: AI Never Replaces Developer | Пользователь принимает решение, не AIS | Scenario C, G: AIS рекомендует, пользователь решает |
| D4: All Recommendations Explained | Пользователь может объяснить, почему рекомендация дана | §16: Explainability Validation |
| D5: Context Over Rules | Рекомендации учитывают контекст проекта, не universal rules | Scenario D: security priority отличается от формального severity |
| D6: Security With Architecture | Security findings в архитектурном контексте | Scenario D: finding → model → impact |
| D7: Knowledge Accumulates | Повторное использование даёт более точные ответы | Gate 4: Repeat Value, H6 |
| D8: Unified Platform | Пользователь использует одну платформу, не комбинацию | §27: Competitive Substitution Test |
| D9: Understanding Over Error Hunting | Пользователь описывает понимание, не количество findings | §13: Quality of Understanding, не count of issues |
| D10: New Features Strengthen Model | Validation не требует новых capabilities | §22: Feature Factory Protection |

### Правило

> Validation должна проверять эти решения реальным поведением, а не переписывать их.

Если validation показывает, что D3 не работает (пользователь слепо следует рекомендациям) — это finding для Product Decision, не для изменения D3. Решение: улучшить explainability (D4), не ослабить D3.

## §42. Key Constraints

### Что этот документ НЕ делает

1. Не гарантирует, что AIS будет успешным коммерческим продуктом.
2. Не заменяет MVP implementation.
3. Не является statistical significance testing.
4. Не генерирует vanity metrics.
5. Не позволяет искусственно повысить Commercial Score.
6. Не определяет pricing.
7. Не определяет Go-to-Market стратегию.

### Что этот документ ДЕЛАЕТ

1. Определяет **как** получить реальный evidence.
2. Определяет **что** считать evidence.
3. Определяет **когда** достаточно evidence для next step.
4. Определяет **что делать** с negative results.
5. Связывает evidence с **Product Decision Framework**.
6. Связывает evidence с **Architecture Decisions D1–D10**.
7. Защищает от **confirmation bias** и **feature factory**.

### Final statement

> Следующая коммерческая оценка должна основываться уже не преимущественно на качестве наших документов, а на поведении реальных пользователей и накопленном evidence.

Текущий Commercial Score: **3.0/5.0**. Цель: не обязательно поднять score. Цель — **сделать score измеримым**.

Если evidence покажет, что ценности нет — мы узнаем это как можно раньше. Если покажет, что ценность есть — это станет первым серьёзным основанием переходить от архитектурной готовности к реализации и выпуску MVP.
