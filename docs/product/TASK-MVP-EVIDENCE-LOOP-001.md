# TASK-MVP-EVIDENCE-LOOP-001

### Evidence-First MVP Foundation

**Цель:** подготовить AIS к бесплатному MVP-релизу, где главной задачей первого этапа является **сбор качественной информации о реальном использовании платформы**, а не максимизация количества функций или ранняя коммерциализация.

---

## 1. Стратегическое решение

На текущем этапе:

> **AIS не оптимизируется под продажу. AIS оптимизируется под получение evidence.**

Коммерциализация переносится на этап, когда накопленные данные позволят подтвердить реальную ценность платформы.

### Приоритеты

1. **Достоверность**
2. **Сбор evidence**
3. **Наблюдение за реальным использованием**
4. **Выявление ошибок и ограничений AIS**
5. **Улучшение качества понимания**
6. **Повторная проверка**
7. **Формирование доказанной ценности**
8. **Коммерческая оценка**
9. **Монетизация**

---

# 2. Что НЕ является целью задачи

Запрещается превращать эту задачу в:

* разработку новых пользовательских функций ради количества;
* полноценный redesign платформы;
* enterprise-функциональность;
* autonomous agent;
* сложную систему аналитики;
* платёжную систему;
* коммерческий onboarding;
* попытку доказать Product-Market Fit;
* искусственное повышение Commercial Score.

**STOP CONDITION:** если предлагаемое изменение не улучшает способность AIS получать или сохранять качественное evidence — оно не входит в эту задачу.

---

# 3. Основной принцип

Каждая значимая пользовательская сессия должна оставлять после себя структурированный след:

```text
Project
   ↓
User Intent
   ↓
Context
   ↓
AIS Understanding
   ↓
AIS Claim
   ↓
Evidence
   ↓
User Verification
   ↓
Feedback
   ↓
Quality Signal
   ↓
Learning Opportunity
```

Важно:

> **Feedback не становится автоматически Truth.**

Пользовательское исправление должно оставаться evidence о качестве понимания, пока не выполнены условия его превращения в более сильное знание.

---

# 4. Что именно мы хотим узнать от MVP

MVP должен позволить ответить на вопросы:

### Пользователь

* Что человек пытается понять?
* Какие архитектурные вопросы возникают?
* Что он делает до обращения к AIS?
* Что он делает после ответа AIS?

### AIS

* Что AIS понял?
* На каких данных основывался?
* Какие утверждения сделал?
* Какие утверждения оказались правильными?
* Где появились ошибки?
* Где недостаточно контекста?

### Ценность

* Помог ли AIS решить задачу?
* Сэкономил ли он время?
* Нашёл ли то, что пользователь самостоятельно не нашёл?
* Был ли результат проверяемым?
* Вернулся ли пользователь к AIS для следующей задачи?

---

# 5. Evidence Model

Каждое значимое утверждение AIS должно по возможности иметь связь:

```text
Claim
 ├── Context
 ├── Source
 ├── Reasoning basis
 ├── Confidence / uncertainty
 └── Verification status
```

Минимально сохранять:

* session ID;
* project/scope;
* user intent;
* timestamp;
* AIS response;
* relevant sources;
* claims;
* evidence;
* user feedback;
* verification result;
* quality classification.

---

# 6. Не собирать «всё подряд»

Это принципиально.

Мы не строим систему:

> «давайте запишем абсолютно каждое действие пользователя».

Нужны **meaningful signals**.

Например:

### Сильный сигнал

> Пользователь проверил утверждение AIS и подтвердил его.

### Очень сильный сигнал

> Пользователь использовал результат AIS для решения реальной задачи.

### Сильный отрицательный сигнал

> Пользователь обнаружил конкретную архитектурную ошибку AIS.

### Слабый сигнал

> Пользователь открыл экран.

---

# 7. Evidence Hierarchy

Вводим чёткое разделение:

### Synthetic Evidence

Получено от:

* тестов;
* LLM agents;
* automated validation.

Используется для технического улучшения.

### Human Evidence

Получено от реального человека.

Используется для проверки реального поведения.

### Product Evidence

Накопленные повторяющиеся наблюдения о реальном использовании.

### Commercial Evidence

Данные, связанные с реальной экономической ценностью.

**Никогда не смешивать эти уровни.**

---

# 8. MVP Release Gate

MVP можно выпускать бесплатно, если выполнены технические условия:

### G1 — Runtime

AIS способен выполнить полный цикл:

```text
Discovery
→ Context
→ Inference
→ Evidence
→ Response
```

### G2 — Grounding

AIS способен показать, **на чём основан ответ**.

### G3 — Evidence Capture

Сессия может быть сохранена.

### G4 — Feedback

Пользователь может сообщить:

* correct;
* incorrect;
* incomplete;
* unclear;
* useful;
* not useful.

### G5 — Quality Loop

Feedback можно связать с конкретным:

* claim;
* session;
* context;
* evidence.

### G6 — Safety

Никакие пользовательские feedback-сигналы не должны автоматически изменять архитектурную модель.

---

# 9. Что пока НЕ требуется

Для бесплатного MVP **не требуется**:

* billing;
* subscriptions;
* sales dashboard;
* enterprise permissions;
* сложная CRM;
* маркетинговая воронка;
* десятки режимов анализа;
* автономное изменение модели;
* полноценная Knowledge Persistence;
* идеальная точность.

Это всё может появиться позже.

---

# 10. MVP UX

Сохраняем уже принятое решение:

> **Understanding-Centered Interaction.**

Не показываем пользователю огромную панель:

```text
Modules
Dependencies
Metrics
Graphs
Events
Policies
Logs
...
```

по умолчанию.

Пользователь формулирует намерение.

Например:

> **«Что произойдёт, если мы изменим этот компонент?»**

AIS отвечает:

1. **Короткий вывод**
2. **Почему**
3. **На что опирается**
4. **Что стоит проверить**
5. **Уровень уверенности**

Детали открываются **progressively**.

---

# 11. Главный объект MVP

Не dashboard.

Не chatbot.

Не architecture graph.

Главный объект:

> **Verified Understanding**

То есть:

```text
User Question
       ↓
AIS Understanding
       ↓
Evidence
       ↓
Human Verification
```

---

# 12. Feedback Loop

После результата пользователь должен иметь возможность сказать:

> **Верно**

> **Неверно**

> **Неполно**

> **Не понимаю**

> **Полезно**

> **Не помогло**

При отрицательном feedback желательно получить:

> **Что именно неверно?**

Это создаёт гораздо более ценное evidence.

---

# 13. Quality Learning Loop

Накопленные данные должны позволять формировать backlog:

```text
Evidence
   ↓
Finding
   ↓
Root Cause
   ↓
Improvement Candidate
   ↓
Implementation
   ↓
Regression
   ↓
New Evidence
```

Это становится основным циклом развития AIS.

---

# 14. Запрет Feature Factory

Каждый новый feature request проходит фильтр:

### Вопрос 1

Какое evidence показывает необходимость?

### Вопрос 2

Какую проблему пользователя он решает?

### Вопрос 3

Можно ли решить проблему улучшением существующего механизма?

### Вопрос 4

Как мы проверим результат?

Если нет evidence:

> **Feature откладывается.**

---

# 15. Метрики первого MVP

Мы пока **не оптимизируем DAU, MAU и revenue**.

Основные показатели:

### Understanding Quality

* grounded claims;
* unsupported claims;
* hallucination rate;
* verification success.

### User Value

* task completion;
* useful / not useful;
* repeat usage;
* user correction rate.

### Learning Value

* quality findings/session;
* actionable findings;
* recurring failure patterns;
* improvement candidates.

Не пользовательский dashboard.

**Internal quality view.**

Он должен позволить нам увидеть:

```text
Sessions
   ↓
Questions
   ↓
Claims
   ↓
Evidence
   ↓
Corrections
   ↓
Failures
   ↓
Patterns
```

Причём сначала это может быть даже простой структурированный отчёт.

Не нужно строить отдельный большой продукт.

---

# 17. Definition of Done

TASK считается выполненной, если:

* [ ] MVP способен провести реальную AIS-сессию;
* [ ] session ID создаётся;
* [ ] intent сохраняется;
* [ ] AIS response сохраняется;
* [ ] evidence сохраняется;
* [ ] claims могут быть связаны с evidence;
* [ ] пользовательский feedback сохраняется;
* [ ] feedback связан с конкретной сессией;
* [ ] quality finding может быть создан;
* [ ] synthetic и human evidence разделены;
* [ ] feedback не изменяет Model автоматически;
* [ ] данные можно использовать для следующего цикла улучшения;
* [ ] MVP не требует коммерческой инфраструктуры.

---

# 18. Самое важное ограничение

### Мы не пытаемся доказать, что AIS уже хороший.

Мы создаём систему, которая позволит **объективно узнать, насколько он хорош**.

Это две совершенно разные задачи.
